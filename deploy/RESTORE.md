# Восстановление БД из бэкапа

> Непроверенный бэкап равен отсутствующему. Эта процедура — не документация «на
> будущее», а то, что должно быть **воспроизведено руками** (владельцем, через неделю,
> не подглядывая — Definition of Done фазы 10). Прогнав её, впишите замер времени в
> конец файла.

Бэкапы снимает [`backup.sh`](backup.sh): `pg_dump -Fc` → шифрование `age` на публичный
ключ → S3 (Yandex Object Storage, отдельный от медиа провайдер). Ключи:

- `daily/trillix-ГГГГ-ММ-ДД-ЧЧММ.sql.age` — каждые 6 часов, хранится 14 суток;
- `weekly/trillix-ГГГГ-ММ-ДД-Wнн.sql.age` — снимок по понедельникам, хранится 8 недель.

## Что нужно под рукой

1. **Приватный ключ age** (`identity`). На сервере его НЕТ — сервер умеет только
   шифровать. Ключ лежит офлайн у владельца (менеджер паролей / офлайн-носитель).
   Без него бэкап не расшифровать — это и есть смысл офсайт-шифрования. Файл вида:
   ```
   # created: ...
   # public key: age1...    ← это BACKUP_AGE_RECIPIENT
   AGE-SECRET-KEY-1........
   ```
2. **Креды S3-бакета бэкапов** (`BACKUP_S3_*`) — на чтение достаточно.
3. **`age`, `awscli`, `docker`** на машине, где восстанавливаете.
4. **Прежний `FORM_TOKEN_SECRET`** — тот, что стоял на сервере в момент снятия бэкапа.
   **В бэкап он не входит** (`backup.sh` снимает только Postgres, `.env` не трогает), а
   часть колонок дампа — шифротекст под ключом, выведенным из него. Без прежнего секрета
   дамп восстановится целиком и молча потеряет три вещи — см. §4.6. Держите его там же,
   где приватный ключ `age`: офлайн у владельца. **Внутрь бэкапа его класть нельзя** —
   тогда утечка одного архива отдаёт и данные, и ключ к их секретам.

## Процедура

Засеките время с этого места.

### 1. Скачать вчерашний бэкап

```bash
export AWS_ACCESS_KEY_ID=...        # BACKUP_S3_ACCESS_KEY
export AWS_SECRET_ACCESS_KEY=...    # BACKUP_S3_SECRET_KEY
export AWS_DEFAULT_REGION=ru-central1
EP=https://storage.yandexcloud.net  # BACKUP_S3_ENDPOINT
BUCKET=...                          # BACKUP_S3_BUCKET

# посмотреть, что есть, и взять последний суточный
aws --endpoint-url "$EP" s3 ls "s3://$BUCKET/daily/"
aws --endpoint-url "$EP" s3 cp "s3://$BUCKET/daily/trillix-ГГГГ-ММ-ДД-ЧЧММ.sql.age" ./dump.sql.age
```

### 2. Расшифровать

```bash
age -d -i ~/age-identity.txt -o dump.sql dump.sql.age
```

Ошибка `no identity matched` → взят не тот приватный ключ (публичный в заголовке
бэкапа не совпал с вашим `identity`).

### 3. Поднять чистый Postgres и восстановить

Отдельный контейнер, чтобы не задеть рабочую базу:

```bash
docker run -d --name trillix-restore -e POSTGRES_PASSWORD=restore \
  -e POSTGRES_USER=trillix -e POSTGRES_DB=trillix -p 55432:5432 postgres:16
# дождаться готовности
until docker exec trillix-restore pg_isready -U trillix -d trillix; do sleep 1; done

# кастомный формат (-Fc) восстанавливается pg_restore, не psql
cat dump.sql | docker exec -i trillix-restore \
  pg_restore -U trillix -d trillix --clean --if-exists --no-owner
```

`--clean --if-exists` делает шаг идемпотентным (повторный прогон не падает на
существующих объектах). Предупреждения о несуществующих объектах при первом
`--clean` — норма.

### 4. Проверить, что приложение с базой работает

Быстрая проверка целостности — данные на месте:

```bash
docker exec trillix-restore psql -U trillix -d trillix -c \
  "SELECT (SELECT count(*) FROM forms)        AS forms,
          (SELECT count(*) FROM submissions)  AS submissions,
          (SELECT count(*) FROM form_visits)  AS visits;"
```

Полная проверка — поднять `api` против восстановленной базы (укажите в его
`DATABASE_URL` порт `55432`) и открыть кабинет: вчерашние формы на месте, ответы
открываются, сводка считается.

### 4.5. Файлы в ответах — отдельный объект восстановления

**База и бакет файлов восстанавливаются по отдельности.** Дамп несёт строки
`submission_files` (имя, размер, ключ объекта), но не сами файлы: они лежат в бакете
`S3_FILES_BUCKET` у провайдера хранилища.

Что это значит на практике:

- восстановленная база показывает ответы, имена вложений и всё остальное; не
  открывается только само вложение, если бакет потерян;
- копия бакета в бэкапе появляется, **только если** в `.env` сервера стоит
  `BACKUP_FILES=1` (см. `backup.sh`); по умолчанию шаг выключен — он платный и это
  решение владельца;
- восстановление копии — обратная синхронизация:
  `aws --endpoint-url "$BACKUP_S3_ENDPOINT" s3 sync "s3://$BACKUP_S3_BUCKET/files/" ./files`
  и затем `aws --endpoint-url "$S3_ENDPOINT" s3 sync ./files "s3://$S3_FILES_BUCKET"`
  с кредами хранилища.

⚠ Этот путь **не проверялся учебным восстановлением** — он написан вместе с фазой 24.
Первый прогон стоит сделать на непустом бакете и внести сюда замеры, как сделано для
базы.

### 4.6. Секреты в базе — что не переживёт чужой `FORM_TOKEN_SECRET`

**Это единственный класс отказа, который проверка целостности выше пройти НЕ мешает.**
Счётчики строк сойдутся, кабинет откроется, формы и ответы будут на месте — а сломано
окажется ровно то, на что вы не смотрите. Поэтому проверка вынесена отдельным шагом.

Три колонки лежат шифротекстом под ключом, выведенным HKDF из `FORM_TOKEN_SECRET`
(своих env-переменных у них нет сознательно — ADR §10, плата названа там же):

| Колонка | Что молча ломается |
|---|---|
| `user_totp.secret` | все включённые вторые факторы: люди с 2FA не войдут |
| `integration_accounts.refresh_token` | все подключения Google; связки форм с листами встают, экран говорит «подключите заново» |
| `forms.password` (`0047`) | все формы под паролем |

**Ловушка провижининга.** Раннбук развёртывания ([`README.md`](README.md)) велит
сгенерировать секрет заново (`openssl rand -base64 32`). Если вы поднимаете сервер с нуля
И восстанавливаете базу из бэкапа, эти два шага противоречат друг другу: свежий секрет
превращает три колонки в мусор. **При восстановлении в `.env` идёт ПРЕЖНИЙ секрет, а не
новый.**

**Как проверить, что секрет тот самый** (одной из трёх колонок достаточно — ключ у них
общий):

```bash
# форма под паролем: с верным паролем ручка обязана отдать 200 и токен
curl -sS -o /dev/null -w '%{http_code}\n' -X POST \
  -H 'Content-Type: application/json' -d '{"password":"<пароль формы>"}' \
  http://localhost:8080/public/v1/forms/<slug>/unlock
```

`200` — секрет верный. `500` — секрет чужой (в логе api будет `open form password …`).
`401` — пароль действительно не тот, попробуйте другую форму.

⚠ **Симптом обманчив:** респонденту на форме при чужом секрете показывается
«Пароль не подошёл» — то есть форма говорит участникам, что ошиблись они. Настоящая
причина видна только в логе api.

**Если прежний секрет утрачен безвозвратно** — данные целы, восстанавливается всё, но
руками и разными людьми: владельцы форм заново вводят пароли в настройках, владельцы
аккаунтов заново подключают Google, пользователи с 2FA проходят сброс второго фактора.
Ни одна из трёх колонок не мешает работе остального продукта.

**Не проверялось учебным восстановлением** — раздел написан вместе с миграцией `0047`
(2026-09-01), когда третья колонка появилась. Первый прогон стоит сделать вместе со
следующим учебным восстановлением и внести сюда замер.

### 5. Убрать за собой

```bash
docker rm -f trillix-restore
rm -f dump.sql dump.sql.age
```

Остановите таймер.

## Замеры

Каждый учебный прогон — новая строка (append-only): дата, кто, полное время «от
скачивания до открытого кабинета», что мешало.

> **Замер зависит от размера базы.** Время ниже снято на почти пустой БД (~20 КБ).
> На загруженной базе и скачивание из Yandex, и `pg_restore` вырастут — перемеряй
> хронометраж, когда данных станет заметно больше, иначе цифра вводит в заблуждение.
