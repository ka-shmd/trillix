# База данных и миграции

- Миграция = пара `NNNN_name.up.sql` / `.down.sql`, следующая по номеру; down обязан реально откатывать up. Проверяет это тест `migrations/roundtrip_test.go` на одноразовой базе (`make test-go`) — накат, откат по одному шагу до пустой схемы, повторный накат. **По dev-базе этот цикл руками не гоняют:** откат уносит из неё данные, которых повторный накат не вернёт (подключённые аккаунты внешних сервисов — согласие живого человека, а не строки).
- `make migrate-down` называет миграцию до отката и требует ввести `yes`, если её down удаляет строки (`DROP TABLE`, `DROP COLUMN`, `DROP SCHEMA`, `TRUNCATE`, `DELETE FROM`). Неинтерактивно (контейнер, CI) — только с флагом: `make migrate-down FORCE=1`.
- Миграции **обратно совместимы с работающим кодом предыдущей версии**: добавить колонку/таблицу/индекс — можно; переименовать или удалить — только в два релиза (сначала код перестаёт использовать, потом отдельная миграция удаляет).
  - **Исключение, действующее ровно до первых пользователей** (решение владельца 2026-08-02, применено в `0016`): правило страхует старый бинарник на тех секундах выкатки, пока он работает с новой схемой, — а пока продукт никем не пользуется, страховать некого, и снятие колонки едет той же миграцией. **Как только у продукта появятся живые пользователи, эта строка удаляется, а правило действует без исключений** — «переезд в один шаг» с работающим сервисом означает пятисотки на выкатке.
- Уже смерженная миграция никогда не редактируется — только новая поверх.
- Иммутабельность `form_versions` — священна: никакой код не делает UPDATE строк этой таблицы, ни при каких обстоятельствах. То же — `submissions.answers` (кроме явного DELETE ответа пользователем).
- Каждый новый запрос со сканом по большой таблице (`forms`, `submissions`) — проверить план (`EXPLAIN` на сидированных данных, `make seed`) и наличие индекса. Индекс добавляется той же миграцией, что и запрос, который его требует.
- JSONB-схемы валидируются в приложении (`ValidateSchema` / `ValidateAnswers`) — БД-констрейнты на структуру JSONB не вешаем, но NOT NULL / FK / CHECK на реляционные поля обязательны.
- Идентификаторы — UUIDv7, генерируются в приложении. Схема БД и её обоснование — `docs/ARCHITECTURE.md` §3.
