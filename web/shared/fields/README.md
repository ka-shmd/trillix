# Полотно формы (`@fields`) — как устроено и как расширять

Как выглядит и рендерится форма. Одна форма живёт в коде для **трёх поверхностей**, и
их вид обязан совпадать (WYSIWYG — это ядро UX продукта). Этот файл фиксирует, где
что менять, чтобы поверхности не разъезжались.

## Три поверхности одной формы

| Поверхность | Компонент | Что делает | Стек |
|---|---|---|---|
| **Редактор** | `web/app/.../builder/BlockRow.tsx`, `SlashEditor.tsx` | автор собирает форму (инлайн-правка, dnd, «/») | Tailwind + shadcn на layout/взаимодействие, `rf-*` на вид |
| **Превью** | `web/app/.../builder/PreviewPane.tsx` | «как увидит респондент» в кабинете | `@fields` + `rf-*` |
| **Рендерер** | `web/renderer/.../form/FormView.tsx` | публичная форма для респондента | react+zod, `@fields` + `rf-*` (Tailwind нельзя — бюджет 95 КиБ) |

Редактор — **источник истины вида**. Превью и рендерер обязаны выглядеть как он.

## Единый вид: `fields.css` + классы `rf-*`

Весь вид формы описан один раз в [`fields.css`](./fields.css) — plain-CSS, независимый от
Tailwind/shadcn (чтобы рендерер читал его без Tailwind). Классы:

- `rf-page` — холст (ширина, отступы, вертикальный ритм заголовок→поля→кнопка);
- `rf-title` — заголовок формы;
- `rf-field` / `rf-label` / `rf-text` / `rf-required` / `rf-desc` — обёртка поля, вопрос, абзац-контент, звёздочка, описание;
- `rf-input` — текстовое поле/`textarea`/date;
- `rf-options` / `rf-option` / `rf-mark` (`--radio`/`--check`) — список выбора и глиф (нативный `<input appearance:none>`);
- `rf-submit` — кнопка отправки; `rf-empty` / `rf-error` — заметки.

Цвета/радиусы — токены `--rf-*` (значения = палитра shadcn редактора: `--rf-text`,
`--rf-muted`, `--rf-surface`, `--rf-primary`, `--rf-danger`, `--rf-radius`, …). Приложение
может переопределить `--rf-*` (напр. кабинет в `.dark`), по умолчанию — не переопределяет.

`fields.css` импортируется в `main.tsx` **обоих** фронтов **после** их `index.css`
(unlayered `rf-*` перебивают base-слой Tailwind). `oklch()`/`color-mix()` в рендерере
поддержаны — можно использовать.

## Правило №1: вид правится только в `fields.css`

Меняешь как выглядит поле/заголовок/кнопка — правь `fields.css`, и все три поверхности
едут вместе. **Не** заводи вид полей Tailwind-классами в `BlockRow`/`SlashEditor` — там
Tailwind только на layout/dnd/hover; визуал поля берётся из `rf-*`. Не тащи Tailwind в
`@fields`.

## Как добавить элемент полотна (заголовок, кнопка, …)

1. Добавь класс `rf-<что-то>` (+ при нужде токен `--rf-*`) в `fields.css`.
2. Надень его во **всех трёх**: редактор (`BlockRow`/`SlashEditor`), превью (`PreviewPane`),
   рендерер (`FormView`).
3. Сверь computed-стили по трём поверхностям (см. «Проверка»).

## Как добавить новый тип поля (вертикальный срез)

Тип блока — сквозное изменение контракта. Порядок (образец — 8-й тип `text`, см.
`[[builder-is-provisional]]` в памяти и коммиты фазы 6.5):

1. **Zod** `web/shared/entities/formSchema.ts` — значение в `blockTypeSchema`; при нужде
   в наборы `CHOICE_TYPES`/`SINGLE_CHOICE_TYPES`/`PLACEHOLDER_TYPES`; хелперы
   `isChoiceType`/`isSingleChoiceType`/`supportsPlaceholder`/`isContentType`/`isAnswerableType`.
2. **Go-домен** `internal/domain/schema.go` — константа `Block…`, `isChoice()`/
   `isSingleChoice()`/`isContent()`, `ValidateSchema`. Это контракт → **синхронно** с Zod,
   в одном PR, с тестами обеих сторон.
3. **Контрол** `web/shared/fields/BlockField.tsx` — ветка в `switch (block.type)`
   (`FieldControl`), при нужде стиль в `fields.css`.
4. **Редактор** `BlockRow.tsx` — как тип правится автором (поле ответа/варианты/абзац);
   `SlashMenu.tsx` / `BlockTypeDialog.tsx` — пункт в выборе типа.
5. **Валидация ответа**: рендерер `web/renderer/.../form/validation.ts` (+ `answers.ts`),
   Go `internal/domain/answers*.go`.
6. **Экспорт/таблица**: Go `internal/domain/csv.go`, кабинет
   `web/app/src/features/submissions/answerFormat.ts`.
7. `schemaVersion` не трогаем, если новое enum-значение обратно совместимо.

**Три грабли этого среза** (все наступлены в фазе 8.5 шаг 2, все — молчаливые):

- **Ветвись предикатом, а не `type == …`.** Забытая ветка не падает — она трактует новый
  тип как соседний: `dropdown`, не попавший в `isSingleChoice()`, уезжает в ветку
  `multi_choice` и начинает ждать массив вместо строки. Места, которые обязаны знать
  семантику: `ValidateAnswers`, `csv.go` (`formatCell`), `answerFormat.ts` кабинета.
- **Кодируй ответ строкой.** `Answer` = `string | string[]`; число, дата, шкала, согласие —
  строки. Булев `false` не равен `''`, не попадёт в `isEmpty` (`renderer/.../validation.ts`),
  и `required` молча перестанет работать.
- **Новая настройка со значимым нулём — указатель** (Go) / явная проверка на `undefined`
  (Zod). `omitempty` у `int` выбрасывает 0 из JSON, и «не задано» становится неотличимо от
  «задано 0» (`scaleMin: 0` в NPS). А если валидатор строг к настройке — не давай её
  вводить свободным текстом: `<select>` вместо числового поля, иначе автосейв ловит 422 на
  каждое нажатие (см. `ScaleInline` и ту же историю с `redirectUrl`).

Не забудь **иконку типа** (`blockTypeIcons.tsx` — `Record<BlockType, …>`, tsc поймает) и
**редактор**: `AnswerField` рисует `<input type="date">` всем типам без плейсхолдера, так
что типу со своими настройками нужна своя ветка (образец — `ScaleInline`).

## Картинка (`image`) и медиа

`image` — контентный (неотвечаемый) тип, как `text`, но с бинарным содержимым в
объектном хранилище (S3; полный дизайн — `docs/DESIGN-s3-media.md`). Что важно для
полотна:

- **Схема:** `settings.imageKey` (ключ объекта в бакете, не URL) и `settings.alt`.
  Хранится ключ — URL вычисляется, чтобы данные не привязывались к провайдеру.
- **URL:** `mediaSrc(key)` (`@fields/media`) → относительный `/media/<key>`, одинаков
  для кабинета и рендерера (раздаётся same-origin: в проде Caddy, в dev vite-proxy;
  `docs/DESIGN-s3-media.md` §8). Покрывается CSP `img-src 'self'`.
- **Рендер (все три поверхности):** `BlockField` рисует `<img class="rf-image">` по
  `mediaSrc` (пустой ключ → ничего). `rf-image` — в `fields.css`. Превью и рендерер
  едут автоматически; **редактор** рисует свой `ImageField` (зона загрузки, прогресс,
  `alt`, замена/удаление) — его editor-only вид на Tailwind, но саму картинку он
  показывает тем же `rf-image`.
- **Загрузка:** `mediaUpload.ts` — XHR `POST /api/v1/forms/{id}/media` (multipart,
  прогресс через `upload.onprogress`, CSRF из cookie); ответ `{ imageKey }` пишется в
  `settings.imageKey`, автосейв кладёт в схему. Валидация (PNG/JPEG, размер, ре-энкод)
  — на сервере (`internal/media`).

## Тонкости (не сломай синхрон)

- **Холст `rf-page`** несёт метрики полотна редактора (десктоп 144/80/96, мобильный
  40/20/64 по `@media <=640`). Редактор держит те же значения **своим Tailwind**
  (`px-5 pt-10 … sm:px-20 sm:pt-36`) под тем же брейкпоинтом (`sm`=640). Меняешь одно —
  правь оба, иначе на узком экране разъедется.
- **Глиф выбора**: рендерер — нативный `<input type=radio/checkbox class="rf-mark …">`
  с `appearance:none` (рабочий и доступный); редактор — декоративный `<span class="rf-mark …">`.
  Один вид, разные элементы.
- **Заголовок**: в редакторе это `<textarea>` с автовысотой (а не `<input>`) — чтобы длинное
  название переносилось так же, как `<h1 rf-title>` у респондента. `title` живёт **вне
  схемы и стора** (колонка `forms.title`, сохраняется отдельным rename-PATCH); в превью
  приходит пропом `detail.title`, а `submitLabel` — из стора.
- **Экран «после отправки»** (`thankYouText`/`redirectUrl`, форма-уровень схемы) — это
  **четвёртая поверхность вне `rf-*`**: рендерер рисует её статус-экраном
  (`.status`/`.status-title`/`.status-detail` в `web/renderer/src/index.css`), а редактор —
  страницей настроек (`FormSettings.tsx`, иконка-шестерёнка в шапке подменяет полотно —
  третий режим `Mode` в `BuilderScreen`). Превью её не показывает, WYSIWYG сюда не
  распространяется — сверять три поверхности не нужно.
- **Полотно — только блоки** (плюс кнопка отправки: её видит респондент, и правится она
  на месте — это WYSIWYG). Настройка, которой на форме не видно, живёт на странице
  настроек, а не на полотне.
  Решение экрана (что показать, уходить ли и когда) — в чистой `planThankYou`
  (`web/renderer/.../thankYouPlan.ts`), покрыто юнитами без DOM: у рендерера нет
  testing-library, и заводить её — вопрос человеку.
- **Новое поле документа (форма-уровень) — не забудь `Snapshot`** в сторе билдера:
  поле, не попавшее в снапшот, молча теряется при undo. `undo`/`redo` разворачивают
  снапшот целиком (`...prev`) именно поэтому.
- **Известные микро-остатки** (приняты): заголовок-`textarea` на ~4px выше `<h1>`
  (интринсик контрола); под заголовком в редакторе +~6px от `py-1.5` первого блока (место
  под hover-контролы). Незаметно; чистого способа свести в ноль нет.
- **Бюджет рендерера** — 95 КиБ gzip JS (`npm run check:bundle`). Новых зависимостей во
  фронты — только через вопрос человеку (`web/CLAUDE.md`). CSS в бюджет не входит.

## Проверка

Скриншоты бывают ненадёжны — сверяй **computed-стили одного элемента по трём
поверхностям** (`getComputedStyle` в браузере): вопрос, поле, глиф, заголовок, кнопка,
холст (ширина/отступы/ритм) должны совпадать. Проверь и десктоп (≥640), и мобильный
(≤640, рендерер ужимается). `make lint` + сборка + `check:bundle` — зелёные.

Меняешь вид/ассеты формы, которую видит респондент — **проверь на прод-сборке**, а не
только в dev: `make prod-local`, открой `https://f.localhost/r/{slug}`, прогони e2e
(`cd e2e && npm test`). Dev инжектит стили/скрипты через JS и прячет прод-баги; страницу
формы Go строит из собранного `index.html` рендерера (ассеты берёт оттуда как есть,
плейсхолдер `<!--og-meta-->` не трогай), а внешние ресурсы режет CSP (см. «Прод-контур»
в `web/CLAUDE.md`).
