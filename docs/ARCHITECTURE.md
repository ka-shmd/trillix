# Архитектура SaaS-конструктора форм (аналог Tally) — MVP

Документ описывает архитектуру MVP с прицелом на рост: решения принимаются так, чтобы их не пришлось переделывать при масштабировании, но без преждевременного усложнения. Стек: Go (минимум зависимостей), PostgreSQL, React + TypeScript + TanStack. Деплой — один VPS.

---

## 1. Скоуп MVP

Прежде чем проектировать, фиксируем границы. Это самое важное архитектурное решение: всё остальное вытекает отсюда.

**Входит в MVP:** регистрация и вход по email/паролю; создание, редактирование и удаление форм; конструктор с базовыми типами блоков (короткий текст, длинный текст, email, число, одиночный выбор, множественный выбор, дата); публикация формы по публичной ссылке; приём ответов анонимными респондентами; просмотр ответов в таблице; экспорт ответов в CSV; черновик/публикация как два состояния формы.

**Не входит в MVP (но архитектура должна это допускать):** команды и воркспейсы с несколькими участниками (сущность workspace закладываем сразу, UI для приглашений — нет); условная логика (branching); интеграции и вебхуки; кастомные домены; загрузка файлов респондентом в ответах (POST-MVP, Фаза 17); платные тарифы и биллинг; email-уведомления о новых ответах.

*Отступление (пост-фаза-8):* загрузка **автором** картинок для лейаут-блока введена сверх исходного MVP — это первая подсистема объектного хранилища (S3) в продуктовом контуре. Обоснование и дизайн — `docs/DESIGN-s3-media.md`; ключевые решения — в ADR-сводке §10. Загрузка файлов респондентом в ответах (private-бакет, presigned) остаётся Фазой 17 и переиспользует этот слой.

Принцип: сущности, которые дорого добавлять задним числом (workspace, версионирование форм), закладываем в схему данных сразу. Функциональность, которую дёшево добавить позже (вебхуки, логика), — не закладываем вообще.

## 2. Общая архитектура

### 2.1. Модульный монолит

Один Go-бинарник, один процесс, одна база. Микросервисы на этом этапе — антипаттерн: они добавляют сетевые границы, распределённые транзакции и операционную сложность, не давая ничего взамен при нагрузке MVP. Вместо этого — **модульный монолит**: жёсткие границы между доменными модулями внутри одного процесса. Если через два года понадобится вынести приём ответов в отдельный сервис — границы уже будут прочерчены.

### 2.2. Два фронтенд-приложения

Ключевое продуктовое наблюдение: у сервиса форм два принципиально разных потребителя фронтенда.

**Приложение-конструктор (app)** — SPA для авторизованных пользователей: билдер, список форм, таблица ответов. Здесь уместен тяжёлый бандл, TanStack Router/Query, сложный стейт.

**Публичный рендерер форм (renderer)** — то, что видит респондент по ссылке `f.example.com/r/{slug}`. Здесь критичны скорость первой отрисовки и вес бандла: респондент открывает ссылку один раз, часто с телефона, и любая задержка — потерянный ответ. Это отдельная точка сборки Vite с минимумом зависимостей (React + лёгкая форма-логика, без роутера и без TanStack Query — там буквально один GET и один POST).

Оба приложения живут в одном монорепозитории и собираются одной командой, но деплоятся как разные наборы статики.

### 2.3. Схема системы

```
                        ┌─────────────────────────── VPS ───────────────────────────┐
                        │                                                            │
  app.example.com ────► │  Caddy: статика app + /api/* ─┐                            │
  f.example.com   ────► │  Caddy: статика renderer +    ├──► Go API (один бинарник)  │
                        │         /r/*, /public/*  ─────┘        │                   │
                        │                                        ▼                   │
                        │                                   PostgreSQL 16            │
                        │                                        │                   │
                        │                              pg_dump → S3-совместимое      │
                        │                                        offsite-хранилище   │
                        └────────────────────────────────────────────────────────────┘
```

Два домена, а не три (ADR §10). `app` — кабинет и его приватный API на одном origin: статику Caddy отдаёт напрямую, `/api/*` проксирует в Go. Раз origin один — **CORS не нужен**, а cookie сессии остаётся host-only на `app`. `f` — публичный рендерер отдельным origin: это осознанная граница безопасности (cookie кабинета туда не попадает, XSS в чужой форме не достанет сессию), плюс формы можно позже вынести за CDN; `/r/*` (HTML c OG-мета) и `/public/*` (публичный API) проксируются в тот же Go same-origin. Выделенного `api`-домена в MVP нет: он не давал ничего, кроме CORS и cross-site-cookie; появится вместе с публичным API-продуктом (пост-MVP).

## 3. Модель данных

Это сердце проекта. Здесь два нетривиальных решения senior-уровня, разберём их подробно.

### 3.1. Решение №1: схема формы — JSONB, а не нормализованные таблицы

Наивный путь — таблицы `questions`, `options`, `question_settings` с внешними ключами. Для конструктора форм это ловушка: структура блоков эволюционирует быстро (новые типы полей, новые настройки), каждое изменение требует миграции, а собирать форму из пяти таблиц с сортировками — дорого и хрупко. При этом реляционные запросы «внутрь» схемы формы почти не нужны: форма всегда читается и пишется целиком.

Поэтому схема формы (список блоков с настройками) хранится как **один JSONB-документ**, валидируемый на уровне приложения строгими Go-типами. Реляционная модель остаётся для того, что действительно реляционно: пользователи, воркспейсы, формы как сущности, ответы.

### 3.2. Решение №2: иммутабельные версии-снапшоты при публикации

Классическая ошибка конструкторов форм: ответы ссылаются на «живую» форму, автор удаляет вопрос — и старые ответы становятся неинтерпретируемыми (в данных есть ответ на вопрос, которого больше нет).

Решение: у формы есть мутабельный **черновик** (`forms.draft_schema`) и иммутабельные **версии** (`form_versions`). Публикация = снятие снапшота черновика в новую строку `form_versions`. Каждый ответ ссылается на конкретную версию, по которой он был отправлен. Это даёт корректную интерпретацию любого исторического ответа, бесплатную «историю изменений» и безопасное редактирование опубликованной формы (респонденты видят старую версию, пока автор не нажмёт «Опубликовать» снова).

### 3.3. Схема PostgreSQL

```sql
-- Идентификаторы: UUIDv7 (упорядочены по времени → дружелюбны к btree-индексам,
-- в отличие от UUIDv4). Генерируются в приложении, 5 строк кода без зависимостей.

CREATE TABLE users (
    id            UUID PRIMARY KEY,
    email         TEXT NOT NULL UNIQUE CHECK (email = lower(email)),
    password_hash TEXT,                        -- argon2id; NULL — вход только через провайдера (0009)
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Способы входа через внешних провайдеров (0009). Отдельной таблицей, а не
-- колонками в users: к аккаунту привязываются оба провайдера сразу, а третий
-- не требует миграции users. Аккаунт на адрес один (email остаётся UNIQUE),
-- способов входа в него несколько.
CREATE TABLE user_identities (
    provider         TEXT NOT NULL,   -- yandex | vk
    provider_user_id TEXT NOT NULL,
    user_id          UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (provider, provider_user_id)
);

-- Воркспейс закладываем сразу: перевести single-user SaaS на команды задним
-- числом — одна из самых болезненных миграций в индустрии. В MVP при регистрации
-- молча создаётся личный воркспейс, UI его не показывает.
CREATE TABLE workspaces (
    id         UUID PRIMARY KEY,
    name       TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE workspace_members (
    workspace_id UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    user_id      UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role         TEXT NOT NULL DEFAULT 'owner',  -- owner | editor (на будущее)
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (workspace_id, user_id)
);

CREATE TABLE forms (
    id            UUID PRIMARY KEY,
    workspace_id  UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    title         TEXT NOT NULL DEFAULT 'Untitled form', -- ПУБЛИЧНЫЙ заголовок (его видит респондент, OG-мета)
    name          TEXT,                          -- ВНУТРЕННЕЕ имя для дашборда (NULL → показываем title); ADR §10, миграция 0006
    slug          TEXT NOT NULL UNIQUE,          -- короткий id для публичной ссылки, nanoid(10)
    status        TEXT NOT NULL DEFAULT 'draft', -- draft | published | closed
    draft_schema  JSONB NOT NULL DEFAULT '{"blocks": []}',
    published_version_id UUID,                   -- FK на form_versions, ставится после публикации
    close_at       TIMESTAMPTZ,                  -- закрыть приём ПОСЛЕ момента (NULL=без даты); фаза 8.5 шаг 4, миграция 0007
    response_limit INT CHECK (response_limit > 0),-- жёсткий кап принятых ответов (NULL=без лимита)
    closed_message TEXT,                          -- текст экрана «приём закрыт» (NULL/пусто → дефолт рендерера)
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_forms_workspace ON forms (workspace_id, updated_at DESC);

CREATE TABLE form_versions (
    id         UUID PRIMARY KEY,
    form_id    UUID NOT NULL REFERENCES forms(id) ON DELETE CASCADE,
    version    INT  NOT NULL,
    schema     JSONB NOT NULL,                   -- иммутабельный снапшот
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (form_id, version)
);

CREATE TABLE submissions (
    id              UUID PRIMARY KEY,            -- UUIDv7 → сортировка по времени бесплатно
    form_id         UUID NOT NULL REFERENCES forms(id) ON DELETE CASCADE,
    form_version_id UUID NOT NULL REFERENCES form_versions(id),
    answers         JSONB NOT NULL,              -- { "<block_id>": <значение> }
    meta            JSONB NOT NULL DEFAULT '{}', -- user_agent, referer (без IP в открытом виде)
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_submissions_form ON submissions (form_id, created_at DESC);
-- Листинг ответов кабинета идёт курсором по id (UUIDv7 монотонен → «новые сверху»;
-- created_at при пакетной вставке нестабилен). Индекс покрывает фильтр по form_id
-- и keyset/сортировку по id одной структурой.
CREATE INDEX idx_submissions_form_id ON submissions (form_id, id DESC);

-- Визиты публичной формы (фаза 8.5 шаг 6, ADR §10): знаменатель к числу ответов и
-- фундамент воронки. Строка на визит, а не лог событий: воронке нужно одно число —
-- докуда дошёл человек. IP не пишется; cookie/localStorage рендерер не заводит.
CREATE TABLE form_visits (
    id              UUID PRIMARY KEY,            -- UUIDv7 клиента → второй бикон визита становится апсертом
    form_id         UUID NOT NULL REFERENCES forms(id) ON DELETE CASCADE,
    form_version_id UUID NOT NULL REFERENCES form_versions(id),
    last_block_id   TEXT,                        -- самая дальняя точка; NULL = ушёл, не тронув вопросов
    seq             SMALLINT NOT NULL DEFAULT 0 CHECK (seq >= 0), -- порядок биконов (sendBeacon его не гарантирует)
    submitted       BOOLEAN NOT NULL DEFAULT false, -- ставит ТОЛЬКО сервер при приёме ответа
    meta            JSONB NOT NULL DEFAULT '{}', -- user_agent, referer, utm (без IP)
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- Покрывающий: счётчики карточки, конверсия и GROUP BY воронки идут index-only
-- (замер: 6 буферов против 536 у индекса по одному form_id).
CREATE INDEX idx_form_visits_form ON form_visits (form_id, last_block_id, submitted);

-- Сессии в БД, а не JWT: мгновенный отзыв, «выйти со всех устройств»,
-- нет проблемы ротации ключей. Хранится только SHA-256 от токена.
CREATE TABLE sessions (
    token_hash BYTEA PRIMARY KEY,
    user_id    UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    expires_at TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_sessions_expires ON sessions (expires_at);
```

Ответы (`answers`) хранятся как JSONB по ключу `block_id`, а не нормализованной таблицей `answer_values` — по тем же причинам, что и схема формы: ответ читается и пишется атомарно, аналитические запросы «внутрь» ответов в MVP сводятся к экспорту CSV, который собирается в приложении. Если позже понадобится тяжёлая аналитика — данные денормализуются в отдельную таблицу фоновым процессом, исходник в JSONB ничего не теряет.

### 3.4. Формат JSONB-схемы формы

Схема версионируется полем `schemaVersion` — это позволит эволюционировать формат без миграций БД (читатель применяет upgrade-функции на лету). Текущая версия — **2**: вопрос разложен на самостоятельные блоки, объединённые в группу (ADR §10).

```jsonc
{
  "schemaVersion": 2,
  "blocks": [
    // Вопрос = группа блоков с общим groupId: подпись (title/label) + поле (input).
    {
      "id": "blk_9f2k1x",
      "groupId": "grp_a1",
      "type": "title",
      "label": "Ваше имя"
    },
    {
      "id": "blk_7ab3m2",
      "groupId": "grp_a1",
      "type": "short_text",
      "required": true,
      "settings": {}
    },
    // Голое поле без подписи: своя группа; подпись в аналитике генерится.
    {
      "id": "blk_2m8q0",
      "groupId": "grp_a2",
      "type": "email",
      "required": false,
      "settings": { "placeholder": "you@example.com" }
    },
    // Секционный контент вне вопроса (heading | text | image) — своя группа.
    {
      "id": "blk_5h1td",
      "groupId": "grp_a3",
      "type": "heading",
      "label": "О компании"
    }
  ],
  "submitLabel": "Отправить",
  "thankYouText": "Ждём вас!",
  "redirectUrl": ""
}
```

**Вопрос — это группа блоков, а не один блок.** Блоки одного вопроса несут общий `groupId` и идут подряд; в группе не более одного отвечаемого блока. Подпись вопроса — блок `title` (крупная) или `label` (мелкая) той же группы; между подписью и полем можно вставлять контент (`heading`/`text`/`image`). Голое поле — группа из одного отвечаемого блока: допустимо, форма может состоять из одних полей без подписей. Типы блоков: отвечаемые (`short_text`, `long_text`, `email`, `phone`, `number`, `scale`, `single_choice`, `dropdown`, `multi_choice`, `date`, `consent`), подписи (`title`, `label`) и контент (`heading`, `text`, `image`).

**Подпись для аналитики берётся из группы, а не из поля.** `QuestionOrder` (единая точка на CSV, сводку и воронку) для каждого отвечаемого блока читает подпись из `title`/`label` его группы; нет подписи — **генерирует** имя (плейсхолдер, иначе тип+номер), чтобы колонка и шаг воронки не остались безымянными. Привязка подписи к полю **явная, по `groupId`, не по позиции**: перетаскивание блоков не переклеивает подпись на чужой инпут — тот класс молчаливых расхождений, которого избегает `internal/domain/questions.go`.

Критично: `id` **отвечаемых** блоков стабильны и генерируются один раз при создании — `answers` и `form_visits.last_block_id` ссылаются на них, поэтому ни переименование, ни разложение вопроса на подпись+поле связь ответа с вопросом не рвут. Апгрейд v1→v2 сохраняет id отвечаемого блока: старый блок `{label, description}` превращается в группу `title(label) + text(description) + input` с тем же id у инпута.

Типы различаются не только контролом, но и **семантикой ответа**, и она задаётся предикатами, а не сравнением с конкретным типом: `isChoice()` (у типа есть список опций — `single_choice`, `dropdown`, `multi_choice`), `isSingleChoice()` (ответ — один id, а не массив: `single_choice`, `dropdown`), `isCaption()` (подпись группы — `title`, `label`), `isContent()` (блок не собирает ответ вовсе: `title`, `label`, `heading`, `text`, `image`). Новый тип добавляется в предикат, а не в цепочку `if type == …` по коду: ветка, забывшая новый тип, не падает — она молча трактует его как что-то другое (`dropdown`, забытый в `isSingleChoice`, начинает ждать массив вариантов). Полный чек-лист сквозного среза — `web/shared/fields/README.md`.

Значение ответа хранится **строкой** у всех скалярных типов, включая число, дату, шкалу и согласие (`"yes"`/пусто) — раскладка по типам в `docs/SCHEMA.md`. Это держит клиентский тип `Answer` в границах `string | string[]` и делает «пусто» единым признаком «не отвечено» для проверки обязательности.

Поля формы-уровня (`submitLabel`, `thankYouText`, `redirectUrl`) лежат в схеме, а не в колонках `forms`, осознанно: схема снапшотится при публикации, поэтому респондент видит тот экран благодарности, который был в версии, по которой он отправил ответ — иммутабельность достаётся без отдельного механизма. Обратная сторона того же выбора: настройка, обязанная быть **живой** (лимит ответов, дата закрытия — фаза 8.5 шаг 4), в схеме жить не должна. Такие настройки получили **колонки** `forms.close_at`/`response_limit`/`closed_message` (ADR §10): владелец меняет их без перепубликации, проверка идёт против текущего значения. «Фактически закрыта» не хранится, а **вычисляется** на чтении — `status='closed'` (снята вручную) ИЛИ `status='published'` и (дата прошла ИЛИ `count ≥ лимит`); `status` по дате/лимиту не флипается, поэтому крон не нужен и продление даты переоткрывает форму мгновенно.

`redirectUrl` — единственное место схемы, где **черновик проверяется строго**: разрешён только абсолютный `http(s)`-адрес с хостом (`ValidateSchema` → 422). Значение уходит в `window.location` рендерера, поэтому чужая схема (`javascript:`, `data:`) — это XSS на публичном домене формы (инвариант 4), и пускать её в JSONB нельзя даже как «недособранное состояние». Строгость оплачена на фронте: редактор коммитит поле по `blur`, поэтому автосейв не видит недопечатанный URL. Рендерер проверяет ссылку повторно перед переходом — доверять содержимому схемы на месте использования нельзя.

## 4. Backend на Go

### 4.1. Философия зависимостей

Требование «как можно меньше зависимостей» с Go 1.22+ выполняется почти буквально. Runtime-зависимостей четыре:

```
github.com/jackc/pgx/v5          — драйвер PostgreSQL (стандарт де-факто, database/sql ему проигрывает)
golang.org/x/crypto              — argon2id для паролей (квазистандартная библиотека)
github.com/golang-migrate/migrate — миграции (или goose; можно и свой раннер на 100 строк)
github.com/google/uuid           — UUID (v7 поддерживается; альтернатива — 30 строк своего кода)
```

Всё остальное — стандартная библиотека: роутинг (`net/http` с method-паттернами из Go 1.22: `mux.HandleFunc("GET /api/v1/forms/{id}", ...)`), логирование (`log/slog`), конфигурация (env-переменные через `os.Getenv` + маленький хелпер), JSON (`encoding/json`), тесты (`testing` + `net/http/httptest`). Никаких Gin/Echo/Fiber — они не дают ничего, чего нет в stdlib 1.22+, но приносят чужие абстракции.

Отдельно про SQL: вместо ORM — **sqlc** как dev-time кодогенератор. Пишете SQL, получаете типизированные Go-функции. В рантайме зависимость нулевая (генерирует код поверх pgx), а класс ошибок «опечатка в имени колонки» ловится на этапе сборки. Это компромисс senior-уровня: сырой pgx без sqlc тоже допустим, но sqlc убирает boilerplate без ORM-магии.

### 4.3. Слои и их ответственность

**Handler (transport)** — только HTTP: декодировать запрос, вызвать сервис, закодировать ответ. Ни одной бизнес-проверки. Ошибки домена маппятся на HTTP-статусы в одном месте (`respond.go`): `ErrNotFound → 404`, `ErrForbidden → 403`, `ErrValidation → 422` с деталями по полям.

**Service** — вся бизнес-логика и авторизация. Пример инварианта, живущего здесь: «публиковать форму может только участник её воркспейса; публикация создаёт новую версию и обновляет `published_version_id` в одной транзакции».

**Repository** — только SQL. Интерфейсы репозиториев объявляются на стороне сервиса (потребителя), а не реализации — классический Go-идиоматичный DIP, позволяющий тестировать сервисы с фейками без mock-библиотек.

**Domain** — типы и чистые функции. Ключевой обитатель: валидатор `ValidateAnswers(schema FormSchema, answers map[string]any) error`, который проверяет ответ респондента против конкретной версии схемы (обязательность, типы, принадлежность выбранных опций). Он используется и при приёме ответа, и в тестах, и нигде не касается ни HTTP, ни SQL.

### 4.4. Сквозные механики

**Контексты и таймауты.** Каждый запрос несёт `context.Context` с дедлайном (middleware ставит, например, 10 секунд); pgx его уважает, зависшие запросы отменяются. У `http.Server` выставлены `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout` — без них публичный эндпоинт уязвим к slowloris.

**Graceful shutdown.** По SIGTERM: перестать принимать соединения, дождаться активных запросов (с потолком 15 секунд), закрыть пул БД. Это не роскошь — это то, что делает деплой без ошибок 502.

**Структурные логи.** `slog` в JSON, в stdout (докер соберёт). Middleware генерирует `request_id` (отдаётся и в заголовке ответа) и кладёт логгер с ним в контекст — каждая строка лога любого слоя привязана к запросу.

**Единый формат ошибок API:**

```json
{ "error": { "code": "validation_failed", "message": "...", 
             "fields": { "blk_9f2k1x": "обязательное поле" } } }
```

**Rate limiting.** Один VPS — значит in-memory token bucket (реализация на `map` + `sync.Mutex`, ~60 строк, без Redis). Ведро на эндпоинт, ключ — IP: жёсткие на `POST /public/.../submissions`, `POST /auth/login`, `POST /auth/register` и `POST /public/.../visits` (у визитов щедрее — один визит шлёт минимум два бикона), мягкий на остальное. Обёртка одна на всех — `httpserver.RateLimitByIP(limiter, trustedProxy, msg)`; ёмкость ведра остаётся у модуля. При переезде на несколько инстансов заменяется на Redis — интерфейс `RateLimiter` закладывается сразу.

**Периодические задачи.** Отдельная горутина в том же процессе: чистка истёкших сессий раз в час. Не cron, не отдельный воркер — незачем.

### 4.5. Аутентификация

Пароли — argon2id с параметрами по рекомендациям OWASP (память 64 МБ, итерации 3). Сессия — 256-битный случайный токен; клиенту уходит в httpOnly, Secure, SameSite=Lax cookie host-only на домене кабинета `app.example.com` (API — same-origin под `/api`, отдельного домена нет, ADR §10); в БД хранится только его SHA-256 (утечка дампа БД не даёт живых сессий). CSRF: для мутирующих запросов SPA шлёт заголовок `X-CSRF-Token`, выданный при логине (double-submit); плюс строгая проверка заголовка `Origin` против сконфигурированного origin кабинета (`APP_ORIGIN`) — чужой Origin отклоняется до сверки токена, пустой (редкие клиенты) падает на double-submit. Вместе с `SameSite=Lax` на cookie сессии это перекрывает CSRF и в same-origin-схеме (ADR §10). Публичный эндпоинт отправки форм CSRF-защиты не требует (он и так анонимный), но защищается rate-limit'ом и антиспамом.

### 4.6. Контракт API

```
Приватный API (cookie-сессия), префикс /api/v1:

POST   /auth/register                 регистрация (создаёт user + личный workspace)
POST   /auth/login                    вход
POST   /auth/logout                   выход
GET    /auth/me                       текущий пользователь
GET    /auth/providers                включённые провайдеры входа (пусто → кнопок нет)
GET    /auth/oauth/{provider}/start   уход к провайдеру (302; ставит state+verifier cookie)
GET    /auth/oauth/{provider}/callback возврат от провайдера (302 в кабинет; email занят → экран привязки, сессии нет)
POST   /auth/oauth/link               привязка провайдера к существующему аккаунту по паролю

GET    /workspaces                    список воркспейсов текущего пользователя (в MVP — один личный)

GET    /forms                         список форм воркспейса (курсорная пагинация, поиск q, сортировка sort)
POST   /forms                         создать форму
GET    /forms/{id}                    форма + draft_schema
GET    /forms/lookup?slug={slug}      то же по slug (URL кабинета адресует форму slug'ом, как рендерер /r/{slug}; slug в query — путь by-slug/{slug} конфликтует с {id}/submissions)
PATCH  /forms/{id}                    обновить name / title / draft_schema / closeSettings (ровно одно; автосейв билдера / настройки закрытия)
DELETE /forms/{id}
POST   /forms/{id}/publish            снапшот черновика → новая версия
POST   /forms/{id}/unpublish

GET    /forms/{id}/submissions        ответы (курсорная пагинация по UUIDv7-id)
GET    /forms/{id}/submissions/export CSV (стриминг, encoding/csv прямо в ResponseWriter)
GET    /forms/{id}/submissions/summary сводка: распределения/статистика (агрегирует сервер — наружу только счётчики)
GET    /forms/{id}/funnel             воронка визитов: докуда дошли и где остановились (наружу только счётчики)
DELETE /forms/{id}/submissions/{sid}  удалить один ответ (GDPR-гигиена)

Публичный API (без авторизации), префикс /public/v1:

GET    /forms/{slug}                  опубликованная версия схемы (Cache-Control + ETag); закрытая → 410 «приём закрыт» (title+closedMessage); черновик/нет → 404
POST   /forms/{slug}/submissions      отправка ответа (закрытая/лимит → 410; черновик/нет → 404); необязательный visit_id → отметка конверсии
POST   /forms/{slug}/visits           визит формы биконом рендерера, 204 (закрытая → 410; черновик/нет → 404); своё ведро rate-limit
```

Пагинация — курсорная с первого дня (`?cursor=<непрозрачный токен>&limit=50`): offset-пагинация на больших таблицах ответов деградирует и её пришлось бы переделывать. Ключ курсора зависит от порядка сортировки списка. Для ответов (`submissions`) он одноколоночный — сам UUIDv7-id: они иммутабельны и монотонны по времени создания. Для форм список сортируется по свежести правки (`updated_at DESC`), а `updated_at` меняется при переименовании/автосейве, поэтому курсор **составной** — пара `(updated_at, id)` с keyset-условием `(updated_at, id) < (курсор)`: стабилен, если форму отредактировали во время листания. Клиенту токен непрозрачен (сервер кодирует пару в base64url).

### 4.7. Приём ответа: полный путь запроса

Самый нагруженный и самый атакуемый эндпоинт, поэтому распишем его целиком. `POST /public/v1/forms/{slug}/submissions`: (1) rate-limit по IP; (2) `http.MaxBytesReader` на 256 КБ — потолок размера тела; (3) поиск формы по slug (черновик/нет формы → 404, приватное не раскрывается); (3b) **проверка «форма закрыта»**: снята вручную или наступила дата закрытия → `410 Gone` «приём закрыт» (лимит здесь не проверяется — см. (6)); (4) антиспам: honeypot-поле (скрытое поле, заполнил — молча отвечаем 200 и выбрасываем) и минимальное время заполнения (в схему при выдаче кладётся подписанный HMAC-токен с временем выдачи; ответ, пришедший быстрее 3 секунд, — бот); (5) `ValidateAnswers` против схемы опубликованной версии; (6) INSERT с `form_version_id` — при заданном лимите под `pg_advisory_xact_lock` по форме: **жёсткий кап** (ADR §10), счёт и вставка сериализованы одной транзакцией, перебор невозможен; порядок «вставка → счёт» сохраняет идемпотентность (ретрай упирается в PK, `n=0`, проходит мимо лимита), новая вставка сверх лимита откатывается → `410`; форма без лимита пишется без блокировки; (7) 201. Идемпотентность: клиент генерирует `submission_id` (UUIDv7) сам и шлёт его в теле; повторная отправка после сетевого сбоя упирается в PRIMARY KEY и возвращает тот же 201 — двойных ответов от ретраев не бывает, даже у заполненной формы.

## 5. Frontend

### 5.1. Приложение-конструктор (web/app)

Стек: Vite, React 18, TypeScript strict, TanStack Router (file-based, типобезопасные параметры маршрутов), TanStack Query (весь серверный стейт). Дополнительно оправданы только три маленькие зависимости: Zod (валидация ответов API и единый источник типов), zustand (локальный стейт билдера, ~1 КБ) и dnd-kit (drag-and-drop блоков — писать своё здесь неоправданно).

Для UI-слоя кабинета (фаза 6.5, Notion/Tally-редизайн) заморозка зависимостей снята: подключены **Tailwind CSS v4 + shadcn/ui** (Radix-примитивы, `class-variance-authority`, `tailwind-merge`, `clsx`, `lucide-react`). Обоснование в ADR-сводке. Это касается **только web/app**: рендерер (web/renderer) остаётся на react+zod, а общие компоненты полей `@fields` (используются обоими приложениями) не переводятся на Tailwind — сохраняют фреймворко-независимые `rf-*` CSS-классы, чтобы не тянуть Tailwind в рендерер и не ломать его бюджет 95 КиБ.

Вид всей формы — заголовок (`rf-title`), поля (`rf-label`/`rf-input`/`rf-mark`), кнопка отправки (`rf-submit`), раскладка (`rf-page`) — описан один раз в `web/shared/fields/fields.css` (правила `rf-*` + токены `--rf-*`, независимые от Tailwind/shadcn) и надевается **тремя** поверхностями: редактором (`BlockRow`/`SlashEditor` навешивают `rf-*` поверх Tailwind-layout/dnd), превью билдера (`PreviewPane`) и рендерером (`FormView`). Источник истины вида — форма в режиме редактирования; значения `rf-*` повторяют токены/утилиты shadcn-редактора, но в plain-CSS, чтобы рендерер читал их без Tailwind. Так все три вида формы совпадают (WYSIWYG), а бюджет рендерера не затронут (перенесён CSS, не JS). Практический гайд «как добавить тип поля/элемент/стиль в полотно и не разъехаться» — `web/shared/fields/README.md`.

Организация кода — feature-sliced, зеркально бэкенду:

```
web/app/src/
├── app/                # провайдеры, router, QueryClient, error boundary
├── routes/             # file-based маршруты TanStack Router
│   ├── _auth/          #   layout-группа: login, register
│   └── _app/           #   layout-группа с проверкой сессии
│       ├── forms.index.tsx          # список форм
│       ├── forms.$slug.edit.tsx     # билдер (URL адресует форму slug'ом, как /r/{slug})
│       └── forms.$slug.responses.tsx
├── features/
│   ├── auth/           # api.ts, hooks.ts, компоненты
│   ├── form-builder/   # стор билдера, палитра блоков, канвас, панель настроек
│   └── submissions/    # таблица ответов, экспорт
├── entities/           # типы домена (Zod-схемы FormSchema, Block — общие с renderer)
└── shared/             # api-клиент (fetch-обёртка), ui-кит, утилиты
```

**Разделение стейта — главное фронтовое решение.** Серверный стейт (списки форм, ответы, профиль) живёт только в TanStack Query: кэш, инвалидация, ретраи. Стейт билдера — принципиально другой зверь: это высокочастотный локальный документ (каждое нажатие клавиши в label), его нельзя гонять через Query. Поэтому билдер работает так: при открытии форма загружается через Query и гидрирует zustand-стор; все правки — синхронные операции над стором (мгновенный UI); дебаунс-автосейв (800 мс тишины) шлёт `PATCH /forms/{id}` целиком с `draft_schema`. Статус «Сохранено / Сохраняется / Ошибка» — из состояния мутации. Undo/redo достаётся почти бесплатно: стор хранит стек снапшотов схемы.

Конфликты редактирования в MVP решаются оптимистичной блокировкой: `PATCH` несёт `updated_at`, при расхождении сервер отвечает 409, клиент предлагает перезагрузить. Дёшево и честно; CRDT — не для MVP.

**Типы — из одного источника.** Zod-схемы `FormSchema`/`Block` лежат в `entities` и импортируются и конструктором, и рендерером. Ответ API парсится через Zod на границе — расхождение контракта ловится сразу, а не глубоко в UI. (Альтернатива посерьёзнее — генерация типов из OpenAPI; для MVP Zod-схемы руками дешевле.)

### 5.2. Публичный рендерер (web/renderer)

Отдельный Vite-проект: React + общие Zod-типы из `entities` и общие компоненты полей из `shared/fields` (те же, что рисуют превью в билдере), ничего больше. Никакого роутера (slug парсится из `location.pathname`), никакого TanStack Query (один `fetch` формы, один `POST` ответа), стейт — `useReducer`. Клиентская валидация дублирует серверную по той же схеме (та же Zod-схема — то же поведение). Ошибки сервера 422 маппятся на поля по `block_id`. После отправки — экран «Спасибо» и очистка черновика ответа из sessionStorage (черновик спасает респондента от потери введённого при случайном обновлении страницы).

**Бандл и запасной выход на Preact.** Целевой вес держим низким, но порог сознательно выше «круглых» 60 КБ gzip: React + react-dom исчерпывают его сами по себе (замерено в фазе 3). Точное число бюджета фиксируется в фазе 4 и проверяется в CI. Если из-за веса рендерер не берёт Lighthouse ≥90 на мобиле — предусмотрен дешёвый свап на Preact: `react → preact/compat` алиасом **только в сборке рендерера**, компоненты остаются написанными на React-API, `shared/fields` не переписываются. Именно ради этого выхода поля пишутся на React-API, а не как SSR-шаблоны: мы не заперты в конкретном рантайме.

**Превью ссылок — «голова» рендерится на сервере.** Рендерер клиентский, поэтому мета для превью в мессенджерах/соцсетях (Open Graph) он сам дать не может: краулеры читают HTML, не выполняя JS. Поэтому HTML-документ страницы формы (`/r/{slug}`) отдаёт **Go**, а не статика: он подтягивает опубликованную форму и подставляет в `<head>` `og:title`/`og:description` из её title и описания, плюс `og:image` — в MVP общая брендовая заглушка (базовый URL — из env; своя картинка на форму — вместе с загрузкой файлов, пост-MVP). Тело того же документа грузит React-SPA. Механически Go **строит страницу из собранного `index.html` рендерера** (паттерн vite-SSR template-replace): читает готовый HTML и заменяет в нём плейсхолдер `<!--og-meta-->` на мету формы, а все ссылки на ассеты берёт из этого HTML как есть — список ассетов имеет единственного владельца (сборку vite), Go его не дублирует, поэтому новый ассет не рождает прод-only расхождения. Пользовательский текст в мета вставляется только через автоэкранирование `html/template` (инъекция вида `"><script>` в названии формы недопустима). **Черновик/несуществующая** форма по этому пути отдаёт 404 — HTML не раскрывает существование приватного больше, чем JSON-ручка. **Закрытая** форма (фаза 8.5 шаг 4) отдаёт тот же SPA-шелл (200): клиент по JSON-ручке получит 410 и нарисует «приём закрыт» — форма была публичной, её существование уже не секрет (инвариант 5 остаётся только за черновиком). Полный SSR формы сознательно отвергнут: он раздул бы рендерер и заставил дублировать рендер полей на сервере, разъехавшись с превью билдера; head-injection даёт превью почти без сложности.

## 6. Инфраструктура на VPS

### 6.1. Состав

Docker Compose из контейнеров: `caddy`, `api`, `postgres` (+ одноразовый `migrate` тем же образом, что и `api`, — гейт «api стартует после миграций»). Caddy выбран вместо Nginx осознанно: автоматический TLS (Let's Encrypt), конфиг в 30 строк, встроенная раздача статики с правильными заголовками. Статика фронтендов (JS/CSS/картинки) кладётся в volume, который Caddy раздаёт напрямую — байты статики Go не отдаёт. Динамику Caddy проксирует в Go same-origin: на `app` — `/api/*` (приватный API кабинета), на `f` — `/public/*` (публичный API) и `/r/{slug}` (HTML-документ формы с превью-мета Open Graph, см. 5.2). Две origin, не три (ADR §10): выделенного `api`-домена нет, поэтому CORS не нужен ни на одном контуре.

```
# deploy/compose.yml (суть)
services:
  caddy:
    image: caddy:2
    ports: ["80:80", "443:443"]
    volumes: [caddy_data:/data, ./caddy:/etc/caddy,
              ./static:/srv/static]
  api:
    image: ghcr.io/you/forms-api:${TAG}
    env_file: .env
    depends_on: { postgres: { condition: service_healthy } }
    restart: unless-stopped
  postgres:
    image: postgres:16
    volumes: [pg_data:/var/lib/postgresql/data]
    healthcheck: { test: ["CMD-SHELL", "pg_isready -U forms"] }
    restart: unless-stopped
    # порт наружу НЕ публикуется
```

```
# Caddyfile (суть). Домены — через env ({$APP_DOMAIN}, {$RENDERER_DOMAIN}), один
# файл на prod-local (*.localhost, внутренний CA) и прод (реальные, Let's Encrypt).
# Две origin: кабинет+API и рендерер+публичный API. Выделенного api-домена нет.
{$APP_DOMAIN} {
    handle /api/* { reverse_proxy api:8080 }   # приватный API — тот же origin, без CORS
    handle {                                   # всё прочее — статика кабинета
        root * /srv/static/app
        try_files {path} /index.html           # SPA fallback
        file_server
        header /assets/* Cache-Control "public, max-age=31536000, immutable"
    }
}
{$RENDERER_DOMAIN} {
    handle /r/*      { reverse_proxy api:8080 } # HTML-документ формы (OG-мета) из Go
    handle /public/* { reverse_proxy api:8080 } # публичный API — рендерер зовёт same-origin
    handle {                                    # ассеты и всё прочее — статикой
        root * /srv/static/renderer
        try_files {path} /index.html
        file_server
    }
}
```

Go-образ — multi-stage: сборка в `golang:1.26` (в тон `go.mod`), рантайм — `gcr.io/distroless/static:nonroot` со статическим бинарником (`CGO_ENABLED=0`). Итоговый образ ~25 МБ, поверхность атаки минимальна. Бинарник умеет `./api migrate up` — миграции гоняются тем же образом перед стартом.

### 6.2. CI/CD

GitHub Actions, два пайплайна. **CI на каждый PR:** `go vet` + `golangci-lint`, `go test -race ./...`, `tsc --noEmit` + `eslint` + `vitest` для обоих фронтов, сборка образа. **CD на тег:** пуш образа в GHCR, сборка статики, затем деплой по SSH: `rsync` статики, `docker compose pull && docker compose up -d` (запускает миграции и перезапускает api). Секреты — в GitHub Secrets и в `.env` на сервере (права 600), не в репозитории. Откат = деплой предыдущего тега; миграции поэтому пишутся обратно-совместимыми (add column — да, drop column — только через релиз после того, как код перестал её читать).

### 6.3. Бэкапы — самое важное после самого кода

Данные форм — это весь бизнес. Скрипт по cron каждые 6 часов: `pg_dump -Fc` → шифрование `age` → загрузка в S3-совместимое хранилище **другого провайдера** (бэкап на том же VPS — не бэкап). Ротация: 14 суточных, 8 недельных. Обязательный ритуал: раз в месяц тестовое восстановление на локальной машине — непроверенный бэкап равен отсутствующему. Для MVP point-in-time recovery через WAL-архивацию избыточен; отметить как апгрейд при появлении платящих клиентов.

### 6.4. Наблюдаемость

Прагматичный минимум, а не карго-культ Prometheus+Grafana на одном VPS. Три слоя: (1) структурные JSON-логи в journald через docker logging driver, с ротацией; (2) эндпоинт `GET /healthz` (проверяет ping БД) + внешний мониторинг аптайма (Uptime Kuma на другой машине или бесплатный внешний сервис) с алертом в Telegram; (3) счётчики в самом приложении — middleware пишет в лог сводку по каждому запросу (метод, путь-паттерн, статус, длительность), и `lnav`/`jq` по логам закрывает 90 % вопросов «что происходило». Sentry-подобный сервис (self-hosted GlitchTip) — полезное раннее дополнение для фронтовых ошибок, но не блокер запуска.

### 6.5. Харденинг VPS

Стандартный чек-лист: вход только по SSH-ключам, root-логин выключен; ufw — открыты только 22/80/443; fail2ban на SSH; автоматические security-обновления (unattended-upgrades); Postgres не слушает наружу вообще (только docker-сеть); отдельный непривилегированный пользователь для деплоя.

## 7. Безопасность приложения

Сводка мер, разбросанных по документу, плюс недостающее. Валидация всего входа на границе (Zod на фронте — UX, Go-валидатор на бэке — истина). Авторизация на каждый ресурс в service-слое: каждый запрос формы проверяет членство в воркспейсе, id из URL никогда не доверяется сам по себе (защита от IDOR). Экранирование пользовательского контента: label'ы блоков рендерятся как текст, никакого `dangerouslySetInnerHTML`; OG-мета публичной формы (title/описание) вставляются в `<head>` только через автоэкранирование `html/template`; CSP-заголовки на обоих доменах (`app`, `f`): `script-src 'self'` (собранные бандлы без inline-скриптов — сильная защита от XSS), `style-src 'self' 'unsafe-inline'` (Radix/dnd-kit пишут инлайн-`style`), прочее `'self'`; отличается только `frame-ancestors` (`'none'` на `app`, `'self'` на `f`). Плюс `X-Content-Type-Options: nosniff` и `X-Frame-Options` (`DENY` на `app`, включая проксируемый `/api/*` — тот же origin; `SAMEORIGIN` на рендерере `f`: позже формам понадобится embed — тогда осознанно ослабим), `Referrer-Policy: strict-origin-when-cross-origin`, `Strict-Transport-Security` (HSTS; срок `max-age` из env `HSTS_MAX_AGE` — на реальном проде год + `includeSubDomains`, на prod-local `0` = «забыть HSTS», иначе `*.localhost` заперся бы на https для всех локальных проектов), снятие заголовка `Server`. Заголовки задаются в Caddy на уровне сайта (общий сниппет), поэтому покрывают и статику, и проксируемую динамику. Ответы респондентов — потенциально персональные данные: IP в чистом виде не храним (только хэш для антиспама в meta), экспорт доступен только участникам воркспейса, `DELETE` формы каскадно уносит ответы.

## 8. Тестирование

Пирамида, смещённая к интеграционным тестам — для CRUD-приложения с БД это честнее юнит-моков. **Юниты** — для чистой логики: `ValidateAnswers` (самая ветвистая функция проекта), апгрейдеры schemaVersion, CSV-маппинг. **Интеграционные** — сервис+репозиторий против настоящего Postgres в контейнере (testcontainers-go — единственная тестовая зависимость, которая того стоит; каждый тест в своей транзакции с откатом). **API-тесты** — `httptest` поверх собранного приложения: сценарий «регистрация → создать форму → опубликовать → отправить ответ анонимно → увидеть его в листинге → экспорт CSV» как один сквозной тест — это живая документация продукта. На фронте: vitest для логики стора билдера (undo/redo, операции над блоками), Playwright — smoke-сценарии против `make prod-local`, гоняются в CI перед деплоем: `full-loop` (тот же сквозной путь), `form-settings` (настройки формы глазами респондента: свой текст благодарности и лимит мест) и `visits-funnel` (аналитика). Два последних отделены намеренно — они не проходят через билдер, иначе краснели бы от правок редактора, ничего не говоря про свой предмет; отсюда общее правило: **через билдер кликами ходит только `full-loop`, остальные строят форму запросами к API**. К тому же бикон визита проверяется **только** там, где есть настоящая CSP (см. `docs/ANALYTICS.md` §7).

## 9. Порядок работ

Разумная последовательность без искусственных дедлайнов. **Этап 1 — скелет:** репозиторий, Makefile, CI, docker compose локально, миграции, healthz, деплой «hello world» на VPS — конвейер до прода должен заработать раньше фич. **Этап 2 — auth:** регистрация, сессии, middleware, `/auth/me`, экраны входа. **Этап 3 — формы:** CRUD, JSONB-схема, публикация с версиями; параллельно билдер с автосейвом. **Этап 4 — публичный контур:** рендерер, приём ответов с валидацией, антиспам, rate limit. **Этап 5 — ответы:** таблица, пагинация, CSV. **Этап 6 — прод-готовность:** бэкапы + тестовое восстановление, мониторинг, харденинг, сквозной Playwright-тест.

После MVP очередь примерно такая: приглашения в воркспейс (схема уже готова) → вебхуки на новый ответ (таблица `outbox` + горутина-доставщик, паттерн transactional outbox) → условная логика (расширение JSONB-схемы полем `logic`, schemaVersion=2) → загрузка файлов (S3-совместимое хранилище, presigned URL) → биллинг.

## 10. Реестр ключевых решений (ADR-сводка)

| Решение | Альтернатива | Почему так |
|---|---|---|
| Модульный монолит | Микросервисы | Нагрузка MVP не оправдывает распределённость; границы модулей дают путь к распилу |
| Схема формы в JSONB | Нормализованные таблицы | Форма читается/пишется целиком; эволюция без миграций |
| Иммутабельные версии при публикации | Ответы ссылаются на живую форму | Интерпретируемость исторических ответов; безопасное редактирование |
| Сессии в Postgres | JWT | Мгновенный отзыв, нет ротации ключей, один SELECT дешёв |
| stdlib `net/http` 1.22 | Gin/Echo | Method-роутинг уже в stdlib; меньше чужих абстракций |
| sqlc | ORM / сырой pgx | Типобезопасный SQL без рантайм-зависимости |
| Два фронт-приложения | Один SPA | Рендерер должен быть лёгким и быстрым для респондентов |
| HTML публичной формы рендерит Go (OG-мета в `<head>`), тело — React-SPA | Полный SSR формы / чистый SPA | Превью ссылок требуют server-side мета; полный SSR раздувает рендерер и дублирует рендер полей, чистый SPA не даёт превью |
| UUIDv7 | serial / UUIDv4 | Нелокальность v4 бьёт по индексам; serial неудобен для клиентской генерации |
| Курсорная пагинация | OFFSET | Не деградирует на больших таблицах ответов |
| Caddy | Nginx | Авто-TLS и конфиг кратно проще при том же результате |
| Две origin (`app` + его API same-origin, `f` — публичный рендерер) | Три домена с выделенным `api.` | Кабинет и его API — один first-party продукт; отдельный API-origin давал только CORS и cross-site-cookie (лишняя сложность и класс тонких багов). Same-origin: cookie host-only на `app`, CSRF-токен + проверка `Origin`, кода менять не нужно (фронты уже зовут относительные `/api`, `/public`). Граница `f` сохранена осознанно — изоляция cookie кабинета от публичной формы. Выделенный `api`-домен вернётся с публичным API-продуктом (пост-MVP) |
| In-memory rate limit | Redis | Один инстанс; интерфейс позволяет заменить позже |
| shadcn/ui + Tailwind в кабинете (web/app) | Ручной CSS / только Radix-примитивы | Notion/Tally-оболочка и slash-редактор требуют богатого набора доступных примитивов (command-палитра, dropdown, dialog, sidebar); скорость сборки UI перевешивает +6 зависимостей. **Только web/app**: рендерер (web/renderer) остаётся на react+zod под бюджетом 95 КиБ, общие компоненты `@fields` не переводятся на Tailwind |
| Вид поля — общий `web/shared/fields/fields.css` (`rf-*` + токены `--rf-*`), надевают редактор, превью и рендерер | Дублировать вид в каждой поверхности (Tailwind в редакторе, `rf-*` в `index.css` фронтов) | Форму видят три поверхности (редактор-эталон, превью, респондент); единый визуальный язык в plain-CSS исключает рассинхрон. Редактор надевает `rf-*` поверх Tailwind-layout, рендерер читает тот же CSS без Tailwind → бюджет 95 КиБ не затронут |
| Внутреннее имя формы (`forms.name`) отдельно от публичного заголовка (`forms.title`) | Один `title` на обе роли | `title` — одно поле было и именем в дашборде, и заголовком для респондента (`rf-title`, OG-мета). Дубликат/организационное переименование меняли и публичный заголовок (например «(копия)» вылезал респонденту). Решение: `name` (NULL=не задано) — внутреннее имя кабинета, `title` остаётся публичным заголовком; дашборд показывает `name ?? title` (фолбэк — нет пустых имён). Дубликат суффиксит только `name`, `PATCH {name}` не трогает `title`. Рендерер/публичный API/OG-мета/схема не затронуты (миграция 0006) |
| Отдельный модуль `workspaces` (в MVP только чтение: `GET /workspaces` — список воркспейсов пользователя) | Имя воркспейса в `/auth/me`; читать из `forms` | Воркспейс — самостоятельная сущность (крошки кабинета, будущие создание/переключение), а не деталь auth или forms. `auth` его лишь создаёт при регистрации, `forms` читает членство для авторизации — владельца-модуля не было. Read-only сейчас (YAGNI): создание остаётся в транзакции регистрации `auth`, `forms` пока резолвит членство сам; оба переедут на модуль с приходом UI управления пространствами (пост-MVP) |
| Слой хранения объектов: агностичный S3-клиент (`internal/blob`) + доменные хранилища | Один `BlobStore` на всех потребителей / локальный диск | Объекты S3 несовместимы по политикам (public-картинки vs private-файлы vs бэкапы); двухслойность + узкие интерфейсы у потребителя дают переиспользование без god-интерфейса. S3 сразу (не диск) — фундамент под Фазы 17/10; MinIO локально, арендованное S3 в проде, разница только env. Дизайн — `docs/DESIGN-s3-media.md` |
| Ручной sigv4 в `internal/blob` | minio-go / AWS SDK | Нужны Put/Delete (чтение public — без подписи); малая поверхность не оправдывает зависимость сверх замороженного списка |
| Картинки форм: public-read бакет `app-media`, раздача Caddy `/media/*` same-origin; ключ в схеме, не URL | Presigned-GET / прямой URL бакета в CSP / URL в JSONB | Картинки публичны по природе; same-origin даёт `img-src 'self'` и прячет endpoint; ключ+`MEDIA_BASE_URL` переносим между провайдерами. Presigned ломает кэш/og:image |
| Тип блока `image` — контентный (не отвечаемый) | Отвечаемый тип / отдельная сущность | Как `text`: статический контент полотна, исключён из ответов/CSV; ложится на существующий каркас 8-го типа |
| Вопрос — группа самостоятельных блоков (`groupId`): подпись `title`/`label` + отвечаемое поле + контент `heading`/`text`/`image` между ними; поле `description` убрано; `schemaVersion 1→2`, upgrade на чтении сохраняет id отвечаемого блока | Приклеенная к полю подпись (welded) / позиционная привязка заголовка / нормализованные таблицы вопросов | Гибкость Tally: `title`/`label`/поле — отдельные блоки (отдельные пункты «/», подсказки «добавить заголовок/поле»), контент между подписью и полем, голые поля, форма без подписей. Аналитика честная: id отвечаемого блока остаётся ключом ответа и шагом воронки; подпись берётся из группы через единую `QuestionOrder` (нет → генерится плейсхолдер/тип+номер); привязка по `groupId`, не по позиции — исключает молчаливое переклеивание подписи (класс багов `questions.go`). Welded не даёт `title`/`label` отдельными сущностями и держит контент только «в строке»; нормализованные таблицы — против решения «схема в JSONB». Цена — бухгалтерия групп (смежность, один инпут в группе) и два пути рендера контента — в TECH-DEBT |
| Аналитика визитов публичной формы — сверх исходного скоупа MVP (решение принято до кода; реализация — DEV-PLAN фаза 8.5, шаг 6) | Отложить в пост-MVP | Воронка «откуда пришли и на каком вопросе ушли» — то, за что платят в этом классе продуктов. Цена — один `SMALLINT`; альтернатива дешевле в коде, но её дефект по факту неотлаживаем: данные уже испорчены, гонку не воспроизвести. `submitted` в теле бикона не принимается никогда (ставит только сервер при приёме ответа) — иначе конверсия подделывается с клиента, а второй бикон затирает её обратно; апсерт скоупится по `form_id`, т.к. Размен «блокировка на hot-path» осознан и записан в TECH-DEBT (вернёмся, если станет узким местом) |

Форма была публичной (ссылку раздали), её существование уже не секрет — дружелюбное «приём закрыт» лучше битого 404.
