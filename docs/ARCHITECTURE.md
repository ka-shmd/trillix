# Архитектура SaaS-конструктора форм (аналог Tally) — MVP

Документ описывает архитектуру MVP с прицелом на рост: решения принимаются так, чтобы их не пришлось переделывать при масштабировании, но без преждевременного усложнения. Стек: Go (минимум зависимостей), PostgreSQL, React + TypeScript + TanStack. Деплой — один VPS.

---

## 1. Скоуп MVP

Прежде чем проектировать, фиксируем границы. Это самое важное архитектурное решение: всё остальное вытекает отсюда.

**Входит в MVP:** регистрация и вход по email/паролю; создание, редактирование и удаление форм; конструктор с базовыми типами блоков (короткий текст, длинный текст, email, число, одиночный выбор, множественный выбор, дата); публикация формы по публичной ссылке; приём ответов анонимными респондентами; просмотр ответов в таблице; экспорт ответов в CSV; черновик/публикация как два состояния формы.

**Не входит в MVP (но архитектура должна это допускать):** команды и воркспейсы с несколькими участниками (сущность workspace закладываем сразу, UI для приглашений — нет); условная логика (branching); интеграции и вебхуки; кастомные домены; файловые аплоады; платные тарифы и биллинг; email-уведомления о новых ответах.

Принцип: сущности, которые дорого добавлять задним числом (workspace, версионирование форм), закладываем в схему данных сразу. Функциональность, которую дёшево добавить позже (вебхуки, логика), — не закладываем вообще.

## 2. Общая архитектура

### 2.1. Модульный монолит

Один Go-бинарник, один процесс, одна база. Микросервисы на этом этапе — антипаттерн: они добавляют сетевые границы, распределённые транзакции и операционную сложность, не давая ничего взамен при нагрузке MVP. Вместо этого — **модульный монолит**: жёсткие границы между доменными модулями внутри одного процесса. Если через два года понадобится вынести приём ответов в отдельный сервис — границы уже будут прочерчены.

### 2.2. Два фронтенд-приложения

Ключевое продуктовое наблюдение: у сервиса форм два принципиально разных потребителя фронтенда.

**Приложение-конструктор (app)** — SPA для авторизованных пользователей: билдер, список форм, таблица ответов. Здесь уместен тяжёлый бандл, TanStack Router/Query, сложный стейт.

**Публичный рендерер форм (renderer)** — то, что видит респондент по ссылке `f.example.com/r/{slug}`. Здесь критичны скорость первой отрисовки и вес бандла: респондент открывает ссылку один раз, часто с телефона, и любая задержка — потерянный ответ. Это отдельная точка сборки Vite с минимумом зависимостей (React + лёгкая форма-логика, без роутера и без TanStack Query — там буквально один GET и один POST).

Оба приложения живут в одном монорепозитории и собираются одной командой, но деплоятся как разные наборы статики.

### 2.3. Схема системы

```
                        ┌─────────────────────────── VPS ───────────────────────────┐
                        │                                                            │
  app.example.com ────► │  Caddy (TLS, статика app)  ──┐                             │
  f.example.com   ────► │  Caddy (TLS, статика renderer)│                            │
  api.example.com ────► │  Caddy (reverse proxy) ──────┴──► Go API (один бинарник)   │
                        │                                        │                   │
                        │                                        ▼                   │
                        │                                   PostgreSQL 16            │
                        │                                        │                   │
                        │                              pg_dump → S3-совместимое      │
                        │                                        offsite-хранилище   │
                        └────────────────────────────────────────────────────────────┘
```

Разделение доменов (`app`, `f`, `api`) — осознанное: публичные формы изолированы от cookie-домена приложения (безопасность), их можно позже вынести за CDN, и rate-limiting настраивается независимо.

## 3. Модель данных

Это сердце проекта. Здесь два нетривиальных решения senior-уровня, разберём их подробно.

### 3.1. Решение №1: схема формы — JSONB, а не нормализованные таблицы

Наивный путь — таблицы `questions`, `options`, `question_settings` с внешними ключами. Для конструктора форм это ловушка: структура блоков эволюционирует быстро (новые типы полей, новые настройки), каждое изменение требует миграции, а собирать форму из пяти таблиц с сортировками — дорого и хрупко. При этом реляционные запросы «внутрь» схемы формы почти не нужны: форма всегда читается и пишется целиком.

Поэтому схема формы (список блоков с настройками) хранится как **один JSONB-документ**, валидируемый на уровне приложения строгими Go-типами. Реляционная модель остаётся для того, что действительно реляционно: пользователи, воркспейсы, формы как сущности, ответы.

### 3.2. Решение №2: иммутабельные версии-снапшоты при публикации

Классическая ошибка конструкторов форм: ответы ссылаются на «живую» форму, автор удаляет вопрос — и старые ответы становятся неинтерпретируемыми (в данных есть ответ на вопрос, которого больше нет).

Решение: у формы есть мутабельный **черновик** (`forms.draft_schema`) и иммутабельные **версии** (`form_versions`). Публикация = снятие снапшота черновика в новую строку `form_versions`. Каждый ответ ссылается на конкретную версию, по которой он был отправлен. Это даёт корректную интерпретацию любого исторического ответа, бесплатную «историю изменений» и безопасное редактирование опубликованной формы (респонденты видят старую версию, пока автор не нажмёт «Опубликовать» снова).

### 3.3. Схема PostgreSQL

```sql
-- Идентификаторы: UUIDv7 (упорядочены по времени → дружелюбны к btree-индексам,
-- в отличие от UUIDv4). Генерируются в приложении, 5 строк кода без зависимостей.

CREATE TABLE users (
    id            UUID PRIMARY KEY,
    email         TEXT NOT NULL UNIQUE CHECK (email = lower(email)),
    password_hash TEXT NOT NULL,               -- argon2id
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Воркспейс закладываем сразу: перевести single-user SaaS на команды задним
-- числом — одна из самых болезненных миграций в индустрии. В MVP при регистрации
-- молча создаётся личный воркспейс, UI его не показывает.
CREATE TABLE workspaces (
    id         UUID PRIMARY KEY,
    name       TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE workspace_members (
    workspace_id UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    user_id      UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role         TEXT NOT NULL DEFAULT 'owner',  -- owner | editor (на будущее)
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (workspace_id, user_id)
);

CREATE TABLE forms (
    id            UUID PRIMARY KEY,
    workspace_id  UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    title         TEXT NOT NULL DEFAULT 'Untitled form',
    slug          TEXT NOT NULL UNIQUE,          -- короткий id для публичной ссылки, nanoid(10)
    status        TEXT NOT NULL DEFAULT 'draft', -- draft | published | closed
    draft_schema  JSONB NOT NULL DEFAULT '{"blocks": []}',
    published_version_id UUID,                   -- FK на form_versions, ставится после публикации
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_forms_workspace ON forms (workspace_id, updated_at DESC);

CREATE TABLE form_versions (
    id         UUID PRIMARY KEY,
    form_id    UUID NOT NULL REFERENCES forms(id) ON DELETE CASCADE,
    version    INT  NOT NULL,
    schema     JSONB NOT NULL,                   -- иммутабельный снапшот
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (form_id, version)
);

CREATE TABLE submissions (
    id              UUID PRIMARY KEY,            -- UUIDv7 → сортировка по времени бесплатно
    form_id         UUID NOT NULL REFERENCES forms(id) ON DELETE CASCADE,
    form_version_id UUID NOT NULL REFERENCES form_versions(id),
    answers         JSONB NOT NULL,              -- { "<block_id>": <значение> }
    meta            JSONB NOT NULL DEFAULT '{}', -- user_agent, referer (без IP в открытом виде)
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_submissions_form ON submissions (form_id, created_at DESC);
-- Листинг ответов кабинета идёт курсором по id (UUIDv7 монотонен → «новые сверху»;
-- created_at при пакетной вставке нестабилен). Индекс покрывает фильтр по form_id
-- и keyset/сортировку по id одной структурой.
CREATE INDEX idx_submissions_form_id ON submissions (form_id, id DESC);

-- Сессии в БД, а не JWT: мгновенный отзыв, «выйти со всех устройств»,
-- нет проблемы ротации ключей. Хранится только SHA-256 от токена.
CREATE TABLE sessions (
    token_hash BYTEA PRIMARY KEY,
    user_id    UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    expires_at TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_sessions_expires ON sessions (expires_at);
```

Ответы (`answers`) хранятся как JSONB по ключу `block_id`, а не нормализованной таблицей `answer_values` — по тем же причинам, что и схема формы: ответ читается и пишется атомарно, аналитические запросы «внутрь» ответов в MVP сводятся к экспорту CSV, который собирается в приложении. Если позже понадобится тяжёлая аналитика — данные денормализуются в отдельную таблицу фоновым процессом, исходник в JSONB ничего не теряет.

### 3.4. Формат JSONB-схемы формы

Схема версионируется полем `schemaVersion` — это позволит эволюционировать формат без миграций БД (читатель применяет upgrade-функции на лету).

```jsonc
{
  "schemaVersion": 1,
  "blocks": [
    {
      "id": "blk_9f2k1x",            // стабильный id, генерируется на клиенте
      "type": "short_text",           // short_text | long_text | email | number
                                      // | single_choice | multi_choice | date
      "label": "Ваше имя",
      "description": "",
      "required": true,
      "settings": {}                  // типоспецифичные настройки
    },
    {
      "id": "blk_7ab3m2",
      "type": "single_choice",
      "label": "Как вы о нас узнали?",
      "required": false,
      "settings": {
        "options": [
          { "id": "opt_1", "label": "Друзья" },
          { "id": "opt_2", "label": "Поиск" }
        ]
      }
    }
  ]
}
```

Критично: `id` блоков и опций стабильны и генерируются один раз при создании. Ответы ссылаются на эти id, поэтому переименование вопроса не ломает связь ответа с вопросом, а сопоставление ответа с версией формы всегда однозначно.

## 4. Backend на Go

### 4.1. Философия зависимостей

Требование «как можно меньше зависимостей» с Go 1.22+ выполняется почти буквально. Runtime-зависимостей четыре:

```
github.com/jackc/pgx/v5          — драйвер PostgreSQL (стандарт де-факто, database/sql ему проигрывает)
golang.org/x/crypto              — argon2id для паролей (квазистандартная библиотека)
github.com/golang-migrate/migrate — миграции (или goose; можно и свой раннер на 100 строк)
github.com/google/uuid           — UUID (v7 поддерживается; альтернатива — 30 строк своего кода)
```

Всё остальное — стандартная библиотека: роутинг (`net/http` с method-паттернами из Go 1.22: `mux.HandleFunc("GET /api/v1/forms/{id}", ...)`), логирование (`log/slog`), конфигурация (env-переменные через `os.Getenv` + маленький хелпер), JSON (`encoding/json`), тесты (`testing` + `net/http/httptest`). Никаких Gin/Echo/Fiber — они не дают ничего, чего нет в stdlib 1.22+, но приносят чужие абстракции.

Отдельно про SQL: вместо ORM — **sqlc** как dev-time кодогенератор. Пишете SQL, получаете типизированные Go-функции. В рантайме зависимость нулевая (генерирует код поверх pgx), а класс ошибок «опечатка в имени колонки» ловится на этапе сборки. Это компромисс senior-уровня: сырой pgx без sqlc тоже допустим, но sqlc убирает boilerplate без ORM-магии.

### 4.2. Структура проекта

Слоистая архитектура с направлением зависимостей строго внутрь: `transport → service → repository`. Доменные типы — в центре, ни от чего не зависят.

```
/
├── cmd/
│   └── api/main.go              # composition root: конфиг, пул БД, DI руками, запуск
├── internal/
│   ├── config/                  # чтение и валидация env
│   ├── domain/                  # чистые типы: Form, Block, Submission, ошибки домена
│   │   ├── form.go              #   + валидация схемы формы, валидация ответов
│   │   └── errors.go            #   ErrNotFound, ErrForbidden, ErrValidation...
│   ├── auth/                    # модуль: регистрация, вход, сессии, argon2id
│   │   ├── service.go
│   │   ├── repo.go
│   │   └── handler.go
│   ├── forms/                   # модуль: CRUD форм, публикация, версии
│   │   ├── service.go
│   │   ├── repo.go
│   │   └── handler.go
│   ├── submissions/             # модуль: приём ответов, листинг, CSV-экспорт
│   │   ├── service.go
│   │   ├── repo.go
│   │   ├── handler.go           #   приватный API (просмотр)
│   │   └── public_handler.go    #   публичный API (получение формы, отправка)
│   ├── httpserver/              # сборка mux, middleware, JSON-хелперы
│   │   ├── server.go
│   │   ├── middleware.go        #   request_id, логирование, recover, auth, rate limit
│   │   └── respond.go           #   единый формат ответов и ошибок
│   └── postgres/                # пул, транзакции-хелперы, sqlc-сгенерированный код
├── migrations/                  # 0001_init.up.sql / .down.sql
├── web/
│   ├── app/                     # Vite-проект конструктора
│   └── renderer/                # Vite-проект публичного рендерера
├── deploy/                      # compose.yml, Caddyfile, скрипты бэкапа
├── Makefile
└── go.mod
```

Каждый доменный модуль (`auth`, `forms`, `submissions`) самодостаточен: свой сервис, свой репозиторий, свой handler. Модули общаются только через интерфейсы сервисов — это и есть границы будущих сервисов, если монолит когда-нибудь придётся пилить.

### 4.3. Слои и их ответственность

**Handler (transport)** — только HTTP: декодировать запрос, вызвать сервис, закодировать ответ. Ни одной бизнес-проверки. Ошибки домена маппятся на HTTP-статусы в одном месте (`respond.go`): `ErrNotFound → 404`, `ErrForbidden → 403`, `ErrValidation → 422` с деталями по полям.

**Service** — вся бизнес-логика и авторизация. Пример инварианта, живущего здесь: «публиковать форму может только участник её воркспейса; публикация создаёт новую версию и обновляет `published_version_id` в одной транзакции».

**Repository** — только SQL. Интерфейсы репозиториев объявляются на стороне сервиса (потребителя), а не реализации — классический Go-идиоматичный DIP, позволяющий тестировать сервисы с фейками без mock-библиотек.

**Domain** — типы и чистые функции. Ключевой обитатель: валидатор `ValidateAnswers(schema FormSchema, answers map[string]any) error`, который проверяет ответ респондента против конкретной версии схемы (обязательность, типы, принадлежность выбранных опций). Он используется и при приёме ответа, и в тестах, и нигде не касается ни HTTP, ни SQL.

### 4.4. Сквозные механики

**Контексты и таймауты.** Каждый запрос несёт `context.Context` с дедлайном (middleware ставит, например, 10 секунд); pgx его уважает, зависшие запросы отменяются. У `http.Server` выставлены `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout` — без них публичный эндпоинт уязвим к slowloris.

**Graceful shutdown.** По SIGTERM: перестать принимать соединения, дождаться активных запросов (с потолком 15 секунд), закрыть пул БД. Это не роскошь — это то, что делает деплой без ошибок 502.

**Структурные логи.** `slog` в JSON, в stdout (докер соберёт). Middleware генерирует `request_id` (отдаётся и в заголовке ответа) и кладёт логгер с ним в контекст — каждая строка лога любого слоя привязана к запросу.

**Единый формат ошибок API:**

```json
{ "error": { "code": "validation_failed", "message": "...", 
             "fields": { "blk_9f2k1x": "обязательное поле" } } }
```

**Rate limiting.** Один VPS — значит in-memory token bucket (реализация на `map` + `sync.Mutex`, ~60 строк, без Redis). Два контура: жёсткий на `POST /public/.../submissions` и на `POST /auth/login` (по IP), мягкий на остальное. При переезде на несколько инстансов заменяется на Redis — интерфейс `RateLimiter` закладывается сразу.

**Периодические задачи.** Отдельная горутина в том же процессе: чистка истёкших сессий раз в час. Не cron, не отдельный воркер — незачем.

### 4.5. Аутентификация

Пароли — argon2id с параметрами по рекомендациям OWASP (память 64 МБ, итерации 3). Сессия — 256-битный случайный токен; клиенту уходит в httpOnly, Secure, SameSite=Lax cookie на домене `api.example.com`; в БД хранится только его SHA-256 (утечка дампа БД не даёт живых сессий). CSRF: для мутирующих запросов SPA шлёт заголовок `X-CSRF-Token`, выданный при логине (double-submit), плюс проверка `Origin` на API. Публичный эндпоинт отправки форм CSRF-защиты не требует (он и так анонимный), но защищается rate-limit'ом и антиспамом.

### 4.6. Контракт API

```
Приватный API (cookie-сессия), префикс /api/v1:

POST   /auth/register                 регистрация (создаёт user + личный workspace)
POST   /auth/login                    вход
POST   /auth/logout                   выход
GET    /auth/me                       текущий пользователь

GET    /forms                         список форм воркспейса (курсорная пагинация)
POST   /forms                         создать форму
GET    /forms/{id}                    форма + draft_schema
PATCH  /forms/{id}                    обновить title / draft_schema (автосейв билдера)
DELETE /forms/{id}
POST   /forms/{id}/publish            снапшот черновика → новая версия
POST   /forms/{id}/unpublish

GET    /forms/{id}/submissions        ответы (курсорная пагинация по UUIDv7-id)
GET    /forms/{id}/submissions/export CSV (стриминг, encoding/csv прямо в ResponseWriter)

Публичный API (без авторизации), префикс /public/v1:

GET    /forms/{slug}                  опубликованная версия схемы (Cache-Control + ETag)
POST   /forms/{slug}/submissions      отправка ответа
```

Пагинация — курсорная с первого дня (`?cursor=<непрозрачный токен>&limit=50`): offset-пагинация на больших таблицах ответов деградирует и её пришлось бы переделывать. Ключ курсора зависит от порядка сортировки списка. Для ответов (`submissions`) он одноколоночный — сам UUIDv7-id: они иммутабельны и монотонны по времени создания. Для форм список сортируется по свежести правки (`updated_at DESC`), а `updated_at` меняется при переименовании/автосейве, поэтому курсор **составной** — пара `(updated_at, id)` с keyset-условием `(updated_at, id) < (курсор)`: стабилен, если форму отредактировали во время листания. Клиенту токен непрозрачен (сервер кодирует пару в base64url).

### 4.7. Приём ответа: полный путь запроса

Самый нагруженный и самый атакуемый эндпоинт, поэтому распишем его целиком. `POST /public/v1/forms/{slug}/submissions`: (1) rate-limit по IP; (2) `http.MaxBytesReader` на 256 КБ — потолок размера тела; (3) поиск формы по slug, проверка `status = published`; (4) антиспам: honeypot-поле (скрытое поле, заполнил — молча отвечаем 200 и выбрасываем) и минимальное время заполнения (в схему при выдаче кладётся подписанный HMAC-токен с временем выдачи; ответ, пришедший быстрее 3 секунд, — бот); (5) `ValidateAnswers` против схемы опубликованной версии; (6) INSERT с `form_version_id`; (7) 201. Идемпотентность: клиент генерирует `submission_id` (UUIDv7) сам и шлёт его в теле; повторная отправка после сетевого сбоя упирается в PRIMARY KEY и возвращает тот же 201 — двойных ответов от ретраев не бывает.

## 5. Frontend

### 5.1. Приложение-конструктор (web/app)

Стек: Vite, React 18, TypeScript strict, TanStack Router (file-based, типобезопасные параметры маршрутов), TanStack Query (весь серверный стейт). Дополнительно оправданы только три маленькие зависимости: Zod (валидация ответов API и единый источник типов), zustand (локальный стейт билдера, ~1 КБ) и dnd-kit (drag-and-drop блоков — писать своё здесь неоправданно).

Организация кода — feature-sliced, зеркально бэкенду:

```
web/app/src/
├── app/                # провайдеры, router, QueryClient, error boundary
├── routes/             # file-based маршруты TanStack Router
│   ├── _auth/          #   layout-группа: login, register
│   └── _app/           #   layout-группа с проверкой сессии
│       ├── forms.index.tsx          # список форм
│       ├── forms.$formId.edit.tsx   # билдер
│       └── forms.$formId.responses.tsx
├── features/
│   ├── auth/           # api.ts, hooks.ts, компоненты
│   ├── form-builder/   # стор билдера, палитра блоков, канвас, панель настроек
│   └── submissions/    # таблица ответов, экспорт
├── entities/           # типы домена (Zod-схемы FormSchema, Block — общие с renderer)
└── shared/             # api-клиент (fetch-обёртка), ui-кит, утилиты
```

**Разделение стейта — главное фронтовое решение.** Серверный стейт (списки форм, ответы, профиль) живёт только в TanStack Query: кэш, инвалидация, ретраи. Стейт билдера — принципиально другой зверь: это высокочастотный локальный документ (каждое нажатие клавиши в label), его нельзя гонять через Query. Поэтому билдер работает так: при открытии форма загружается через Query и гидрирует zustand-стор; все правки — синхронные операции над стором (мгновенный UI); дебаунс-автосейв (800 мс тишины) шлёт `PATCH /forms/{id}` целиком с `draft_schema`. Статус «Сохранено / Сохраняется / Ошибка» — из состояния мутации. Undo/redo достаётся почти бесплатно: стор хранит стек снапшотов схемы.

Конфликты редактирования в MVP решаются оптимистичной блокировкой: `PATCH` несёт `updated_at`, при расхождении сервер отвечает 409, клиент предлагает перезагрузить. Дёшево и честно; CRDT — не для MVP.

**Типы — из одного источника.** Zod-схемы `FormSchema`/`Block` лежат в `entities` и импортируются и конструктором, и рендерером. Ответ API парсится через Zod на границе — расхождение контракта ловится сразу, а не глубоко в UI. (Альтернатива посерьёзнее — генерация типов из OpenAPI; для MVP Zod-схемы руками дешевле.)

### 5.2. Публичный рендерер (web/renderer)

Отдельный Vite-проект: React + общие Zod-типы из `entities` и общие компоненты полей из `shared/fields` (те же, что рисуют превью в билдере), ничего больше. Никакого роутера (slug парсится из `location.pathname`), никакого TanStack Query (один `fetch` формы, один `POST` ответа), стейт — `useReducer`. Клиентская валидация дублирует серверную по той же схеме (та же Zod-схема — то же поведение). Ошибки сервера 422 маппятся на поля по `block_id`. После отправки — экран «Спасибо» и очистка черновика ответа из sessionStorage (черновик спасает респондента от потери введённого при случайном обновлении страницы).

**Бандл и запасной выход на Preact.** Целевой вес держим низким, но порог сознательно выше «круглых» 60 КБ gzip: React + react-dom исчерпывают его сами по себе (замерено в фазе 3). Точное число бюджета фиксируется в фазе 4 и проверяется в CI. Если из-за веса рендерер не берёт Lighthouse ≥90 на мобиле — предусмотрен дешёвый свап на Preact: `react → preact/compat` алиасом **только в сборке рендерера**, компоненты остаются написанными на React-API, `shared/fields` не переписываются. Именно ради этого выхода поля пишутся на React-API, а не как SSR-шаблоны: мы не заперты в конкретном рантайме.

**Превью ссылок — «голова» рендерится на сервере.** Рендерер клиентский, поэтому мета для превью в мессенджерах/соцсетях (Open Graph) он сам дать не может: краулеры читают HTML, не выполняя JS. Поэтому HTML-документ страницы формы (`/r/{slug}`) отдаёт **Go**, а не статика: он подтягивает опубликованную форму и подставляет в `<head>` `og:title`/`og:description` из её title и описания, плюс `og:image` — в MVP общая брендовая заглушка (базовый URL — из env; своя картинка на форму — вместе с загрузкой файлов, пост-MVP). Тело того же документа грузит React-SPA. Пользовательский текст в мета вставляется только через автоэкранирование `html/template` (инъекция вида `"><script>` в названии формы недопустима), а черновик/закрытая форма и по этому пути отдают 404 — HTML не раскрывает существование приватного больше, чем JSON-ручка. Полный SSR формы сознательно отвергнут: он раздул бы рендерер и заставил дублировать рендер полей на сервере, разъехавшись с превью билдера; head-injection даёт превью почти без сложности.

## 6. Инфраструктура на VPS

### 6.1. Состав

Docker Compose из трёх контейнеров: `caddy`, `api`, `postgres`. Caddy выбран вместо Nginx осознанно: автоматический TLS (Let's Encrypt), конфиг в 30 строк, встроенная раздача статики с правильными заголовками. Статика фронтендов (JS/CSS/картинки) кладётся в volume, который Caddy раздаёт напрямую — байты статики Go не отдаёт. Единственное исключение — HTML-документ публичной формы `f.example.com/r/{slug}`: его Caddy проксирует в Go ради превью-мета Open Graph (см. 5.2), а ассеты остаются статикой.

```
# deploy/compose.yml (суть)
services:
  caddy:
    image: caddy:2
    ports: ["80:80", "443:443"]
    volumes: [caddy_data:/data, ./Caddyfile:/etc/caddy/Caddyfile,
              ./static:/srv/static]
  api:
    image: ghcr.io/you/forms-api:${TAG}
    env_file: .env
    depends_on: { postgres: { condition: service_healthy } }
    restart: unless-stopped
  postgres:
    image: postgres:16
    volumes: [pg_data:/var/lib/postgresql/data]
    healthcheck: { test: ["CMD-SHELL", "pg_isready -U forms"] }
    restart: unless-stopped
    # порт наружу НЕ публикуется
```

```
# Caddyfile (суть)
app.example.com {
    root * /srv/static/app
    try_files {path} /index.html      # SPA fallback
    file_server
    header /assets/* Cache-Control "public, max-age=31536000, immutable"
}
f.example.com {
    root * /srv/static/renderer
    @doc path /r/*                    # HTML-документ формы — из Go (OG-мета)
    reverse_proxy @doc api:8080
    try_files {path} /index.html      # ассеты и всё прочее — статикой
    file_server
}
api.example.com {
    reverse_proxy api:8080
}
```

Go-образ — multi-stage: сборка в `golang:1.22`, рантайм — `gcr.io/distroless/static` со статическим бинарником (`CGO_ENABLED=0`). Итоговый образ ~15 МБ, поверхность атаки минимальна. Бинарник умеет `./api migrate up` — миграции гоняются тем же образом перед стартом.

### 6.2. CI/CD

GitHub Actions, два пайплайна. **CI на каждый PR:** `go vet` + `golangci-lint`, `go test -race ./...`, `tsc --noEmit` + `eslint` + `vitest` для обоих фронтов, сборка образа. **CD на тег:** пуш образа в GHCR, сборка статики, затем деплой по SSH: `rsync` статики, `docker compose pull && docker compose up -d` (запускает миграции и перезапускает api). Секреты — в GitHub Secrets и в `.env` на сервере (права 600), не в репозитории. Откат = деплой предыдущего тега; миграции поэтому пишутся обратно-совместимыми (add column — да, drop column — только через релиз после того, как код перестал её читать).

### 6.3. Бэкапы — самое важное после самого кода

Данные форм — это весь бизнес. Скрипт по cron каждые 6 часов: `pg_dump -Fc` → шифрование `age` → загрузка в S3-совместимое хранилище **другого провайдера** (бэкап на том же VPS — не бэкап). Ротация: 14 суточных, 8 недельных. Обязательный ритуал: раз в месяц тестовое восстановление на локальной машине — непроверенный бэкап равен отсутствующему. Для MVP point-in-time recovery через WAL-архивацию избыточен; отметить как апгрейд при появлении платящих клиентов.

### 6.4. Наблюдаемость

Прагматичный минимум, а не карго-культ Prometheus+Grafana на одном VPS. Три слоя: (1) структурные JSON-логи в journald через docker logging driver, с ротацией; (2) эндпоинт `GET /healthz` (проверяет ping БД) + внешний мониторинг аптайма (Uptime Kuma на другой машине или бесплатный внешний сервис) с алертом в Telegram; (3) счётчики в самом приложении — middleware пишет в лог сводку по каждому запросу (метод, путь-паттерн, статус, длительность), и `lnav`/`jq` по логам закрывает 90 % вопросов «что происходило». Sentry-подобный сервис (self-hosted GlitchTip) — полезное раннее дополнение для фронтовых ошибок, но не блокер запуска.

### 6.5. Харденинг VPS

Стандартный чек-лист: вход только по SSH-ключам, root-логин выключен; ufw — открыты только 22/80/443; fail2ban на SSH; автоматические security-обновления (unattended-upgrades); Postgres не слушает наружу вообще (только docker-сеть); отдельный непривилегированный пользователь для деплоя.

## 7. Безопасность приложения

Сводка мер, разбросанных по документу, плюс недостающее. Валидация всего входа на границе (Zod на фронте — UX, Go-валидатор на бэке — истина). Авторизация на каждый ресурс в service-слое: каждый запрос формы проверяет членство в воркспейсе, id из URL никогда не доверяется сам по себе (защита от IDOR). Экранирование пользовательского контента: label'ы блоков рендерятся как текст, никакого `dangerouslySetInnerHTML`; OG-мета публичной формы (title/описание) вставляются в `<head>` только через автоэкранирование `html/template`; CSP-заголовки на всех трёх доменах. Заголовки `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` на app и api (рендерер — SAMEORIGIN, позже формам понадобится embed — тогда осознанно ослабим). Ответы респондентов — потенциально персональные данные: IP в чистом виде не храним (только хэш для антиспама в meta), экспорт доступен только участникам воркспейса, `DELETE` формы каскадно уносит ответы.

## 8. Тестирование

Пирамида, смещённая к интеграционным тестам — для CRUD-приложения с БД это честнее юнит-моков. **Юниты** — для чистой логики: `ValidateAnswers` (самая ветвистая функция проекта), апгрейдеры schemaVersion, CSV-маппинг. **Интеграционные** — сервис+репозиторий против настоящего Postgres в контейнере (testcontainers-go — единственная тестовая зависимость, которая того стоит; каждый тест в своей транзакции с откатом). **API-тесты** — `httptest` поверх собранного приложения: сценарий «регистрация → создать форму → опубликовать → отправить ответ анонимно → увидеть его в листинге → экспорт CSV» как один сквозной тест — это живая документация продукта. На фронте: vitest для логики стора билдера (undo/redo, операции над блоками), Playwright — один smoke-сценарий на тот же сквозной путь, гоняется в CI перед деплоем.

## 9. Порядок работ

Разумная последовательность без искусственных дедлайнов. **Этап 1 — скелет:** репозиторий, Makefile, CI, docker compose локально, миграции, healthz, деплой «hello world» на VPS — конвейер до прода должен заработать раньше фич. **Этап 2 — auth:** регистрация, сессии, middleware, `/auth/me`, экраны входа. **Этап 3 — формы:** CRUD, JSONB-схема, публикация с версиями; параллельно билдер с автосейвом. **Этап 4 — публичный контур:** рендерер, приём ответов с валидацией, антиспам, rate limit. **Этап 5 — ответы:** таблица, пагинация, CSV. **Этап 6 — прод-готовность:** бэкапы + тестовое восстановление, мониторинг, харденинг, сквозной Playwright-тест.

После MVP очередь примерно такая: приглашения в воркспейс (схема уже готова) → вебхуки на новый ответ (таблица `outbox` + горутина-доставщик, паттерн transactional outbox) → условная логика (расширение JSONB-схемы полем `logic`, schemaVersion=2) → загрузка файлов (S3-совместимое хранилище, presigned URL) → биллинг.

## 10. Реестр ключевых решений (ADR-сводка)

| Решение | Альтернатива | Почему так |
|---|---|---|
| Модульный монолит | Микросервисы | Нагрузка MVP не оправдывает распределённость; границы модулей дают путь к распилу |
| Схема формы в JSONB | Нормализованные таблицы | Форма читается/пишется целиком; эволюция без миграций |
| Иммутабельные версии при публикации | Ответы ссылаются на живую форму | Интерпретируемость исторических ответов; безопасное редактирование |
| Сессии в Postgres | JWT | Мгновенный отзыв, нет ротации ключей, один SELECT дешёв |
| stdlib `net/http` 1.22 | Gin/Echo | Method-роутинг уже в stdlib; меньше чужих абстракций |
| sqlc | ORM / сырой pgx | Типобезопасный SQL без рантайм-зависимости |
| Два фронт-приложения | Один SPA | Рендерер должен быть лёгким и быстрым для респондентов |
| HTML публичной формы рендерит Go (OG-мета в `<head>`), тело — React-SPA | Полный SSR формы / чистый SPA | Превью ссылок требуют server-side мета; полный SSR раздувает рендерер и дублирует рендер полей, чистый SPA не даёт превью |
| UUIDv7 | serial / UUIDv4 | Нелокальность v4 бьёт по индексам; serial неудобен для клиентской генерации |
| Курсорная пагинация | OFFSET | Не деградирует на больших таблицах ответов |
| Caddy | Nginx | Авто-TLS и конфиг кратно проще при том же результате |
| In-memory rate limit | Redis | Один инстанс; интерфейс позволяет заменить позже |
