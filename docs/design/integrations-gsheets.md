## 1. Что решается

Ответы формы сегодня живут только в кабинете: таблица ответов, сводка, выгрузка CSV.
Выгрузка — снимок, который устаревает в момент скачивания, и любой процесс поверх ответов
(обзвон, сверка с CRM, отчёт для заказчика) начинается с ручного «скачай ещё раз».

Интеграция снимает именно это: ответ попадает в Google Таблицу **сам**, через секунды после
отправки, в лист, который автор дал коллегам, свёл формулами и подшил в свой отчёт.

Экран «Интеграции» заводится сразу как пятый таб формы — рядом с «Поделиться», «Ответы»,
«Сводка», «Воронка», — а не как настройка внутри «Поделиться»: интеграций будет больше
одной, и место для них должно существовать до второй.

## 2. Рамка: что входит и что сознательно не входит

**Входит.** Подключение аккаунта Google к пространству. Привязка формы к таблице, которую
**создаём мы**. Догрузка уже накопленных ответов при подключении. Живая доставка каждого
нового ответа. Экран состояния с ссылкой на таблицу, отключением и кнопкой «Перезалить всё».

**Не входит — и каждый пункт по своей причине:**

- **Выбор существующей таблицы.** Требует либо полного scope `spreadsheets` (сенситивный —
  проверка приложения в Google с видеодемо), либо Google Picker в браузере (новая
  JS-зависимость, список заморожен). Обе цены — не за первую интеграцию. Следствие §5.
- **Обратная запись** (правка ответа в таблице меняет ответ в базе). Таблица — витрина, а не
  источник истины: у ответов иммутабельные версии схемы, и обратная запись ломает их смысл.
- **Удаление ответа в кабинете не удаляет строку из таблицы.** Строку удаляет автор руками
  либо кнопка «Перезалить всё». Названо явно, потому что ожидание обратного естественно.
- **Несколько таблиц на форму и несколько аккаунтов Google на пространство.** Второй
  потребитель не появился (YAGNI); ключи в БД уникальны так, что снять ограничение можно
  миграцией, не переделывая модель.
- **Другие провайдеры** (Excel Online, Airtable) и **вебхуки** — своя работа со своим ADR.

## 3. Кому принадлежит подключение

Кредс всегда персональный: согласие в окне Google даёт живой человек, и refresh-токен — его.
Но **область действия подключения — пространство**, потому что формы лежат в пространствах
([`0003_forms.up.sql`](../../migrations/0003_forms.up.sql)), а не на пользователях.

Подключение на `user_id` открывало бы три дыры: кредс участника доступен формам чужой
команды, куда его позвали; после снятия доступа ответы формы продолжают течь в Drive
бывшего участника; владелец пространства не может ни увидеть чужую строку, ни переподключить.

Отсюда строка `(workspace_id, connected_by)`: пространство — область видимости и
ответственности, пользователь — аудит «чьим согласием ответы уезжают наружу» (он же нужен
152-ФЗ, §10). Для одиночки с личным пространством это неотличимо от привязки к аккаунту.

Два следствия, обязательные к реализации, — без них дыра из абзаца выше остаётся открытой:

- **Ушёл человек — ушло его согласие.** Снятие доступа участнику и удаление аккаунта
  отключают подключение, которым он владел. Формы остаются, доставка встаёт со статусом
  «нужно переподключить», данные в таблице не трогаются.
- **Отзыв на стороне Google — best effort.** Дёргаем `POST /revoke`, но исход не гейтит
  отключение: наша строка удаляется в любом случае, иначе недоступность Google запирала бы
  человека в подключении, которое он хочет разорвать.

**Права.** Новое действие `ActionIntegrationManage` в матрице `internal/workspaces/access.go`:
`owner` — да, `editor` — нет. Подключение аккаунта решает, куда уезжают персональные данные
респондентов, — это решение владельца пространства. **Привязка формы к таблице** идёт под
существующим `ActionFormWrite`: `editor` правит формы и видит ответы, и запрет отправлять их
в таблицу владельца ничего не защищает. Не участник → 404, участник без права → 403.

**Тариф.** Интеграция бесплатна (решение владельца 2026-08-23), ключ в
`entitlements.Catalog` не заводится. Шов для платных интеграций уже существует и будет
использован, когда появится первая платная.

## 4. Модель данных (миграция `0029_integrations`)

```
integration_accounts                     -- подключённый внешний аккаунт
  id                   UUID PK           -- UUIDv7
  workspace_id         UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE
  provider             TEXT NOT NULL     -- 'google' (второй провайдер — без миграции)
  external_account_id  TEXT NOT NULL     -- sub из id_token: стабилен при смене почты
  external_email       TEXT NOT NULL     -- «подключён как …» на экране
  refresh_token        BYTEA NOT NULL    -- AES-256-GCM, ключ — HKDF (§5)
  scopes               TEXT NOT NULL     -- что реально выдал Google (проверяем, а не верим)
  connected_by         UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE
  connected_at         TIMESTAMPTZ NOT NULL DEFAULT now()
  UNIQUE (workspace_id, provider)        -- одно подключение на пространство (§2)

form_integrations                        -- форма ↔ таблица
  id                   UUID PK
  form_id              UUID NOT NULL REFERENCES forms(id) ON DELETE CASCADE
  account_id           UUID NOT NULL REFERENCES integration_accounts(id) ON DELETE CASCADE
  spreadsheet_id       TEXT NOT NULL
  spreadsheet_url      TEXT NOT NULL     -- показываем ссылкой, не собираем строкой в UI
  sheet_id             INT  NOT NULL     -- gid листа: имя листа автор волен переименовать
  columns              JSONB NOT NULL    -- порядок ключей колонок, зафиксированный у листа (§8)
  status               TEXT NOT NULL     -- backfilling | live | broken
  backfill_before      TIMESTAMPTZ       -- отсечка догрузки (§7); NULL после её конца
  last_error           TEXT              -- диагностика для экрана; не секрет
  last_delivered_at    TIMESTAMPTZ
  created_at           TIMESTAMPTZ NOT NULL DEFAULT now()
  UNIQUE (form_id)                       -- одна таблица на форму (§2)
```

`ON DELETE CASCADE` у `connected_by` — это и есть правило «ушёл человек — ушло согласие»
(§3), выраженное схемой, а не проверкой в сервисе.

Доставка новых строк идёт через **существующий `outbox`** (`channel = 'gsheets'`), своей
таблицы очереди нет: ретраи, бэкофф и диспетчер там уже написаны и обкатаны почтой.

## 5. OAuth Google

Свой клиент на stdlib по образцу [`internal/oauth`](../../internal/oauth/oauth.go) — новых
зависимостей нет, `google.golang.org/api` не берём (список заморожен, а нужны три вызова).

**Scope — только `https://www.googleapis.com/auth/drive.file`.** Он даёт доступ ровно к тем
файлам, которые создало наше приложение, относится к несенситивной группе и потому **не
требует проверки приложения в Google**. Это и есть причина, по которой таблицу создаём мы, а
не даём выбрать существующую: полный `spreadsheets` — сенситивный scope, недели проверки с
видеодемо. Классификация scope перепроверяется по документации Google **перед слайсом A** —
она у Google дрейфует, и решение §2 держится на ней.

`access_type=offline` + `prompt=consent` — иначе refresh-токен приходит только при первом в
жизни согласии, и переподключение молча даёт интеграцию, которая умрёт через час.

Ответ Google проверяем, а не принимаем на веру: если в `scope` выданного токена нет
`drive.file`, подключение отклоняется с человеческим текстом (пользователь снял галочку на
экране согласия — обычный исход, а не сбой).

**Хранение.** Refresh-токен шифруется AES-256-GCM ключом HKDF от `FORM_TOKEN_SECRET` с
меткой назначения `integrations/google` — тот же приём, что у секрета TOTP
(`sealSecret` в [`internal/auth/totp.go`](../../internal/auth/totp.go)), и та же плата: ротация `FORM_TOKEN_SECRET`
рвёт все подключения (в раннбук ротации). Access-токен не хранится вовсе: живёт час, берётся
по refresh при доставке и держится в памяти процесса. Ни один из двух не попадает в логи,
ответы API и отчёты (инвариант 2/7 по духу: это чужой секрет).

**Конфигурация.** `GOOGLE_OAUTH_CLIENT_ID` и `GOOGLE_OAUTH_CLIENT_SECRET` — заданы оба или
ни одного (как у Яндекса). Не заданы — таб живёт, но говорит «на этом контуре интеграция не
настроена»: dev-контур без проекта в Google Cloud обязан оставаться рабочим. Переменные
идут в `.env.example` (иначе краснеет `make check-docs`), `deploy/compose.prod.yml` и
`deploy/README.md`.

**Возврат из окна Google** — существующий путь `oauth.done.tsx` (отдельное окно, фаза 23):
второй такой же поток, а не второй способ.

## 6. Доставка ответа

Продюсер — `submissions.Submit`: строка outbox с намерением доставки ставится **после
коммита ответа, best-effort** — рядом с конверсией визита и письмом владельцу.

**Здесь текст спеки разошёлся с реальностью и исправлен по факту (слайс C).** Первая
редакция обещала запись «в той же транзакции». Транзакции на этом пути нет: приём ответа
у формы без лимита и файлов — **одна вставка на пуле** (`ARCHITECTURE.md` §4.7), и
атомарность стоила бы транзакции на самом горячем эндпоинте продукта ради события, чья
потеря стоит одной строки в чужой таблице. Цена названа вслух: краш в узком окне между
коммитом и постановкой теряет одну строку; данные целы (ответ в базе, в выгрузке и в
сводке), лечение — «Перезалить всё».

**Payload несёт идентификаторы, а не готовую строку:** `{form_integration_id, submission_id}`.
Это осознанное отступление от «диспетчер — тупой релей»: собрать строку в момент приёма
значило бы прочитать версии схемы и построить `CSVBuilder` внутри самого горячего и самого
атакуемого эндпоинта продукта (`ARCHITECTURE.md` §4.7). Транспорт `gsheets` читает ответ сам
— в фоне, где лишний запрос ничего не стоит. Отступление названо строкой ADR (§11).

**Вызов Google:** `spreadsheets.values.append` с `valueInputOption=RAW`. RAW обязателен:
`USER_ENTERED` разбирает `=…` как формулу, то есть ответ респондента исполнялся бы в чужой
таблице. Это тот же класс дефекта, от которого в CSV защищает `sanitizeCSVField`, но лечится
он здесь **режимом вставки, а не префиксом апострофа**: апостроф в RAW останется видимым
символом в ячейке. Поэтому `CSVBuilder` получает вариант строки без CSV-санитайзинга
(`Row` для файла остаётся как есть — его поведение не меняется), и слайс C **проверяет
эмпирически**, что `=1+1` доезжает текстом.

**Идемпотентность — at-least-once, и это названо вслух.** У `values.append` нет ключа
идемпотентности. Дубль возможен ровно в одном окне: append прошёл, а пометка `sent_at` не
успела. Ретраи при сетевом сбое до ответа Google дубля не дают (запрос не дошёл). Окно
узкое, ущерб — лишняя строка, лечение — «Перезалить всё». Строить дедупликацию поиском по
листу перед каждой вставкой не будем: это второй запрос к Google на каждый ответ ради
события, которого может не случиться ни разу.

**Батч на тик диспетчера ограничен**, чтобы догрузка чужой формы (§7) не задерживала письма:
почта и таблицы делят один диспетчер, и голодание почты недопустимо — там сброс пароля.

## 7. Догрузка накопленных ответов

При подключении таблицу создаём мы, значит она пуста: затирать нечего, дублировать нечего, а
пустая таблица после подключения читается как «не заработало». Поэтому догрузка **делается**,
и делается так:

1. В момент привязки фиксируется отсечка `backfill_before`, статус — `backfilling`.
2. Догрузка берёт ответы **строго до** отсечки, живая доставка — **после**. Границы не
   пересекаются: ни дублей, ни пропусков.
3. Пока статус `backfilling`, живые строки **ждут в outbox** (`next_attempt_at` уже есть,
   ожидание бесплатное и ничего не теряет) — иначе новые ответы легли бы поверх старых.
4. Пишем пачками (сотни строк за один `append`): форма с 20 000 ответов не должна упереться
   в лимит 60 запросов в минуту на пользователя.
5. Тот же код — кнопка **«Перезалить всё»**: лист очищается и наполняется заново. Она нужна
   независимо от догрузки (схема формы поменялась, строки удалили руками, интеграция висела
   сломанной), и именно она — лечение дублей из §6.

## 8. Колонки и изменение формы

Колонки берутся из общей модели вопросов `QuestionOrder` — той же, что у CSV, сводки и
воронки; порядок ключей фиксируется в `form_integrations.columns` при создании листа.

**Правило: колонка только добавляется.** Новый вопрос в форме → новая колонка в конце листа
и в `columns`. Удалённый вопрос колонку не теряет: в ней живут ответы прошлых версий, и
сдвиг колонок разъехался бы с тем, что автор уже свёл формулами справа. Заголовок
переименованного вопроса обновляется на месте (ключ тот же).

`CSVBuilder` получает `Columns()` — ключи колонок (метаколонки + id вопросов): сегодня
наружу торчат только человеческие подписи `Header()`, а сопоставление «колонка листа ↔
вопрос» обязано идти по ключу, иначе переименование вопроса перемешало бы данные.

## 9. Экран «Интеграции» и окно настройки

**Дополнено по запросу владельца 2026-08-23** (образец — Tally): экран интеграций —
**список**, а настройки живут в **окне**, которое открывается кликом по строке. Это общий
жест продукта для всех будущих интеграций, а не особенность Таблиц.

Почему окно, а не поля в списке: у интеграции есть решения, которые принимают **до** первой
записи в чужие данные (какой аккаунт, какая таблица, заливать ли историю). В списке они
превратились бы в цепочку мелких кнопок, каждая из которых уже что-то поменяла, а сам
список — в простыню, где непонятно, что к чему относится. Отмена в окне — Escape, и не
произошло ничего.

**Поля окна** (взято у Tally, отвергнутое названо):

- **Название подключения** — необязательная подпись связки; нужна, когда интеграций у формы
  станет несколько (в списке они иначе различаются только значком провайдера).
- **Аккаунт Google** — показывается, а не выбирается: подключение принадлежит пространству,
  и оно одно (§2). «Сменить аккаунт» ведёт в тот же поход за согласием и **заменяет**
  подключение пространства; предупреждение о последствиях — в подсказке кнопки.
- **Таблица** — один дропдаун на три ответа одного вопроса: «создать новую», одна из
  **созданных нами ранее** и «выбрать на Google Диске» (пункт списка, а не кнопка рядом:
  разносить их по разным элементам значит делать вид, что вопросов два).
- **Лист** — появляется, когда выбрана существующая книга: «создать новый лист» либо один из
  её листов. Существующий годится, только если его **первая строка свободна** — шапка ложится
  в A1, и затирать чужую работу продукт не станет.
  Список созданных нами не требует ни Picker'а, ни сенситивного scope: под `drive.file`
  приложению видны ровно свои файлы. Новый лист в чужой книге получает имя со slug'ом формы —
  Google запрещает две вкладки с одинаковым именем.
- **Тумблер «Перенести уже накопленные ответы»**, по умолчанию включён. Раньше перенос был
  безусловным; выбор отдан человеку — у формы может быть двадцать тысяч ответов, которые ему
  в новой таблице не нужны.
- **«Выбрать на Диске» — берём** (решение владельца 2026-08-23, **отменяет** прежний отказ от
  Picker'а). Под `drive.file` «вставьте ссылку на таблицу» не работает физически: сервер не
  видит файл, которого не создавал. Picker обходит это, не трогая scope: выбранный человеком
  файл Google выдаёт нашему приложению. Цена — скрипт `apis.google.com` в кабинете и живой
  токен Google в браузере; смягчения и отвергнутая альтернатива (Picker на origin рендерера) —
  строка ADR §10.

## 9.1. Состояния пункта в списке

Маршрут `/forms/{slug}/integrations` — настоящий маршрут в pathless-группе `_manage`, как
остальные табы ([`forms.$slug._manage.tsx`](../../web/app/src/routes/_app/forms.$slug._manage.tsx)).

Один живой пункт — «Google Таблицы». Заглушек «скоро будет» нет: они обещают срок, которого
никто не давал. Состояния пункта:

- **не подключено** → кнопка «Подключить Google» (владельцу; `editor` видит текст «попросите
  владельца пространства»);
- **аккаунт подключён, форма не привязана** → «Создать таблицу для этой формы»;
- **привязано** → ссылка на таблицу, «подключено как `почта`», время последней доставки,
  «Перезалить всё», «Отключить»;
- **`backfilling`** → «переносим накопленные ответы»;
- **`broken`** → человеческая причина из `last_error` и что делать.

## 10. Безопасность и 152-ФЗ

SSRF-защиты не требуется: хосты Google фиксированы в коде, пользовательских URL здесь нет.
Формулы — §6. Токены — §5. Анти-IDOR: каждый метод сервиса начинается с `Can` по действию.

**Трансграничная передача.** Ответы респондентов уезжают в Google (США). Юридически это
забота владельца формы, но продукт обязан не делать этого молча: на экране подключения —
явная строка о том, что ответы, включая персональные данные, будут передаваться в сервис
Google, и `connected_by` в базе как запись о том, кто это разрешил. Нужно ли упоминание в
уведомлении РКН и в политике обработки — **вопрос владельца, вынесен из кода** (§13).

## 11. Строки ADR (вносятся в `ARCHITECTURE.md` §10 до кода)

1. **Продукт начинает хранить чужие refresh-токены** — у интеграций, но не у входа.
   **Не отменяет** строку «токен провайдера одноразовый»: вход по-прежнему выбрасывает токен
   после чтения профиля. Появилась ровно та возможность, ради отсутствия которой та строка
   отказывалась от хранения, — и вместе с ней обязанность шифровать, обновлять и отзывать.
2. **Подключение принадлежит пространству, человек — аудит** (§3).
3. **Таблицу создаёт продукт; scope — `drive.file`** (§5): обход проверки приложения в Google
   ценой отказа от «подключить существующую таблицу».
4. **Канал `gsheets` в существующем outbox** вместо своей очереди и своего воркера.
5. **Payload канала — идентификаторы, а не готовая строка** (§6): отступление от «тупого
   релея» ради неприкосновенности горячего пути приёма.
Шестое решение — `ActionIntegrationManage` у владельца, привязка формы под `ActionFormWrite`
(§3) — строки ADR не требует: это **применение** уже принятого «право спрашивается по
действию, а не по роли», и его место — матрица в [`WORKSPACES.md`](../WORKSPACES.md).

## 12. Критерий приёмки (демо) и Definition of Done

**Демо.** В кабинете открываете форму → таб «Интеграции» → «Подключить Google» → окно
согласия Google → возврат в кабинет, видно «подключено как `почта`» → «Создать таблицу» →
по ссылке открывается таблица, в ней шапка с вопросами и **все ранее накопленные ответы** →
отправляете форму в другом окне → через секунды строка появляется в таблице сама →
`«=1+1»`, отправленный в текстовое поле, лежит в ячейке **текстом** → «Отключить» → новые
ответы в таблицу не идут, старые строки на месте.

**Definition of Done.** Refresh-токен в БД только шифротекстом, в логах и ответах API его
нет (тест на `queries` + греп по логам); чужой пользователь и `editor` получают отказ на
подключение (анти-IDOR-тесты обеих ролей); поставленное событие переживает падение процесса
(лежит в outbox и доезжает следующим прогоном диспетчера); недоступность Google не роняет приём ответа и не плодит
дублей после восстановления; догрузка 1000 ответов не задерживает письма (тест на
ограничение батча); `make lint` и `make test` зелёные; `docs/INTEGRATIONS.md`, `API.md`,
`SCHEMA.md`, `.env.example` обновлены в тех же PR, что код.

## 13. Что решает человек, а не код

- **Доступность `googleapis.com` с прода** — проверка до слайса A. Закрыт исходящий доступ →
  меняется вся конструкция (прокси), и это решается до кода, а не после.
- **Проект в Google Cloud**: OAuth-клиент, экран согласия, redirect URI трёх контуров.
  Секреты выдаёт владелец, в репозиторий они не попадают.
- **Упоминание трансграничной передачи** в политике обработки и уведомлении РКН (§10).
