# Спека. Админка сервиса: отдельное приложение для поддержки, операций и модерации

> **На согласовании, код не начат.** Источник — продуктовый запрос владельца 2026-09-14;
> готового критерия приёмки у такого источника нет (`PROCESS.md` §1.0), поэтому он записан
> здесь, в §1, по этапам, и согласуется до кода. Затронуты схема БД, контракт API и контур
> выкатки — план каждого этапа показывается владельцу (`PROCESS.md` §1.3).
>
> **Решения владельца, принятые 2026-09-14** (обсуждение в сессии, до этой спеки):
>
> 1. Админка — **отдельное фронтенд-приложение** `web/admin` на **отдельном origin**.
> 2. Интерфейс — **дефолтные компоненты shadcn**. Красота и сходство с кабинетом не важны:
>    дизайн-система кабинета (`DESIGN-SYSTEM.md`, скилл `ui-kit`) к админке не применяется,
>    UI-кит с кабинетом не делится.
> 3. Администратор **никогда** не видит содержимое ответов респондентов; «войти как
>    пользователь» нет.
> 4. Заблокированная форма показывает респонденту **явный экран блокировки**, а не 404.
> 5. Жалобы принимаются **только адресом abuse@** — ссылки «Пожаловаться» на форме нет.
> 6. Ошибка в админке показывается **сообщением сервера + кодом + `request_id`**: правило
>    кабинета «никакой латиницы на экране» здесь осознанно не действует.

## 1. Критерий приёмки

Работа режется на четыре этапа (§11); у каждого — свой критерий. Этап закрывается, когда его
сценарий пройден на prod-local глазами и тесты из списка зелёные.

### 1.0. Каркас

> Открываю `https://admin.localhost`. Ввожу email и пароль администратора — в Mailpit
> приходит код, ввожу его — вижу пустую оболочку админки со своим email и кнопкой «Выйти».
>
> Тот же вход аккаунтом без `is_admin` отвечает ровно тем же «Неверный email или пароль»,
> что и неверный пароль, и письма с кодом не приходит.
>
> Кабинет `app.localhost` в соседней вкладке остаётся залогиненным и продолжает работать.
> `UPDATE users SET is_admin = false` — следующее же действие в админке выбрасывает на вход.

Проверяется тестами:

1. **Сессии не взаимозаменяемы.** Токен сессии кабинета, предъявленный админскому API, —
   `401`; токен админской сессии, предъявленный API кабинета, — `401`.
2. **Отказ не-админу неотличим** от неверного пароля: тот же статус, то же тело, код не
   отправлен (в `login_codes` строки нет).
3. **Снятие флага действует на следующем запросе**, без выхода и без истечения сессии.
4. **Админских ручек нет на listener'е кабинета:** любой путь админского API на `:8080` —
   `404`.
5. Вход в админку под rate limit'ом — тем же, что вход в кабинет (инвариант 6).

### 1.1. Просмотр

> Вставляю в поиск ссылку `https://f.localhost/r/<slug>` чужой формы — открывается карточка
> формы: название, статус, пространство, владелец с email, его тариф, число ответов за месяц
> и скрытых сверх лимита, цели доставки и их поломки. Ссылка на владельца ведёт в карточку
> аккаунта: пространства, формы, расход ассистента, число активных сессий.
>
> Нигде в админке нет ни одного значения из ответов.
>
> «Здоровье» показывает тег и коммит образа, номер последней миграции, очередь писем (сколько
> ждут, возраст самой старой, строки с многими попытками и их ошибкой) и последние прогоны
> фоновых задач. «Метрики» — таблица по дням за 30 дней: регистрации, новые формы,
> публикации, ответы, генерации ассистента.

Проверяется тестами:

1. **Ответы не утекают.** В базе форма с ответом, содержащим уникальную строку; ни одна
   ручка админского API эту строку не отдаёт (проверка по сырому JSON всех ответов
   карточек и поиска).
2. Поиск находит одну и ту же сущность по email, UUID, slug формы и полной ссылке на форму.
3. Секреты не отдаются: пароль формы, секрет подписи и свои заголовки вебхука, токены
   аккаунтов Google отсутствуют в ответах карточек (тем же способом, что п. 1).

### 1.2. Операции

> Аккаунт на Free, у формы в его командном пространстве пять ответов скрыты сверх лимита. В
> карточке аккаунта «Сменить тариф» → Pro, причина «оплата по счёту №12». В кабинете
> владельца скрытые ответы видны **во всех** его пространствах, плашки нет. В «Журнале» —
> строка: кто, когда, Free → Pro, причина. Без причины кнопка не активна, а API отвечает `422`.
>
> В «Тарифах» ставлю Free `submissions_per_month` = 100: диалог перед сохранением называет
> число аккаунтов на этом плане; после сохранения — строка журнала «было / стало».
>
> Витрина: загружаю JSON шаблона — он появляется в галерее кабинета; снимаю с публикации —
> исчезает из галереи, форма, созданная из него раньше, живёт.
>
> «Отозвать сессии» у пользователя — его кабинет на следующем запросе показывает экран входа.
>
> В «Здоровье» письмо с отравленной строкой (TD-64) → «Отменить» — строка уходит из очереди,
> в журнале запись.

Проверяется тестами:

1. **Аудит в транзакции действия.** Сбой изменения — строки аудита нет; сбой вставки аудита —
   изменение откачено.
2. **Редактор лимитов не пропускает то, что ловит `TestPlansCoverCatalog`:** неизвестный
   ключ, отсутствующий ключ, значение не того вида (число вместо булева) — `422`.
3. **Перевод аккаунта открывает скрытые во всех пространствах, где он владелец**, а не в
   одном (см. §7.2).
4. `POST /api/v1/admin/templates` на listener'е кабинета больше нет; `scripts/seed-templates.sh`
   удалён.

### 1.3. Модерация

> Блокирую опубликованную форму с причиной. Респондент по ссылке видит «Форма заблокирована
> за нарушение правил» — без названия формы и без бейджа; превью ссылки в мессенджере
> заголовка формы не показывает. Отправка ответа запросом — `410 form_blocked`.
>
> Автор в кабинете видит у формы плашку «Заблокирована администратором»; «Опубликовать»
> отказывает. Разблокирую — форма снова принимает ответы; в журнале две строки.
>
> Блокирую аккаунт с отметкой «и все его опубликованные формы» — вход в кабинет отвечает
> «Аккаунт заблокирован», его сессии отозваны, формы показывают экран блокировки.

Проверяется тестами:

1. **Блокировку повторяет каждый публичный вход формы** (§8.4) — тест перебирает их все.
2. HTML `/r/{slug}` заблокированной формы не содержит её `title` ни в `<title>`, ни в OG-мете.
3. Разблокировка возвращает форму в прежний статус (`published` остаётся `published`).

## 2. Что делаем и чего не делаем

**Делаем:** отдельное приложение `web/admin` на своём домене; вход администратора с кодом на
каждый вход и своей сессией; модуль `internal/admin` на отдельном listener'е того же процесса;
журнал действий администратора; поиск и карточки аккаунта, пространства и формы; операции,
которые сегодня делаются `psql` (§3); здоровье контура и метрики продукта; блокировку формы и
аккаунта.

**Не делаем:**

- **Просмотр ответов и «войти как пользователь»** — решение владельца (§4, п. 2 и 3).
- **Ссылку «Пожаловаться» на форме и приём жалоб в продукте** — решение владельца: жалобы
  приходят письмом на abuse@ (§9).
- **Роли администраторов** (поддержка / биллинг / модератор). Администраторов единицы (ADR
  §10, строка про `is_admin`); кто что сделал, видно в журнале.
- **Аудит чтений.** Журнал пишет только изменения; просмотр карточек не журналируется.
- **Объявления на весь сервис, фича-флаги.** Выключатели возможностей уже есть — `plans.limits`.
- **Чистка данных по 152-ФЗ и операции с платежами** (возвраты, ручное продление) — придут
  со своими фазами `POST-MVP` и получат в админке свою кнопку.
- **Графики.** Метрики — таблицами чисел; recharts в админку не ставится.

## 3. Зачем: что сегодня делается руками

Администрирование сегодня — `psql` против прод-базы и один скрипт. Инвентаризация на 2026-09-14:

| Операция | Как сейчас | Где описано |
|---|---|---|
| Перевести аккаунт на другой тариф | два `UPDATE`; забыть второй — скрытые ответы остаются скрытыми | `BILLING.md` §6 |
| Включить/снять гейт тарифа | `jsonb_set` по `plans.limits` | `BILLING.md` §6, `STATUS.md` «Гейты, закрытые данными» |
| Обнулить квоту ассистента | `UPDATE account_usage` | `BILLING.md` §6 |
| Кто упирается в лимиты | ручной `SELECT` | `BILLING.md` §6 |
| Выдать `is_admin` | `UPDATE users` | `SCHEMA.md`, `users` |
| Пополнить витрину шаблонов | `scripts/seed-templates.sh`; повторный прогон плодит дубли, снять — только SQL | сам скрипт |
| Письмо с отравленной строкой в `outbox` | ретраится вечно, видно только в базе | `TECH-DEBT.md` TD-64 |
| Узнать, что крутится на проде | никак: бинарник собирается `-ldflags="-s -w"` без версии | `deploy/Dockerfile` |

И того, что не делается вовсе: снять чужую форму, заблокировать аккаунт, отозвать сессии
человека, узнать, кто и почему менял тариф.

**Модерация — риск, а не удобство.** Конструктор форм — типовой инструмент фишинга («подтвердите
вход в Госуслуги»). Одна такая форма, и Safe Browsing помечает `f.trillix.ru` целиком: красный
экран получают респонденты всех клиентов. Вторая ветка того же риска — предписание РКН.
Сегодня снять форму можно только SQL.

## 4. Принципы

1. **Отдельный origin и отдельная сессия.** Права администратора распространяются на всех
   клиентов. В общей с кабинетом сессии любая XSS в кабинете, где рендерится пользовательский
   контент, давала бы доступ ко всем пространствам, а не к одному. Это тот же довод, по
   которому `f` отделён от `app` (ADR §10, «Две origin»).
2. **Администратор видит метаданные и счётчики, но не ответы.** Ответы — персональные данные
   респондентов, которые сервис обрабатывает по поручению клиента (152-ФЗ). Опубликованная
   форма публична, и админка ведёт на неё ссылкой. Секреты (пароль формы, секрет и заголовки
   вебхука, токены Google) не отдаются никогда.
3. **Никакого «войти как пользователь».** Это доступ к ответам в обход п. 2. Поддержка
   работает по метаданным: журнал доставок, строки `outbox` на адрес человека, статус подписки.
4. **Каждое изменение пишет строку аудита в той же транзакции**, с обязательной причиной.
   Действие без следа невозможно по построению.
5. **Изменения идут через сервис модуля-владельца.** `internal/admin` не пишет в
   `subscriptions`, `forms`, `sessions` своим SQL — он вызывает метод модуля, который держит
   инварианты этой таблицы. Своим SQL админка только читает.

## 5. Устройство

### 5.1. Контур

```
admin.trillix.ru ──► Caddy ──► /srv/static/admin            (статика web/admin)
                        └──── /api/* ──► api:8081           (админский listener)
app.trillix.ru   ──► Caddy ──► /api/* ──► api:8080          (админских ручек здесь нет)
f.trillix.ru     ──► Caddy ──► /r/*, /public/* ──► api:8080
```

**Админский API — отдельный listener того же процесса** (`ADMIN_LISTEN`, по умолчанию
`:8081`). Caddy проксирует на него только с сайта `admin`. С origin кабинета до админских ручек
не добраться никаким путём: их нет в mux'е `:8080`, и ответ «не-админу — 404» (ADR §10, строка
про `is_admin`) становится свойством конструкции, а не проверки. Порт наружу не публикуется,
как и `:8080`.

**Переменные контура:** `ADMIN_DOMAIN`, `ADMIN_ORIGIN` (сверка `Origin` для CSRF),
`ADMIN_LISTEN`. Пустой `ADMIN_ORIGIN` — админка выключена: listener не поднимается, контур
работает как раньше (тот же приём, что у необязательных подсистем: печать, Яндекс ID).

**Заголовки сайта `admin`** — общий сниппет `secheaders` с `frame-ancestors 'none'` и
`X-Frame-Options: DENY`, как у `app`; плюс `X-Robots-Tag: noindex`.

### 5.2. Вход и сессия

Идентичность та же — строка `users` с `is_admin = true`. Сессия — своя.

- **`sessions.scope`** — `app | admin`, `NOT NULL DEFAULT 'app'`. `GetSessionUser` кабинета
  фильтрует `scope = 'app'`, `RequireAdmin` — `scope = 'admin'`. ⚠ Cookie host-only сама по
  себе не разделяет сессии: браузер не отправит чужую cookie, но токен — это строка, и
  подставить её руками можно. Разделяет только фильтр по `scope` на сервере.
- **Код на почту при каждом входе,** а не только на незнакомом устройстве: `known_devices` для
  админского входа не читается и не пишется.
- **Срок жизни — 8 часов** от входа, без продления. Кабинетные 30 суток здесь не нужны:
  админку открывают под задачу.
- **`RequireAdmin` перечитывает `is_admin` на каждом запросе** одним `JOIN users` в том же
  запросе, что сессию. Снятие флага действует на следующем запросе (сессии в Postgres, ADR §10).
- **Отказ не-админу неотличим от неверного пароля:** проверка флага стоит после проверки
  пароля и отвечает тем же `401 invalid_credentials`, без отправки кода. Иначе форма входа в
  админку перечисляла бы администраторов.
- ⚠ **Активный код входа — один на аккаунт** (`login_codes`, PK `user_id`): одновременный вход
  в кабинет и в админку перетирают код друг друга. Принимается как есть — повторный запрос
  кода лечит.
- «Выйти везде» и сброс пароля удаляют сессии по `user_id` — админские уходят вместе с
  кабинетными, отдельной ветки не нужно.

Проверка пароля и код входа — существующие методы `internal/auth`; новое в `auth` — только
создание сессии со `scope` и фильтр по нему.

### 5.3. Бэкенд: модуль `internal/admin`

```
internal/admin/
├── handler.go     # ручки админского API за RequireAdmin; mux listener'а :8081
├── service.go     # транзакция → метод модуля-владельца → строка аудита
├── audit.go       # реестр действий (код действия, вид цели) и запись в admin_audit
├── repo.go        # только чтение по всем клиентам: поиск, карточки, счётчики, метрики
└── queries.sql
```

**Интерфейсы модулей-владельцев объявляются в `admin`** (на стороне потребителя, как везде в
проекте) и принимают `postgres.DBTX`, чтобы изменение и аудит легли в одну транзакцию.
Предварительный состав:

| Интерфейс | Модуль-владелец | Методы |
|---|---|---|
| тариф | `entitlements` | сменить план аккаунта (с открытием скрытых, §7.2), обнулить квоту месяца, записать `plans.limits` с проверкой по каталогу |
| аккаунт | `auth` | отозвать сессии, заблокировать/разблокировать, восстановить помеченный удалённым |
| форма | `forms` | заблокировать/разблокировать |
| витрина | `templates` | завести публичный шаблон, снять с публикации |
| письма | `mail` | повторить сейчас, отменить строку `outbox` |

Методов «обойти проверку членства» в модулях не появляется: админские методы — отдельные, с
другим именем, и сами проверок членства не делают, потому что их вызывает только `admin` за
`RequireAdmin`.

**Ошибки** — тот же формат и тот же `respond.go`, что у API кабинета.

### 5.4. Журнал действий

Таблица `admin_audit` (§7.1). Правила:

- **Строка на каждое изменяющее действие, в транзакции действия.** Сервис `admin` открывает
  транзакцию, передаёт её модулю-владельцу, пишет аудит, коммитит.
- **Причина обязательна** — непустая строка до 1000 символов; пустая — `422`.
- **В `details` — только изменённые поля и идентификаторы**, не снимки строк: снимок строки
  `outbox` или ответа унёс бы персональные данные в журнал, который живёт дольше исходной строки.
- **Только дописывание.** В `repo` нет `UPDATE`/`DELETE` по таблице.
- Исполнитель хранится и id, и email на момент действия: журнал обязан пережить снятие флага
  и пометку удаления исполнителя.

### 5.5. Фронт: `web/admin`

Третий Vite-проект рядом с `web/app` и `web/renderer`.

- **Стек:** React, TanStack Router (file-based) и Query, zod, Tailwind v4, shadcn со стилем и
  темой по умолчанию (`radix-ui`, `class-variance-authority`, `tailwind-merge`, `clsx`,
  `lucide-react`, `sonner`). Все пакеты уже есть в кабинете — новых зависимостей в проекте нет,
  но у `web/admin` свой `package.json`, и его список фиксируется в `web/CLAUDE.md`.
- **Из `web/app` и `web/shared` не импортирует ничего.** Форма «глазами респондента» — ссылка
  на `f.trillix.ru/r/{slug}`, поэтому `@fields` не нужен; типы админского API — свои zod-схемы
  в `web/admin/src/api`.
- **Не применяются:** дизайн-система и скилл `ui-kit`, `humanError`, бюджет бандла.
- **Применяются:** серверные данные только в TanStack Query; ответ API парсится zod-схемой на
  границе; мутация инвалидирует свои ключи.
- **Ошибка на экране** — `message` сервера, если он есть; иначе код (`not_found`, `internal`);
  всегда — `request_id` из заголовка `X-Request-Id` с копированием, для поиска в логах
  (`deploy/README.md` §«Логи»).
- Тёмной темы и отдельной мобильной вёрстки нет.

### 5.6. Сборка и выкатка

Третье приложение подключается в пяти местах:

| Где | Что |
|---|---|
| `.github/workflows/ci-code.yml` | `admin` в матрице `project` |
| `Makefile` | `lint-web`, `test-web` |
| `scripts/build-static.sh`, `deploy/remote-update.sh` | каталог `static/admin` (сейчас стираются только `app` и `renderer`) |
| `deploy/caddy/Caddyfile` | сайт `{$ADMIN_DOMAIN}` |
| `deploy/compose*.yml` | переменные `ADMIN_*` у `api` |

**Версия в бинарнике:** `deploy/Dockerfile` получает `ARG VERSION`/`ARG COMMIT` и собирает
с `-ldflags "-s -w -X main.version=… -X main.commit=…"`; релизный путь тега передаёт их.
Значения показывает «Здоровье» (§6.6).

## 6. Функции

### 6.1. Поиск

Одно поле. Распознаёт email, UUID (аккаунт, пространство, форма), slug формы, slug
пространства и полную ссылку на форму `https://f.trillix.ru/r/{slug}` — жалобы приходят
ссылками. Результат — список сущностей с видом и переходом в карточку.

### 6.2. Аккаунт

**Видно:** email, имя, дата регистрации, подтверждение почты, способы входа (пароль, Яндекс),
второй фактор, пометка удаления, блокировка; тариф и статус подписки; расход ассистента за
месяц; пространства (где владелец, где участник) со счётчиками форм и ответов за месяц; число
активных сессий; строки `outbox` на адрес аккаунта за 7 дней (шаблон, попытки, ошибка, отправлено
ли — без payload).

**Действия:** сменить тариф; обнулить квоту ассистента за текущий месяц; отозвать все сессии;
заблокировать / разблокировать (§8.5); восстановить помеченный удалённым, пока строка жива.

### 6.3. Пространство и форма

**Пространство:** название, личное или командное, владелец, участники, план (владельца),
расход ответов за месяц, формы.

**Форма:** название, slug и ссылка на публичную форму, статус, номер опубликованной версии,
дата последней публикации, ответы за месяц и всего, скрытые сверх лимита, закрытие (дата,
лимит), есть ли пароль (факт, не значение), цели доставки: вид, состояние, последняя ошибка.

**Действия с формой:** заблокировать / разблокировать (§8.4).

### 6.4. Тарифы

Каталог планов с их `limits`. Редактор значений знает каталог возможностей
(`internal/entitlements/catalog.go`, отдаётся ручкой): вид значения, `null` — безлимит, `0` —
запрет, булев — да/нет. Перед сохранением — число аккаунтов на плане. Сохранение проходит те же
правила, что `TestPlansCoverCatalog`: ключи плана совпадают с каталогом в обе стороны.

### 6.5. Витрина шаблонов

Список публичных шаблонов; загрузка JSON-документа (через тот же `ValidateSchema`, что у
нынешней ручки); снятие с публикации. Скрипт `scripts/seed-templates.sh` и ручка
`POST /api/v1/admin/templates` на listener'е кабинета удаляются; шесть заготовок из
`scripts/templates/*.json` заливаются через админку.

### 6.6. Здоровье

- версия и коммит образа, время старта процесса, номер последней применённой миграции
  (`schema_migrations`);
- `outbox`: сколько ждёт, возраст самой старой неотправленной строки, строки с 10+ попытками
  с `last_error`; действия «повторить сейчас» и «отменить» (§8.6);
- `webhook_queue`, `sheet_queue`: хвост по целям (топ-20 по размеру и возрасту), цели в
  состоянии поломки;
- фоновые задачи `periodic`: имя, последний прогон, длительность, последняя ошибка.
  Раннер держит это **в памяти процесса**: инстанс один (ADR §10, тот же довод, что у
  in-memory rate limit), после рестарта таблица пуста до первых прогонов;
- печать PDF: настроена ли на контуре, отвечает ли `printer`.

Эта страница заодно закрывает «выкатка не подтверждается сама» (`STATUS.md`): после тега видно,
какая версия реально отвечает.

### 6.7. Метрики продукта

Таблица по дням за 30 или 90 дней: регистрации (`users.created_at`), новые формы
(`forms.created_at`), публикации (`form_versions.created_at`), ответы (`submissions.created_at`,
видимые и сверх лимита отдельно), генерации ассистента (`account_usage`, по месяцам).
Распределение аккаунтов по планам. «Кто упирается»: топ пространств по расходу ответов
относительно лимита их плана (запрос из `BILLING.md` §6).

Всё — из существующих таблиц, без `product_events` (`POST-MVP.md`, «Аналитика продукта»).
Запросы не на горячем пути и ограничены окном; при росте объёма упираются в те же места, что
TD-78…TD-86.

### 6.8. Журнал

Лента `admin_audit` новыми сверху, курсорная пагинация, фильтр по исполнителю, виду действия и
цели. Из карточки аккаунта или формы — журнал, отфильтрованный по ней.

### 6.9. Модерация

Жалоба приходит письмом на abuse@ (§9). Разбор: ссылка из письма — в поиск → карточка формы →
«Заблокировать» с причиной (номер или тема письма). Очереди жалоб в продукте нет.

## 7. Схема (предварительно)

### 7.1. Новые таблицы и колонки

| Где | Что | Этап |
|---|---|---|
| `sessions.scope` | `TEXT NOT NULL DEFAULT 'app'`, `CHECK (scope IN ('app','admin'))` | 1.0 |
| `admin_audit` | `id` UUIDv7 PK; `actor_user_id` UUID без FK; `actor_email` TEXT; `action` TEXT; `target_kind` TEXT; `target_id` UUID; `reason` TEXT NOT NULL; `details` JSONB; `created_at`. Индексы `(target_kind, target_id, id DESC)`, `(id DESC)` | 1.2 |
| `forms.blocked_at` | `TIMESTAMPTZ` nullable; `NOT NULL` = заблокирована администратором | 1.3 |
| `users.suspended_at` | `TIMESTAMPTZ` nullable; `NOT NULL` = аккаунт заблокирован | 1.3 |

`actor_user_id` без FK сознательно: журнал не должен ни каскадиться, ни мешать удалению строки
пользователя, когда появится реальная чистка по 152-ФЗ. Причина блокировки хранится только в
журнале — колонки причины у формы и аккаунта нет (§8.4).

### 7.2. Смена тарифа — по всем пространствам

`BILLING.md` §6 переводит аккаунт и открывает скрытые ответы **одного** пространства
(`RevealHidden(ctx, db, workspaceID)`). Подписка аккаунтная: план покрывает все пространства,
где аккаунт владелец, поэтому метод смены плана обязан открыть скрытые во **всех** них, в той же
транзакции. Иначе после перевода ответы в командном пространстве остаются скрытыми, хотя тариф
их вмещает.

Открывать скрытые при переводе на план, лимит которого их **не вмещает**, нельзя; правило «когда
открывать» живёт в `entitlements`, а не в админке.

## 8. Контракт: админский API (эскиз)

Префикс `/api/v1` на listener'е `ADMIN_LISTEN`. CSRF — тот же double-submit и сверка `Origin`
с `ADMIN_ORIGIN`. Изменяющие ручки принимают `reason` в теле.

### 8.1. Вход

```
POST /auth/login          email + пароль → код на почту (всегда)
POST /auth/login-code     код → сессия scope=admin
POST /auth/logout
GET  /auth/me
```

### 8.2. Чтение

```
GET /search?q=
GET /users/{id}
GET /workspaces/{id}
GET /forms/{id}
GET /plans                 планы с limits
GET /plans/catalog         каталог возможностей: ключ, вид значения, скоуп
GET /templates
GET /health
GET /outbox?state=stuck
GET /metrics?days=30
GET /audit?actor=&action=&targetKind=&targetId=&cursor=
```

### 8.3. Изменения

```
POST   /users/{id}/plan               { plan, reason }
POST   /users/{id}/ai-quota/reset     { reason }
POST   /users/{id}/sessions/revoke    { reason }
POST   /users/{id}/suspend            { reason, blockForms }
POST   /users/{id}/unsuspend          { reason }
POST   /users/{id}/restore            { reason }
POST   /forms/{id}/block              { reason }
POST   /forms/{id}/unblock            { reason }
PUT    /plans/{code}/limits           { limits, reason }
POST   /templates                     { document, reason }
POST   /templates/{id}/unpublish      { reason }
POST   /outbox/{id}/retry             { reason }
DELETE /outbox/{id}                   { reason }
```

### 8.4. Заблокированная форма

- **Публичные входы.** Каждый вход, который сегодня отвечает `410 form_closed` закрытой форме,
  заблокированной отвечает `410 form_blocked`: `GET /public/v1/forms/{slug}`, `…/submissions`,
  `…/partial`, `…/visits`, `…/unlock`, `…/uploads`, `…/slots`, `…/slots/hold`. ⚠ `API.md` уже
  требует, чтобы отказы записи повторяли отказы отдачи формы; блокировка — пятый такой отказ, и
  пропуск одного входа оставляет у заблокированной формы работающую запись.
- **Тело 410** — `{ "blocked": true }`, **без `title`, `closedMessage` и бейджа.** Заголовок
  фишинговой формы и есть приманка; экран «приём закрыт» его показывает, экран блокировки — нет.
- **`GET /r/{slug}`** заблокированной формы отдаёт оболочку без названия формы в `<title>` и
  OG-мете: иначе превью ссылки в мессенджере продолжает показывать приманку.
- **Рендерер** по `form_blocked` рисует экран «Форма заблокирована за нарушение правил». Текст
  фиксированный, причина из журнала респонденту не показывается.
- **Кабинет автора:** плашка «Заблокирована администратором» с фиксированным текстом и адресом
  поддержки; причина из журнала автору не показывается (в ней может быть отправитель жалобы).
  Публикация отвечает `409 form_blocked`. Снятие с публикации, правка черновика, ответы и
  удаление формы автору доступны.
- **Статус не меняется:** `blocked_at` — отдельный факт поверх `status`, разблокировка
  возвращает форму в то состояние, в котором её заблокировали.

### 8.5. Заблокированный аккаунт

- Вход паролем и через провайдера после успешной проверки отвечает `403 account_suspended`
  («Аккаунт заблокирован») — после, а не до проверки пароля, чтобы не подтверждать существование
  адреса.
- Сессии отзываются в транзакции блокировки.
- С `blockForms = true` в той же транзакции блокируются все опубликованные формы пространств,
  где аккаунт **владелец**; каждая форма получает свою строку журнала.
- Публичные формы без `blockForms` продолжают работать: у командного пространства могут быть
  другие участники, и блокировка человека не обязана гасить их работу.

### 8.6. Отмена письма

`DELETE /outbox/{id}` удаляет строку. В журнал идут id, канал, шаблон, число попыток и
`last_error` — без `payload` (§5.4). Колонки «отменено» у `outbox` не появляется: диспетчер и
частичный индекс `idx_outbox_pending` остаются без изменений.

## 9. Жалобы: только abuse@

Решение владельца: ссылки на форме нет, жалобы приходят письмом.

**Следствия, которые нужно закрыть до этапа 1.3 (за владельцем, кода нет):**

- **Ящик `abuse@trillix.ru`** должен существовать и читаться.
- **Адрес негде опубликовать.** Страниц `/privacy` и `/terms` в продукте нет (фаза 12
  `POST-MVP` не делалась), а апекс `trillix.ru` Caddy не обслуживает (`STATUS.md`). Пока адрес
  нигде не написан, жалоб не будет вовсе.
- **Основной канал узнать о фишинге при таком решении — не жалобы, а уведомления поисковиков.**
  `f.trillix.ru` подключается в Яндекс.Вебмастер и Google Search Console: о «проблемах
  безопасности» на домене они пишут владельцу раньше, чем пометка доезжает до браузеров.

## 12. Отвергнутые альтернативы

| Вариант | Почему нет |
|---|---|
| Раздел `/admin` внутри кабинета | Админские права в одной сессии с кабинетом (§4, п. 1). Маршруты кабинета собраны в один чанк (TD-86) — код админки грузился бы у всех пользователей |
| Только CLI (`./api admin …` через `docker compose exec`) | Карточки, поиск по ссылке и журнал в терминале не разобрать, с телефона не открыть. CLI остаётся аварийным путём, как сегодня `UPDATE` |
| Второй вход в `web/app` (одна сборка, два приложения, общий `components/ui`) | Решение владельца: отдельное приложение |
| Общий UI-кит в `web/shared/ui` / копия компонентов кабинета / импорт из `web/app` | Решение владельца: красота и сходство с кабинетом не важны, берутся дефолтные компоненты shadcn |
| Отдельный бинарник `cmd/admin` | Дублирование composition root и всех сервисов; модульный монолит (ARCHITECTURE §2.1) решает изоляцию listener'ом, а не процессом |
| Один listener и проверка `Host` | Защита держится на одном `if` и на правильности прокси. Отдельный порт делает недоступность админских ручек с `app` структурной |
| Просмотр ответов по запросу с причиной в журнале | Решение владельца: никогда (§4, п. 2) |
| Ссылка «Пожаловаться» на каждой форме, очередь жалоб в админке | Решение владельца: только abuse@ (§9) |
| Заблокированная форма отвечает 404 | Решение владельца: явный экран. Прецедент — закрытая форма отвечает 410 со своим экраном; блокированная была публичной, инвариант 5 про приватное её не касается |
| Колонка причины блокировки у формы и аккаунта | Вторая копия того же факта рядом с журналом; автору и респонденту причина не показывается (§8.4) |
| Колонка `cancelled_at` у `outbox` | Меняет запрос диспетчера и частичный индекс ради строки, которую никто не будет читать; след остаётся в журнале (§8.6) |
