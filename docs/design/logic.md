## 1. Что решается

Форма сегодня линейна: все вопросы видят все. Из этого следуют три ежедневные проблемы автора
анкеты — вопрос «какой у вас питомец?» показывается тем, у кого питомца нет; уточнения по
редкой ветке удлиняют форму для всех; обязательное поле нельзя сделать обязательным «только
если». Лечится это одним механизмом — **условием на видимость и на путь**.

**Критерий приёмки (черновик, требует согласования).** В билдере у вопроса задаётся условие
«показывать, если» с вложенными группами И/ИЛИ; у варианта выбора — своё; у разрыва страницы —
переходы «если … то на страницу N»; обязательность задаётся по условию. По публичной ссылке и
в превью билдера форма ведёт себя одинаково: скрытые вопросы не показываются и не требуются,
пропущенные страницы не открываются, линии шагов считают путь, который получается при
текущих ответах. Присланный curl'ом ответ на скрытый вопрос **не попадает в базу** и не виден
ни в таблице, ни в CSV, ни в сводке. Форма без единого правила ведёт себя ровно как сегодня —
байт в байт.

### 1.1 Чем этот текст расходится с фазой 16 `POST-MVP`

| Текст фазы | Реальность 2026-08 | Что вместо |
|---|---|---|
| «`schemaVersion: 2`, апгрейдер v1→v2 на чтении» | версия 4; правило только расширяет множество принимаемых документов | **версия не поднимается**, апгрейдера нет — довод `page_break` (фаза 19) и `ColumnLeft` |

## 2. Скоуп v1 (решение владельца 2026-08-06)

Входит всё четыре:

1. **Видимость вопроса** — `visibleIf` у группы (вопрос, заголовок, абзац, картинка).
2. **Обязательность по условию** — `requiredIf` у отвечаемого блока.
3. **Скрытие отдельных вариантов** выбора — `visibleIf` у `Option` (каскадные списки).
4. **Условные переходы между страницами** — `jumpIf` у разрыва страницы. Хвост фазы 19,
   отложенный в фазу 16 `POST-MVP` ([`STATUS.md`](../STATUS.md), «Что решено НЕ делать сейчас»).

Плюс **вложенные группы условий** (`(А и Б) или В`) вместо плоского AND.

**Логика бесплатна на всех тарифах** (решение владельца): гейта в `entitlements` нет.
Закрыть потом — строка в каталоге и вызов `Check`, [`BILLING.md`](../BILLING.md) §6.

**Скоуп большой, и это осознанно.** Четыре возможности — четыре потребителя **одного** ядра:
дерево условий и вычислитель. Поэтому порядок работ (§11) кладёт ядро в первый слайс, а
возможности — отдельными слайсами поверх; остановка после любого из них оставляет продукт
целым.

### 2.1 Вне скоупа v1 (осознанно)

- **Вычисления и баллы** (scoring, арифметика по ответам) — другой механизм, не условие.
- **Маршрутизация уведомлений** («если выбрал X — письмо в отдел Y») — ждёт фазы почты.
- **Скрытые поля и подстановка из URL** — предзаполнение уже есть у встраивания
  ([`EMBED.md`](../EMBED.md)); «скрытое поле, которого респондент не видит вовсе» — отдельная
  задача про приватность данных, не про логику.
- **Условия на настройки формы** (текст «Спасибо», редирект по ветке) — просят реже, чем
  всё перечисленное, и трогают другую поверхность.
- **Условие по метаданным визита** (устройство, источник, время) — ответов не касается.

## 3. Модель данных

### 3.1 Дерево условий — одна форма на все четыре правила

```
Cond ::= { all: [Cond, …] }            // все обязаны выполниться
       | { any: [Cond, …] }            // достаточно одного
       | { blockId, op, value? }       // лист: сравнение ответа
```

Один тип на все четыре правила: у автора одна модель в голове, у нас один вычислитель, один
редактор в билдере и один набор тестов. В Go — одна рекурсивная структура (три формы, ровно
одна из которых заполнена), в Zod — `z.lazy`; лишние поля запрещены обеими сторонами, как и
везде в схеме.

**Лимиты (новые константы, зеркалятся):** `MaxLogicDepth = 4` (глубина вложенности),
`MaxLogicNodes = 40` (узлов в одном правиле), `MaxLogicValueLen = 200` (как placeholder).
Оба первых обязательны: без них дерево из чужого документа — это стоимость вычисления,
умноженная на 200 блоков, то есть тот же класс проблемы, что `MaxSpans` у богатого текста.

### 3.2 Операторы

| `op` | Смысл | Осмыслен у типов |
|---|---|---|
| `answered` / `empty` | ответ есть / ответа нет | любой отвечаемый |
| `is` / `is_not` | равно / не равно | single_choice, dropdown (id варианта), scale, number, consent, текстовые (точная строка) |
| `includes` / `excludes` | содержит / не содержит вариант | multi_choice (id варианта) |
| `gt` / `lt` | больше / меньше | scale, number |

`value` — строка **в том же виде, в каком хранится ответ** (`answer.ts`: id варианта, число
строкой, `yes` у согласия). Второго формата не заводим: любое расхождение здесь — это молчащее
«условие никогда не срабатывает».

**Совместимость оператора с типом источника схемой НЕ проверяется** (§4.3): `changeBlockType`
у источника иначе ронял бы 422 в автосейв. Несовместимая пара **инертна**, а предупреждает о
ней билдер.

### 3.3 Где живёт каждое правило

| Правило | Носитель | Почему там |
|---|---|---|
| `visibleIf` | **головной блок группы**, верхний уровень блока | Видимость — свойство вопроса целиком (подпись + поле + контент прячутся вместе). Прямой прецедент — бит ряда: «на первом блоке группы бит значит „моя группа…"» ([`EDITOR.md`](../EDITOR.md) §13) |
| `requiredIf` | **отвечаемый блок**, рядом с `required` | Обязательность — свойство поля, а не вопроса; `required` там же |
| `visibleIf` у варианта | `Option` | Тот же приём, что у бита колонки: один ключ у блока и у варианта |
| `jumpIf` | блок `page_break` | Разрыв — единственная сущность страницы, которая есть в схеме и имеет стабильный id (страница выводится `splitPages`) |

`visibleIf` — верхний уровень блока, а не `settings`: это свойство любого блока, а не типа —
ровно довод, которым туда попало `name` (фаза 16).

**Ссылка `blockId` — всегда на отвечаемый блок** источника: тот же id, которым вопрос зовётся
в CSV, воронке и сводке. Ссылаться на подпись или на группу нельзя — у них нет ответа.

### 3.4 Переходы между страницами

```
page_break.jumpIf: [ { when: <Cond>, to: "<id другого page_break>" | "end" }, … ]
```

Правило висит на разрыве, который **закрывает** покидаемую страницу: «ухожу с этой страницы —
куда». `to` — id разрыва, **открывающего** целевую страницу, либо `"end"` = «страниц дальше
нет, здесь кнопка „Отправить"». Порядок массива = приоритет: побеждает первое сработавшее
правило, не сработало ни одно — идём на следующую страницу, как сегодня.

**Эффективны только переходы ВПЕРЁД.** Цель раньше носителя (или её нет вовсе) — правило
инертно. Это не вкус: обход страниц становится строго монотонным, то есть **завершается по
построению**, циклов «страница 2 → страница 1 → страница 2» не существует, а линии шагов
остаются считаемыми. Переход назад («вернись и переспроси») в v1 не нужен ни одному
названному сценарию.

### 3.5 `schemaVersion` не поднимается (остаётся 4)

Все четыре поля необязательны и только расширяют множество принимаемых документов; старые
формы валидны как были, форма без правил ведёт себя точно как сегодня. Тот же довод, по
которому версию не поднимали `page_break` (фаза 19) и `ColumnLeft`
([`internal/domain/schema.go`](../../internal/domain/schema.go)). Апгрейдер не нужен.

### 3.6 Что проверяется схемой, а что нет

Граница ровно одна: **внутриблочное проверяем, кросс-блочное — нет** (§4.3).

**Проверяется** (нарушение → 422): форма узла (заполнена ровно одна из трёх веток), `op` из
списка, непустой `blockId` у листа, лимиты глубины/размера/длины значения, `jumpIf` только у
`page_break` и `visibleIf` у `page_break` **запрещён** (условный разрыв — это переходы, а не
исчезающая граница), `requiredIf` только у отвечаемого блока, `required` и `requiredIf`
взаимоисключающи. Всё это — свойства одного блока: промежуточных состояний драга и undo,
на которых они ломались бы, не существует.

**Не проверяется:** существование блока-источника, его позиция относительно носителя,
совместимость оператора с типом источника, достижимость цели перехода, и **то, что
`visibleIf` стоит на голове группы**. Последнее особенно важно: голова меняется драгом и
удалением подписи, поэтому правило на негодном носителе не отвергается, а **читается только
с головы** — на любом другом блоке оно инертно, как инертен бит ряда, которому некуда
примениться. Стор переносит правило вместе с носителем, как переносит бит.

## 4. Семантика: как считается видимость

### 4.1 Один проход в порядке документа

Вычислитель — чистая функция `planForm(schema, answers)` (в Go — `PlanForm`), возвращающая
**план формы**: посещаемые страницы в порядке прохода, видимые блоки, эффективно обязательные
блоки, видимые варианты у каждого choice-блока.

```
1. Разбить документ на страницы (splitPages — уже общий на три поверхности).
2. Идти по страницам, начиная с первой. Для текущей страницы, по блокам в порядке документа:
     - у головы группы посчитать visibleIf по ответам УЖЕ РЕШЁННЫХ блоков;
     - у видимого отвечаемого блока посчитать requiredIf;
     - у вариантов видимого choice-блока посчитать их visibleIf.
3. В конце страницы взять jumpIf её закрывающего разрыва: первое сработавшее правило с
   эффективной целью задаёт следующую страницу; иначе — следующая по порядку.
4. Ответ невидимого блока и выбор невидимого варианта считаются ПУСТЫМИ для всех
   последующих условий.
```

Один проход, никаких фикспойнтов и итераций до сходимости: обход монотонный (§3.4), а условие
смотрит только назад. Стоимость — O(блоки × узлы правил).

### 4.2 Три случая «источник не решён» — и они РАЗНЫЕ

Место, где легче всего ошибиться, поэтому вслух:

| Что со ссылкой | Как считаем | Почему так |
|---|---|---|
| Блока-источника (варианта) **нет в документе** | правило **инертно** → показываем | Сломанное правило скорее покажет лишнее, чем спрячет нужное. Автор удалил вопрос-источник — форма продолжает работать, а не теряет ветку молча |
| Источник **лежит позже** по проходу (следующая страница, ниже на этой) | правило **инертно** → показываем | Иначе порядок вычисления неопределён: результат зависел бы от того, с какого конца считать |
| Источник **раньше**, но скрыт / на пропущенной странице | ответ считается **пустым**, условие считается по пустому (обычно даёт «скрыть») | Ровно то, чего ждёт автор: «покажи Б, если А = Да» при непоказанном А означает «Б не показывать». Инертность здесь показала бы всю ветку целиком |
| Оператор **не подходит** типу источника | правило **инертно** → показываем | Автор сменил тип вопроса-источника; форма обязана продолжать работать |

### 4.3 Почему инертность, а не запрет в валидаторе

Фаза 16 `POST-MVP` обещает валидацию «ссылки только на предыдущие блоки». **Так делать
нельзя**: автор тащит вопрос-источник ниже зависимого — и автосейв ловит 422 посреди драга,
а `Ctrl+Z` через промежуточное состояние вообще перестаёт работать. Проект дважды на этом
обжигался и вывел правило: **кросс-блочные условия в схеме не валидируются** — инертный бит
ряда ([`formSchema.ts`](../../web/shared/entities/formSchema.ts), `packCells`), инертный
разрыв страницы (`splitPages`), обе цитаты прямым текстом в коде.

Поэтому запрет заменён семантикой: сломанная и «смотрящая вперёд» ссылка **инертна**, циклы
невозможны по построению обхода, а 422 при драге и undo не бывает вовсе. Кривое правило ловит
не валидатор, а **предупреждение в билдере** (§6.4) — там оно к месту: автор видит его сразу
и в контексте, а не в виде отказа сохранить документ.

### 4.4 Инвариант, который делает данные читаемыми потом

Сервер сохраняет **нормализованные** ответы (§5), то есть ответов на скрытое в базе нет.
Отсюда свойство, на которое опираются сводка и выгрузка:

> `plan(schema, normalize(answers)) == plan(schema, answers)`

Пересчёт видимости по сохранённому ответу даёт **тот же** результат, что был у респондента:
удалённые ответы считались пустыми и при первом счёте. Проверяется тестом-инвариантом, а не
на глазок.

## 5. Бэкенд — финальная инстанция

`ValidateAnswers` перестаёт быть единственной точкой: появляется нормализация.

```go
// внутри submissions.Submit, вместо голого ValidateAnswers
clean, err := domain.NormalizeAnswers(schema, answers) // план + отбрасывание + валидация
```

Что делает нормализация:

1. Считает `PlanForm` по присланным ответам.
2. **Отбрасывает** ответы на невидимые блоки и id невидимых вариантов из массивов
   `multi_choice`. Молча, а не 422: у респондента законно остаётся в стейте ответ, данный до
   того, как он переключил вопрос-источник, и наказывать его за это нечем. Ответ на блок,
   которого в схеме нет вообще, по-прежнему 422 («ответ на несуществующий вопрос»).
3. Требует обязательные **только среди видимых**, с учётом `requiredIf`.
4. Возвращает очищенную карту — **её и пишем в базу**.

Без пункта 2 автор увидел бы в CSV ответы на вопросы, которых человек не видел, — то есть
данные, которых не было. Клиентская видимость при этом не значит ничего: сервер считает
план сам (инвариант 3 проекта).

## 6. Три поверхности фронта

Вычислитель — один исходник, `web/shared/entities/logic.ts`, рядом с контрактом схемы
(чистый домен, DOM не нужен). Его импортируют рендерер, превью билдера и полотно.

### 6.1 Рендерер

- Скрытые вопросы не рисуются; проверка «Далее» смотрит только видимые блоки страницы.
- **Ответ скрытого вопроса остаётся в стейте** и не стирается: переключил «Нет» → «Да» —
  введённое вернулось. Из отправки его вычищает та же `planForm` (и сервер повторно).
- **«Назад» ходит по стеку посещённых страниц**, а не по индексу: с переходами «предыдущая»
  арифметикой не выражается. Стек — новое состояние рендерера, единственное, что фаза
  добавляет в его `useReducer`.
- **Линии шагов** считают путь, который получается **при текущих ответах**: пройденные +
  текущая + предсказанные до конца. Цена решения названа вслух: число линий может меняться
  по ходу заполнения. Альтернатива «показывать все страницы документа» врёт сильнее — обещает
  шаги, которых у этого человека не будет.
- Бюджет: 45 КиБ gzip, занято 34.54. Ожидаемая цена ядра — 2–3 КиБ; замер (`npm run
  check:bundle`) входит в критерий слайсов 2 и 5, а не в финализацию.

### 6.2 Превью билдера

Ведёт себя как рендерер — тем же `planForm`, как страницы уже режутся тем же `splitPages`.
Расхождение превью с публичной формой здесь дороже обычного: логику автор проверяет **только**
превью, вслепую собрать ветвление нельзя.

### 6.3 Полотно редактора

Полотно показывает форму **как автор её строит**, а не как видит респондент: скрытые вопросы
на полотне видны всегда. Иначе автор потерял бы доступ к тому, что сам же и спрятал.

### 6.4 Билдер: где задаётся

- **Секция «Логика» в попапе настроек блока** (`BlockActionMenu`, вход по грипу — фаза 16):
  «Показывать, если» + редактор дерева (условие, кнопка «добавить условие», кнопка
  «добавить группу», переключатель И/ИЛИ у группы), «Обязательный: нет / всегда / если …».
- **Попап варианта** (у него уже есть «удалить»/«дублировать») получает «Показывать, если».
- **Строка разрыва страницы** получает «Переходы»: список правил «если … → страница N».
  Номер страницы берётся из `pageNumbers` — того же, что рисует метку на разделителе.
- **Бейдж на строке** с логикой (иконка ветки) — как обещал шаг 4 фазы 16 `POST-MVP`.
- **Предупреждения вместо отказов:** «источник ниже — правило не действует», «оператор не
  подходит типу источника», «переход назад — не действует». Иконка на строке + текст в попапе.
- Выбор источника предлагает **вопросы выше по документу** (остальные — под предупреждением).
- Значение — контрол по типу источника (`select` вариантов, число, дата), а не свободный
  ввод: правило [`fields/README.md`](../../web/shared/fields/README.md) — строгий валидатор
  требует `select`, иначе автосейв ловит 422 на каждом нажатии.
- **Гранулярность undo:** правки логики кладутся одним видом правки «настройка» со склейкой
  (долг из [`block-settings.md`](block-settings.md) §4.6 — иначе один шаг мастера = десяток
  `Mod+Z`).

## 7. Зеркало Go ↔ TS

Ядро существует дважды — `internal/domain/logic.go` и `web/shared/entities/logic.ts` — и это
не недоделка, а конвенция проекта: так же живут `ValidateSchema`/Zod, `PlainText`/`plainText`,
`scaleRange`. Держится оно тремя вещами:

1. **Табличные тесты одинакового состава** с обеих сторон: один список кейсов
   («условие по скрытому источнику», «переход назад инертен», «глубина 5 отвергается»,
   «вариант скрыт — id вычищен из массива») — и он одинаков в Go и в vitest.
2. **Паритет-тест на состав операторов** по образцу
   [`blockkinds_parity_test.go`](../../internal/domain/blockkinds_parity_test.go): оператор,
   добавленный в один язык и забытый в другом, обязан валить сборку, а не тихо не срабатывать.
3. Правка любой из сторон — **тем же PR**, что вторая (правило `web/CLAUDE.md`).

## 8. Аналитика

- **Сводка: знаменатель = «показан»** (решение владельца). `asked` считается не «блок был в
  этой версии», а «блок был видим этому респонденту» — тем же `PlanForm` по сохранённым
  ответам (§4.4 гарантирует, что пересчёт даёт то же, что видел человек). Без этого вопрос
  редкой ветки читался бы как «заполнили 12 из 400», и владелец сделал бы неверный вывод
  про вопрос, который на самом деле работает.
- **Воронка занижает скрытые вопросы, и починить это нечем.** Визит не хранит ответов
  ([`ANALYTICS.md`](../ANALYTICS.md): два источника данных, и делить их нельзя), поэтому
  «дошёл до вопроса» по вопросу за условием посчитать не из чего. Записываем известным
  ограничением в `ANALYTICS.md` — а не чиним и не прячем.
- **CSV не различает «пропустил» и «не показывали»** — обе ячейки пусты. Ограничение v1;
  различение потребовало бы второго измерения в выгрузке.

## 10. Строки ADR §10, которые фаза вносит (предложение)

1. Носитель `visibleIf` — **головной блок группы**; видимость — свойство вопроса, не блока.
2. **Инертность вместо валидации** ссылок: тройное правило §4.2; **отменяет** обещание фазы 16
   `POST-MVP` «валидация запрещает ссылки вперёд, циклы запрещены по построению».
3. Вычислитель **дублируется** в Go и TS; **отменяет** «общий пакет на три потребителя» из
   той же фазы.
4. Переходы между страницами — **только вперёд**, назад и битые инертны (завершение обхода
   по построению).
5. Сервер **отбрасывает** ответы на скрытое и хранит нормализованные, а не отвечает 422.
6. Сводка: знаменатель — «показан», а не «был в версии».
7. `required` и `requiredIf` **взаимоисключающи** (одно поле, три состояния в UI).
8. `schemaVersion` **не поднимается** (остаётся 4).

## 11. Слайсы (порядок работ)

Каждый заканчивается зелёными `make lint && make test` и оставляет продукт целым — после
любого можно остановиться.

0. **ADR + спека.** Строки §10 в `ARCHITECTURE.md`, этот файл согласован.
1. **Ядро.** Дерево условий в Zod и Go (форма, лимиты, паритет), `planForm`/`PlanForm` с
   табличными тестами обеих сторон, инвариант §4.4. Ни UI, ни применения — только движок.
2. **Видимость вопросов.** Рендерер + превью, `NormalizeAnswers` на приёме, секция
   «Показывать, если» с вложенными группами, бейдж, предупреждения. Замер бюджета.
3. **Обязательность по условию.** `requiredIf` в схеме, в нормализации, в UI (радио).
4. **Скрытие вариантов.** `Option.visibleIf`, вычистка id из ответа, попап варианта.
5. **Переходы между страницами.** `jumpIf`, стек посещённых страниц, линии шагов по
   симуляции, обход на бэке. Замер бюджета.
6. **Сводка: знаменатель «показан».**
7. **Финализация.** Сценарий e2e `logic` (ветвление + пропуск страницы + скрытый вариант),
   `npm run perf` на полотне, документы: `EDITOR.md` (новый раздел про логику),
   `ANALYTICS.md` (ограничение воронки), `API.md`/`SCHEMA.md`, `STATUS.md`, скилл-справочник.

**Демо в конце фазы.** Форма «Есть ли у вас питомец?» → при «Да» появляется «Какой?», при
«Собака» в следующем списке нет варианта «лоток»; ветка «Нет» перескакивает страницу с
уточнениями и приходит сразу к отправке; поле «Телефон» обязательно только при выборе «Хочу
звонок»; попытка прислать curl'ом ответ на скрытый вопрос — ответ принят, скрытого значения
в таблице и CSV нет; сводка показывает «заполнили 12 из 34, кому вопрос показали».
