DEV-PLAN**. Платежи (ЮKassa, вебхуки, рекурренты, чеки 54-ФЗ) — отдельная будущая фаза;

Решения, принятые в `POST-MVP.md` до этой спеки и здесь **подтверждаемые, а не
переоткрываемые**: субъект подписки — воркспейс; личный воркспейс — платёжный якорь аккаунта;
лимиты данными, а не константами; единая точка проверки; аналитика собирается всем, гейтится
чтение; `legacy_free` для уже существующих пользователей; просроченная подписка не закрывает
форму.

## 1. Философия (критерий всей фазы)

**Гейт — это данные, а не код.** Проектное требование фазы — не «запереть три вещи», а
**сделать четвёртую дешёвой**: одна строка в каталоге возможностей, одна в лимитах плана, один
вызов в сервис-методе. Всё, что делает добавление гейта дороже трёх строк, — ошибка
конструкции, а не мелочь. Симметрично: **снятие** гейта («открыли воронку всем», «Free стал
250 ответов вместо 100») обязано быть изменением **данных без выкатки кода**.

**Гейт стоит на созданной ценности, а не на настройке.** За право завести пустую папку не
платят — платят, упёршись в стену на работающей вещи.

**Ни один ответ респондента не теряется и не отвергается ни при каком состоянии подписки.**
Респондент вообще не знает, что у владельца формы есть тариф. Деградация живёт **только**
в кабинете владельца.

**Сквозной критерий фазы (наблюдаемый, проверяется руками).** Воркспейс на плане с лимитом
**5** ответов/месяц (боевой Free — 100, §11.1; пятёрка взята, чтобы демо не требовало сотни
`curl`, и ставится тем же `UPDATE`, которым меняется любой лимит, — то есть демо заодно
проверяет главное обещание фазы):

1. шестой ответ через публичную форму принимается — `curl` отдаёт 200, `SELECT count(*)` даёт 6;
2. в кабинете видно 5 ответов и плашку «1 ответ скрыт — лимит тарифа исчерпан»;
3. `GET /forms/{id}/funnel` отдаёт 402 `plan_required`, в кабинете вместо воронки — заглушка
   с **настоящим** числом («51 человек не дошёл до конца»);
4. `UPDATE subscriptions SET plan_code = 'pro'` → **без перелогина и без деплоя**: таблица
   показывает 6 ответов, воронка открывается, плашка исчезает.

## 2. Что фаза НЕ делает (осознанно)

- **Не принимает деньги.** Ни платёжного провайдера, ни `payments`, ни вебхуков, ни чеков,
  ни автосписаний. Смена плана в этой фазе — `UPDATE` в БД рукой владельца. Кнопка «Перейти
  на Pro» ведёт на страницу-заглушку «скоро».
- **Не вводит статус `past_due` и рекурренты.** Их нечему выставлять: статусов в этой фазе
  два — `active` и `canceled`. Триал — тоже не здесь (`trialing` появится с платежами: триал
  без последующей оплаты не имеет смысла).
- **Не строит гейт на число воркспейсов** — см. §11, решение владельца: сегодня в продукте
  **нет действия «создать воркспейс»** (`GET /workspaces` есть, `POST` нет), то есть запирать
  нечего, и демо-критерий у такого гейта невозможен.
- **Не строит экран источников трафика.** `utm_*` собираются с фазы 8.5 и лежат в мете визита,
  но экрана нет. Гейт ставится на воронку (она есть); ключ `analytics_sources` заводится
  данными и включится вместе с экраном.
- **Не трогает `TD-16`** (осиротевшие медиа) и не вводит квоту на хранилище: учёта байт на
  воркспейс нет, счёт за чужой мусор выставлять нельзя.

## 3. Модель данных

```sql
-- Каталог тарифов. Лимиты — JSONB, а не колонки: добавление возможности не должно
-- требовать миграции (см. §4). Цена лежит здесь с самого начала, хотя в этой фазе
-- ни на что не влияет: колонка, добавленная вместе с платежами, потребовала бы
-- миграции ровно тогда, когда трогать биллинг страшнее всего.
CREATE TABLE plans (
    code        TEXT PRIMARY KEY,          -- free | pro | legacy_free
    title       TEXT NOT NULL,             -- то, что видит человек: «Бесплатный», «Pro»
    price_kopeks INTEGER NOT NULL DEFAULT 0,
    limits      JSONB NOT NULL,            -- {"submissions_per_month": 100, "analytics_funnel": false}
    is_public   BOOLEAN NOT NULL DEFAULT true,  -- legacy_free не показывается в списке тарифов
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Подписка воркспейса. Ровно одна на воркспейс (PK по workspace_id): «история
-- подписок» — это журнал платежей будущей фазы, а не набор строк здесь.
CREATE TABLE subscriptions (
    workspace_id   UUID PRIMARY KEY REFERENCES workspaces(id) ON DELETE CASCADE,
    plan_code      TEXT NOT NULL REFERENCES plans(code),
    status         TEXT NOT NULL DEFAULT 'active',  -- active | canceled (past_due — с платежами)
    current_period_end TIMESTAMPTZ,                 -- NULL у бесплатных планов
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Расход за период. Отдельной таблицей, потому что COUNT(*) по растущим
-- submissions стоит на ГОРЯЧЕМ пути приёма ответа: незаметно на десяти формах,
-- ложится на тысяче.
CREATE TABLE workspace_usage (
    workspace_id UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    period       DATE NOT NULL,            -- первое число месяца по Europe/Moscow
    submissions  BIGINT NOT NULL DEFAULT 0,
    PRIMARY KEY (workspace_id, period)
);

-- Ответ, пришедший сверх квоты тарифа. Пометка на строке, а не вычисление
-- «хвоста» на чтении: см. §6.
ALTER TABLE submissions ADD COLUMN over_quota BOOLEAN NOT NULL DEFAULT false;
```

**Заполнение при миграции.** Все существующие воркспейсы получают строку `subscriptions`
с планом **`legacy_free`** (§8). Регистрация нового пользователя заводит `subscriptions`
со `free` **в той же транзакции**, что и `user + workspace + membership` — инвариант
транзакции регистрации из `internal/CLAUDE.md` расширяется четвёртой строкой, а не
обрастает вторым местом, где «иногда подписки нет». Воркспейс без подписки — это ветка
«а если NULL» в каждой проверке; её не будет.

**Рассматривал** нормализованные колонки лимитов (`plans.max_submissions INTEGER`,
`plans.has_funnel BOOLEAN`) — **выбрал JSONB**, потому что в колонках каждая новая
возможность стоит миграции, а вся цель фазы — чтобы она стоила строки данных. Цена
решения названа вслух: БД не проверяет содержимое `limits`; сторожем работает Go-каталог
(§4) и тест, проходящий по всем ключам каталога во всех строках `plans`.

## 4. Каталог возможностей: ключи — в коде, значения — в данных

Это ядро ответа на «как легко добавлять и убирать». Три уровня, которые обычно слипаются
в один `if`, разведены:

| Что | Где живёт | Кто меняет | Цена изменения |
|---|---|---|---|
| **Какие гейты бывают** | `internal/entitlements/catalog.go` | разработчик | строка + деплой |
| **Что даёт каждый план** | `plans.limits` (JSONB в БД) | владелец | `UPDATE`, **без деплоя** |
| **Где гейт применяется** | вызов в сервис-методе | разработчик | строка + деплой |

```go
// internal/entitlements/catalog.go — единственное место, где заводится гейт.
type Key string

const (
    SubmissionsPerMonth Key = "submissions_per_month" // квота: число за период
    Workspaces          Key = "workspaces"            // квота: число всего
    AnalyticsFunnel     Key = "analytics_funnel"      // возможность: да/нет
    AnalyticsSources    Key = "analytics_sources"     // возможность: да/нет
)

// Catalog — исчерпывающее описание. Kind разделяет «число» и «да/нет»: от него
// зависит разбор значения из plans.limits и форма ответа кабинету.
var Catalog = map[Key]Feature{
    SubmissionsPerMonth: {Kind: Quota, Scope: Workspace, Title: "Ответов в месяц"},
    AnalyticsFunnel:     {Kind: Toggle, Scope: Workspace, Title: "Воронка отвала"},
    ...
}
```

**Значение `null` в `limits` = безлимит.** Отсутствие ключа в `limits` — **не** «безлимит»
и **не** «запрещено», а ошибка конфигурации: тест `TestPlansCoverCatalog` проходит по всем
планам и всем ключам каталога и краснеет, если план молчит про возможность. Молчание не
должно означать ничего — именно из «забыли ключ → случайно раздали Pro бесплатно» и берутся
дорогие сюрпризы.

**Рецепт «добавить возможность в платный тариф» (три строки):**

1. `catalog.go` — константа + строка в `Catalog`;
2. миграция на 2–3 строки: `UPDATE plans SET limits = limits || '{"новый_ключ": …}'` для
   каждого плана;
3. вызов `CheckWorkspace(ctx, wsID, entitlements.НовыйКлюч)` в сервис-методе фичи.

**Рецепт «убрать возможность из платного тарифа» (одна строка, без деплоя):**
`UPDATE plans SET limits = jsonb_set(limits, '{analytics_funnel}', 'true') WHERE code = 'free';`
Код при этом не меняется вовсе: вызов `Check…` остаётся на месте и с этого момента всегда
разрешает. Мёртвый вызов не удаляется — он и есть выключатель обратно.

## 5. Единая точка проверки

```go
// Decision — почему не просто error: у двух потребителей разные потребности.
// Чтению (воронка) нужен отказ, приёму ответа отказывать НЕЛЬЗЯ — ему нужен факт
// «сверх квоты», чтобы пометить строку и пропустить ответ дальше (§6).
type Decision struct {
    Allowed bool
    Used    int64
    Limit   *int64 // nil — безлимит
}

func (s *Service) CheckWorkspace(ctx context.Context, workspaceID uuid.UUID, key Key) (Decision, error)
func (s *Service) Snapshot(ctx context.Context, workspaceID uuid.UUID) (Snapshot, error) // для кабинета
```

`CheckAccount` (второй скоуп для аккаунт-уровневых лимитов, `POST-MVP.md` шаг 3) **в этой
фазе не пишется**: его единственный потребитель — лимит на число воркспейсов, а действия
«создать воркспейс» в продукте нет (§11). Функция без вызывающего — ровно та
«расширяемость, которой не требует текущая фаза», что запрещает `PROCESS.md` §2. Решение
из `POST-MVP.md` про два скоупа остаётся в силе и исполняется тогда, когда появится, что
проверять.

**Точки вызова этой фазы — все три, поимённо:**

| Гейт | Файл | Поведение при отказе |
|---|---|---|
| Квота ответов | `internal/submissions/service.go`, `Submit` | ответ **принимается**, строка помечается `over_quota` |
| Воронка | `internal/visits/service.go`, `Funnel` | `domain.ErrPlanRequired` → **402** `plan_required` |
| Снимок для кабинета | `internal/entitlements/handler.go` | — |

**`if plan == "free"` вне пакета `entitlements` запрещён** — правило уровня «маппинг ошибок
на HTTP живёт только в `respond.go`» (`internal/CLAUDE.md`). Причина не в красоте: рассыпанные
проверки означают, что через полгода на вопрос «что входит в Pro» никто не сможет ответить
иначе как грепом, а страница тарифов начнёт врать. Правило вносится в `internal/CLAUDE.md`
вместе с кодом фазы.

**Цена на горячем пути названа вслух:** приём каждого ответа получает +1 индексированный
SELECT (join `subscriptions` × `plans` по воркспейсу). Это осознанно и не кэшируется в v1:
кэш плана — это инвалидация при смене плана, то есть ровно тот баг «оплатил, а лимит не
расширился», который бьёт по деньгам. Мерять и кэшировать — если замер покажет.

## 6. Мягкая деградация: что происходит при исчерпании квоты

**Респондент не видит ничего.** Ответ принимается, «Спасибо» показывается, данные в БД.

**Владелец видит плашку** в таблице ответов: «3 ответа скрыты — исчерпан лимит тарифа
(100/мес). Они сохранены и откроются сразу после перехода на Pro». Формулировка важна
буквально: человек должен понимать, что данные **целы**, иначе он уйдёт, решив, что сервис
их выбросил.

**Механика — пометка строки, а не вычисление хвоста на чтении.** При приёме ответа читается
`Decision`; если квота уже исчерпана, строка вставляется с `over_quota = true`. Кабинет
(список, экспорт CSV, сводка, воронка) фильтрует `WHERE NOT over_quota`. Апгрейд плана —
одна транзакция: `UPDATE submissions SET over_quota = false` по воркспейсу.

**Рассматривал** вычисление «сверхлимитного хвоста» на чтении (самые новые `used - limit`
строк периода) — **выбрал колонку**, потому что хвост на чтении не дружит с курсорной
пагинацией (`ARCHITECTURE.md` §10), просачивается в три независимых запроса (список,
экспорт, сводка) и каждый раз считается заново, а колонка — одно условие в `WHERE` и один
`UPDATE` при апгрейде.

**Экспорт CSV скрывает сверхлимитные так же, как таблица** (решение владельца, §11.3). Иначе
гейт обходится в один клик и не гейт вовсе.

**Инкремент счётчика — тем же запросом, что вставка ответа** (CTE `WITH ins AS (INSERT …
RETURNING 1) INSERT INTO workspace_usage … ON CONFLICT DO UPDATE SET submissions =
workspace_usage.submissions + 1`). Одно утверждение атомарно само по себе, поэтому быстрый
путь приёма (без транзакции, когда у формы нет своего капа) остаётся быстрым, а счётчик не
разъезжается с фактом при падении между двумя запросами. Идемпотентный ретрай (`ON CONFLICT
DO NOTHING` по PK ответа) не даёт строк из `ins` — счётчик не растёт, что и требуется.

**Мягкий лимит не сериализуется.** В отличие от жёсткого капа формы (advisory-lock,
`ARCHITECTURE.md` §10), квота тарифа на границе допускает ±1 ответ при одновременных
запросах: решение `over_quota` принимается по счётчику, прочитанному до вставки. Это
осознанно — цена сериализации всего приёма ответов ради точности «101-го против 100-го»
не окупается ничем.

**Квота тарифа и кап формы — разные вещи, и в коде их путать нельзя.** Кап (`ResponseLimit`,
фаза 8.5) настраивает владелец, он **закрывает форму** для респондента — это его прямой
смысл. Квота тарифа не закрывает ничего. Сторож — тест «форма на исчерпанной квоте
продолжает принимать ответы и отдаёт 200».

## 7. Аналитика: собираем всем, гейтим чтение

Визиты пишутся для всех планов без исключения. Проверка стоит на `Funnel` — на **показе**.

Причина продуктовая: если не собирать бесплатным, то в момент апселла показать нечего, и
плашка «откройте Pro» рекламирует пустоту. Собирая всем, та же плашка показывает настоящее
число владельца — «51 человек не дошёл до конца; откройте Pro, чтобы увидеть, на каком
вопросе». Цена — строка на визит для тех, кто никогда не заплатит; это выдерживается.

Практическое следствие для кабинета: экран воронки при отказе рисует **не** пустоту с
замком, а реальную сводную цифру (её отдаёт тот же 402-ответ в теле) и предложение
открыть разбивку.

## 8. Грандфазеринг и порядок включения на проде

**`legacy_free` — план для тех, кто пришёл до тарифов.** Свои лимиты, в списке тарифов не
показывается (`is_public = false`), на новый Free не мигрирует никогда. Строка в `plans`
стоит копейки сейчас и стоит доверия задним числом: ввести её после того, как люди упрутся
в стену, уже нельзя.

**Порядок выкатки — гейты приезжают выключенными.** `legacy_free.limits` в миграции
получает **безлимит по всем ключам** (`null` / `true`). То есть код с гейтами уезжает на
прод, ничего никому не запирая; включение — `UPDATE` тогда, когда владелец решит, и по
одному ключу за раз. Это же и аварийный тумблер: если гейт повёл себя не так, его снимают
изменением данных за секунды, а не откатом релиза.

**Что получают новые пользователи после включения** — план `free` с реальными лимитами;
цифры — решение владельца (§11).

## 9. Кабинет: страница «Тариф»

Новый эндпоинт: `GET /api/v1/workspaces/{id}/entitlements` → текущий план, его лимиты,
расход за период, дата сброса. Одна поездка, из которой кабинет рисует всё: прогресс-бар
ответов, замки, плашки.

**Фронт прячет ради UX, бэк отказывает ради правды.** Спрятанная кнопка обходится
в DevTools за десять секунд; проверка на бэке — то, что делает гейт гейтом (инвариант
безопасности 3 проекта: весь ввод валидируется на бэке независимо от фронта). Ни один
гейт этой фазы не существует только на фронте.

Страница `/settings/plan` в кабинете: текущий план, «Ответов в этом месяце: 87 из 100»,
список того, что входит в Pro, кнопка «Перейти на Pro» → заглушка «скоро» (денег нет, §2).

## 10. Риски и как их ловим

| Риск | Чем ловим |
|---|---|
| План забыли в `plans.limits` → случайно раздали Pro | `TestPlansCoverCatalog`: все ключи каталога × все планы |
| Квота закрыла форму респонденту | тест «исчерпанная квота → приём 200, ответ в БД» |

| Скрытые ответы приняты за потерянные | формулировка плашки; апгрейд возвращает всё одной транзакцией — тест |
| Гейт просочился мимо `entitlements` | правило в `internal/CLAUDE.md` + греп-проверка в `check-docs` на `plan ==` вне пакета |
| Чужой воркспейс в `Check…` | анти-IDOR-тест, как у всякого service-метода (`PROCESS.md` §3) |

## 11. Решения владельца — приняты 2026-08-01

Пять развилок, которые нельзя вывести из кода. Все закрыты; открытых решений в спеке
не осталось.

1. **Лимит Free — 100 ответов в календарный месяц.** Совпадает с рыночным ориентиром
   (Tally — 100/мес, Typeform — 10). Живые данные прода до фиксации не смотрели: цифра
   меняется одним `UPDATE` без выкатки (§4), поэтому её стоимость как решения близка к нулю.
2. **Период квоты — календарный месяц по Europe/Moscow.** «Лимит обнуляется 1-го числа» —
   объяснимо пользователю одной фразой. Отвергнуты скользящие 30 дней: честнее в учёте,
   но человек не может предсказать, когда ему «вернут» ответы. Следствие для будущей фазы
   платежей: оплата с 15-го числа даёт полный лимит на текущий календарный месяц — это
   щедро и осознанно, привязывать период квоты к периоду подписки не будем.
3. **Экспорт CSV скрывает сверхлимитные ответы** — так же, как таблица и сводка. Иначе гейт
   обходится в один клик и гейтом не является. Отвергнут мягкий вариант «в CSV видно всё».
4. **Гейт «число воркспейсов» — ключ заводится данными, проверка не пишется.**
   `CheckAccount` появится в фазе, где появится действие «создать воркспейс»; **само создание
   воркспейса откладывается** (решение владельца) и в эту фазу не входит. Отвергнут вариант
   «внести создание воркспейса сюда» — расширение скоупа отдельной продуктовой фичей вопреки
   `PROCESS.md` §2.
5. **В списке Pro на странице тарифа — только то, что работает сегодня.** Обещания будущих
   фаз в прайс не идут: невыполненное обещание в прайсе дороже пустого места.

## 12. Шаги фазы

1. **Миграция и сид.** `plans`, `subscriptions`, `workspace_usage`, `submissions.over_quota`;
   три плана; все существующие воркспейсы → `legacy_free` с безлимитом; регистрация заводит
   `subscriptions` в транзакции регистрации. Обновить `SCHEMA.md`.

3. **Квота ответов.** `WorkspaceID` в `PublicForm`, CTE-инкремент, пометка `over_quota`.
   Интеграционные тесты: приём сверх квоты даёт 200 и `over_quota = true`; ретрай не растит
   счётчик; форма не закрывается.
4. **Скрытие сверхлимитных в кабинете** (список, CSV, сводка) и снятие пометки при апгрейде.
5. **Гейт воронки** (402 + число в теле) и заглушка на экране воронки в кабинете.
6. **Страница «Тариф»** + эндпоинт `GET /workspaces/{id}/entitlements`; обновить `API.md`.
7. **Документы:** `ARCHITECTURE.md` §3.3 (схема) и §10 (ADR-строки), `internal/CLAUDE.md`

## 13. ADR-строки, которые фаза вносит в `ARCHITECTURE.md` §10

| Решение | Альтернатива | Почему так |
|---|---|---|
| Субъект подписки — воркспейс; личный воркспейс — платёжный якорь аккаунта | Подписка на пользователя | Монетизация (объём, места) — свойство воркспейса; перевод денег на другую сущность задним числом — самая дорогая миграция |
| Ключи гейтов в коде, значения — в `plans.limits` (JSONB) | Всё в коде / всё в БД | Компилятор ловит опечатку в ключе; политика меняется без выкатки |
| Единая точка `entitlements`, `if plan ==` вне пакета запрещён | Проверки по месту | Иначе «что входит в Pro» отвечается только грепом, а прайс начинает врать |
| Квота тарифа — мягкая: ответ принимается, строка помечается `over_quota` | Отказ приёма сверх квоты | Отказ теряет данные клиента за неоплату владельцем; жёсткий кап формы — отдельная семантика |
| Расход считается в `workspace_usage`, инкремент тем же CTE | `COUNT(*)` по `submissions` | `COUNT` растёт на горячем пути приёма ответа |
| Аналитика собирается всем, гейтится чтение | Не собирать бесплатным | Иначе в момент апселла показывать нечего |
| `legacy_free` заводится до первого тарифа | Мигрировать старых на новый Free | Обещанную бесплатность нельзя отнять задним числом |
