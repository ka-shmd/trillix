# Конвейер: от коммита до прода (CI/CD)

Практический справочник: что проверяется автоматически, когда это происходит, как
воспроизвести проверку локально и что делать, когда красное. **Живой документ** —
пополняется при любых работах по конвейеру (новый шаг, новая проверка, новый секрет).

**Это производный справочник, а не источник истины.** При конфликте побеждают
`docs/ARCHITECTURE.md` (§«три контура», ADR §10) и `docs/DEV-PLAN.md` (фазы 7 и 9).
Здесь — «как оно работает и как расширять».

**Почему один документ, а не отдельные «CI» и «CD».** Разделение уже есть, но по
более полезной оси: **конвейер против сервера**. Этот файл — про конвейер (что бежит,
что доказывает, как чинить). Операции на самом сервере — провижининг, секреты, первый
деплой, откат, ловушки конфига Caddy — в **[`deploy/README.md`](../deploy/README.md)**.
Резать по границе «CI/CD» значило бы разорвать один континуум (PR → merge → тег →
прод) и дважды описывать один и тот же контур prod-local.

Смежные документы: `deploy/README.md` (runbook сервера), `docs/TECH-DEBT.md`
(TD-27..TD-29 — дефекты конвейера и чем они закрыты), `web/CLAUDE.md` (раздел
«Прод-контур: что dev не показывает»), `internal/CLAUDE.md` (почему `GO_PKGS`,
а не `./...`).

---

## 1. Карта: что где лежит

| Файл | Роль |
|---|---|
| `.github/workflows/ci.yml` | Лёгкие `check-docs` и `check-comments` на **каждый** PR и push в `main` (секунды) |
| `.github/workflows/ci-code.yml` | Тяжёлые проверки (Go + оба фронта) — **только когда менялся код** (path-фильтр) |
| `.github/workflows/e2e.yml` | Сквозные сценарии против prod-local (ночью и по кнопке) |
| `.github/workflows/release.yml` | Релиз по тегу: образ → GHCR, статика → Release, деплой на прод |
| `deploy/remote-update.sh` | То, что выполняется **на сервере**: обновление до тега + самопроверки |
| `scripts/prod-local-smoke.sh` | Тонкий смоук prod-local (запускается из `make prod-local`) |
| `scripts/deploy-no-502.sh` | Проба «выкатка не видна пользователю» (шаг ночного e2e) |
| `Makefile` | Единая точка входа: те же команды локально и в CI |

## 2. Что запускается когда

| Событие | Что бежит | Что доказывает | Примерно |
|---|---|---|---|
| Любой PR / push в `main` | `ci.yml`: `check-docs` + `check-comments` | Документы сходятся с кодом (дерево модулей, миграции, env, ссылки на техдолг, единая точка лимитов тарифа, токены и шкала кеглей `fields.css`); в комментариях нет рассказов о прошлом без ссылки на журнал | секунды |
| Изменение **тронуло код** | `ci-code.yml`: `go` + `web` (матрица app/renderer) | Код собирается, линт чист, юниты и интеграционные зелёные, бандл рендерера в бюджете | ~3 мин |
| Ночью 03:00 UTC, и по кнопке | `e2e.yml` | Продукт работает **в прод-сборке** целиком: три сценария + выкатка без 502 | ~4 мин |
| Пуш тега `v*` | `release.yml`: `image` + `static` → `deploy` | Собран релизный комплект и **выкачен на прод** | ~2,5 мин |

Ключевое: **тяжёлые проверки не запускаются на изменениях, тронувших только
документацию/прозу.** `ci-code.yml` несёт `paths-ignore: [docs/**, **/*.md]`, выстроенный
fail-closed: прогон пропускается, только если в изменении нет ни одного файла вне списка;
любая правка кода (в т.ч. вместе с доками) гонит `go` + `web` как раньше. Поэтому правка
`BACKLOG.md`, `TECH-DEBT.md` или любого `docs/*` проходит за секунды на одном `check-docs` —
и её можно коммитить прямо в `main` без ветки и PR (`PROCESS.md` §5).

**e2e — не на каждый PR** — стек тяжёлый (Docker + браузер), а обратная связь
нужна быстрая. Это осознанный размен: функциональный гейт ночной, а не поштучный.

## 3. Проверки на PR (`ci.yml` + `ci-code.yml`)

**`ci.yml` (job `docs`):** два шага — `check-docs.sh` и `check-comments.sh` (регистр
комментариев: история в коде без ссылки на `JOURNAL.md` + отчёт о доле токенов). Оба
гоняются на любое изменение, включая docs-only: греп по репозиторию стоит секунды и
тулчейнов не требует. Тяжёлое ниже — в отдельном `ci-code.yml` под path-фильтром (см. §2).

**Job `go`** (`ci-code.yml`)**:** `golangci-lint` → **`sqlc drift check`** (сгенерированный код не разошёлся
с `.sql`-запросами) → `go test` (юниты + интеграционные под тегом `integration`,
Postgres поднимается testcontainers'ом).

**Job `web`** (матрица `app` / `renderer`): `tsc --noEmit`, `eslint`, `vitest`, сборка.
У рендерера дополнительно: **бюджет бандла 60 КиБ gzip** (`scripts/check-bundle.mjs`)
и **Lighthouse mobile Performance ≥ 90**.

`npm run build` рендерера делает **два прохода**: обычную сборку формы и загрузчик
встроенной формы (`vite.embed.config.ts` → `dist/embed/v1.js`, IIFE, имя без хеша).
У загрузчика **свой бюджет — 5 КиБ gzip**, он считается отдельно от формы: это разные
файлы для разных страниц, и ни один посетитель не скачивает оба веса разом. Отдельные
шаги в CI и деплое не нужны — оба прохода живут внутри `npm run build`, поэтому
`build-static.sh` и релизный тарболл забирают загрузчик сами.

Локально то же самое:

```bash
make lint          # golangci-lint + eslint + tsc
make test          # go test -race + vitest (интеграционные — через testcontainers)
make test-unit     # только герметичные, без Docker — быстрый цикл
```

**Go-инструменты идут по списку пакетов, а не по `./...`** — иначе они заползают в
`web/**/node_modules`, где npm-пакеты приносят посторонние `.go`-файлы и ломают прогон.
Переменная `GO_PKGS` в `Makefile`, те же пути в CI. Новый top-level Go-каталог → добавить
в оба места (`internal/CLAUDE.md`).

## 4. Ночной e2e (`e2e.yml`)

Поднимает **настоящий прод-контур** (`make prod-local`: distroless-образ, Caddy, https
на `*.localhost`) и гоняет по нему Playwright. Ловит класс «прод-сборка ≠ dev», который
не виден ни в юнитах, ни в dev-режиме.

Сценарии (`e2e/`): `full-loop` (регистрация → билдер → публикация → ответ с мобильного
→ таблица → CSV), `builder-keyboard` (сборка формы одной клавиатурой), `form-settings`
(свой текст благодарности, лимит мест, «приём закрыт»), `visits-funnel` (бикон визита
под прод-CSP, конверсия, воронка, `410` на закрытой), `workspace-team` (приглашение,
роли, отзыв доступа), `multipage` (страницы формы, пошаговая валидация, воронка по
переходу) и `embed` (форма на постороннем origin, отправка из фрейма, заголовки
фрейминга).
Плюс шаг **«выкатка без 502»** (см. §5.4).

Локально:

```bash
make prod-local            # поднять контур (внутри — smoke)
cd e2e && npm test         # три сценария
```

**Две ловушки, о которых надо знать заранее.**

*Через билдер кликами ходит только `full-loop`* — остальные строят форму запросами к API.
Иначе правка редактора красит тесты, которые про редактор ничего не проверяют.

*Регистрация под rate-limit, и запас исчерпывается сюитой.* Каждый сценарий заводит свой
аккаунт, а `registerBurst = 3` при пополнении ~1/30 с. Холодный прогон проходит, **повторный
в течение ~1,5 минут падает на шаге регистрации** и выглядит как сломавшийся тест. Лимит
ради тестов не ослабляется (инвариант 6) — надо просто подождать. Реальный случай: во время
разбора фазы 9 этот симптом трижды принимался за регресс.

## 5. Релиз и деплой (`release.yml`)

### 5.1 Путь тега

```
git tag v0.9.6 && git push origin v0.9.6
        │
        ├── job image  → сборка Dockerfile          → ghcr.io/ka-shmd/trillix-api:v0.9.6
        │                 сборка Dockerfile.printer  → ghcr.io/ka-shmd/trillix-printer:v0.9.6
        ├── job static → vite build обоих фронтов → tar.gz в GitHub Release
        │
        └── job deploy (needs: image, static)
              ssh deploy@<host> "TAG=v0.9.6 bash -s" < deploy/remote-update.sh
```

**Слои кешируются между релизами** (`cache-from`/`cache-to: type=gha`, у каждого образа своя область). Без кеша каждая сборка идёт с нуля, слой `apt install` пересоздаётся с новыми метаданными, digest получается другой — и прод тянет его целиком на каждый тег: у образа печати это ~800 МБ. С кешем неизменившийся слой переиспользуется, и выкатка везёт только бинарь.

**Образов ДВА, тег у них один.** Второй — сервис печати PDF (headless-Chromium, ADR §10):
в distroless-образ api браузер не кладётся, поэтому у него свой `deploy/Dockerfile.printer`
и своя строка в том же job. Тег общий не для красоты — `compose.prod.yml` подставляет один
`${TAG}` обоим сервисам, и разъехаться версиям нечем. Печать на контуре включает переменная
`PRINTER_URL` в серверном `.env`: без неё api поднимается, а кнопка «Скачать PDF» отвечает
503 «печать не настроена».

### 5.2 Почему сервер тянет готовое сам

CI **не копирует артефакты на сервер** — он только запускает обновление. Сервер своими
кредами (PAT в `gh` + `docker login`) забирает образ из GHCR и статику из Release. Так
секреты доступа живут в одном месте (на сервере), а не размазаны по шагам workflow, и
ручной деплой ничем не отличается от автоматического — тот же скрипт.

Что делает `remote-update.sh`: `git checkout <тег>` → скачать статику релиза → обновить
`TAG` в `.env` → `docker compose pull && up -d --remove-orphans` → **`caddy reload`** →
**самопроверки конфига** → prune.

### 5.3 Деплой проверяет сам себя

Код возврата `caddy reload` доказывает «конфиг валиден», но **не** «конфиг тот самый»
(на этом обжёгся TD-27). Поэтому две сверки, любая валит выкатку:

- **A (обязательная):** `sha256` Caddyfile в репозитории == в контейнере. Ловит устаревший
  bind-mount, не тот путь, недокопированный файл.
- **B (если на сервере есть `python3`):** конфиг, порождаемый файлом (`caddy adapt`), ==
  конфиг живого процесса (админ-API `127.0.0.1:2019`). Ловит «reload вернул успех, но не
  применился». Питон нужен для нормализации JSON: порядок ключей у `adapt` и админ-API
  разный, а `jq` внутри контейнера нет. Без питона сверка **честно печатает, что пропущена**.

Проверено мутацией: правка конфига без reload → **A проходит, B краснеет**. По отдельности
каждая пропустила бы свой сценарий.

### 5.4 Выкатка не должна быть видна пользователю

`docker compose up -d` пересоздаёт контейнер `api`, и между остановкой старого и
готовностью нового отвечать некому. Graceful shutdown в Go щель **не закрывает** — он
докручивает уже принятые запросы. Лечится удержанием на стороне Caddy: сниппет
`(apiproxy)` даёт `lb_try_duration 5s` / `lb_try_interval 250ms`.

Замерено: щель — **2,07 с**; после починки **0 ошибок из 196** на проде. Значение `5s`
взято из замера (2,4× щели), а не «с запасом»: этот параметр равен времени ожидания
пользователя при **настоящей** аварии.

Сторожит регресс шаг ночного e2e: проба долбит путь Caddy→Go→Postgres, посреди
пересоздаётся `api`, любой 5xx валит job. Мутация: убрать `lb_try_duration` → 7×502 → job
падает.

### 5.4а Смена версии схемы формы — единственная выкатка с окном рассинхрона

Щель 5.4 — про то, что API на секунды недоступен. Есть и вторая, другой природы, и
касается она **только релизов, меняющих `schemaVersion`** (v1→v2 в фазе 8.7, v2→v3 в
фазе 14). Обе стороны знают ровно один формат — текущий: `formSchemaSchema` объявляет
`schemaVersion: z.literal(SCHEMA_VERSION)`, и документ прошлой версии Zod отвергает.
Сервер от этого защищён апгрейдом на чтении (`ValidateSchema`, `CanonicalV3`), а вот
клиент — нет, и на минуту-другую после выкатки возможны две встречи:

- **новый бандл ↔ старый ответ из кэша браузера.** `GET /public/v1/forms/{slug}` отдаётся
  с `Cache-Control: public, max-age=60`, поэтому свежий рендерер может получить схему
  прошлой версии из кэша и не отрисовать форму;
- **старый бандл ↔ новый ответ.** Вкладка кабинета, открытая до выкатки, получит
  черновик уже новой версии и упадёт на разборе.

Оба лечатся перезагрузкой и живут не дольше `max-age`. Специально ничего не делаем —
цена (версионирование ответа, «мягкий» разбор с двумя схемами или сброс кэша при
релизе) выше ущерба, а случай — раз в несколько фаз. **Что делать при таком релизе:**
знать про окно и не пугаться единичной жалобы «форма не открылась» в первые минуты
после тега; если жалоба пришла позже — это уже не оно, ищите настоящую причину.

### 5.5 Два деплоя одновременно невозможны

Workflow-level `concurrency` ключуется на `github.ref`, поэтому разные теги попадали бы
в разные группы и могли деплоить параллельно. Защита в двух местах:

- job-level `concurrency: deploy-prod` — фиксированная группа, не зависящая от тега
  (сборкам параллелиться можно, они независимы; деплою нет);
- **`flock`** в `remote-update.sh` — CI не защищает от ручного запуска скрипта параллельно
  с автодеплоем. Ждём до 10 минут, а не падаем сразу: второй релиз должен выкатиться
  следом, а не потеряться.

| Имя | Тип | Зачем |
|---|---|---|
| `DEPLOY_SSH_KEY` | secret | Приватный ключ CI → сервер (отдельный, не личный) |
| `DEPLOY_HOST` / `DEPLOY_USER` | variable | Адрес и пользователь деплоя |
| `VITE_PUBLIC_BASE_URL` | variable | База публичной части, печётся в бандл кабинета |

Настройка — в `deploy/README.md` §«Автодеплой (CD)».

## 6. Грабли, оплаченные кровью

Каждая стоила времени и найдена только потому, что проверяли **результат**, а не факт
зелёного шага.

**Зелёный деплой ≠ применённый конфиг (TD-27).** `Caddyfile` монтировался одиночным
файлом, а такой bind-mount привязан к иноде: `git checkout` создаёт новую, контейнер
продолжает видеть старое содержимое, `caddy reload` честно перечитывает устаревший файл
и возвращает `0`. Правки не доезжали **месяцами и молча**. Лечение: монтировать **каталог**
(`deploy/caddy/`), а не файл. Правило: для конфигов — всегда каталог.

**`docker … exec` съедает stdin.** Скрипт подаётся на сервер через stdin
(`ssh … bash -s < remote-update.sh`), а `exec` без `< /dev/null` забирает тот же stdin и
съедает **остаток скрипта**. Команды ниже просто не выполняются, деплой остаётся зелёным.
Проверка, которая не запускается, хуже отсутствующей — она создаёт ложную уверенность.

**`$VAR arg` для команды разбивается в bash, но НЕ в zsh.** Приём `PC="docker compose …"`
+ `$PC exec …` молча ломается при запуске из другой оболочки, а `|| echo 0` превращает
поломку в правдоподобное число. Использовать **функции**. (Обжигались трижды за один день.)

**Зелёный тест без контрольной точки ничего не доказывает.** Замер «после» показал 0 ошибок
и был принят за доказательство починки — на деле фикс тогда вообще не применялся.
Порядок: воспроизвести дефект замером → починить → перемерить **тем же способом**.

**Мониторинг может смотреть не туда (TD-28).** `/healthz` чинили в обработчике, но снаружи
он не был проксирован и отдавал `200` со **статикой** — SPA-fallback. Смоук проверял его
по внутренней сети и потому проходил всегда. Проверять надо тем же путём, каким пойдёт
потребитель.

## 7. Чек-листы

**Добавляю проверку в CI:** решить, в какой контур (быстрый `ci.yml` или тяжёлый
`e2e.yml`) → добавить эквивалентную команду в `Makefile`, чтобы воспроизводилось локально
→ **прогнать мутацию**: сломать то, что проверка сторожит, и убедиться, что она краснеет →
дописать сюда строку в §2.

**Добавляю шаг в деплой:** помнить про stdin (`< /dev/null` у любого `docker exec`) →
шаг должен быть идемпотентным (повторный прогон того же тега безопасен) → падение шага
обязано валить деплой (`set -euo pipefail` уже стоит) → проверить, что шаг реально
выполнился, в логе job'а, а не поверить зелёному статусу.

**Добавляю секрет/переменную:** `gh secret set` / `gh variable set` (значение не проходит
через историю и логи) → описать в таблице §5.6 и в `deploy/README.md` → проверить, что
без него workflow падает **внятно**, а не молча пропускает шаг.

## 8. Границы и известные гэпы

- **PAT сервера истекает ~2026-10-19.** После этого `git fetch`, `gh release download` и
  `docker pull` на сервере сломаются, автодеплой начнёт падать на шаге деплоя. Продление —
  `deploy/README.md`.
- **E2E ночной, не поштучный.** Регресс, пойманный им, обнаруживается с задержкой до суток.
  Перед релизом имеет смысл дёрнуть его руками (`workflow_dispatch`).
- **Откат — это выкатка предыдущего тега.** Отдельного механизма нет; миграции вперёд-
  совместимы в рамках MVP, откат со снятием миграции — вручную.
- **Сверка B зависит от `python3` на сервере.** Его отсутствие не валит деплой, а печатает,
  что глубокая сверка пропущена. Осознанно: сверка A и так обязательна.
- **Прод один.** Стейджинга нет; prod-local — репетиция, а не среда. Проверять
  функциональность до тега можно только им.
