# Печать ответа в PDF

Практический справочник: как получается PDF одного ответа и обо что здесь бьются.
**Живой документ** — пополняется по мере работ по печати (новый потребитель документа,
правка вида листа, второй тип печатаемого документа).

**Это производный справочник, а не источник истины.** При конфликте побеждает
[`ARCHITECTURE.md`](ARCHITECTURE.md) (ADR §10 — решение о headless-Chromium, §4.4 —
сквозная механика печати). Контракт ручек — [`API.md`](API.md), конвейер образов —
[`CI-CD.md`](CI-CD.md), вид самой формы — [`../web/shared/fields/README.md`](../web/shared/fields/README.md)
(скилл `form-field`).

---

## 1. Ментальная модель: PDF не собирается, а фотографируется

Документ не строится в Go примитивами. Печатается **страница формы** — та же самая, что
видит респондент, только в режиме чтения и с подставленными ответами. Её рисуют те же
`@fields` и тот же `fields.css`, а в PDF её превращает headless-Chromium.

Это главное решение подсистемы, и оно принято не ради простоты кода: генератор на Go завёл
бы **четвёртую верстку формы** рядом с редактором, превью и рендерером — ту, которая
расходится молча при каждом новом типе поля и каждой правке шторки «Оформление».
Расхождение вида здесь дороже железа (ADR §10).

Следствие, с которым живём: в контуре появляется контейнер с браузером (образ ~1.2 ГБ
против 29 МБ у api), а печать становится сетевой операцией с таймаутами и очередью.

## 2. Путь одной печати

```
клик «Скачать PDF» в кабинете
  │
  ├─ api: AuthorizePrint — членство в воркспейсе + ответ существует и не скрыт квотой
  │        (чужой, удалённый, over_quota → 404 ДО того, как поднимется браузер)
  ├─ api: issuePrintToken — HMAC над парой «форма+ответ» и сроком (2 мин)
  ├─ api → printer:  POST /print {"path": "/internal/print/doc/<токен>"}
  │
  ├─ printer: checkPage — GET той же страницы, ждём 200 и text/html
  ├─ printer: chromium --headless --print-to-pdf <origin><path>
  │     └─ браузер: GET /internal/print/doc/<токен>
  │          ├─ api читает print.html с диска, подставляет JSON ответа в маркер
  │          ├─ браузер тянет /internal/print/assets/*.js|css|woff2
  │          ├─ скрипт рисует форму (PrintView), надевает оформление
  │          └─ картинки — /internal/print/media/<key>
  └─ api: отдаёт байты как attachment
```

**Вторая поверхность — вложение в письме владельцу** (настройка «Уведомления мне» →
«Прикрепить PDF с ответом»). Путь тот же, начиная с токена, но входит в него не клик:

```
диспетчер outbox видит письмо со ссылкой на вложение (payload.attachments)
  │
  ├─ mail: бюджет печатей на тик не исчерпан? нет → письмо ждёт следующего тика
  ├─ submissions.PrintAttachments: имя формы и дата ответа (ответ удалён → без вложения)
  ├─ … дальше как выше: токен → принтер → браузер → байты …
  └─ mail: multipart/mixed, письмо уходит с файлом
```

Отличий от клика три, и все три названы решением (ADR §10):

- **прав пользователя нет** — письмо шлём мы, адресат уже выбран (владелец пространства),
  поэтому вместо `AuthorizePrint` вызывается `PrintAccessForDelivery`: существование ответа
  проверяется, членство спрашивать не у кого;
- **потолок печатей на тик** (`outboxPrintsPerTick`, сейчас 3) — пачка диспетчера едет одним
  тиком с общим таймаутом, и в ней же лежит письмо со сбросом пароля. Замер на dev: печать
  одного листа заняла **2,1 с** (`printed elapsed` в логе принтера), то есть три вложения
  съедают около трети тика в 15 с. Письмо, которому бюджета не хватило, НЕ помечается
  неудачей: `attempts` не растёт, оно просто ждёт;
- **сбой печати не откладывает письмо** — уведомление важнее вложения. Владелец получает
  письмо без файла, а дефолтный шаблон добавляет строку о том, что PDF приложить не удалось
  (в СВОЁМ тексте автора такой строки нет: свой текст заменяет тело целиком).

**Где что лежит:**

| Кусок | Файл |
|---|---|
| Право + данные листа | `internal/submissions/service.go` (`AuthorizePrint`, `PrintDocFor`, `PrintAccessForDelivery`) |
| Вложение письма | `internal/submissions/print_attachments.go`, `internal/mail/` (`AttachmentRef`, `attachFiles`) |
| Токен печати | `internal/submissions/printtoken.go` |
| Документ и его ассеты | `internal/submissions/print_page.go` |
| Ручка PDF и кнопка | `internal/submissions/handler.go` (`pdf`), `web/app/src/features/submissions/` |
| Клиент печати (семафор, очередь) | `internal/printer/` |
| Сам сервис печати | `cmd/printer/`, образ `deploy/Dockerfile.printer` |
| Страница | `web/renderer/print.html`, `web/renderer/src/print/`, сборка `vite.print.config.ts` |
| Картинки для принтера | `internal/media` (`Fetch`, роут `/internal/print/media/{key...}`) |

## 3. Почему у страницы своя сборка

`dist/print/` собирается отдельным проходом (`npm run build:print`), а не входит в бандл
формы. Причина не в аккуратности: у страницы **другой читатель**. Форму качает респондент с
телефона, печатную страницу открывает наш же принтер по внутренней сети — и её код в общем
бандле означал бы вес, который респондент скачивает зря, при бюджете формы 60 КиБ.

Отсюда три следствия, о которые бьются:

- **Vite её не обслуживает.** Go читает файл с диска, поэтому в dev страницу надо собрать
  (`make dev-all` это делает). Правишь её вид — пересобирай, hot-reload не работает.
- **Ассеты и шрифты приезжают своими копиями** — общего чанка у раздельных сборок нет.
  `check-bundle.mjs` считает `print/` отдельным порогом и не смешивает с формой.
- **Путь ассетов вшит в сборку** (`base: '/internal/print/'`). Меняешь его — меняй и раздачу
  в `print_page.go`.

## 4. Данные впечатаны, а не запрошены

В `print.html` есть один плейсхолдер `<!--print-data-->`; Go подставляет на его место
`<script type="application/json" id="print-data">…</script>` и отдаёт документ. Тот же приём
и тот же тип маркера, что у публичной страницы формы (`internal/forms/public_page.go`,
`<!--og-meta-->`), и по той же причине: **список ассетов знает только сборка**, Go его не
ведёт и потому не может с ней разойтись.

Почему не запросом к API: страницу открывает браузер без cookie и без сессии. Запрос
потребовал бы дать ему авторизацию — то есть или чужую сессию, или второй токен.

**Файл перечитывается на КАЖДУЮ печать.** Выкатка может обновить только статику (тег образа
тот же → контейнер api не пересоздаётся), и разобранный при старте документ ссылался бы на
несуществующие ассеты навсегда. У формы та же беда решена сверкой mtime и кешем; здесь кеш
не нужен — печатей единицы, файл несколько килобайт.

**Зеркало контракта:** `printPayload` (Go) ↔ `printDataSchema` (Zod, `src/print/data.ts`).
Разъедутся — страница честно скажет «печатать нечего» вместо листа с ответом.

**Пояс расписания едет данными** (`timezone`, пусто = записи у формы нет). Время записи
печатается в нём и подписывается им, как в письме. Взять его у браузера нельзя: лист
рисует headless-контейнер, у которого пояса нет вовсе, — время встало бы на бумагу в UTC
и разошлось бы с письмом и кабинетом на три часа, ничем себя не выдав.

## 5. Токен печати

Формат: `<formID>.<submissionID>.<unixMillis истечения>.<base64url(hmac)>`. Подпись покрывает
всё, что перед ней, поэтому подменить id ответа в готовом токене нельзя.

- **Право проверяется до выдачи** (`AuthorizePrint`), токен только переносит уже принятое
  решение через сетевую границу. Сам по себе он не «даёт доступ» — он его предъявляет.
- **Секрет выведен из `FORM_TOKEN_SECRET`** меткой `trillix/print-token/v1` — тот же приём и
  тот же довод, что у ключа посетителя (`internal/visits/visitorkey.go`): своей переменной
  окружения у печати нет, а подписывать её токены тем же ключом, что и токены публичной
  формы, нельзя.
- **TTL две минуты.** Долгоживущий токен был бы ссылкой на чужой ответ, работающей без
  логина, — то есть тем, чего нет ни у одной другой ручки кабинета.
- Любая беда с токеном — **404**, а не 401/403: наружу этот путь не существует.

## 6. Что удерживает страницу в безопасности

**CSP ставит Go, а не Caddy.** На странице лежит CSS автора формы (платная возможность), и
`web/shared/fields/customCss.ts` прямо называет политику единственной стеной вокруг него.
Публичной форме политику печатает Caddy, но `/internal/*` он не проксирует вовсе — значит на
этом пути её обязан поставить сам обработчик (`printCSP` в `print_page.go`). Без неё чужой
CSS получал бы право звать внешние адреса из браузера, который стоит во внутренней сети
рядом с api и базой: не утечка ответа, а чужой запрос нашими руками.

Политика уже, чем у формы: `connect-src 'none'`, ни фреймов, ни `blob:` — данные приезжают
впечатанными. `unsafe-inline` для стилей остаётся: на нём и стоит своё оформление.

**Ответы респондента едут внутрь `<script>`.** `json.Marshal` экранирует `<`, `>` и `&` даже
внутри `json.RawMessage`, поэтому `</script>` в чужом ответе документ не рвёт. ⚠ Перейдёшь на
`json.Encoder` — не забудь, что `SetEscapeHTML(false)` это ломает.

**Принтер печатает только пути на нашем api.** Origin знает он сам (`PRINTER_API_ORIGIN`), а
api присылает только путь: попросить принтер сходить на чужой хост нельзя в принципе — иначе
ручка печати была бы SSRF-примитивом, который ходит куда скажут и приносит результат
картинкой.

**Страница проверяется до запуска браузера** (`checkPage`: 200 и `text/html`). Без этого
отказ api превращался бы в валидный PDF с текстом ошибки внутри — худший вид отказа, потому
что он выглядит успехом.

## 7. Ресурсы: два ограничителя, а не один

- **Семафор** (`internal/printer`) держит число одновременных браузеров — по умолчанию 2. Он
  ОДИН на обе поверхности: клики в кабинете и вложения писем делят те же два браузера, потому
  что защищают они одну машину, а не свою очередь каждый.
- **Потолок очереди** (вчетверо больше слотов) держит число ожидающих. Без него пачка кликов
  или скрипт по списку ответов дали бы сотню горутин и соединений, каждое из которых висит до
  своего дедлайна.

Переполнение обоих — `503` с `Retry-After`, а не растущее ожидание. Печать **синхронна**:
документ готовится около полусекунды, и очередь с уведомлением «файл готов» стоила бы больше,
чем экономила. Пакетная выгрузка, когда появится, синхронной быть не сможет — но это другая
ручка и другой механизм.

Браузер запускается **на документ** и умирает вместе с ним: ни пула, ни CDP, ни резидентной
вкладки. В простое подсистема стоит ноль памяти. `WaitDelay` у процесса обязателен —
`CommandContext` убивает сам chromium, но `CombinedOutput` ждёт закрытия pipe, а его держат
внуки (браузер плодит дочерние процессы).

## 8. Вид листа

Печатная страница — **четвёртая поверхность формы** и единственная, которую не заполняют.
Отличий от рендерера ровно три, и каждое следует из того, что документ уже отправлен: один
лист вместо шагов (`page_break` рисуется пустым), нет кнопок, контролы получают `readOnly`.

- **`readOnly` сильнее `disabled`.** Неинтерактивный `input` всё равно обрезает длинный ответ
  по своей ширине, `textarea` — по высоте, и увидеть потерю по PDF нельзя. В читаемом режиме
  текстовые типы рисуются коробкой `.rf-input--static` с тем же видом, но с переносом; выбор,
  шкала и согласие флаг игнорируют — они и так показывают состояние целиком.
- **Условная логика на бумаге не применяется.** Печатаются все вопросы версии; скрытый у
  респондента остаётся пустым — это честнее листа, из которого молча пропала часть формы.
- **Поля листа делятся между `@page` и колонкой.** Вертикальные — у страницы (только так они
  повторяются на каждом листе), горизонтальных у страницы нет вовсе: холст и обложка тянутся
  во всю ширину экрана, и боковые поля обрывали бы их в сантиметре от края. Фон доходит до
  среза, отступ текста держит `.rf-page`. Цена: у цветного холста верх и низ каждого листа
  остаются белыми — область полей страницы браузер не закрашивает ничем.
- **Имена файлов приезжают контекстом** `KnownFilesProvider` (в ответе лежат только id),
  **адреса картинок** — через `setMediaBase`: у браузера принтера нет раздачи Caddy, поэтому
  обложка, логотип и блоки `image` идут через `/internal/print/media`.

## 9. Конфигурация (env)

| Переменная | Читает | Значение |
|---|---|---|
| `PRINTER_URL` | api | Где принтер. dev — `http://127.0.0.1:8090` (контейнер в хостовой сети), prod-local/прод — `http://printer:8090` |
| `PRINT_PAGE_PATH` | api | Что печатать: собранный `print.html`. dev — `web/renderer/dist/print/print.html`, прод — `/srv/renderer/print/print.html` |
| `PRINTER_ADDR` | printer | Адрес внутри контейнера (`:8090`); наружу порт не публикуется |
| `PRINTER_API_ORIGIN` | printer | Откуда брать страницы — только этот origin и никакой другой |
| `CHROMIUM_BIN` | printer | Имя бинаря: разнится между базовыми образами |

Обе переменные api **опциональны**: пусто — печати на контуре нет, ручка отвечает 503
«печать не настроена», а не молчит. Путь неверен — api не стартует (fail-fast, заметно).
При старте api пингует принтер и пишет `printer configured` либо
`printer configured, but does not answer` — опечатка в адресе видна сразу, а не при первом
клике у того, кто её не делал.

Путь к странице **задаётся явно на каждом контуре** и не выводится из
`PUBLIC_RENDERER_INDEX_PATH` (решение владельца 2026-08-30): вывод работал везде, кроме dev,
и делал печать единственной подсистемой, которую нельзя пощупать при `make dev-all`.

## 10. Как это трогать

**Правишь вид листа** → `web/renderer/src/print/` и `@media print` в `print.css`; общий вид
полей — только через `@fields` (иначе поверхности разъедутся). Пересобери `build:print`.

**Добавляешь тип поля** → он приезжает на лист сам, вместе с `@fields`. Проверь читаемый
режим: обрезает ли контрол значение по своим размерам; если да — ветка `readOnly`.

**Добавляешь второго потребителя печати** (вложение в письмо, пакетная выгрузка) → бери
`Service.PrintDocFor` и клиента `internal/printer`, а не копируй путь. Пакет обязан быть
асинхронным: держать соединение на сотне документов нельзя.

**Смотришь глазами** → в dev печать работает (см. §9); лист удобно проверять
`pdftotext`/`pdftoppm` по скачанному файлу.

## 11. Известные границы

- **Печатаются только отправленные ответы.** У черновика нет ни версии, по которой рисовать
  лист, ни события отправки, которым его подписывать; кнопки у такой строки нет.
- **Кеша PDF нет.** Ответ иммутабелен, и документ кешировался бы тривиально, но повторные
  скачивания одного ответа редки, а кеш тянет таблицу, ключи и уборку при удалении ответа.
  Момент завести — пакетная выгрузка.
- **Вложение письма не проверяется в CI живьём.** Резолвер, потолок печатей на тик и сборка
  multipart покрыты юнитами с фейковым принтером; настоящая печать в письме проверяется
  руками на контуре, где принтер поднят.
- **Печать не покрыта e2e.** Интеграционные тесты доходят до страницы (роль браузера играет
  фейковый принтер), сам chromium в CI не гоняется — проверяется руками и на prod-local.
- **Строгий Zod бьёт по всему документу.** Схема версии, в которой встретится незнакомый
  сегодняшнему валидатору ключ, отвергается целиком, и лист скажет «печатать нечего». То же
  поведение у публичной формы, поэтому расхождения между ними нет.
- **Образ принтера ~1.2 ГБ**, и это не оптимизируется сменой базы: замер на Alpine дал
  1.13 ГБ (−8%) — chromium в любом дистрибутиве тянет мультимедийный и GL-стек, а половина
  веса приходится на его десктопную обвязку, а не на движок. Путь к ~400 МБ существует один —
  `chrome-headless-shell` мимо apt, ценой фиксации версии и обновлений безопасности на нас.
  Вес лежит в стабильном слое: при релизе меняется только бинарь, а слой пакетов
  переиспользуется из кеша сборки (`CI-CD.md` §5.1).
- **`f.<домен>/print/print.html` доступен как статика** — пустая страница со словами
  «печатать нечего». Безвредно; закрывается строкой в Caddyfile, если понадобится.
