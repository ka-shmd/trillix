# Очередь задач вне плана

Место для работы, которой нет ни в одном из существующих списков: продуктовые идеи,
замеченное по ходу, «надо бы» из головы владельца. Появился, потому что MVP-план кончается
фазой 10, а задачи вне фаз — нет.

**Куда что идёт (проверь, прежде чем писать сюда):**

| Это | Туда |
|---|---|
| Дефект кода, расхождение доков, осознанная граница | `TECH-DEBT.md` |
| Крупная функциональность на фазу | `POST-MVP.md` |
| Шаг текущей фазы MVP | `DEV-PLAN.md` |
| Всё остальное | **сюда** |

**Правила ведения:**

- Это **очередь, а не архив**. Пункт уходит отсюда, когда сделан (разбор → `JOURNAL.md`),
  когда вырос до фазы (→ `POST-MVP.md`) или когда решено не делать (удаляется со строкой
  «почему» — отказ тоже решение).
- Порядок = приоритет. Верхний пункт — следующий кандидат.
- У пункта нет критерия приёмки, пока его не начали (`PROCESS.md` §1.0): формулируется
  и согласуется **до кода**, а не при записи сюда. Здесь достаточно одной фразы «что и зачем».
- Нумерация не ведётся: ссылаться на пункт очереди неоткуда, а номера создают
  иллюзию учёта. Нужен номер — значит, пункту место в `TECH-DEBT.md`.

## Очередь

- **Реворк полотна редактора — UX базовых операций и ревизия логики.** Владелец 2026-07-24:
  «ужасный UX даже на базовых функциях, возможно есть проблемы в логике». Полотно — корневая
  механика сервиса, поэтому заход **начинается с обдумывания/аудита** (что именно ломает UX, где
  логика полотна расходится с ожиданием), а не сразу с кода. Зона — `web/app/src/features/forms/builder/`
  целиком (скилл `editor-canvas`). Может вырасти до отдельной фазы POST-MVP — решать по итогу аудита.
  Пересекается с богатым текстом ниже: §5 `TECH-DEBT.md` уже показал, что клавиатурный поток строки
  (`BlockRow.tsx:158-188`) всё равно переписывается под форматирование, поэтому если оба захода
  близко — порядок «сначала формат хранения текста, потом UX-реворк» может сэкономить двойную
  переписку тех же ~200 строк.

  Конкретика, замеченная владельцем (не полный список — заход начинается с аудита):
  - **Разделить Enter и Shift+Enter в клавиатурном потоке строки.** Enter — добавить блок
    **после группы** (новый вопрос/одиночка ниже); Shift+Enter — добавить блок **внутрь текущей
    группы**. Сейчас такого разделения нет — это часть ревизии клавиатурного потока (`BlockRow`/
    `SlashEditor`, модель групп из `editor-canvas`).
  - **Вывести подсказки прямо на полотно** (что можно добавить/как, доступные действия строки).
    Пересекается с TD-26 (`TECH-DEBT.md` §3): контекстные подсказки «добавить заголовок/поле» у
    одинокого поля/подписи уже помечены как не выведенные на экран — свести к одному решению.

- **Богатый текст в блоках (жирность/цвет/ссылки), возможно через Tiptap/Lexical.** Владелец
  называл желаемым 2026-07-21 и повторил 2026-07-24 («работа с текстом как в нормальных
  редакторах»). **НЕ начинать с выбора библиотеки:** разбор в §5 `TECH-DEBT.md` уже посчитал
  ограничения по коду — Tiptap/ProseMirror (40–50 КиБ) и Lexical (~25 КиБ) в свободный бюджет
  рендерера (~14 КиБ) не влезают, `dangerouslySetInnerHTML` запрещён инвариантом 4, Go обязан
  валидировать содержимое (инвариант 3). Вывод оттуда: сперва решается **формат хранения**
  (кандидат — плоский массив спанов `[{t,m[]}]`, свой контракт), и только потом редактор, чей
  вывод не тянет схему библиотеки в рендерер. Закрытие TD-33 (литерал «/» с клавиатуры) этим же
  заходом — вероятно бесплатно: slash-меню с откатом на литерал идёт в таких редакторах штатно.

- **Сайдменю с перетаскиванием блоков мышью на полотно.** Панель, откуда блок таскается
  drag-and-drop прямо на холст — в дополнение к вводу с клавиатуры. Владелец 2026-07-24 ставит
  этот пункт **после** реворка полотна и готовой клавиатурной механики: сначала стабильный
  клавиатурный поток строки, затем мышиный слой поверх него. Второй слой dnd на полотне уже
  есть (скилл `editor-canvas`) — новый источник перетаскивания встраивается в него.

- **Вход через VK ID** — второй провайдер в каркас, построенный фазой 11 (маршруты `{provider}`,
  таблица `user_identities`, правила связывания уже есть). Отложен решением владельца 2026-07-22:
  фаза обкатывает механику на одном провайдере; опущен в конец очереди 2026-07-24 — работы по
  полотну редактора приоритетнее второго OAuth-провайдера. Что уже выяснено и не нужно выяснять
  заново — эндпоинты, обязательный PKCE, `state` от 32 символов, `device_id` при обмене кода,
  email только по scope — записано в шаге 1 фазы 11 (`DEV-PLAN.md`). Отдельно понадобится добор
  почты: у VK-аккаунта, заведённого на телефон, email может не быть вовсе.

Первый заход сюда — после закрытия фазы 10: тогда MVP-план исчерпан, и очередь становится
одним из источников задач наряду с `TECH-DEBT.md` и `POST-MVP.md` (у пост-MVP фаз
демо-критерии уже написаны, у пунктов очереди — нет).
