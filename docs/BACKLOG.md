# Очередь задач вне плана

Место для работы, которой нет ни в одном из существующих списков: продуктовые идеи,
замеченное по ходу, «надо бы» из головы владельца. Появился, потому что MVP-план кончается
фазой 10, а задачи вне фаз — нет.

**Куда что идёт (проверь, прежде чем писать сюда):**

| Это | Туда |
|---|---|
| Дефект кода, расхождение доков, осознанная граница | `TECH-DEBT.md` |
| Крупная функциональность на фазу | `POST-MVP.md` |
| Шаг текущей фазы MVP | `DEV-PLAN.md` |
| Всё остальное | **сюда** |

**Правила ведения:**

- Это **очередь, а не архив**. Пункт уходит отсюда, когда сделан (разбор → `JOURNAL.md`),
  когда вырос до фазы (→ `POST-MVP.md`) или когда решено не делать (удаляется со строкой
  «почему» — отказ тоже решение).
- Порядок = приоритет. Верхний пункт — следующий кандидат.
- У пункта нет критерия приёмки, пока его не начали (`PROCESS.md` §1.0): формулируется
  и согласуется **до кода**, а не при записи сюда. Здесь достаточно одной фразы «что и зачем».
- Нумерация не ведётся: ссылаться на пункт очереди неоткуда, а номера создают
  иллюзию учёта. Нужен номер — значит, пункту место в `TECH-DEBT.md`.

## Очередь

- **Вход через VK ID** — второй провайдер в каркас, построенный фазой 11 (маршруты `{provider}`,
  таблица `user_identities`, правила связывания уже есть). Отложен решением владельца 2026-07-22:
  фаза обкатывает механику на одном провайдере. Что уже выяснено и не нужно выяснять заново —
  эндпоинты, обязательный PKCE, `state` от 32 символов, `device_id` при обмене кода, email только
  по scope — записано в шаге 1 фазы 11 (`DEV-PLAN.md`). Отдельно понадобится добор почты: у
  VK-аккаунта, заведённого на телефон, email может не быть вовсе.

Первый заход сюда — после закрытия фазы 10: тогда MVP-план исчерпан, и очередь становится
одним из источников задач наряду с `TECH-DEBT.md` и `POST-MVP.md` (у пост-MVP фаз
демо-критерии уже написаны, у пунктов очереди — нет).

Известные кандидаты на перенос сюда, когда дойдут руки (сейчас лежат в других документах,
переносить преждевременно):

- колонки первых вопросов в таблице ответов — хвост шага 3 фазы 8.5, владелец дорабатывает
  таблицу отдельным заходом;
- UI дубликации блока в билдере — стор-операция `duplicateBlock` уже есть и покрыта тестом,
  контрола нет;
- богатый текст в блоках — решение не принято, ограничения посчитаны (`TECH-DEBT.md` §5).
