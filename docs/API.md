# Справочник API

Производная справка «как вызывать» по эндпоинтам, реализованным на текущий момент (healthz, аутентификация, CRUD форм, публикация и публичная выдача формы, приём ответов и их листинг в кабинете). **Источник истины — `docs/ARCHITECTURE.md`** (модель, контракт, «почему»); при расхождении побеждает он, а эта справка правится в том же PR, что и код.

## Общие правила

- **Базовый префикс приватного API:** `/api/v1`. В dev Vite проксирует `/api → :8080` (CORS не нужен).
- **Формат:** запрос и ответ — JSON (`Content-Type: application/json`). Тело каждого эндпоинта ограничено `MaxBytesReader`: auth — 4 КБ, forms — 64 КБ (`PATCH` несёт весь `draft_schema` автосейва; внутренние лимиты документа стережёт `ValidateSchema`).
- **Идентификаторы** в путях и телах — UUIDv7-строки; `slug` формы и пространства — nanoid из 10 символов (у пространства он живёт только в адресах кабинета, API его не принимает).

### Аутентификация и сессия

- После `register`/`login` сервер ставит две cookie: `session` (httpOnly, `SameSite=Lax`, флаг `Secure` — из конфигурации: в dev по http выключен) и `csrf_token` (читаемая JS).
- Приватные эндпоинты требуют живой сессии (`session` cookie). Промах — `401 unauthorized` (не 403: существование ресурса не раскрывается).
- **CSRF (double-submit):** мутирующие запросы (`POST`/`PATCH`/`DELETE`) обязаны прислать заголовок `X-CSRF-Token`, равный значению cookie `csrf_token`. Несовпадение — `403 forbidden`.
- Браузерный `fetch` должен идти с `credentials: 'include'` (в кабинете это делает `shared/api/client.ts`).

### Формат ошибок

Любой не-2xx ответ — единый конверт:

```json
{ "error": { "code": "validation_failed", "message": "…", "fields": { "title": "…" } } }
```

`fields` присутствует не всегда (карта «поле → сообщение» для валидации). Тела 5xx не раскрывают внутренний текст (в логах он есть, с request_id).

**`message` — текст для человека, и только он.** Доменные ошибки заворачиваются в Go как `fmt.Errorf("%w: человеческий текст", domain.ErrValidation)`, поэтому `err.Error()` начинается с текста самого сентинела («validation failed: …»). В конверт этот префикс не попадает: он английский, он повторяет то, что уже сказано полем `code`, и посреди русского сообщения на экране читался бы утечкой внутренностей. Режется в единственной точке раскладки ошибок на HTTP (`internal/httpserver/respond.go`), поэтому кабинет вправе показывать `message` как есть.

| HTTP | `code`                | Когда |
|------|-----------------------|-------|
| 401  | `unauthorized`        | нет живой сессии |
| 401  | `invalid_credentials` | неверный email или пароль (одинаковое время ответа с «нет такого email») |
| 403  | `forbidden`           | не прошёл CSRF-проверку |
| 404  | `not_found`           | ресурс не найден **или** нет доступа (анти-IDOR: не 403) |
| 409  | `email_taken`         | повторная регистрация на занятый email |
| 409  | `conflict`            | оптимистичная блокировка: присланный `updatedAt` устарел (форму изменили в другой вкладке) |
| 410  | `form_closed`         | форма была публичной, но больше не принимает ответы (снята / дата закрытия / лимит) |
| 422  | `validation_failed`   | невалидное тело/параметры (детали — в `fields`) |
| 413  | `payload_too_large`   | тело запроса превысило потолок (приём ответа — 256 КБ) |
| 429  | `rate_limited`        | сработал лимит (`POST /auth/register`, `POST /auth/login`, `POST …/submissions`); заголовок `Retry-After` |
| 500  | `internal`            | внутренняя ошибка |

### Пагинация

Курсорная: `?cursor=<непрозрачный токен>&limit=<n>` (`limit` по умолчанию 50, максимум 100). Ответ листаемого эндпоинта содержит `nextCursor` (`null` на последней странице) — его значение передаётся в `?cursor` следующего запроса. Токен непрозрачен для клиента.

## Аутентификация — `/api/v1/auth`

Объект пользователя во всех ответах:

```json
{ "id": "019f…", "email": "user@example.com", "emailVerified": false, "firstName": "Иван", "lastName": "Петров", "hasPassword": true, "twoFactorEnabled": false }
```

`emailVerified` — подтверждён ли адрес (слайс C): кабинет по нему рисует баннер «подтвердите почту».
`twoFactorEnabled` — включён ли второй фактор (фаза 23, слайс F): по нему экран настроек рисует раздел, а вход знает, что будет второй шаг.
`hasPassword` — есть ли у аккаунта пароль вообще (у заведённого через провайдера его нет): кабинет по нему решает, спрашивать ли текущий пароль. Наружу едет факт, не хеш.
`firstName`/`lastName` — имя человека (фаза 23). **Пустая строка = не указано** (в БД там `NULL`): на границе оба состояния сведены к строке, потому что показать потребитель может только строку. Кабинет зовёт человека по имени, а без него — по email (`entities/user.ts`, `displayName`).

### `POST /auth/register`
Регистрация. Создаёт пользователя, личный воркспейс и членство одной транзакцией, открывает сессию. **Rate limit по IP** (отдельное ведро, жёстче логина: ≈3 запроса, пополнение ~1 / 30 c — argon2id дорог по памяти).
- **Тело:** `{ "email": string, "password": string }` (пароль 8–128 символов).
- **200/201:** `201` + объект пользователя; ставит cookie `session` и `csrf_token`.
- **Ошибки:** `409 email_taken`, `422 validation_failed`, `429 rate_limited`.

### `POST /auth/login`
Вход. **Rate limit по IP** (≈5 попыток, пополнение ~1 / 12 c).
- **Тело:** `{ "email": string, "password": string }`.
- **200:** объект пользователя + cookie. **Либо** `{"twoFactorRequired": true}` — у аккаунта включён второй фактор: **сессия НЕ выдаётся**, ставится HttpOnly-cookie `two_factor` (подписанный пропуск на один шаг, TTL 15 минут), клиент ведёт человека на ввод кода.
- **Ошибки:** `401 invalid_credentials`, `429 rate_limited`.

### `POST /auth/login-2fa`
Второй шаг входа. Без сессии (её ещё нет) — аутентифицирует подписанная cookie `two_factor` плюс код. Принимает **код из приложения или резервный**; и тот и другой одноразовые: код TOTP не проходит второй раз в пределах своих 30 секунд (хранится номер израсходованного шага), резервный гасится. **Rate limit — два ведра.** По IP — общее с `/auth/login` (иначе перебор переезжает на менее защищённую дверь). По **аккаунту** (ключ — id из подписанного пропуска) — своё и самое строгое: ≈5 попыток, пополнение ~1 в минуту. Второе ведро здесь и есть защита от перебора: код привязан к аккаунту, а не к адресу, и с пула IP лимит по адресу не ограничивает попытки по аккаунту вовсе. Лока после N неудач нет сознательно — им запирали бы чужой аккаунт, зная один только адрес.
- **Тело:** `{ "code": string }`.
- **200:** объект пользователя + cookie сессии; пропуск гасится.
- **Ошибки:** `401 unauthorized` (пропуска нет или истёк), `401 invalid_credentials` (код не подошёл), `429 rate_limited`.

### `POST /auth/forgot-password`
Без авторизации. Запрос ссылки сброса пароля. **Всегда `204`, одинаково для любого адреса** — существование аккаунта не раскрывается (есть аккаунт → письмо со ссылкой ушло в очередь; нет → молча тот же ответ). Работает и для аккаунта, заведённого через провайдера (у него нет пароля — сброс его задаёт). **Rate limit по IP** (≈5 запросов, ~1 / 30 c) **и по email** (≈3, медленное пополнение ~1 / 5 мин — нельзя завалить чужой ящик письмами с разных IP).
- **Тело:** `{ "email": string }`.
- **204:** запрос принят (письмо — асинхронно через outbox; синхронной отправки нет).
- **Ошибки:** `429 rate_limited`.

### `POST /auth/reset-password`
Без авторизации (аутентификация самим одноразовым токеном; CSRF не нужен). Ставит новый пароль по токену из письма и **рвёт все сессии пользователя**. Токен одноразовый (SHA-256 в БД, TTL 30 мин). Автологина нет — после успеха фронт ведёт на вход. **Rate limit по IP** (≈5, ~1 / 12 c).
- **Тело:** `{ "token": string, "password": string }` (пароль 8–128 символов).
- **204:** пароль обновлён.
- **Ошибки:** `422 validation_failed` (токен недействителен/использован/истёк, либо пароль вне границ), `429 rate_limited`.

### `POST /auth/verify-email`
Без авторизации (аутентификация самим одноразовым токеном; CSRF не нужен). Подтверждает email по токену из письма — проставляет `users.email_verified_at`. Токен одноразовый (SHA-256 в БД, TTL 24 ч). **Rate limit по IP** (≈5, ~1 / 12 c).
- **Тело:** `{ "token": string }`.
- **204:** email подтверждён.
- **Ошибки:** `422 validation_failed` (токен недействителен/использован/истёк), `429 rate_limited`.

### `POST /auth/resend-verification`
За сессией и CSRF. Повторно ставит письмо подтверждения в очередь текущему пользователю. Уже подтверждённому — тот же `204` без письма (состояние не раскрывается). **Rate limit по пользователю** (≈3, медленное пополнение ~1 / 5 мин — кнопка не должна слать письма пачками).
- **Тело:** пустое.
- **204:** запрос принят (письмо — асинхронно через outbox).
- **Ошибки:** `401 unauthorized`, `403` (провал CSRF), `429 rate_limited`.

### `GET /auth/providers`
Без авторизации. Список включённых провайдеров входа: `200 → {"providers":["yandex"]}`. Пустой массив — ключей нет в окружении, кнопки не рисуются.

### `GET /auth/oauth/{provider}/start`
Начало входа через провайдера. Отвечает `302` на страницу согласия провайдера и ставит HttpOnly-cookie `oauth_state` (`state` + `code_verifier`, TTL 15 минут, `SameSite=Lax` — иначе cookie не доедет на возврате).
- `?mode=popup` — поход начат из отдельного окна: ставится ещё и HttpOnly-cookie `oauth_mode`, по которой колбэк выберет служебный возврат (см. ниже). Любое другое значение (и отсутствие параметра) **гасит** `oauth_mode`: она живёт 15 минут, и брошенное окно не должно уводить следующий вход в той же вкладке на служебный экран.
- **Ошибки:** `404` — провайдер не включён.

### `GET /auth/oauth/{provider}/callback`
Возврат от провайдера. **Rate limit по IP** (≈10 попыток, пополнение ~1 / 6 c). Сверяет `state` с cookie, меняет код на профиль, дальше три исхода — все редиректом на кабинет, а не JSON:
- у аккаунта включён второй фактор → `302` на `/two-factor` + cookie `two_factor`; **сессия не выдаётся** (фактор применяется ко всем путям входа, иначе обходится в один клик);
- привязка найдена или адрес свободен → `302` на `/`, cookie `session` и `csrf_token` выставлены. Тем же шагом заполняются **пустые** имя и фамилия аккаунта данными профиля (фаза 23): заполненное не трогается, негодное (пустое, длиннее 100 символов) игнорируется молча — вход из-за него не отказывает. На шаге `POST /auth/oauth/link` имени нет: до него доезжает только пара (провайдер, идентификатор);
- аккаунт с таким email уже есть → `302` на `/link-account?provider=…` + подписанная cookie `oauth_pending`; **сессия не выдаётся** (провайдеры не сообщают, подтверждён ли адрес — ADR §10);
- адрес занят аккаунтом **без пароля** (личность у провайдера сменилась) → `302` на `/login?oauth=provider_only`: доказывать владение нечем, см. TD-34;
- отказ пользователя, протухшая cookie, несовпавший `state`, отсутствие email, недоступность провайдера или сбой БД → `302` на `/login?oauth=<причина>` (`denied` · `expired` · `state` · `no_email` · `failed`). Причина отказа уходит в лог с провайдером и стадией; JSON-ошибку колбэк не отдаёт никогда — это навигация браузера, и человеку нужен экран, а не тело ответа.

**Поход из отдельного окна** (cookie `oauth_mode`, ставит её `?mode=popup`) кончается иначе: вместо экрана кабинета — `302` на служебный `/oauth/done?r=<исход>`, который передаёт код вкладке-опекуну через `postMessage` и закрывается. Перечень кодов закрытый и общий с фронтом (`oauthOutcome` в `internal/auth/handler_oauth.go` ↔ `oauthOutcomeSchema` в `web/app/src/features/auth/oauthPopup.ts`): `ok` · `two_factor` · `link_required` · `denied` · `expired` · `state` · `no_email` · `failed` · `provider_only` · `link_ok` · `link_conflict` · `link_expired` · `link_failed`. Cookie сессии, `oauth_pending` и пропуск второго фактора выставляются ровно те же — окно и вкладка живут в одном браузере на одном origin, поэтому дальше человек продолжает во вкладке. **Экран по коду выбирает вкладка**, а не сообщение: путь в `postMessage` сделал бы его управляемым редиректом.

### `POST /auth/oauth/link`
Второй шаг привязки: пароль от существующего аккаунта. Требует cookie `oauth_pending`. **Rate limit — общее ведро с `/auth/login`** (иначе перебор переезжает на менее защищённую дверь); время ответа выровнено.
- **Тело:** `{ "email": string, "password": string, "code": string }`. `code` — второй фактор; в первом запросе пустой (фронт не знает, включён ли он).
- **200:** объект пользователя + cookie сессии; привязка создана.
- **200 `{ "twoFactorRequired": true }`:** пароль верен, но у аккаунта включён второй фактор. **Привязки ещё нет и сессии нет** — тот же запрос повторяется с `code`, cookie `oauth_pending` для этого остаётся жить. Отдельного пропуска (как у `/auth/login`) здесь не ставится: шаг один и тот же, а не второй.
- **Ошибки:** `401 unauthorized` (привязка не начата или истекла), `401 invalid_credentials` (пароль либо код), `409 conflict` (аккаунт провайдера уже привязан), `429 rate_limited`.

Привязка создаётся **после** проверки второго фактора, а не до неё: иначе знающий пароль, но не знающий кода прицепил бы к чужому аккаунту свою личность у провайдера и получил бы вход на тот день, когда владелец выключит фактор.

### `POST /auth/logout`
Требует сессии + CSRF. Удаляет сессию и гасит cookie. **204** без тела.

### `GET /auth/me`
Требует сессии. **200** + объект текущего пользователя. Используется гардом кабинета.

## Аккаунт — `/api/v1/account`

Настройки собственного аккаунта. Все эндпоинты требуют сессии **и** CSRF-заголовка; тело ограничено 4 КБ, как у `auth`. Адреса вида «правь пользователя N» здесь нет и не будет: субъект всегда берётся из сессии (инвариант безопасности 1). Замысел и границы — [`design/account-settings.md`](design/account-settings.md).

### `PATCH /account/profile`
Имя и фамилия. Оба поля обязательны в теле и присылаются всегда: **пустая строка означает «стереть»** — «прислать только имя» лишило бы возможности стереть фамилию. Окружающие пробелы обрезаются, потолок — 100 символов (считается в рунах).
- **Тело:** `{ "firstName": string, "lastName": string }`.
- **200:** объект пользователя целиком (кабинет патчит им кэш профиля).
- **Ошибки:** `401 unauthorized`, `403` (провал CSRF), `422 validation_failed` (длиннее 100 символов либо неизвестное поле в теле).

### `POST /account/avatar`
Фото профиля. Тело — **multipart**, а не JSON: это файл. Картинка валидируется по содержимому (PNG/JPEG, не по имени и не по `Content-Type`), пере-кодируется (снимая EXIF/GPS) и ужимается до 512 по длинной стороне; в `users.avatar_key` уезжает **ключ** объекта (`avatars/<sha256>.<ext>`), не адрес — URL собирает кабинет. **Rate limit по пользователю** (≈5, пополнение ~1 / 20 с): каждая загрузка стоит декода и двух ре-энкодов.
- **Тело:** `multipart/form-data`, поле `file` (до 5 МиБ).
- **200:** объект пользователя целиком (кабинет патчит им кэш профиля).
- **Ошибки:** `401 unauthorized`, `403` (провал CSRF), `413 payload_too_large` (файл больше 5 МиБ), `422 validation_failed` (нет поля `file`, битый multipart, не PNG/JPEG, картинка больше 24 Мпикс), `429 rate_limited`.

### `DELETE /account/avatar`
Снять фото: `avatar_key` уходит в `NULL`, кабинет возвращается к кружку с инициалами. Повторный вызов — не ошибка. Объект в хранилище **не удаляется** (ключи контент-адресны, одну картинку могут делить несколько аккаунтов — TD-16).
- **200:** объект пользователя целиком.
- **Ошибки:** `401 unauthorized`, `403` (провал CSRF).

### `POST /account/password`
Смена пароля. **Рвёт ВСЕ сессии пользователя, включая текущую**, и тут же открывает новую — ответ переставляет cookie `session` и `csrf_token`, поэтому человек, менявший пароль, остаётся в кабинете, а остальные устройства выходят. На адрес аккаунта уходит письмо-уведомление (через outbox, в той же транзакции). **Rate limit по пользователю** (≈3, пополнение ~1 / мин) — не от подбора (сессия уже своя), а от argon2id: 64 МиБ на вызов.
- **Тело:** `{ "currentPassword": string, "newPassword": string }` (новый — 8–128 символов). `currentPassword` **не проверяется у аккаунта без пароля** (`hasPassword: false`, заведён через провайдера): требовать несуществующий пароль значит запереть человека в аккаунте, доказательством служит живая сессия.
- **204:** пароль изменён.
- **Ошибки:** `401 unauthorized` (нет сессии) и `401 invalid_credentials` (текущий пароль неверный), `403` (провал CSRF), `422 validation_failed`, `429 rate_limited`.

### `POST /account/email`
Запрос смены адреса — **первый из двух шагов**. `users.email` **не меняется**: ответ `204` означает «письма поставлены в очередь», а не «адрес сменился». Уходят два письма: ссылка подтверждения — на **новый** адрес, уведомление без ссылки — на **старый** (единственный сигнал хозяину, если сессию увели). Занятость нового адреса проверяется здесь и ещё раз при подтверждении. **Rate limit по пользователю** (≈3, пополнение ~1 / 5 мин): письмо уходит на произвольный адрес из формы — то же соображение, что у приглашений.
- **Тело:** `{ "newEmail": string, "currentPassword": string, "code": string }`. Подтверждение — **пароль, если он есть, И код второго фактора, если тот включён** (`hasPassword` / `twoFactorEnabled` в `/auth/me`): тот же состав, что у `POST /account/delete`. Смена адреса уводит канал восстановления (сброс пароля пойдёт на новый ящик), поэтому по последствиям она ближе к удалению, чем к правке профиля; у аккаунта через провайдера код — единственное доказательство, какое вообще есть.
- **204:** письма поставлены в очередь.
- **Ошибки:** `401 unauthorized`, `401 invalid_credentials` (пароль либо код — ответ один на оба), `403` (провал CSRF), `409 email_taken`, `422 validation_failed` (некорректный адрес либо это уже адрес аккаунта), `429 rate_limited`.

### `GET /account/identities`
Способы входа через провайдеров у текущего аккаунта. Требует сессии (CSRF не нужен — чтение).
- **200:** `[{ "provider": "yandex", "providerEmail": "ivan@yandex.ru", "connectedAt": "2026-08-13T21:00:00Z" }]`. `providerEmail` — адрес аккаунта **у провайдера** (обновляется на каждом входе); пустой у привязок старше миграции `0021`. Идентификатор у провайдера наружу не отдаётся.

### `GET /account/identities/{provider}/start`
Начало привязки провайдера **к текущему аккаунту**. Требует сессии. Отвечает `302` к провайдеру и ставит две HttpOnly-cookie: обычную `oauth_state` и `oauth_link` — подписанное намерение «привязку начал вот этот аккаунт» (HMAC от `FORM_TOKEN_SECRET` со своей меткой, TTL 15 минут). `?mode=popup` работает так же, как у `/auth/oauth/{provider}/start`.

**Отдельный адрес, а не `?intent=link` у `/auth/oauth/{p}/start`:** тот публичный (им входят), а этот обязан быть за `RequireAuth`. Намерение в query-параметре означало бы, что жертву можно заманить пройти привязку и прицепить к её аккаунту **личность атакующего** — то есть выдать ему постоянный вход. Возврат обрабатывает **тот же** `/auth/oauth/{provider}/callback`: увидев `oauth_link`, он сверяет id из подписи с текущей сессией и вместо входа делает привязку, уводя на `/settings/account?link=ok|conflict|expired|failed`.
- **Ошибки:** `401 unauthorized`, `404` — провайдер не включён.

### `DELETE /account/identities/{provider}`
Отвязка. Требует сессии + CSRF. Идемпотентна: отсутствующая привязка — тоже `204` (повторный клик не авария).
- **204:** привязки нет.
- **Ошибки:** `401 unauthorized`, `403` (провал CSRF), **`409 conflict`** — у аккаунта нет пароля и это последний способ войти (данные внутри стали бы недостижимы).

Гейт «останется ли способ войти» считает привязки и удаляет **одной транзакцией, под `FOR UPDATE`**: он решает по составу, и без блокировки две одновременные отвязки разных провайдеров проходят обе — аккаунт без пароля теряет вход насовсем. При одном включённом провайдере сценарий недостижим; блокировка стоит на день, когда провайдеров станет два.

### `POST /account/2fa/setup`
Начало настройки второго фактора. Заводит секрет и отдаёт его человеку; фактор при этом **ещё не включён**. Требует сессии + CSRF, лимит по пользователю (≈5, ~1 / 12 c).
- **200:** `{ "secret": "ABCD EFGH …", "otpauthUrl": "otpauth://totp/Trillix:user@example.com?…" }`. QR не рисуется (решение владельца 2026-08-13): кодировщик — ~500 строк или новая зависимость, а ссылка на телефоне открывает приложение сама.
- **Ошибки:** `401`, `403`, `409 conflict` (фактор уже включён — сначала выключить), `429`.

### `POST /account/2fa/enable`
Включение по первому сошедшемуся коду. Отдаёт резервные коды **ровно один раз** (в БД лежат хеши).
- **Тело:** `{ "code": string }`.
- **200:** `{ "recoveryCodes": ["…", …] }` — 10 штук.
- **Ошибки:** `401`, `403`, `401 invalid_credentials` (код не подошёл), `409 conflict`, `422 validation_failed` (настройка не начата), `429`.

### `POST /account/2fa/disable`
Выключение. Требует **и** пароль (если он есть), **и** код — украденной сессии с известным паролем не должно хватать, чтобы снять защиту, ради которой её включали. Код принимается и резервный.
- **Тело:** `{ "currentPassword": string, "code": string }`.
- **204:** фактор и резервные коды удалены.
- **Ошибки:** `401`, `403`, `401 invalid_credentials`, `429`.

### `POST /account/delete`
Удаление аккаунта. Ставит `users.deleted_at`, рвёт **все** сессии и гасит cookie ответом. Данные остаются в базе, но становятся недостижимыми: помеченного не видит ни один способ узнать пользователя (вход паролем, вход провайдером, живая сессия, второй шаг входа), а **опубликованная форма его пространства отвечает 404**. Самостоятельного восстановления нет — снимается `UPDATE`-ом руками. **Адрес остаётся занятым**: завести на него новый аккаунт нельзя до реальной чистки данных (152-ФЗ, POST-MVP). **Rate limit по пользователю** (≈3, ~1 / мин).
- **Тело:** `{ "currentPassword": string, "code": string }`. Пароль требуется, если он есть; код второго фактора — если тот включён (у аккаунта без пароля и без фактора доказательством служит сама сессия). Спека §10 требует «пароль **или** код»; реализовано строже, по образцу выключения второго фактора: удаление необратимо.
- **204:** аккаунт помечен удалённым.
- **Ошибки:** `401 unauthorized`, `401 invalid_credentials` (пароль или код не подошли), `403` (провал CSRF), **`409 conflict`** — спрашивающий владеет командным пространством, в котором есть другие участники (сначала передать владение или удалить пространство), `429 rate_limited`.

### `POST /auth/confirm-email-change`
Второй шаг. Без авторизации (аутентификация самим одноразовым токеном; CSRF не нужен — по ссылке ходят из почтового клиента, где сессии кабинета может не быть). Переносит `users.email` и проставляет `email_verified_at`: владение доказано переходом по ссылке, отправленной именно на этот адрес. Токен одноразовый (SHA-256 в БД, TTL 24 ч). **Сессии не рвутся** — пароль не менялся. **Rate limit по IP** (≈5, ~1 / 12 c).
- **Тело:** `{ "token": string }`.
- **204:** адрес перенесён.
- **Ошибки:** `409 email_taken` (за сутки адрес заняли), `422 validation_failed` (токен недействителен/использован/истёк), `429 rate_limited`.

## Воркспейсы — `/api/v1/workspaces`

### `GET /workspaces`
Требует сессии. Возвращает пространства текущего пользователя (JOIN через членство — только те, где он состоит). Порядок — по `createdAt`. **Личное при этом не обязано быть первым:** сортируются все пространства с членством, включая чужие, которые могут быть старше вашей регистрации. Ищите личное по `isPersonal`, а не по позиции. Используется сайдбаром и крошками кабинета.

`slug` — короткий публичный ключ (nanoid(10), `0035`). Им кабинет адресует пространство в СВОИХ URL (`/workspaces/{slug}`, `?w={slug}`), как формой — `form.slug`. **Запросы API по-прежнему ждут `id`**: ручки вида `/workspaces/{id}` и параметр `workspaceId` принимают UUID и только его. Перевод одного в другой делает кабинет по этому же ответу — отдельной ручки-резолвера (как `/forms/lookup?slug=`) пространству не нужно, потому что список приезжает целиком.

`isPersonal` — личное пространство **спрашивающего**: его нельзя удалить, покинуть, и оно не замораживается при даунгрейде (ADR §10).

`formCount` — сколько форм в пространстве (подпись рядом с названием в обзоре кабинета). Считает тот же запрос, что отдаёт список: обзор рисует все пространства разом, и отдельный поход за каждым числом был бы N+1. Точен **только здесь**; у ответов мутаций пространства он `0` — они отвечают вывеской, а не сводкой.

**200:**
```json
{
  "workspaces": [
    { "id": "019f…", "slug": "tI3WKsJ5R5", "name": "Личное пространство", "isPersonal": true,  "formCount": 12 },
    { "id": "019g…", "slug": "oV1wCDfWSp", "name": "Команда",             "isPersonal": false, "formCount": 3  }
  ]
}
```

### `POST /workspaces`
Создать пространство. Требует сессии и CSRF. Создатель становится его **владельцем** — он же плательщик, и он ровно один: пространство работает по плану своего владельца (ADR §10, фаза 18).

Подписка здесь не создаётся: субъект тарифа — аккаунт, и она у него уже есть с регистрации.

- **Тело:** `{ "name": string }` — 1–60 символов после обрезки пробелов.
- **201:** объект пространства (как в списке, `isPersonal: false`).
- **Ошибки:** `422 validation_failed` (пустое или слишком длинное имя); `402 plan_required` — лимит числа пространств у плана исчерпан. Лимит считает пространства, которыми аккаунт **владеет**: членство в чужом места не занимает.

### `PATCH /workspaces/{id}`
Переименовать пространство. Требует сессии и CSRF; право — `workspace.manage`, то есть **только владелец** (редактор получает `403`). Личное переименовывается наравне с остальными: «личное» — технический признак, а не запрет на вывеску.

- **Тело:** `{ "name": string }` — 1–60 символов после обрезки пробелов (та же проверка, что у создания).
- **200:** объект пространства (`formCount` в нём `0` — за числом форм идут в список).
- **Ошибки:** `422 validation_failed` (пустое или слишком длинное имя); `403 forbidden` (роль не даёт); `404 not_found` (пространства нет или спрашивающий не участник — существование чужого не раскрывается).

### `DELETE /workspaces/{id}`
Удалить пространство со всем содержимым. Требует сессии и CSRF; право — `workspace.delete`, то есть **только владелец** (редактор получает `403`).

Каскад БД уносит формы, их версии, ответы, визиты, участников и приглашения. **Файлы ответов сносятся из хранилища до строк** — иначе объекты остались бы в бакете без единой записи о них; сбой сноса отменяет удаление целиком.

- **204** — удалено. Восстановления нет.
- **Ошибки:** `422 validation_failed` — **личное пространство не удаляется** (человеку негде было бы жить); `403 forbidden` (роль не даёт); `404 not_found` (пространства нет или спрашивающий не участник).

### `POST /workspaces/{id}/invitations`
Пригласить человека в пространство. Требует сессии и CSRF; право — `member.manage`, то есть **только владелец** (редактор получает `403`).

- **Тело:** `{ "email": string, "role": "editor" }`. Владельцем пригласить нельзя (`422`): он ровно один, передача владения — отдельное действие.
- **204** — приглашение создано, письмо поставлено в очередь (одной транзакцией с токеном).
- Повторное приглашение тому же адресу **заменяет непринятое**: годной остаётся ровно одна ссылка, иначе отозвать приглашение было бы невозможно.
- **Ошибки:** `422 validation_failed` (кривой email, роль `owner`); `403 forbidden` (не владелец); `404 not_found` (пространства нет или спрашивающий не участник); `409 conflict` (человек уже в пространстве); `402 plan_required` (мест по тарифу больше нет); `429 rate_limited` — **ведро по пользователю**: это единственная ручка, отправляющая письмо на произвольный адрес, и без лимитера один аккаунт превращается в рассылку с нашего домена.

### `GET /workspaces/{id}/members`
Состав пространства. Требует сессии; право — `member.read` (видит и редактор).

**`402 workspace_frozen`** может прийти на любом эндпоинте пространства: тариф владельца больше не покрывает столько пространств (ADR §10). Заморожен только кабинет — **опубликованные формы продолжают принимать ответы**. Личное пространство не замораживается никогда; из дополнительных место занимают самые старые.

- **200:** `{ "members": [{ "userId", "email", "role", "joinedAt" }], "invites": [{ "email", "role", "expiresAt" }], "permissions": ["form.read", …] }`.
- `invites` (позвали, но ещё не вошёл) отдаётся **только тому, кто может ими управлять**: адреса позванных — не то, что нужно знать редактору. У редактора массив пуст.
- `permissions` — что может **спрашивающий** в этом пространстве. Кабинет прячет по нему кнопки и не дублирует матрицу прав в TypeScript.
- **Ошибки:** `404 not_found` (пространства нет или спрашивающий не участник).

### `DELETE /workspaces/{id}/members/{userId}`
Снять доступ участнику. Требует сессии и CSRF; право — `member.manage` (только владелец).

- **204** — доступ снят.
- **Ошибки:** `403 forbidden` (не владелец); `404 not_found`; `422 validation_failed` — **владельца снять нельзя ни чужой рукой, ни своей**: пространство без владельца не имеет плана. Сторож стоит в самом SQL-запросе, а не только в Go.

### `POST /workspaces/{id}/leave`
Выйти из пространства. Требует сессии и CSRF; доступно любому участнику, включая редактора.

- **204** — вышел.
- **Ошибки:** `404 not_found` (не участник — существование чужого пространства не раскрывается даже отказом); `422 validation_failed` (владелец выйти не может — та же причина, что выше).

### `GET /forms/{id}/integrations`
Всё, что рисует таб «Интеграции», одной поездкой (фаза 25): состояние аккаунта в пространстве формы и привязка самой формы. Требует сессии; право — `form.read` (кто видит форму и её ответы, тот вправе знать, куда они уезжают). Пространство формы резолвит сервер — кабинету не нужно узнавать его отдельным запросом.

- **200:**
  ```json
  {
    "workspaceId": "018f…",
    "account": { "enabled": true, "pickerEnabled": true,
                 "accounts": [ { "id": "018f…", "email": "автор@gmail.com",
                                 "needsReconnect": false,
                                 "connectedAt": "2026-08-23T10:00:00Z" } ] },
    "connections": [
      { "id": "018f…", "url": "https://docs.google.com/spreadsheets/d/…/edit",
        "accountId": "018f…", "accountEmail": "автор@gmail.com",
        "spreadsheetId": "1AbC…", "sheetId": 0,
        "enabled": true, "name": "Заявки с лендинга",
        "status": "live", "lastDeliveredAt": "2026-08-23T10:05:00Z" }
    ]
  }
  ```
- `account.enabled` — настроен ли провайдер **на контуре** (ключи в env). `false` означает «интеграции здесь нет вовсе» и это другой экран, чем «есть, но ничего не подключено»: путать их значит советовать нажать кнопку, которой не появится.
- `account.pickerEnabled` — настроено ли окно выбора файла на Диске (отдельный ключ на контуре). Интеграция работает и без него — просто без «выбрать свою таблицу».
- `account.accounts` — подключения **СПРАШИВАЮЩЕГО**, из них он выбирает в окне связки. Не «аккаунт пространства»: подключение принадлежит человеку (ADR §10), и в команде каждый видит здесь свои. Пустой список — состояние экрана, а не ошибка.
- `accounts[].needsReconnect` — подключение есть, но пользоваться им нельзя: refresh-токен не расшифровывается ключом контура (ротация `FORM_TOKEN_SECRET`). Лечение другое, чем у «аккаунта нет», — «подключите **заново**», и до этого не работает ни одна связка этого аккаунта, хотя её собственный `status` всё ещё `live`.
- `connections` — связки формы, **их сколько угодно**, в том числе в одну и ту же книгу: интеграция это правило доставки, а не состояние формы (ADR §10). Пустой список — состояние экрана, а не ошибка. `status` — `backfilling | live | broken`, при `broken` приходит `lastError` человеческим текстом; `enabled` — тумблер связки.
- `connections[].accountId` и `accountEmail` — каким подключением едет связка. Почта приходит и когда аккаунт **чужой** (его нет в `accounts` спрашивающего): в команде связку заводит один участник, а смотрит другой, и без подписи он увидит интеграцию, которой нет в его селекте.
- **Ошибки:** `404 not_found` (формы нет или спрашивающий не участник её пространства).

### `GET /integrations/google/accounts/{accountId}/spreadsheets`
Таблицы, куда можно положить ответы, — для окна настройки. Требует сессии; право — **принадлежность аккаунта спрашивающему**.

Адрес по аккаунту, а не по форме: аккаунт принадлежит человеку и пространства не знает вовсе (ADR §10, 2026-08-27). Прежний адрес `/forms/{id}/integrations/google/spreadsheets` под `integration.manage` отменён вместе с этим правом.

Под scope `drive.file` это **только файлы, созданные нами**: чужие документы Диска в список не попадают и попасть не могут. Список не ограничен пространством и ограничен быть не может — но он **свой собственный**, и раскрывать в нём человеку нечего.

- **200:** `{ "spreadsheets": [{ "id": "1AbC…", "name": "Заявки" }] }`.
- **Ошибки:** `422 validation_failed` — аккаунта нет **либо он чужой** (случаи неразличимы снаружи: иначе перебором id можно узнать, что подключено у соседа); `404 not_found` (провайдер не настроен на контуре).

### `GET /integrations/google/accounts/{accountId}/sheets?spreadsheetId={id}`
Листы выбранной книги — второй шаг выбора («положить в существующий лист или завести новый»). Требует сессии; право — принадлежность аккаунта: книга лежит в его Диске.

Книга приезжает **параметром, а не сегментом пути**: её id — чужая строка произвольного вида, и в пути он требовал бы экранирования на каждом клиенте.

- **200:** `{ "sheets": [{ "id": 0, "title": "Лист1" }] }`. `id` — gid листа; у первого листа книги он **равен нулю**, поэтому «не выбрано» на клиенте — это отсутствие значения, а не ноль.
- **Ошибки:** `422 validation_failed` (книга не названа либо аккаунт не ваш); `404 not_found`.

### `GET /integrations/google/accounts/{accountId}/picker`
Учётные данные окна выбора файла на Диске (Google Picker). Требует сессии; право — **принадлежность аккаунта спрашивающему**. Есть, только если на контуре задан `GOOGLE_PICKER_API_KEY`, иначе `404`.

- **200:** `{ "accessToken": "ya29…", "developerKey": "AIza…", "appId": "442272803444" }`, `Cache-Control: no-store`.
- **`accessToken` — живой токен Google**, единственное место, где он уезжает в браузер: окно выбора рисует сам Google. Живёт час, scope `drive.file`. Ручка отдельная и дёргается по нажатию кнопки — токен не лежит в состоянии экрана. Плата и смягчения — ADR §10; **смягчение усилилось** переездом на личные аккаунты: токен выдаётся только на СВОЙ аккаунт, и «прочитать чужие таблицы ответов» стало невозможным по модели, а не по роли.
- **Ошибки:** `422 validation_failed` (аккаунта нет либо он чужой); `404 not_found` (окно выбора не настроено на контуре).

### `POST /forms/{id}/integrations/google`
Завести таблицу для формы и привязать её. Требует сессии и CSRF; право — **`form.write`** (то есть и редактор): решение «вывозить ли ответы наружу» уже принято владельцем при подключении аккаунта, а выбрать, для какой формы завести таблицу, вправе тот, кто эти формы правит.

**Тело обязательно:** `accountId` подразумевать нечем — аккаунтов у человека сколько угодно, и «первый попавшийся» отправил бы ответы не в тот Диск молча.

```json
{ "accountId": "018f…", "name": "Заявки с лендинга", "spreadsheetId": "", "sheetId": null, "backfill": true }
```

- `accountId` — **обязателен**, и аккаунт обязан принадлежать спрашивающему. Чужой неотличим от несуществующего: один и тот же `422`, иначе перебором id можно узнать, что подключено у соседа.
- `name` — необязательная подпись связки, до 80 символов (валидируется на бэке независимо от фронта).
- `spreadsheetId` пуст — заводим **новую книгу**; иначе работаем в выбранной (её id — из списка выше либо из окна выбора на Диске).
- `sheetId` — существующий лист книги; отсутствует или `null` — **завести новый лист**. Существующий годится, только если его **первая строка свободна**: шапка ложится в A1, и затирать чужую работу продукт не станет — иначе `422` с человеческим текстом и предложением создать новый лист.
- `backfill` — переносить ли уже накопленные ответы. `false` — связка сразу `live`, история не едет.

Таблицу создаёт продукт (scope `drive.file`, ADR §10) и сразу пишет в неё шапку — колонки те же, что у выгрузки CSV: метаколонки `_id`, `_submitted_at`, `_form_version`, затем вопросы в порядке общей модели. Значения кладутся режимом `RAW`: `USER_ENTERED` исполнил бы `=…` из подписи вопроса формулой в чужой таблице.

- **201:** `{ "id": …, "url": …, "enabled": true, "name": …, "status": "backfilling" }` — при включённом переносе сразу после привязки идёт **перенос уже накопленных ответов**: таблицу создали мы и она пуста, а пустая таблица после подключения читается как «не заработало». Отсечка переноса — момент привязки: всё, что придёт после, доставляет живая очередь, и границы не пересекаются. Новые ответы ждут в очереди, пока перенос не кончится, — иначе они легли бы в лист поверх старых.
**Повторный вызов заводит ЕЩЁ ОДНУ связку**, в том числе в ту же книгу: одну форму льют и в рабочую таблицу, и в архивную (ADR §10).

- **Ошибки:** `422 validation_failed` — аккаунт не назван, не ваш или не существует, либо выбранный лист не пустой (шапка ложится в A1, и затирать чужую работу продукт не станет); `403 forbidden`; `404 not_found` (формы нет, не участник **либо провайдер не настроен на контуре**).

### `PATCH /forms/{id}/integrations/{connectionId}`
Правка связки: подпись и тумблер. Требует сессии и CSRF; право — `form.write`.

```json
{ "name": "Архив", "enabled": false, "accountId": "018f…", "spreadsheetId": "1AbC…", "sheetId": 0, "backfill": false }
```

- **204** — записано. `enabled` не назван — связка остаётся включённой: правка подписи не должна исподтишка что-то выключать.
- `spreadsheetId` **отсутствует в теле — цель не трогаем вовсе** (так шлёт тумблер из списка). Присутствует и отличается от текущей — связка **переезжает**: в новом листе пишется шапка, колонки собираются заново, при `backfill: true` начинается перенос. Строки, уже доставленные в прежний лист, остаются там — убирать за человеком в его же таблице продукт не станет.
- `accountId` едет **вместе с целью** и отдельно от неё смысла не имеет: под scope `drive.file` таблица видна только своему аккаунту, поэтому «сменить аккаунт, оставив лист» — это запись чужим токеном в невидимый ему файл. Не назван либо совпал с текущим — связка остаётся на своём аккаунте; отличается — обязан принадлежать спрашивающему.
- **Связку, заведённую коллегой, править можно** (право — `form.write`): требование «аккаунт мой» относится только к СМЕНЕ аккаунта. Иначе участник не смог бы даже переименовать связку, которую экран ему штатно показывает.
- Владелец аккаунта, которым едет связка, обязан **оставаться участником** пространства формы: иначе `422` — операция пошла бы его токеном в его Диск.
- **Выключенная связка сохраняет таблицу, колонки и историю** — «выключить на время» и «удалить навсегда» разные намерения. Новые ответы ей не доставляются и событий для неё не заводится вовсе.
- **Ошибки:** `422 validation_failed` (подпись длиннее 80 символов); `403 forbidden`; `404 not_found` — связки нет **либо она принадлежит другой форме**: id из адреса правом доступа не является, и оба случая неразличимы снаружи.

### `POST /forms/{id}/integrations/{connectionId}/refill`
Перезалить лист одной связки с нуля. Требует сессии и CSRF; право — `form.write`.

Чистит **значения** листа (формат, ширина колонок и закрепление шапки, которые настроил автор, остаются), пишет свежую шапку по сегодняшней форме и переносит все ответы заново. Это лечение всего, что накопилось: дубль после ретрая (доставка at-least-once, ADR §10), строки, удалённые автором руками, колонки, отставшие от формы, интеграция, простоявшая сломанной.

Это лечение всего, что накопилось, **и единственный выход** из раскладки, за которой мы перестали следовать (`INTEGRATIONS.md` §8). Кнопка есть в окне настройки связки, рядом с её состоянием.

- **202** — перенос начат: он идёт пачками в фоне, и экран показывает его статусом `backfilling`.
- **Ошибки:** `403 forbidden`; `404 not_found` — связки нет либо она чужой формы; `422 validation_failed` — владелец аккаунта, которым едет связка, больше не участник пространства (перезалив пошёл бы его токеном в его Диск).

### `DELETE /forms/{id}/integrations/{connectionId}`
Удалить одну связку. Требует сессии и CSRF; право — `form.write`.

- **204** — удалено. Соседние связки этой формы не затронуты.
- **Ошибки:** `404 not_found` — связки нет либо она чужой формы (неразличимо снаружи).
- **Сама таблица и её строки остаются** в Диске автора: продукт не удаляет чужие файлы — ни за человека, ни «прибираясь».

### `GET /integrations/google/start?accountId={id}`
Начать подключение аккаунта Google. Требует сессии; **прав пространства не спрашивает** — человек подключает свой аккаунт, и гейт по роли здесь был бы пуст (личное пространство есть у каждого, и в нём каждый владелец). Это не JSON-ручка, а **навигация**: отвечает `302` на экран согласия Google и ставит две HttpOnly-cookie на 15 минут — `integration_state` (state + PKCE-verifier) и `integration_intent` (подписанное «кто начал»).

Кто начал, едет подписанной cookie, а не параметром колбэка: параметр означал бы, что жертву можно заманить пройти согласие и подключить её Google к аккаунту атакующего.

- `accountId` **необязателен**. Без него это «подключить ещё один аккаунт»: Google показывает свой выбор. С ним — «переподключить»: сервер берёт почту названного аккаунта и передаёт её провайдеру подсказкой `login_hint`, чтобы человек попал сразу в нужный. Адрес и обработка возврата у обоих путей общие, вся разница в подсказке.
- **302** — на `accounts.google.com`. Scope: `openid`, `email`, `drive.file`; `access_type=offline`, `prompt=consent`.
- **Ошибки:** `422 validation_failed` — названный аккаунт не ваш или не существует (подсказка несёт **почту**, и отдавать её по перебору id нельзя); `404 not_found` (провайдер не настроен на контуре).

### `GET /integrations/google/callback`
Возврат из окна согласия Google. **Без сессии и без CSRF** — сюда браузер приходит по редиректу провайдера; доказательство намерения — подписанная cookie, а право на пространство сервис проверяет заново.

Отвечает всегда `302` на `/oauth/done?r=<исход>` в кабинете — тот же служебный экран отдельного окна, что у входа. JSON-ошибку сюда отдавать нельзя: человек остался бы на origin API без пути назад. Исходы: `integration_ok`, `integration_denied` (отклонил согласие, снял галочку Диска или провайдер не отдал refresh-токен), `integration_expired` (cookie истекла, state не сошёлся), `integration_forbidden` (право отобрали, пока он ходил), `integration_failed` (сбой; причина — в логе).

### `DELETE /integrations/google/accounts/{accountId}`
Отключить ОДИН свой аккаунт Google. Требует сессии и CSRF; право — **принадлежность аккаунта спрашивающему** (фильтр по `user_id` стоит в самом SQL). Связки, которые им ехали, уносит каскад БД — во всех формах и пространствах разом, иначе форма осталась бы «привязанной» к таблице, писать в которую больше нечем; **сами таблицы и их строки остаются** у автора. Соседние аккаунты не затронуты.

**Входа в интерфейсе у ручки нет** (решение владельца 2026-08-27): окно настройки одной связки не место для действия такого масштаба, её место — экран аккаунта ([`BACKLOG.md`](BACKLOG.md)).

- **204** — отключено. Идемпотентно: отключать нечего (или аккаунт чужой, что снаружи неотличимо) — тоже `204`.
- Отзыв согласия на стороне Google — **best effort**: недоступный провайдер не запирает человека в подключении, которое он разрывает. Неудача уходит в лог.
- **Ошибки:** `403 forbidden`; `404 not_found`.

### `GET /invitations/{token}`
Что за приглашение — **без сессии**: аккаунта у приглашённого может ещё не быть, а понять, куда его зовут, он должен до регистрации. Право здесь — сам токен.

- **200:** `{ "workspaceName": "Команда", "email": "bob@example.com", "role": "editor", "state": "usable" }`. `state` — `usable | used | expired`.
- **Ошибки:** `404 not_found` (такого токена нет).

Ни id пространства, ни состав участников до принятия не отдаются: пока приглашение не принято, человек посторонний.

### `POST /invitations/{token}/accept`
Принять приглашение. Требует сессии и CSRF.

- **200:** объект пространства (как в списке).
- **Ошибки:** `403 forbidden` — ссылка открыта не тем адресом (переслать письмо можно кому угодно, поэтому «тот ли это человек» проверяет сервер); `410 link_expired` — по ссылке уже вошли либо вышел срок (различать эти два случая незачем: действие одно — попросить новую); `404 not_found` (нет такого токена); `402 plan_required` — мест в пространстве больше нет. **Места проверяются и здесь, а не только на выписке:** гейт считает участников, а не выписанные приглашения, поэтому несколько приглашений проходят по одному свободному месту.

### `GET /workspaces/{id}/entitlements`
Снимок тарифа пространства (фаза 17): текущий план, лимиты, расход за период и дата обнуления. Требует сессии; право — `billing.view`, **то есть только владелец** (редактор получает `403`: тариф — не его дело). Не участник получает `404` — существование чужого пространства не раскрывается (инвариант 1).
- **200:**
  ```json
  {
    "planCode": "free",
    "planTitle": "Бесплатный",
    "periodEnd": "2026-09-01",              // когда обнулится расход (первое число, МСК)
    "features": [
      { "key": "submissions_per_month", "title": "Ответов в месяц",
        "kind": "quota",  "allowed": true, "used": 87, "limit": 100 },
      { "key": "analytics_funnel", "title": "Воронка отвала",
        "kind": "toggle", "allowed": false, "used": 0, "limit": null }
    ]
  }
  ```
  - `limit: null` — **безлимит**, и это не то же самое, что `0`: ноль запрещает всё.
  - `kind` различает два вида: `quota` (число, есть `used`) и `toggle` (да/нет, `used`/`limit` не заполняются).
  - Порядок `features` стабилен и задаётся каталогом возможностей в коде (`internal/entitlements`), а не обходом карты.
  - Аккаунт-уровневые возможности (сегодня — число воркспейсов) в снимок **не входят**: их разрешает план личного воркспейса-якоря, и показывать их здесь значило бы врать.
- **Ошибки:** `404 not_found` (не член / нет воркспейса / кривой id).

## Формы — `/api/v1/forms`

Все эндпоинты требуют сессии; мутации — ещё и CSRF. Каждый по ресурсу проверяет членство в воркспейсе формы: чужая или несуществующая форма → `404 not_found`.

Объект формы (`Form`):

```json
{
  "id": "019f…",
  "name": null,                      // внутреннее имя для дашборда | null
  "title": "Опрос клиентов",
  "slug": "59LfFK0F4X",
  "status": "draft",                 // draft | published | closed
  "createdAt": "2026-07-11T18:33:43.335082+03:00",
  "updatedAt": "2026-07-11T18:33:43.335082+03:00",
  "publishedVersion": null,          // номер опубликованной версии | null
  "publishedVersionId": null,        // id опубликованной версии | null
  "hasUnpublishedChanges": false,    // черновик разошёлся с опубликованной версией
  "submissionCount": 0,              // число ответов формы (счётчик на карточке)
  "visitCount": 0,                   // просмотры формы (фаза 8.5 шаг 6)
  "visitSubmittedCount": 0           // из них закончились ответом
}
```

`name` vs `title` (ADR §10): **`title`** — публичный заголовок формы, его видит респондент (`<h1>`, OG-мета). **`name`** — внутреннее имя для дашборда кабинета; `null` = не задано, тогда кабинет показывает `title` (фолбэк). Дубликат и переименование на дашборде меняют `name`, публичный заголовок не трогают.

`publishedVersion`/`publishedVersionId` — `null`, пока форму не публиковали. После `closed` сохраняются (кабинет показывает «была версия N»).

`hasUnpublishedChanges` — `true`, когда черновик формы отличается от опубликованной версии (сравнение `draft_schema` со снапшотом; переименование, не входящее в версию, его не поднимает). **Точен на `GET /forms/{id}` и `GET /forms`;** в ответах мутаций (create/publish/unpublish/rename) всегда `false` — актуальное значение кабинет берёт из `GET`.

`submissionCount` — число ответов формы. **Точен на `GET /forms/{id}` и `GET /forms`;** в ответах мутаций всегда `0` (карточка обновляется из списка).

`visitCount`/`visitSubmittedCount` — просмотры формы и сколько из них закончились ответом (фаза 8.5 шаг 6). Точность та же, что у `submissionCount`. **Конверсия считается как `visitSubmittedCount / visitCount`, а не делением `submissionCount` на `visitCount`:** это разные множества — ответ мог прийти без визита (бикон не дошёл, страница из кэша прежней версии рендерера), и частное двух независимых счётчиков конверсией не является (ADR §10). Поэтому на карточке «M ответов» — это `submissionCount` (то же число, что в таблице ответов), а процент — по визитам.

### `GET /forms`
Список форм пространства, свежие правки сверху. Курсорная пагинация.
- **Параметры:** `cursor?`, `limit?` (1–100, дефолт 50), `q?`, `sort?`, `workspaceId?`.
- `workspaceId` — в каком пространстве смотрим. **Отсутствует = личное** (так работают ссылки, не знающие про параметр). Чужое пространство неотличимо от несуществующего: `404`, не `403` — id в запросе правом доступа не является (инвариант 1). Не-uuid → `422`, а не молчаливый откат к личному.
- `q` — поиск по **отображаемому** имени (`name ?? title` — ровно то, что видно на карточке), подстрокой, без учёта регистра. Спецсимволы `%`/`_`/`\` экранируются сервером и ищутся как обычные символы. Длиннее 200 символов → `422` (столько же, сколько потолок названия формы).
- `sort` — порядок: `updated` (дефолт, по последней правке), `created` (по дате создания), `responses` (по числу ответов). Неизвестное значение → `422`.
- **Курсор непрозрачен и несёт в себе порядок, которым выдан.** Листать с ним другую сортировку нельзя (`422 validation_failed`): ключ курсора у разных порядков измеряет разные величины, и молча перемешанная выдача с пропусками хуже явной ошибки. Смена `sort` или `q` = листание с первой страницы (без `cursor`).
- **200:**
  ```json
  { "forms": [ /* Form */ ], "nextCursor": "eyJ…" }   // nextCursor: string | null
  ```
- **Погрешность `sort=responses` при листании:** ключ этой сортировки — счётчик, который меняется между запросами страниц, поэтому форма, получившая ответы посреди листания, может выпасть из выдачи (её ключ перепрыгнул курсор). Детали и почему это пока не чинится — `SCHEMA.md`.
- **Ошибки:** `422 validation_failed` (неизвестный `sort`; неверный курсор; курсор от другой сортировки; `q` длиннее 200 символов).

### `POST /forms`
Создать форму с пустым черновиком (`{"blocks":[]}`).
- **Тело:** `{ "title"?: string, "workspaceId"?: string }` (title ≤200 символов; пусто/нет тела → `"Untitled form"`). `workspaceId` отсутствует = личное пространство.
- **201:** объект `Form`.
- **Ошибки:** `422 validation_failed` (title длиннее лимита; `workspaceId` не uuid); `404 not_found` — пространство чужое или не существует.

### `GET /forms/{id}`
Форма целиком, включая черновик схемы и настройки закрытия.
- **200:** `Form` + `draftSchema` (JSON черновика) + `closeAt` (ISO-строка или `null`), `responseLimit` (число или `null`), `closedMessage` (строка или `null`) — живые настройки закрытия (фаза 8.5 шаг 4) + `notifyOnSubmission` (boolean, слайс D) + `collectPartial` (boolean) — тумблер сбора незавершённых ответов + `linkPreview` (объект `{siteName, title, description, imageKey, iconKey}` или `null`) — своя карточка ссылки. Отдаётся **независимо от тарифа**: окно кастомизации показывает сохранённое всем, а применяет карточку к публичной странице тот, кто её отдаёт.
- **Ошибки:** `404 not_found`.

### `GET /forms/lookup?slug={slug}`
То же, что `GET /forms/{id}`, но форма адресована коротким `slug` (query-параметр) вместо UUID. Кабинет так адресует форму в URL редактора/ответов/шаринга (`/forms/{slug}/edit`), как публичный рендерер — `/r/{slug}`; `slug` глобально уникален и стабилен. Права даёт только членство в воркспейсе формы, не сам `slug`: чужая/несуществующая форма → `404` (существование не раскрывается). UUID (`id`) для последующих мутаций берётся из ответа. `slug` в query, а не в пути: путь `/forms/by-slug/{slug}` конфликтовал бы в net/http-mux с `/forms/{id}/submissions`.
- **200:** `Form` + поле `draftSchema` (идентично `GET /forms/{id}`).
- **Ошибки:** `404 not_found` (нет формы/доступа, либо пустой `slug`).

### `PATCH /forms/{id}`
Переименование, автосейв черновика схемы, настройки закрытия, тумблер уведомлений, тумблер сбора незавершённых **или** карточка ссылки. Требует CSRF. За один запрос меняется **ровно одно** из `name`/`draftSchema`/`closeSettings`/`notifyOnSubmission`/`collectPartial`/`linkPreview`.

**Публичного заголовка (`title`) здесь больше нет** (фаза 15): он стал блоком документа (`form_title`) и приезжает внутри `draftSchema`, а колонку `forms.title` сервер пишет зеркалом. Вторая точка записи того же значения означала бы расхождение колонки с документом. Название при **создании** формы (`POST /forms {title}`) осталось — у документа в этот момент ещё нет ни одного блока.

- **`{ "name": string }`** — внутреннее имя для дашборда (переименование в кабинете; ≤200 символов). Публичный заголовок не трогает. Пустая строка (после trim) **сбрасывает** имя в `null` (кабинет снова показывает `title`).
- **`{ "draftSchema": <схема>, "updatedAt": string }`** — автосейв билдера. `draftSchema` — документ формы (контракт — `docs/SCHEMA.md`), проходит строгую валидацию `ValidateSchema` и пишется канонизированным. **Наружу схема всегда уходит в текущей версии формата** (`CanonicalV4`): документы v1/v2/v3 из БД апгрейдятся на чтении, фронт про старые версии не знает. В черновике кабинета сервер вдобавок **синтезирует блок заголовка** из колонки `forms.title`, если документ его ещё не несёт (фаза 15). `updatedAt` **обязателен**: значение, полученное в последнем ответе по форме; сервер обновляет строку, только если оно совпадает с текущим (оптимистичная блокировка).
- **`{ "closeSettings": { "closeAt": string|null, "responseLimit": number|null, "closedMessage": string } }`** — живые настройки закрытия (фаза 8.5 шаг 4), **полный набор** (отсутствующее/пустое поле = ограничение снято), не частичный патч. `closeAt` — ISO-момент или `null`; `responseLimit` — целое `> 0` или `null`; `closedMessage` ≤2000 рун (пусто → дефолт рендерера). Живут в колонках `forms`, не в схеме, поэтому публикации не требуют. Оптимистичной блокировки нет.
- **`{ "notifyOnSubmission": boolean }`** — тумблер письма владельцу о новом ответе (слайс D). Живая колонка, применяется немедленно.
- **`{ "collectPartial": boolean }`** — тумблер сбора незавершённых ответов. Живая колонка. **Включение требует платного тарифа** (`402 plan_required`) — единственный гейт продукта, стоящий на СБОРЕ, а не на показе (ADR §10); выключение доступно всегда, на любом плане: запрет остановить сбор данных о людях был бы дефектом. Право спрашивается ещё раз при отдаче публичной формы, поэтому даунгрейд останавливает сбор, не дожидаясь владельца.

- **`{ "linkPreview": {siteName, title, description, imageKey, iconKey} }`** — своя карточка ссылки. Полный набор, не частичный патч: пустая строка = «вернуть дефолт», карточка из пустых строк стирает настройку (в колонке `NULL`). Живая, применяется немедленно. **402 здесь не бывает:** сохранять карточку вправе любой тариф, а право её применить спрашивается при отдаче `/r/{slug}` (ключ `form_link_preview`) — тот же приём, что у бейджа. Ключи картинок приходят из `POST /forms/{id}/media` с `purpose=preview` и `purpose=icon`.

- **200:** обновлённый `Form` (в т.ч. новый `updatedAt` — использовать как токен для следующего сохранения). У `closeSettings` и `notifyOnSubmission` ответ — `Form` без самих настроек (их читают `GET /forms/{id}`; кабинет патчит кэш детали из отправленного).
- **Ошибки:** `404 not_found`; `409 conflict` (устаревший `updatedAt`); `422 validation_failed` (длинное name; невалидная схема — в т.ч. `redirectUrl` не абсолютный `http(s)`, единственное поле схемы, которое строго проверяется и в черновике; сломанная ФОРМА правила условной логики — пустое условие, неизвестный оператор, неизвестное действие, действие без цели, `logic` у блока не того типа (сами ссылки правил при этом не проверяются — неразрешимое действие инертно, `SCHEMA.md`); `draftSchema` без `updatedAt`; `responseLimit ≤ 0`; длинный `closedMessage`; больше одного поля сразу или ни одного).

### `DELETE /forms/{id}`
Удаление формы (каскадно уносит версии и, позже, ответы). Требует CSRF.
- **204** без тела.
- **Ошибки:** `404 not_found`.

### `POST /forms/{id}/duplicate`
Дубликация формы: создаёт новую форму в том же воркспейсе с копией черновика (`draft_schema`) исходной и новыми `id`/`slug`. **Публичный заголовок (`title`) копируется дословно** (остаётся чистым), а суффикс `«(копия N)»` уходит во **внутреннее имя (`name`)**: база — отображаемое имя оригинала (`name ?? title`) без старого хвоста `(копия…)`, `N` подбирается без коллизий по соседям воркспейса («(копия)», «(копия 2)», …), длинная база обрезается по рунам под 200 символов. Копия **всегда `draft`** — публикация исходной не переносится. Требует CSRF, тела нет.
- **201:** объект `Form` новой формы (`status: "draft"`, `name` = «(копия N)», `title` — как у оригинала).
- **Ошибки:** `404 not_found` (нет формы или доступа).

### `POST /forms/{id}/publish`
Публикация: одной транзакцией снимает иммутабельный снапшот текущего черновика в новую версию (`version = max+1`, счёт с 1), переводит форму в `published` и привязывает эту версию. Черновик перед снапшотом валидируется `ValidateSchema` — и только: **гейта публикации нет** (ADR §10, решение владельца 2026-07-31), недособранная форма публикуется как есть, а безымянный вопрос получает сгенерированное имя. Повторная публикация (в т.ч. после `closed`) даёт следующий номер версии. Требует CSRF, тела нет.
- **200:** обновлённый `Form` (`status: "published"`, `publishedVersion`/`publishedVersionId` заполнены).
- **Ошибки:** `404 not_found`; `422 validation_failed` (черновик не проходит `ValidateSchema`); `402 plan_required` — в черновике есть **свои значения оформления** (цвета, шрифт, лэйаут, контур, кнопка), а тариф воркспейса их не даёт (ключ `form_design_custom`, фаза 22). Сообщение перечисляет мешающее. Гейта на СОХРАНЕНИИ нет намеренно: автосейв не имеет права вернуть 402 посреди набора — черновик со своими цветами сохраняется на любом тарифе. Тема (светлая/тёмная) и намерение снять бейдж публикацию не держат.

### `POST /forms/{id}/unpublish`
Снятие с публикации: `status='closed'`. `publishedVersion`/`publishedVersionId` **сохраняются** (последняя опубликованная версия). Требует CSRF, тела нет.
- **200:** обновлённый `Form` (`status: "closed"`).
- **Ошибки:** `404 not_found`.

### `POST /forms/{id}/media`
Загрузка автором картинки формы — блока `image`, обложки, логотипа, а также картинки и иконки карточки ссылки (docs/design/s3-media.md). Тело — `multipart/form-data` с полями `file` и необязательным `purpose`. Доступ по членству в воркспейсе формы; ключ картинки неймспейсится этим воркспейсом. Сервер сниффит тип по контенту (**PNG/JPEG**, не по заголовку), гардит площадь (≤ 24 Мпикс), пере-кодирует картинку (снос EXIF/GPS), кладёт в public-read бакет и возвращает стабильный контент-адресный ключ. Байты картинки в БД не попадают. Требует CSRF. Лимит тела — 5 МиБ.
- **`purpose`** — назначение картинки: `block` (дефолт, отсутствие поля читается так же), `cover`, `logo`, `preview`, `icon`. Влияет **ровно на потолок ширины** при нормализации: 1400 / 2000 / 512 / 1200 / 256 — обложка тянется во всю ширину окна, а не колонки, логотип рисуется ~72 CSS-px, а карточку ссылки показывает чужой клиент в каноне площадок (1200×630, значок 16–32 px). Хранилище от назначения не зависит (тот же бакет, тот же контент-адресный ключ), поэтому одна и та же картинка под разными назначениями даёт разные объекты — у них разное содержимое. Неизвестное значение → `422`, а не молчаливый откат к `block`: опечатка означала бы обложку, ужатую до ширины колонки, и заметили бы её глазами через неделю.
- **201:** `{ "imageKey": "<workspaceId>/<sha256>.png" }` — ключ пишется в `settings.imageKey` блока (или в `cover.imageKey`/`logo.imageKey` документа) при автосохранении схемы; у карточки ссылки — в `linkPreview.imageKey`/`iconKey` через `PATCH /forms/{id}`. Публичный URL картинки кабинет/рендерер собирают из базы раздачи (`MEDIA_BASE_URL`, шаг раздачи) + ключ.
- **Ошибки:** `404 not_found` (нет формы или доступа); `422 validation_failed` (не PNG/JPEG, битый файл, превышение площади, нет поля `file`, неизвестный `purpose`); `413` (тело больше 5 МиБ).

### `GET /files/{id}`
Скачивание файла, приложенного респондентом к ответу (фаза 24 `DEV-PLAN`). Требует
сессии; право резолвится **от формы, к которой файл приложен** (членство в её
воркспейсе) — чужой файл отвечает `404`, а не `403`.
- **302** на короткую (60 с) подпись хранилища. Байты через наш процесс не идут ни в
  одну сторону. Подпись переопределяет заголовки выдачи: `Content-Disposition:
  attachment` и `application/octet-stream`, поэтому файл **скачивается**, а не
  открывается — чужой HTML в origin хранилища исполниться не может. Ответ несёт
  `Cache-Control: no-store`: адрес в `Location` — учётные данные.
- **Адрес по файлу, а не по форме и ответу** намеренно: совпадение id в URL правом
  доступа не является, и лишние сегменты дали бы второй, ничего не проверяющий
  источник той же правды.
- **Ошибки:** `404 not_found` (нет файла, файл незаявлен или нет доступа к его форме);
  `401` (нет сессии).

### `GET /forms/{id}/submissions`
Строки раздела «Ответы» для автора формы: новые сверху. Требует сессии; проверяет членство в воркспейсе формы (чужая/несуществующая → `404`).
- **Параметры:** `kind?` (`completed` — умолчание, только отправленные; `all` — отправленные И незавершённые одним списком, вкладка «Все ответы»), `cursor?`, `limit?` (1–100, дефолт 50).
- **Курсор непрозрачен, и внутри он РАЗНЫЙ:** у `completed` — одноколоночный по `id` (UUIDv7 монотонен по времени), у `all` — составной `(время, id)`, потому что склеены два множества с разными id. Парсер выбирается тем же `kind`, что и выборка, поэтому курсор одной вкладки на другой → `422`.
- **200:**
  ```json
  {
    "submissions": [
      {
        "kind": "submission",                 // "submission" | "partial"
        "id": "018f…",                        // UUIDv7 ответа (у черновика — id ВИЗИТА)
        "formVersion": 2,                     // номер версии формы, по которой отправлен
        "createdAt": "2026-07-12T10:00:00Z",
        "answers": { "b1": "Анна", "b7": ["o1","o2"] }
      },
      {
        "kind": "partial",                    // незавершённый — только при kind=all
        "id": "018f…",
        "formVersion": 2,
        "createdAt": "2026-07-12T10:03:00Z",  // когда начали заполнять
        "updatedAt": "2026-07-12T10:04:31Z",  // последняя правка; ТОЛЬКО у черновика
        "lastBlockId": "b7",                  // где остановились; только у черновика
        "answers": { "b1": "Анна" }
      }
    ],
    "nextCursor": "MDE4Zg…",                  // string | null (null на последней странице)
    "total": 137,                             // сколько ответов ВИДНО (сверхлимитные не в счёте)
    "hidden": 3                               // скрыто квотой тарифа; 0 у всех, кто в лимит уложился
  }
  ```
  - `answers` — карта `block_id → значение`, как её прислал респондент (без резолва в подписи опций — это делает CSV-экспорт). `meta` (user_agent/referer) не отдаётся — она для антиспама.
  - `hidden` (фаза 17) — ответы, пришедшие сверх квоты тарифа (`submissions.over_quota`). Они **сохранены**, но не попадают ни в выдачу, ни в `total`, ни в CSV-экспорт, ни в сводку, ни в счётчик на карточке формы; кабинет показывает по этому числу плашку. Приём ответов квота не закрывает — респондент не знает о тарифе (ADR §10).
- **Ошибки:** `404 not_found` (нет формы/не член воркспейса); `422 validation_failed` (битый `cursor`).
- **`kind=all` подмешивает незавершённые, ТОЛЬКО пока форма их собирает** (тумблер `collect_partial` плюс право `submissions_partial`) — тем же вопросом, каким это решается при отдаче публичной формы. Иначе вкладка показывала бы то, что прячет соседняя: у формы со снятым тумблером черновики лежат в базе до чистки. Гейта на самой ленте поэтому нет — без права подмешивать нечего, и `all` вырождается в `completed`.
- **Порядок ленты — по «последней активности»:** у ответа это отправка (`created_at`), у черновика — последняя правка (`updated_at`), то самое, что стоит в колонке даты. Реализация — `UNION ALL` двух выборок, у каждой свой индекс и свой `LIMIT`; `total` = видимые ответы плюс черновики, `hidden` черновиков не касается (в квоту они не входят).

### `GET /forms/{id}/submissions/export`
Экспорт ответов формы в CSV (**только отправленные: незавершённые в выгрузку не входят вовсе, спека §10.5; и кроме скрытых квотой тарифа** — как и таблица, см. `hidden` выше) (обычная навигация браузера — cookie авторизует, файл скачивается). Требует сессии; проверяет членство в воркспейсе (чужая/нет формы → `404`). Ответ стримится порциями, без буферизации всей выборки в памяти.
- **200:** `text/csv; charset=utf-8`, `Content-Disposition: attachment; filename="submissions-{id}.csv"`. Тело начинается с UTF-8 BOM (Excel читает кириллицу).
  - **Колонки:** `ID ответа`, `Отправлен` (RFC3339 UTC), `Версия формы`, далее вопросы — **объединение блоков по всем опубликованным версиям**: сначала блоки свежей версии в её порядке, затем «выбывшие» вопросы старых версий (вопрос, удалённый в v2, остаётся колонкой для ответов v1). Подпись колонки — из самой свежей версии, где блок есть.
  - **Ячейки:** значение ответа как текст; `single_choice` — **подпись** выбранной опции, `multi_choice` — подписи через `; `. Подпись берётся из версии, по которой отправлен ответ (переименование опции в новой версии не искажает старые ответы). Блок, которого нет в версии ответа, — пустая ячейка.
  - Форма без опубликованных версий → валидный CSV с одной строкой заголовка (только метаколонки).
- **Ошибки (до начала стрима):** `404 not_found`. После начала тела статус уже `200` — обрыв (отмена клиентом, ошибка записи) логируется на сервере, файл обрывается.

### Окно наблюдения — общий параметр экранов аналитики

Шесть ручек (`insights`, `insights/visits`, `submissions/count`, `submissions/summary`, `submissions/summary/{block}`, `funnel`) принимают
пару `?from=&to=` (RFC 3339). Интервал **полуоткрытый** `[from, to)`: строка, пришедшая ровно
в `to`, принадлежит следующему периоду, а не обоим сразу. Отсутствие обоих параметров —
«всё время»; отсутствие одного — граница только с другой стороны. `from` не раньше `to`,
иначе `422 validation_error`; будущие даты законны (владелец имеет право спросить про завтра
и получить пустой экран, а не ошибку).

**Ответы и визиты режутся каждый по своему времени** — это два независимых множества
(`ANALYTICS.md` §1), и «привязать ответ к периоду его визита» означало бы третье множество,
которого в данных нет.

Экспорт CSV периодом **не режется** намеренно: это документ «все ответы формы», и молчаливое
урезание окном экрана владелец обнаружил бы уже в чужой таблице.

### `GET /forms/{id}/insights`
Карточки над вкладками раздела «Аналитика» в части **визитов** (спека `design/analytics-tally.md` §5). Требует сессии; проверяет членство в воркспейсе (чужая/нет формы → `404`). **Тарифом не гейтится:** «сколько людей пришло» — первый экран после публикации, замок на нём рекламировал бы Pro вместо продукта.
- **200:**
  ```json
  {
    "visits": 187,               // визитов за период
    "submitted": 12,             // из них закончившихся ответом
    "uniqueVisitors": 96,        // разных посетителей (суточный ключ)
    "timedCompletions": 11,      // визитов с ответом, вошедших в медиану ниже
    "completionDurationSec": 96, // медиана длительности ЗАВЕРШЁННОГО заполнения
    "timedVisits": 130,          // сколько визитов вошло в медиану
    "medianDurationSec": 42.5    // медианная длительность визита
  }
  ```
  - **Числа про ответы сюда не входят** — их отдаёт `submissions/count` (другое множество, другой модуль).
  - **`uniqueVisitors`** считается по суточному ключу посетителя (ADR §10): визиты без ключа (нет адреса) не считаются вовсе, а за период **длиннее суток число завышено** — ключ ротируется, и один человек, заходивший три дня, выглядит тремя. Экран показывает оговорку рядом с числом.
  - **Медиана, а не среднее:** вкладка, забытая открытой на сутки, сдвигает среднее на порядок.
  - **`completionDurationSec`** — та же медиана, но только по визитам, закончившимся ответом: «сколько занимает заполнить форму». Всегда больше длительности визита, в которую входят ушедшие через три секунды. Питает карточки вкладки «Отвалы» вместе с числами воронки.
  - **`timedVisits` — знаменатель медианы**, и он отдаётся наружу не для красоты: в медиану входят только визиты, от которых доехал не один бикон (`updated_at > created_at`). При `timedVisits = 0` число `medianDurationSec` равно нулю и означает «данных нет», а не «нулевая длительность» — экран обязан различать это.
- **Ошибки:** `404 not_found`; `422 validation_error` (кривые границы периода).
- **Стоимость** — один счётный запрос, index-only по `idx_form_visits_form` (`updated_at` в `INCLUDE`); лог `visits insights`.

### `GET /forms/{id}/insights/visits`
Вкладка «Визиты» целиком: ряд по времени, источники, устройства, браузеры, ОС (спека `design/analytics-tally.md` §8). Требует сессии; членство в воркспейсе. Наружу — только счётчики.
- **200:**
  ```json
  {
    "step": "day",                         // hour | day — выбирает СЕРВЕР по ширине окна
    "timeseries": [
      { "at": "2026-08-24T00:00:00Z", "visits": 5, "submitted": 2 },
      { "at": "2026-08-25T00:00:00Z", "visits": 0, "submitted": 0 }
    ],
    "sources": [
      { "source": "newsletter", "medium": "email", "visits": 3 },
      { "source": "vk.com", "medium": "Нет", "visits": 2 }
    ],
    "sourcesLocked": false,                // true = разбивка закрыта тарифом, sources пуст
    "knownSources": 5,                     // визитов с известным источником — настоящее число и под замком
    "countries": [{ "name": "Россия", "countryCode": "RU", "visits": 4 }],
    "cities":    [{ "name": "Москва", "countryCode": "RU", "visits": 4 }],
    "unknownPlace": 2,                     // визитов без определённого места
    "devices":  [{ "label": "Компьютер", "visits": 4 }],
    "browsers": [{ "label": "Chrome", "visits": 5 }],
    "systems":  [{ "label": "Windows", "visits": 4 }]
  }
  ```
  - **Шаг ряда** — решение сервера (`domain.StepFor`): окно до двух суток — часы, дальше — сутки, «всё время» — сутки. Копия этого правила на клиенте разъехалась бы с запросом молча.
  - **Пустые корзины достроены** (`domain.FillBuckets`): дыра в ряду читается как «данных нет», хотя означает «ноль визитов». Ряд целиком пуст только если визитов за период не было вовсе.
  - **Источник** = `utm_source`, иначе хост `referer` без `www.`, иначе `Прямые заходы`; `medium` = `utm_medium`, иначе `Нет`. Неразбираемый referer уходит в прямые заходы, а не в источник с именем-мусором.
  - **Устройства/браузеры/ОС** разбираются из `user_agent` **на чтении** (`domain.ParseUserAgent`), колонок в БД под них нет: различных строк у формы сотни, а не по одной на визит, зато улучшенный разбор чинит и уже собранные данные. Неопознанное собирается в `Не определено`, роботы — в отдельную строку устройств.
  - **Страны и города** выводятся из IP в момент приёма бикона по локальному справочнику; сам адрес не сохраняется (ADR §10). Пустые списки означают, что справочника на контуре нет, — экран прячет блок целиком. `unknownPlace` — визиты без места (справочника нет, приватный адрес, IPv6, которого формат справочника не понимает); число показывается рядом со списком, потому что граница метрики — часть показания.
  - **Гейт `analytics_sources` закрывает ОДНУ секцию**, а не вкладку: `402` на весь запрос унёс бы заодно график и устройства, которые платными не объявлялись.
- **Ошибки:** `404 not_found`; `422 validation_error`.
- **Стоимость** — три счётных запроса по `idx_form_visits_form`; результат размером в число различных агентов/источников, а не визитов. Лог `visits breakdown`.

### `GET /forms/{id}/submissions/count`
Карточка «Ответы» над вкладками аналитики: сколько **видимых** ответов пришло за период (сверхлимитные не считаются — как и в таблице ответов). Требует сессии; членство в воркспейсе.
- **200:** `{ "submissions": 12 }`
- **Ошибки:** `404 not_found`; `422 validation_error`.
- **Своя ручка, а не поле в `insights`:** ответы и визиты — независимые множества, и сведение их в один ответ рано или поздно кончилось бы делением одного на другое.

### `GET /forms/{id}/submissions/summary`
Сводка ответов формы: распределения, статистика чисел и доля заполнивших по каждому вопросу. Требует сессии; проверяет членство в воркспейсе (чужая/нет формы → `404`). **Агрегирует сервер** — наружу уходят только счётчики, сырые ответы в браузер не выгружаются.
- **200:**
  ```json
  {
    "total": 9999,                            // всего ответов у формы
    "blocks": [
      {
        "blockId": "b_src",
        "label": "Как вы о нас узнали?",      // подпись из свежайшей версии, где блок есть
        "type": "single_choice",
        "kind": "distribution",               // distribution | number | fill
        "asked": 9999,                        // сколько человек ВИДЕЛИ этот вопрос
        "answered": 9999,                     // сколько ответили непусто
        "buckets": [                          // только при kind=distribution
          { "key": "o_fr", "label": "Друзья", "count": 3318 }
        ],
        "samples": [                          // до 10 последних значений, новыми сверху
          { "text": "Друзья", "at": "2026-08-24T09:15:00Z" }
        ]
      },
      {
        "blockId": "b_age", "label": "Возраст", "type": "number", "kind": "number",
        "asked": 100, "answered": 87,
        "number": { "avg": 30.5, "min": 18, "max": 64 }   // нет, если никто не ответил
      }
    ]
  }
  ```
  - **Вопросы** — то же объединение блоков по всем опубликованным версиям, что у CSV-экспорта (порядок и подпись — из свежайшей версии, где блок есть); неотвечаемые (`text`, `image`) исключены. Сводка и выгрузка обязаны показывать одно множество вопросов.
  - **`asked`** — знаменатель долей: число ответов по версиям, где вопрос **был**, а не `total`. Вопрос, добавленный в v2, иначе выглядел бы пропущенным у всех, кто отвечал по v1.
  - **`kind`** по типу блока: `distribution` — choice-типы, `dropdown`, `scale`, `consent`; `number` — `number`; `fill` (только `asked`/`answered`) — `short_text`, `long_text`, `email`, `phone`, `date`.
  - **`buckets`/`number`** приходят только там, где осмысленны (иначе ключа нет). У `scale` — все деления диапазона свежей версии, включая нулевые; у `consent` — `Да` (отметившие) и `Нет` (`asked − answered`: снявший галочку и не тронувший вопрос равны). У choice-типов — варианты объединения версий, включая невыбранные (`count: 0`).
  - Форма без опубликованных версий → `{"total": 0, "blocks": []}` (не `404`).
  - **Окно наблюдения** (`?from=&to=`) режет ответы по времени приёма: `total` и все счётчики считаются по попавшим в период.
  - **`samples`** — до 10 последних значений вопроса, новыми сверху; поле с `omitempty`, у вопроса без ответов его нет. Значения приходят ТЕКСТОМ, готовым к показу: подписи опций вместо id, множественный выбор — через `, `. Файловые вопросы значений не отдают (в ответе лежит id загрузки, а имя знает другой модуль). Потолок — часть контракта, а не настройка экрана: аналитическая ручка отдаёт счётчики и небольшую выборку, всё остальное — через листинг ответов (ADR §10).
- **Ошибки:** `404 not_found` (нет формы/не член воркспейса); `422 validation_error` (кривые границы периода).
- **Стоимость** линейна по числу ответов формы; сервер пишет строку лога `submissions summary` с `form_id`, числом свёрнутых ответов и длительностью (замер на dev: 9999 ответов → ~96 мс, тело 666 Б).

### `GET /forms/{id}/submissions/summary/{block}`
Все значения ОДНОГО вопроса, страницами: окно «все ответы» на вкладке «Сводка». Требует сессии; проверяет членство в воркспейсе (чужая/нет формы → `404`). Та же свёртка, что у сводки, в режиме одного вопроса (`domain.SummaryBuilder.AnswerLog`) — подписи опций, тип вопроса и правило «что считать вопросом» обязаны совпасть со сводкой над окном.
- **200:**
  ```json
  {
    "answers": [
      { "text": "Хотелось бы больше вариантов оплаты.", "at": "2026-08-26T15:45:44.019801+03:00" }
    ],
    "nextCursor": "MDFhMDNlMWEtZTBkMy03YWYzLTljYjEtZDkzY2UyZjBhYWI2"
  }
  ```
  - **`text`** — готовое к показу значение, как в `samples` сводки: подпись опции вместо id, множественный выбор через `, `. Разбор ответа на клиенте был бы третьей копией доменных правил после Go и Zod.
  - **Порядок — новые сверху**, сквозной через границу страниц (обход идёт по тому же `id DESC`, что и листинг ответов).
  - **`nextCursor: null`** означает «ответы формы кончились», а НЕ «страница неполная»: вопрос за условием даёт пустые страницы посреди формы, и остановка по длине страницы обрезала бы список на первом таком месте.
  - **`?limit`** зажимается в `[1, 100]` (как у листинга ответов), пустой → 50. **Окно наблюдения** — то же, что у сводки: открыв окно из строки «Ответили 12 из 34» за неделю, автор обязан увидеть те же двенадцать.
  - Вопрос, удалённый из всех версий, — законное состояние: `{"answers": [], "nextCursor": null}`, а не `404`.
  - Файловые вопросы значений не отдают (в ответе лежит id загрузки, а имя знает другой модуль).
- **Ошибки:** `404 not_found` (нет формы/не член воркспейса); `422 validation_error` (кривые границы периода, битый курсор).
- **Стоимость** — скан ответов от курсора до набора страницы: у вопроса, на который отвечают все, страница набирается на первых же строках; у редко заполняемого — досматривает форму до конца.

### `GET /forms/{id}/funnel`
Воронка формы (фаза 8.5 шаг 6б): на каком вопросе люди уходят. Требует сессии; проверяет членство в воркспейсе (чужая/нет формы → `404`). Наружу уходят только счётчики — ни одного ответа респондента.
- **200:**
  ```json
  {
    "visits": 187,                              // всего визитов (верх воронки)
    "submitted": 12,                            // визитов, закончившихся отправкой
    "leftBeforeFirst": 41,                      // ушли, не тронув ни одного вопроса
    "steps": [
      {
        "blockId": "b_inn",
        "label": "ИНН",                         // подпись из свежайшей версии, где блок есть
        "reached": 66,                          // дошли до вопроса (включая ушедших дальше и отправивших)
        "droppedHere": 51                       // остановились здесь и НЕ отправили
      }
    ]
  }
  ```
  - **Вопросы** — то же объединение блоков по всем версиям, что у CSV-экспорта и сводки (`domain.QuestionOrder`): три экрана обязаны показывать один список вопросов.
  - **`reached` невозрастает** по шагам — воронка сужается.
  - **`droppedHere` исключает отправивших.** Отправивший форму тоже имеет `last_block_id` — того поля, которого коснулся последним; считать его отвалом значило бы обвинять вопрос, который люди как раз успешно проходят. То же наверху: отправить, не тронув ни одного поля (все вопросы необязательны), — не уход, в `leftBeforeFirst` такие визиты не попадают.
  - **Неизвестный `block_id`** (подделанный — ручка визитов публична на запись, или из формы, версии которой не читаются) в шаги не попадает и к соседнему вопросу не приписывается; в `visits` он остаётся.
  - **`steps` — всегда массив** (пустой у формы без вопросов), не `null`.
  - **Окно наблюдения** (`?from=&to=`) режет визиты по `created_at`.
  - **Погрешность, которую показывает и сам экран:** пока форма — одна длинная страница, «дошёл» = «коснулся поля». Проскроллившего и ушедшего не видно. С приходом многостраничных форм тот же столбец начнёт заполняться из перехода на страницу — точнее и без миграции.
- **Ошибки:** `404 not_found` (нет формы/не член воркспейса); `402 plan_required` — воронка закрыта тарифом воркспейса (фаза 17).
  - Порядок проверок обязателен: **сначала авторизация, потом тариф**. Посторонний получает `404` независимо от плана чужого воркспейса — иначе код ответа рассказывал бы о существовании формы.
  - Визиты при закрытой воронке **продолжают собираться**: гейт стоит на ЧТЕНИИ разбивки, а не на записи (ADR §10). Число не дошедших кабинет берёт из счётчиков самой формы (`visitCount`/`visitSubmittedCount`), поэтому тело отказа обычное — без дополнительных полей.
- **Стоимость** — один счётный запрос по `idx_form_visits_form` (`GROUP BY last_block_id, submitted` и общие счётчики); результат размером в число вопросов, а не визитов. Сервер пишет строку лога `visits funnel` с `form_id`, числом визитов и длительностью.

### `POST /public/v1/forms/{slug}/partial`
Автосохранение **черновика** — того, что респондент набрал и пока не отправил (спека `design/analytics-tally.md` §10.2). Публичная ручка, без авторизации; своё ведро rate-limit, `MaxBytesReader` 256 КБ, `DisallowUnknownFields`.
- **Тело:** `{visit_id, token, version, answers, last_block_id}` — тот же `visit_id`, что у бикона визита: черновик принадлежит визиту, и повторное сохранение перезаписывает строку, а не плодит новую.
- **204** без тела: клиент ответа не читает (последнее сохранение уходит через `sendBeacon`).
- **Ошибки:** `404 not_found` — формы нет, она черновик, **или сбор выключен** (тумблер снят либо тариф его больше не разрешает: существование настройки чужой формы не раскрывается); `410` — приём закрыт; `422 validation_error` — битое тело, чужой/просроченный токен, неверный `visit_id`, разошедшаяся версия; `413` — тело больше потолка.
- **Отличия от приёма ответа**, и все три следуют из смысла черновика: нет нижней границы возраста токена (первое сохранение уходит через секунды после открытия — «слишком быстро» здесь не признак бота), нет honeypot, и **валидация мягкая** — обязательные поля не требуются, неизвестные ключи молча отбрасываются, файловые ответы не сохраняются вовсе (слот файла живёт сутки, и ссылка в черновике осталась бы битой).
- **Черновик удаляется** при приёме ответа с тем же `visit_id` (после коммита, best-effort) и периодической чисткой по возрасту (30 дней).

### `GET /forms/{id}/partials`
**Незавершённые ответы** формы (`partial_submissions`) для её автора: новые сверху. Требует сессии; проверяет членство в воркспейсе формы (чужая/несуществующая → `404`), затем право тарифа. Курсорная пагинация непрозрачным **составным** курсором `(updated_at, visit_id)` — черновик МЕНЯЕТСЯ, пока человек печатает, и одноколоночного курсора по id (как у иммутабельных ответов) здесь мало: строка прыгала бы между страницами.
- **Параметры:** `cursor?`, `limit?` (1–100, дефолт 50).
- **200:**
  ```json
  {
    "partials": [
      {
        "visitId": "018f…",                   // ключ строки — id ВИЗИТА, не свой
        "formVersion": 2,
        "createdAt": "2026-07-12T10:00:00Z",  // когда начали заполнять
        "updatedAt": "2026-07-12T10:04:31Z",  // последнее автосохранение
        "lastBlockId": "b7",                  // где остановились; "" — рендерер не прислал
        "answers": { "b1": "Анна" }
      }
    ],
    "nextCursor": "MjAyNi0…",                 // string | null (null на последней странице)
    "total": 42
  }
  ```
  - Файлов у черновика нет вовсе (слот файла выдаётся отдельным потоком и черновиком не заявляется), поэтому карты `files` в ответе нет.
- **Ошибки:** `404 not_found` (нет формы/не член воркспейса); `402 plan_required` — тариф воркспейса не даёт `submissions_partial`; `422 validation_failed` (битый `cursor`).
  - Порядок проверок обязателен: **сначала авторизация, потом тариф** — иначе код ответа рассказывал бы о существовании чужой формы.
  - Гейт спрашивается здесь **третий раз** (после включения тумблера и отдачи публичной формы) намеренно: тумблер мог остаться включённым с прежнего плана, а даунгрейд обязан закрывать и показ. Кабинет по `402` рисует не плашку с числом, а предложение включить сбор: не собирали — значит, числа нет.

### `DELETE /forms/{id}/partials/{visitId}`
Удаление одного незавершённого ответа (та же гигиена, что у ответа). Требует сессии + CSRF. Спрашивает право `submission.delete`; удаление ограничено этой формой (черновик чужой формы по угаданному id не удалить). **Гейта тарифа нет** — запрет убрать чужие данные был бы дефектом, а не гейтом.
- **204** без тела.
- **Ошибки:** `404 not_found` (нет формы/не член воркспейса; либо черновика нет / он в другой форме); `403 forbidden` (не прошёл CSRF).

### `DELETE /forms/{id}/submissions/{sid}`
Удаление одного ответа (GDPR-гигиена). Требует сессии + CSRF. Проверяет членство в воркспейсе формы; удаление ограничено этой формой (ответ чужой формы по угаданному id не удалить).
- **204** без тела.
- **Ошибки:** `404 not_found` (нет формы/не член воркспейса; либо ответа нет / он в другой форме); `403 forbidden` (не прошёл CSRF).

## Публичные формы — `/public/v1`

Без авторизации и CSRF. **Черновик и несуществующая** форма неотличимы — `404 not_found` (приватное не раскрывается, инвариант безопасности 5). **Закрытая** форма (снята вручную ИЛИ наступила дата / достигнут лимит — «фактически закрыта») была публичной, поэтому не 404, а `410 Gone` «приём закрыт» (фаза 8.5 шаг 4). Открытая — как раньше.

### `GET /public/v1/forms/{slug}`
Схема опубликованной версии формы по её `slug` — для публичного рендерера.
- **200:**
  ```json
  {
    "title": "Опрос клиентов",
    "version": 2,                       // номер опубликованной версии
    "schema": { "schemaVersion": 1, "blocks": [ /* ... */ ] },  // всегда канон
    "showBadge": true                   // рисовать ли бейдж «Сделано в Trillix» (фаза 22)
  }
  ```
  - **Заголовки:** `Cache-Control: public, max-age=60`; `ETag` = id опубликованной версии плюс метка состояния бейджа (`"<versionId>+b"`, когда бейдж показывается). Запрос с `If-None-Match`, совпавшим с текущим `ETag`, → **304 Not Modified** без тела. Метка нужна потому, что бейдж — свойство ВЫДАЧИ: он меняется от смены тарифа, а не от переиздания, и без неё подписавшийся автор получал бы 304 с прежним телом.
  - `showBadge` — решение сервера: бейдж есть всегда, кроме «автор просил снять (`design.branding: false`) И тариф это разрешает (`form_branding`)». Клиент про тарифы не знает.
  - **Токена в этом теле НЕТ** (ADR §10): ответ кэшируемый, и возраст приехавшего из кэша токена измерял бы возраст записи в кэше браузера, а не время заполнения формы. Токен выдаёт `GET /public/v1/form-token`.
- **410 Gone (форма закрыта):** схемы и токена нет, вместо них текст «приём закрыт»; `Cache-Control: no-store` (закрытость живая). Рендерер по 410 рисует экран «приём закрыт».
  ```json
  { "closed": true, "title": "Опрос клиентов", "closedMessage": "Приём ответов закрыт.", "showBadge": true }
  ```
  `closedMessage` уже разрезолвлен сервером (свой текст владельца или дефолт).
- **Ошибки:** `404 not_found` (черновик / нет формы).

### `GET /public/v1/form-token`
Подписанное время выдачи — токен, который предъявляют **три** публичные ручки: приём
ответа, выдача слота файла и бикон визита. Авторизации нет.
- **Ответ 200:**
  ```json
  { "token": "1752307200000.Yk9f…" }
  ```
- **Заголовки:** `Cache-Control: no-store`, `ETag` не выдаётся. Некэшируемость —
  часть контракта, а не оптимизация: токен из кэша стареет вместе с записью кэша, и
  окно `[3 с, 24 ч]` перестаёт измерять время заполнения формы (ADR §10).
- **Слага в адресе нет:** токен — HMAC над временем и не привязан к конкретной форме;
  обязательный слаг стоил бы запроса в базу на каждое открытие формы ровно ради
  подписи времени. Граница известна и записана в `TECH-DEBT.md` §5.
- **Ошибки:** `429 rate_limited` (своё ведро по IP — единственное, что ограничивает
  заготовку токенов пачкой).

### `POST /public/v1/forms/{slug}/uploads`
Выдача **права загрузить один файл** в ответ (блок `file`, фаза 24 `DEV-PLAN`,
[`design/answer-files.md`](design/answer-files.md)). Байты через API не идут: сервер
подписывает адрес, браузер кладёт файл прямо в хранилище.
- **Тело** (лишние поля запрещены; потолок 8 КБ — здесь только описание файла):
  ```json
  {
    "token": "1752307200000.Yk9f…",   // тот же токен формы, что у приёма ответа
    "block_id": "cv",                  // вопрос типа file в опубликованной версии
    "file_name": "резюме.pdf",         // ДАННЫЕ: чистится и хранится, в ключ объекта не попадает
    "size_bytes": 152344,              // входит в подпись — файл другого размера хранилище отвергнет
    "content_type": "application/pdf"  // из белого списка сервера, не из расширения имени
  }
  ```
- **200:** `{ "upload_id": "018f…", "url": "https://…", "content_type": "application/pdf", "expires_in": 300 }`.
  `url` — **учётные данные на 5 минут**: не логируется, не кэшируется, никуда не пересылается.
  Загрузка идёт `PUT url` с **ровно теми** `Content-Type` и `Content-Length`, что в ответе.
  `upload_id` уезжает в `answers` как элемент массива у этого блока.
- **Ошибки:**
  - `422 validation_failed` — тип файла не разрешён, вопрос его не принимает, блока нет или он не про файлы; либо антиспам (битый токен / быстрее 3 секунд / старше 24 часов — барьеры неотличимы, как на приёме).
  - `413 payload_too_large` — файл больше потолка, заданного автором в блоке.
  - `410 form_closed` — форма закрыта: слот означал бы объект под ответ, которого не будет.
  - `402 plan_required` — в пространстве владельца кончилось место (**единственный** отказ респонденту по чужому тарифу; сам ответ при этом отправляется — без файла).
  - `404 not_found` — формы нет либо она черновик.
- **Лимит:** своё ведро по IP (запас 10, пополнение ~1 в 6 с) — каждый слот это строка в базе и право записи в бакет.

### `POST /public/v1/forms/{slug}/submissions`
Приём ответа респондента. Валидируется против **опубликованной** версии формы; ответ привязывается к её id (правки схемы после отправки не искажают данные). Самый атакуемый эндпоинт — собран сразу с защитами.
- **Тело** (лишние поля запрещены; потолок 256 КБ):
  ```json
  {
    "submission_id": "018f…",              // UUIDv7, генерирует клиент → идемпотентность
    "token": "1752307200000.Yk9f…",        // токен из GET формы (антиспам по времени)
    "answers": { "b1": "Анна", "b7": ["o1","o2"] },
    "website": "",                          // honeypot: скрытое поле, человек его не заполняет
    "visit_id": "018f…"                     // НЕОБЯЗАТЕЛЬНО: визит, из которого пришёл ответ
  }
  ```
  - `answers` — карта `block_id → значение`: текстовые типы и `single_choice` — строка, `multi_choice` — массив id опций, `number`/`date` — строка (формат проверяет сервер), `file` — массив `upload_id`, выданных `POST …/uploads`.
  - `visit_id` — визит из `POST …/visits` (фаза 8.5 шаг 6). Пусто/отсутствует → ответ принимается как раньше (страница из кэша прежней версии рендерера не ломается). Неразбираемый или неизвестный id **не отклоняет ответ**: сервер просто не отметит конверсию — аналитика не повод потерять данные респондента.
- **201:** `{ "id": "018f…" }` — ответ принят. Повтор с тем же `submission_id` (ретрай после обрыва сети) тоже даёт `201`, но второй строки не создаёт.
- **200 (без тела):** honeypot-поле заполнено — ответ молча отброшен (боту неотличимо от успеха), в БД ничего.
- **Ошибки:**
  - `422 validation_failed` — невалидный ответ (детали в `fields`: `block_id → сообщение`); либо антиспам: битый токен / ответ быстрее 3 секунд / токен старше 24 часов (единое сообщение, барьеры неотличимы); либо названный файл неизвестен, приложен к другому вопросу, уже заявлен другим ответом или так и не был загружен — ответ в этом случае **не принимается целиком**.
  - `410 form_closed` — форма закрыта: снята вручную, наступила дата закрытия или достигнут лимит ответов. Лимит — **жёсткий кап** (`pg_advisory_xact_lock`): гонка не пропускает лишнего; ретрай уже принятого `submission_id` проходит и у заполненной формы (идемпотентность).
  - `404 not_found` — форма не существует / черновик.
  - `413 payload_too_large` — тело больше 256 КБ.
  - `429 rate_limited` — превышен жёсткий лимит приёма по IP (отдельный от логина).

### `POST /public/v1/forms/{slug}/visits`
Визит публичной формы (фаза 8.5 шаг 6): знаменатель к числу ответов и фундамент воронки. Шлёт рендерер через `navigator.sendBeacon` — на монтировании формы («открыли») и на `pagehide`/`visibilitychange→hidden` («дошёл до вопроса»).
- **Тело** (лишние поля запрещены; потолок 4 КБ):
  ```json
  {
    "visit_id": "018f…",                    // UUIDv7, генерирует клиент → второй бикон становится апсертом
    "token": "1752307200000.Yk9f…",         // тот же токен формы, что у приёма ответа
    "version": 2,                            // номер версии, которую человек открыл
    "seq": 1,                                // номер бикона в визите (0 — «открыли»)
    "last_block_id": "b7",                   // самая дальняя точка; null = не тронул ни одного вопроса
    "utm": { "utm_source": "telegram" }      // только известные utm_* (закрытый список)
  }
  ```
  - Поля `submitted` в теле **нет и быть не может**: конверсию ставит сервер при приёме ответа. Присланное — 422 (лишнее поле).
  - `seq` задаёт порядок: `sendBeacon` не гарантирует доставку по очереди, а `visibilitychange` срабатывает на каждое переключение вкладки. Апсерт двигает `last_block_id` только при `seq` строго больше сохранённого.
  - **Окно токена другое, чем у приёма ответа:** проверяется только верхняя граница (24 ч). Минимального времени заполнения тут нет — бикон «открыли» уходит через миллисекунды после выдачи токена.
- **204 (без тела):** визит записан или продвинут. Бикон ответ не читает.
- **Ошибки:**
  - `422 validation_failed` — битый токен / токен старше 24 часов; неверный `visit_id`; `version` не совпадает с опубликованной (форму переиздали посреди сессии — визит теряется намеренно, чтобы не приписать его версии, которой человек не видел); неверный `last_block_id`.
  - `410 form_closed` — форма закрыта: визитов не набирает (ответом они закончиться не могли).
  - `404 not_found` — форма не существует / черновик.
  - `413 payload_too_large` — тело больше 4 КБ.
  - `429 rate_limited` — своё ведро лимита по IP, щедрее приёма ответа (один визит = минимум два бикона).

**Приватность.** IP не пишется ни в открытом виде, ни в хеше; cookie и localStorage рендерер не заводит — id визита живёт в памяти страницы и умирает с ней.

### `GET /r/{slug}`
HTML-документ страницы формы — «голова на сервере, тело на клиенте». Отдаёт **Go** (не статика): краулеры превью читают HTML без JS, поэтому OG-мета подставляется на сервере. `<head>` содержит `og:site_name` (имя сервиса), `og:title` (title формы), `og:description` вместе с одноимённым `<meta name="description">` (одно значение на обе меты — общий слоган сервиса), `og:image` (env `OG_IMAGE_URL`, общая заглушка) и `og:url` (`{PUBLIC_RENDERER_BASE_URL}/r/{slug}`). Подписи вопросов в мету **не** попадают: описание — своё поле карточки, и второй, выводимый из полотна источник объяснял бы автору, почему в окне настройки одно, а по ссылке другое. **Своя карточка ссылки** (`forms.link_preview`) перебивает эти дефолты по каждому непустому полю: `og:site_name`, `og:title` (вместе с `<title>` вкладки), `og:description`, `og:image` (абсолютный `{PUBLIC_RENDERER_BASE_URL}/media/<key>` — относительный краулеры не резолвят) и второй `<link rel="icon">` после дефолтного (из двух одинаковых `rel` браузеры берут последний). Право применить карточку спрашивается **здесь, при отдаче** (`form_link_preview`): не разрешено — отдаются дефолты, сама карточка в колонке остаётся; `<body>` — `<div id="root">` + ассеты рендерера. Go строит документ из собранного `index.html` рендерера (`PUBLIC_RENDERER_INDEX_PATH`), заменяя в нём плейсхолдер `<!--og-meta-->` на эту мету; ссылки на ассеты (script/link/preload/favicon) берёт из собранного HTML как есть — не перечисляет их сам, поэтому новый ассет сборки правок Go не требует. Пользовательский текст экранируется `html/template` (инъекция `"><script>` в title обезврежена). В dev собранного HTML нет — `/r` отдаёт vite-dev, Go его не обслуживает.
- **200:** `text/html; charset=utf-8`, `Cache-Control: public, max-age=60`. Закрытая форма тоже отдаёт **200** — тот же SPA-шелл: клиент по JSON-ручке получит `410` и нарисует «приём закрыт» (существование публичной формы не скрываем).
- **Ошибки:** `404 not_found` (черновик / нет формы — как и JSON-ручка; закрытая — не 404).
- **Параметры запроса (читает клиент, не сервер).** `embed=block|widget|page` — форма открыта во фрейме на чужом сайте: компактные поля, статус-экраны без `100vh`, прокрутка и переход после отправки отдаются хост-странице (фаза 20). `bg=transparent` — прозрачный фон формы. `pf.<block_id>=<значение>` — предзаполнение поля: адресуется тем же id, что и ответы, ложится **под** черновик и **не создаёт полей**. `utm_*` — метки источника (их пробрасывает загрузчик с хост-страницы, внутри фрейма `location.search` — уже адрес рендерера). Неизвестное значение `embed` читается как «не встроены». Как это устроено целиком — [`EMBED.md`](EMBED.md).

### `GET /embed/v1.js`
Загрузчик встроенной формы — статика рендерера, не Go. Классический IIFE (не ES-модуль: подключается обычным `<script src>` с чужого домена, а однотеговый сниппет стоит на `document.currentScript`). Заводит `window.Trillix` с `mount`/`open`/`close`, вставляет `<iframe>` на `/r/{slug}` и разговаривает с ним через `postMessage`.
- **200:** `application/javascript`, `Cache-Control: public, max-age=600` — **не** `immutable`, в отличие от `/assets/*`: имя без хеша вписано в сниппеты на чужих сайтах и меняться не может.
- **Контракт бессрочный:** правки только обратно совместимые, ломающее изменение = `/embed/v2.js` (ADR §10).
- Страница `/r/*` отдаётся **без** `X-Frame-Options` и с `frame-ancestors *`; остальные пути домена — `SAMEORIGIN`/`'self'`, кабинет — `DENY`/`'none'`.
