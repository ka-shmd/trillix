## 1. Философия (критерий всей фазы)

**Тип блока описывается в одном месте.** Добавление типа не должно быть походом по девяти
файлам с риском, что забытая ветка не упадёт, а молча оттрактует новый тип как соседний.
Свойства типа живут в его файле; общие правила — в общем коде; ничего посередине.

**Настройки живут у ручки блока, а полотно остаётся WYSIWYG.** На полотне видно то, что
увидит респондент, — и ничего больше. Контрол, которого у респондента нет (выбор диапазона
шкалы), с полотна уходит: он не часть формы, а часть редактора.

**У каждого вопроса есть имя, и это имя автор видит в аналитике.** Сегодня имя выводится и
автору невидимо до первой выгрузки CSV. Имя должно быть свойством вопроса, которое можно
прочитать и переопределить там же, где остальные его свойства.

**Свойство типа — в файле типа, отношение блоков — в центре.** Это правило разграничения,
и нарушать его будет соблазн на каждом шаге: правило про пару блоков, уехавшее в файл одного
из них, воспроизводится половинами в двух файлах и расходится молча.

## 2. Диагноз

### 2.1 Знание о типе размазано по девяти местам

| Место | Что знает о типе |
|---|---|
| [`formSchema.ts`](../web/shared/entities/formSchema.ts) | значение enum, семь наборов-предикатов, ключи `settings`, ветки `superRefine` |
| `internal/domain/schema.go` | зеркало предикатов и валидации |
| [`blockTypes.ts`](../web/app/src/features/forms/builder/blockTypes.ts) | подпись, описание, раздел меню, бандл ли |
| `blockTypeIcons.tsx` | иконка |
| [`store.ts:237`](../web/app/src/features/forms/builder/store.ts:237) (`newBlock`) | дефолты блока |
| [`BlockRow.tsx`](../web/app/src/features/forms/builder/BlockRow.tsx) | поверхность строки, высота кластера значков, свои инлайн-контролы |
| [`BlockField.tsx:232`](../web/shared/fields/BlockField.tsx:232) | контрол для респондента |
| `internal/domain/answers.go`, `csv.go`, `summary.go` | валидация ответа, ячейка, вид агрегата |
| `renderer/validation.ts`, `answerFormat.ts` | валидация и показ ответа |

Из этих девяти мест **больно ровно одно** — редактор: в остальных знание собрано в один
исчерпывающий `switch`/enum, где забытый тип ловит компилятор или тест обеих сторон.

### 2.2 Цепочка аккордов написана трижды

Уникальная логика типа на полотне — это не настройки, а клавиатурное поведение поверхности
строки. Сейчас общая цепочка (меню действий, удаление, ряд, перенос, обход стрелками,
Backspace, засев печатным символом) скопирована в три места по 7–9 ветвей:

- объектная остановка `image`/`date`/`scale` — [`BlockRow.tsx:756`](../web/app/src/features/forms/builder/BlockRow.tsx:756);
- инпут плейсхолдера — [`BlockRow.tsx:962`](../web/app/src/features/forms/builder/BlockRow.tsx:962);
- инпут варианта (`OptionCard`) — там же ниже.

Различия между копиями настоящие и тонкие (проверка каретки на краю, явное исключение
`moveGroup`, что значит Backspace на пустом), поэтому копии не сводятся «в одну функцию»
механически. Но новый тип со своей поверхностью сегодня получает **четвёртую копию**.

### 2.3 Полотно несёт контрол, которого нет у респондента

`ScaleInline` ([`BlockRow.tsx:844`](../web/app/src/features/forms/builder/BlockRow.tsx:844))
рисует под шкалой два нативных `<select>` «от/до». Это единственное место, где полотно
показывает не форму, а редактор, — и заодно открытый пункт **TD-25** (нативный контрол вместо
shadcn там, где `Select` уже вендорен).

### 2.4 Имя вопроса невыразимо

`questionLabel` ([`questions.go:120`](../internal/domain/questions.go:120)) **выводит** имя по
убыванию приоритета: подпись группы → свой текст блока → плейсхолдер → «Шкала 3». Автор не
видит результата до выгрузки, переопределить его нечем, а у безымянного поля колонка CSV
называется «Короткий ответ 2».

### 2.5 Гейта публикации нет вовсе

`Publish` проверяет только разбор схемы
([`service.go:403`](../internal/forms/service.go:403)). Обещанное документами правило момента
публикации («непустая подпись, ≥1 опция» — комментарий `ValidateSchema`, `internal/domain/schema.go`)
не реализовано ни на бэке, ни в кабинете: `canPublish` смотрит только на «черновик сохранён»
([`BuilderScreen.tsx:66`](../web/app/src/features/forms/builder/BuilderScreen.tsx:66)).
Значит, «просим вписать имя перед публикацией» — это **новый механизм**, а не ещё одна
проверка в существующем.

## 3. Архитектура

### 3.1 Три слоя, и файл на тип — в каждом свой

| Слой | Где | Файл на тип (решение владельца 2026-07-30) |
|---|---|---|
| **Контракт** — enum, предикаты, настройки, валидация | `@entities` + зеркало `internal/domain` | **Да** — `entities/blocks/<type>.ts`; двусторонний контракт → ADR и тесты обеих сторон в том же PR |
| **Вид** — контрол респондента | `@fields` + `fields.css` | **Да** — `@fields/kinds/<type>.tsx`; каждый файл под замером бюджета рендерера |
| **Поведение и настройки редактора** | `builder/` | **Да** — `builder/kinds/<type>.tsx` |
| Зеркало в Go | `internal/domain/schema.go` | **Нет** — остаётся предикатным в одном файле (§3.6) |

Соблазн — одна папка на тип поверх слоёв (`kinds/scale/` со схемой, контролом, панелью и
поведением). Он ломает **бюджет рендерера**: рендерер импортирует общий код пофайлово
(`import { BlockField } from '@fields/BlockField'`,
[`FormView.tsx:5`](../web/renderer/src/features/form/FormView.tsx:5)) — именно этим держатся
95 КиБ. Барель `kinds/scale/index.ts`, экспортирующий и контрол, и панель настроек на shadcn,
означает: рендерер, которому нужен контрол, тянет модуль, где рядом лежат `radix-ui` и
Tailwind. Дальше всё зависит от tree-shaking — а он работает, пока никто не добавит в панель
сайд-эффект (импорт CSS, регистрацию при загрузке модуля). Ставить бюджет на «никто не
добавит» нельзя: поломка будет не ошибкой сборки, а выросшим бандлом у респондента.

**Правило: файл на тип в каждом слое, одинаковые имена, слои не импортируют друг друга поперёк.**

### 3.2 Реестр: `builder/kinds/*`

```
web/app/src/features/forms/builder/
  kinds/
    contract.ts         # тип BlockKind, SettingsProps, RowSurface, строки-настройки
    index.ts            # Record<BlockType, BlockKind> — исчерпывающий, без Partial и дефолтов
    scale.tsx           # подпись/описание/иконка, раздел меню, дефолты, поверхность, панель
    single_choice.tsx   # + cluster: 'options'
    short_text.tsx      # поверхность placeholder, панели настроек нет
    form_title.tsx      # запрещает удаление, дублирование и смену типа
    …
  BlockRow.tsx          # читает kinds[block.type]; веток по типу не содержит
```

```ts
export interface BlockKind {
  label: string
  description: string
  icon: ReactNode
  // В каких разделах «/» и «+» стоит тип. MENU_ITEMS становится производным от реестра.
  menu: { question: boolean; field: boolean; layout: boolean }
  // Дефолты блока — сегодня ветви newBlock.
  make(): Block
  // Какую поверхность строки надевает BlockRow (§3.3).
  surface: RowSurface
  // Высота кластера значков = line-height первой строки блока (сегодня if по типу).
  lineH: 'h-6' | 'h-7'
  // Где живёт управление строкой: у самой строки, у вариантов, нигде (§4.4).
  cluster: 'row' | 'options' | 'none'
  // Что переживает смену типа (§5.4). Сегодня — whitelist carryLayout, имя бы потерялось.
  keeps: (keyof BlockSettings)[]
  // Типовая секция попапа. Нет — в попапе только общие пункты.
  Settings?: FC<SettingsProps>
  // Что мешает публикации блока этого типа (§6).
  publishBlockers?(block: Block): Blocker[]
}
```

**Исчерпывающий `Record<BlockType, BlockKind>` без `Partial` и без дефолтных значений.** Это
не стилистика: дефолт превращает забытое поле в молчаливое поведение соседнего типа — ровно
тот класс ошибки, от которого предупреждает чек-лист
[`fields/README.md`](../web/shared/fields/README.md). Приём уже работает у иконок
(`Record<BlockType, …>`, «tsc поймает»).

### 3.3 Контракт поверхности строки

Поверхностей четыре: `text` (подписи, контент, consent), `placeholder` (текстовые поля),
`choice` (список вариантов), `object` (`image`/`date`/`scale`). Общая цепочка аккордов (§2.2)
пишется **один раз** — хук `useRowKeys`, — а поверхность доопределяет только своё:

| Что доопределяет поверхность | Пример различия |
|---|---|
| когда стрелка уходит на соседнюю строку | у текста — на краю каретки, у объекта — всегда |
| что значит `Backspace` | пустой плейсхолдер удаляет поле, объект удаляется сразу |
| куда идёт печатный символ | объект засевает строку ниже, инпут вводит в себя |
| работает ли `Alt+↑↓` | у варианта занят переносом варианта (TD-44) |

Тогда новый тип с уникальной логикой пишется против документированного интерфейса, а не
копированием 40 строк. **Потолок честный:** тип, приносящий принципиально новое
взаимодействие (матрица, ранжирование), приносит и новую поверхность — реестр избавляет от
россыпи `if`, а не от кода.

### 3.4 Что в файл типа не переедет никогда

`regroup`, раскладка рядов и двухколоночных секций, планирование дропа, контракт фокуса §12,
карта клавиш — правила про **пары и последовательности** блоков. Тип объявляет **участие**
(«я отвечаемый», «могу делить ряд», «мне нужен заголовок»), алгоритм остаётся общим. Правило
про двух участников в файле одного из них — баг архитектуры, а не организация кода.

### 3.5 Панель настроек — компонент, а не генератор

Рассмотрен и отклонён генератор форм по спеке (`[{ key:'scaleMin', kind:'select', … }]` +
универсальный интерпретатор). Причина: язык спеки придётся расширять под каждый новый тип и
он всегда будет на шаг позади. Диапазон шкалы — не два независимых `select`, а пара со связью
`min < max`, где максимум подтягивается за минимумом
([`BlockRow.tsx:852`](../web/app/src/features/forms/builder/BlockRow.tsx:852)); картинке нужен
асинхронный аплоад; будущему числу — `min/max/step` с зависимостями. Каждая связь становится
либо новым ключом языка с веткой в интерпретаторе, либо аварийным люком «вставьте свой
компонент».

JSX сам по себе декларация — только типизированная и без интерпретатора. Экономию даёт **набор
готовых строк-настроек** (`SettingRow`, `SelectSetting`, `TextSetting`, `SwitchSetting` на
shadcn) плюс `update`, который мержит в `settings` и не даёт собрать невалидное промежуточное
состояние (правило `fields/README.md`: строгий валидатор → `select`, а не свободный ввод,
иначе автосейв ловит 422 на каждое нажатие).

### 3.6 Глубина среза: все три слоя (решение владельца 2026-07-30)

Владелец выбрал глубокий вариант против моей рекомендации «только редактор». Что это значит
предметно и какой ценой.

**Что получаем.** Семь наборов-предикатов в `formSchema.ts` (`CHOICE_TYPES`,
`SINGLE_CHOICE_TYPES`, `PLACEHOLDER_TYPES`, `CAPTION_REQUIRED_TYPES`, `CONTENT_TYPES`,
`CAPTION_TYPES`, `TEXT_CARRIERS`) перестают быть отдельными списками и **выводятся** из файлов
типов. Класс ошибки «добавил тип, забыл про набор» исчезает вместе с наборами. Это же правило
проекта («ветвись предикатом, а не `type == …`») — только теперь предикат нельзя рассинхронить.

**Три условия, без которых глубокий срез ломает то, что чинит:**

1. **Форма документа на проводе не меняется.** `settings` остаётся одним `strictObject` с тем
   же набором ключей; из реестра выводится не форма, а **проверка «этому типу этот ключ
   разрешён»** — сегодня она написана руками ветвями `superRefine` («тип X не имеет шкалы»,
   «тип X не имеет опций», «тип X не имеет картинки»). Дискриминированное объединение по типу
   (второй мыслимый вариант) меняет пути ошибок и форму зеркала в Go — это уже смена
   контракта, а не уборка, и критерию 16.1 противоречит.
2. **Критерий «без смены поведения» формулируется как множество принимаемых документов**, а не
   как совпадение текстов ошибок: те же документы принимаются, те же отвергаются, а **текст
   сообщения** у сгенерированной проверки может стать другим (и в Zod, и в Go). Тесты обеих
   сторон правятся по формулировке, а не по факту отказа.
3. **Каждый файл `@fields/kinds/*` — под замером бюджета.** `npm run check:bundle` входит в
   критерий этапа, а не в финализацию: разнесённый `switch` — ровно тот случай, где
   tree-shaking может не доехать (§3.1).

**Go остаётся предикатным в одном файле.** Симметрия дерева между TS и Go ничего не покупает:
Go не может импортировать реестр, зеркало и так проверяется тестами обеих сторон, а 16 новых
файлов в `internal/domain` добавили бы работы без единой новой гарантии. Асимметрия
записывается вслух здесь и в ADR, чтобы позже не выглядела недоделкой.

## 4. Попап настроек блока

### 4.1 Входы

Попап уже существует — `BlockActionMenu`, открывается `Mod+.`, и общие пункты в нём те же.
Фаза добавляет **второй вход: клик по грипу** (тащим — драг, кликаем — настройки; так ведёт
себя Notion).

Технически вход бесплатный: у обоих `PointerSensor` стоит
`activationConstraint: { distance: 6 }` ([`SlashEditor.tsx:211`](../web/app/src/features/forms/builder/SlashEditor.tsx:211)) —
порог выбран ровно затем, «чтобы клик по ручке не начинал перетаскивание». Что доделать:

- гасить **тянущийся `click` после настоящего драга** — иначе попап открывается после каждого
  перетаскивания;
- сменить `aria-label` грипа (он перестаёт быть только ручкой);
- поведение на тач-устройствах назвать вслух (тап = настройки, долгое нажатие = драг) или
  честно записать «кабинет desktop-first, тач не поддержан».

### 4.2 Субъект: строка или вопрос

Механизм уже есть и обобщается, а не изобретается: проп `requiredFor`
([`BlockRow.tsx:76`](../web/app/src/features/forms/builder/BlockRow.tsx:76)) — это ровно
«клик по подписи правит отвечаемый блок её группы», потому что состав группы знает `GroupRow`.

| По чему кликнули | Субъект настроек | Субъект общих действий |
|---|---|---|
| подпись мульти-группы | отвечаемый блок группы (его тип и его имя) | вопрос целиком (удалить/дублировать вопрос) |
| голая строка ответа | она сама | она сама |
| контент внутри вопроса (`text`/`image`) | он сам | он сам |
| одинокая подпись (поля ещё нет) | типовой секции нет | подпись |

### 4.4 Строка выбора: отмена решения этапа 15.2

Предлагается: у строки `single_choice`/`dropdown`/`multi_choice` **кластера значков нет**
(`cluster: 'options'`), управление живёт у вариантов, попап адресован вопросу.

Это **разворот решения от 2026-07-29**. Фаза 15 сняла замок `ownedByCaption` и записала как
действующую модель: «кластер значков есть у КАЖДОЙ строки… удалить поле отдельно, утащить
поле из своего вопроса — законные действия» ([`EDITOR.md`](EDITOR.md) §4). Поэтому разворот
идёт через ADR-строку и правку §4, а на TD-44 (список нельзя унести с клавиатуры) он влияет
прямо: с `cluster: 'options'` жест недоступен и мышью, то есть пункт закрывается не починкой,
а решением «строка выбора не покидает свой вопрос».

Отдельный вопрос — **что в попапе варианта** (удалить, дублировать, в колонку?). Пустой попап
хуже отсутствующего, поэтому либо состав определяется здесь, либо варианты остаются без
попапа в v1 (§10, решение 7).

### 4.5 `form_title` — попап ограниченный

Заголовок формы — скелет документа: удалить, дублировать и сменить тип нельзя. Реестр обязан
это выражать (`form_title.tsx`), иначе три «общих» пункта ломают форму. Это первый случай,
который доказывает, что общие пункты — тоже свойство типа, а не константа попапа.

### 4.6 Клавиатура и фокус

- **Глобальные шорткаты протекают в поля попапа.** `Mod+Z`/`Mod+Y`
  ([`BuilderScreen.tsx:87`](../web/app/src/features/forms/builder/BuilderScreen.tsx:87)) и
  `Mod+/` ([`SlashEditor.tsx:204`](../web/app/src/features/forms/builder/SlashEditor.tsx:204))
  висят на `window` **без проверки цели**: `Mod+Z` в поле имени откатит документ, а не ввод.
  Нужен guard по цели события — обязательный, а не полировка.
- **Контракт фокуса §12**: открытие/закрытие попапа и каждое действие из него — строка в
  таблицу `EDITOR.md` §12 и тест в `focusContract.test.tsx` (куда уходит каретка после
  «удалить вопрос» из попапа). Требование чек-листа §9, а не пожелание.
- **Гранулярность undo**: `updateBlock` кладёт шаг истории на каждый вызов, а `UpdateKind`
  знает сегодня только `'format'` ([`store.ts:60`](../web/app/src/features/forms/builder/store.ts:60)).
  Имя из 20 символов = 20 нажатий `Mod+Z`. Нужен вид правки «настройка» со склейкой.

### 4.7 Что остаётся на полотне

Плейсхолдер, варианты, текст согласия правятся **на полотне** и в попапе не дублируются: это
то, что видит респондент (WYSIWYG). В попап уходит только то, что на полотне показать нельзя:
имя, диапазон шкалы, будущие `min/max` числа, alt картинки.

## 5. Имя вопроса

### 5.1 Модель: переопределение, а не копия

| Вариант | Как | Цена |
|---|---|---|
| **А (предлагается)** | `name` — необязательное **переопределение**. Пусто = сегодняшний вывод (§2.4); в попапе выведенное имя стоит **плейсхолдером** — автор видит буквально то, что уйдёт в CSV | Автор не видит имя «вписанным» в поле, только подсказкой |
| Б | имя копируется из заголовка при вводе | Правка заголовка позже расходится с именем **молча** — та самая путаница в аналитике, которую задача лечит. Чтобы сделать честно, нужен третий флаг «переопределено вручную» |

### 5.2 Место в схеме

Верхний уровень блока, рядом с `required` (а не в `settings`): это свойство любого отвечаемого
блока, а не типа. Значит: ключ в `blockSchema`, лимит длины, ветка `superRefine` «имя — только
у отвечаемых», зеркало в `internal/domain/schema.go` — **в одном PR, с тестами обеих сторон**.

`schemaVersion` **не поднимается**: добавление опционального ключа только расширяет множество
принимаемых документов (то же правило, по которому этап 15.6 не поднимал версию). Миграции БД
нет.

### 5.3 Приоритет, версии, дубликаты

- `questionLabel`: **явное имя** → подпись группы → свой текст → плейсхолдер → «Тип N».
  Правится в Go, потребители (CSV, сводка, воронка) не меняются — они ходят через
  `QuestionOrder`.
- **Версии**: `QuestionOrder` берёт подпись из свежайшей версии, где блок есть, — значит
  переименование меняет заголовок колонки и для ранее собранных ответов. Это сегодняшнее
  поведение подписей, оставляем; фиксируем вслух, чтобы не выглядело баг-репортом.
- **Дубликаты**: два поля с одинаковым именем дают две одинаковые колонки CSV — хуже
  сгенерированного имени. Позиция нужна (§10, решение 4).

### 5.4 Имя переживает смену типа

`changeBlockType` собирает блок из `newBlock(type)` и переносит руками только текст,
`required` и биты раскладки ([`store.ts:1090`](../web/app/src/features/forms/builder/store.ts:1090)) —
имя молча потерялось бы. Лечится полем `keeps` реестра. Заодно там же теряется плейсхолдер при
`short_text → email`, хотя оба типа его несут: одно правило чинит оба случая.

## 6. Гейт публикации

### 6.1 Модель

Чистая функция «блокеры публикации» по документу: список `{ blockId, kind, message }`. Первый
блокер — «у безымянного вопроса нет имени» (там, где вывод даёт сгенерированную заглушку вида
«Шкала 3»). Устройство обязано быть **списком**, а не одноразовой проверкой: за ним стоят уже
обещанные документами правила («пустая подпись», «choice без опций»), которые так и не
реализованы (§2.5).

### 6.2 Где считается

Правило доменное → живёт в Go (`domain`), `Publish` отдаёт 422 со списком. Кабинету нужен тот
же список **до** нажатия, чтобы не отправлять заведомо отказную публикацию, — значит зеркало в
TS, как у всей схемы. Это осознанная плата: два места, один PR, тесты обеих сторон.

Альтернатива на v1 — только клиентская проверка (быстрее, но публикация мимо кабинета остаётся
без гейта). Решение — §10, пункт 5.

### 6.3 UI

Список блокеров с переходом к блоку (клик → каретка на строку). Сегодня `canPublish` — это
только «черновик сохранён» ([`BuilderScreen.tsx:66`](../web/app/src/features/forms/builder/BuilderScreen.tsx:66)),
и блокеры встают рядом, не вместо: несохранённый черновик и незаполненное имя — разные
причины.

## 7. Диапазон шкалы уходит с полотна

`ScaleInline` теряет два нативных `<select>`, они переезжают в панель `kinds/scale.tsx` на
shadcn `Select` (вендорен). На полотне остаётся `BlockControl` — ровно то, что увидит

**Гарантированное следствие:** e2e `full-loop` собирает форму мышью «включая шкалу» — его
селекторы ломаются. Правятся в том же PR (`web/CLAUDE.md`: правки разметки ломают e2e).

## 9. Вне скоупа фазы (осознанно)

- **Боковая панель настроек** вместо попапа — переезд возможен позже, реестр к контейнеру не
  привязан.
- **Уникальность имён** как жёсткое правило (§5.3 — только позиция, не механизм).

  картинки. Реестр делает их дешёвыми — но YAGNI: не добавляем без запроса.
- **Пофайловая структура в Go**: зеркало остаётся предикатным в одном файле (§3.6) — симметрия
  дерева не даёт ни одной новой гарантии. (Срез по типам в `@fields` и `entities` изначально
  предлагался вне скоупа; решением владельца 2026-07-30 он **в скоупе** — §3.6.)
- **Условная логика** (пост-MVP фаза 16): стабильные имена ей пригодятся, но она не здесь.
- **TD-41** (goal-column, одна Tab-остановка) — не трогаем.

Порядок неслучаен. 16.1 разбит на три коммита-подэтапа **снизу вверх — контракт, вид,
редактор**: каждый уборка без смены поведения, каждый ревьюится отдельно и откатывается
отдельно. Обратный порядок (сперва редактор) заставил бы `builder/kinds/*` сначала читать
старые наборы-предикаты, а потом переписываться на выведенные — то есть один и тот же код
пришлось бы править дважды.

Ревью субагентом `reviewer` — на каждом подэтапе 16.1, а не в конце: диффы затрагивают
двусторонний контракт и общий с рендерером код, и «уборка без смены поведения» — ровно тот
класс правок, где ошибка не падает, а меняет смысл в третьем месте.
