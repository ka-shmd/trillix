**Статус:** утверждён владельцем 2026-07-24 (итог сессии обсуждения; все решения ниже — согласованы явно).
**Роль документа:** спека фазы 13 [`DEV-PLAN.md`](DEV-PLAN.md) — единственное место, где целиком

**Читать обязательно** перед любым шагом фазы 13 — вместе с [`EDITOR.md`](EDITOR.md)

## 1. Философия (критерий всей фазы)

Сформулирована владельцем 2026-07-24:

> Можно делать что угодно, где угодно, и всегда должен сохраняться флоу. Не должно быть
> никогда такого, что пользоваться мышью — это необходимость.

**Полотно — текстовый документ.** Вопросы, поля, картинки — визуализация поверх текста.
Из этого следуют три инварианта, которыми проверяется каждое решение фазы:

1. **Печатный символ работает всегда**, где бы ни была каретка. Никаких «режимов», между
   которыми надо переключаться, чтобы продолжить писать.
2. **Каретка всегда видима и предсказуема.** Ни одна операция не оставляет фокус в `body`.
3. **Флоу не рвётся.** Ни модальные подтверждения на пути, ни transient-UI, сдвигающий
   лэйаут, ни Tab-марши через десятки кнопок.

Единственное оправданное исключение из «без мыши» — системный контрол, который объективно
нужен (файловый диалог загрузки картинки).

Модель данных **не меняется**: «вопрос = группа блоков» (подпись+контент+поле, `groupId`
выводит `regroup`) владелец подтвердил явно и отказался от «вопрос = один юнит». Фаза меняет
поведение и вид полотна, не его модель (единственная правка контракта — `settings.width`
и удаление `alt`, см. §5–6).

## 2. Модель каретки

### 2.1 Фокус-цели строк

У каждой строки полотна есть фокус-цель — место, куда встаёт каретка/фокус:

| Строка | Фокус-цель |
|---|---|
| Подпись (`title`/`label`), абзац `text`, `heading`, `consent` | textarea строки (как сейчас) |
| Текстовые поля (`short_text`, `long_text`, `email`, `phone`, `number`) | инпут плейсхолдера — **лист**, только явный вход (см. ниже) |
| `single_choice`, `dropdown`, `multi_choice` | инпуты вариантов |
| `image`, `date`, `scale` | **объектная остановка** — строка целиком (§2.2) |
| Заголовок формы | его textarea (уже так) |

Сейчас клавиатурный поток живёт только на строках с textarea; строки-поля фокус молча
теряют (это TD-26 и корень «каретка исчезает»). Alt-инпута у картинки больше нет — удалён
решением владельца (§6).

**Инпут плейсхолдера — лист, а не остановка потока** (решение владельца 2026-07-24,
уточняет таблицу выше). Плейсхолдер — необязательное поле; каретка попадает в него только
ЯВНО — **Cmd/Ctrl+Enter** («действие над ответом», §3.2) или **клик** мышью. Обычная
навигация (стрелки, Backspace-схлопывание, исходы удалений) его **перескакивает**,
приземляясь на подпись группы (`navigation.ts`: `stopNeighbor`/`isFlowLeaf`). Иначе поле
перехватывало каретку на каждом проходе, а пустой Backspace в нём удалял поле и оставлял
подпись сиротой. **Исключение — голое поле** (группа без подписи): у него нет другой
поверхности, поток его пропустить не может (иначе недостижимо с клавиатуры), поэтому оно
остаётся обычной остановкой. Пустой Backspace в поле-листе не удаляет его, а уводит
каретку вверх; сносит поле только явный Cmd+Shift+Backspace (§3.4).

### 2.2 Каретка на объекте — позиция, а не режим

Строки без текстовой поверхности (дата, шкала, картинка) — «объекты», как картинка в
Google Docs: каретка может **стоять на объекте** (строка подсвечена кольцом), и при этом:

- **печатный символ** → немедленно создаётся `text`-блок ниже с этим символом (seed-паттерн,
  как у пустого полотна в `EmptyStarter`) и каретка в нём. Печать работает всегда — это не режим;
- **Enter** → пустая строка ниже (пустой блок легален: явное намерение, не автоматика);
- **«/»** → строка ниже с открытым меню типов;
- **вставка из буфера** → строка ниже, текст туда;
- **Backspace** → удаляет объект (см. §3.4 — у объекта нет текста, правило владельца
  применяется буквально);
- **Cmd/Ctrl+Enter** → главное действие объекта (картинка: файловый диалог загрузки/замены);
- **Alt+↑/↓** → двигает объект (иначе он недвижим с клавиатуры).

### 2.3 Ленивое создание блока (решение владельца)

Блок создаётся **от намерения, а не впрок**. Текущее eager-поведение — «вставил картинку →
под ней сразу рождается пустой text-блок, чтобы каретке было куда встать»
(`SlashEditor.handlePickInsertType`, `BlockRow.pickType`) — **убирается**, потому что:

1. пустой блок — мусор в схеме: он уезжает в `draft_schema` автосейвом и живёт в документе;
2. мусор в истории: вставка картинки — два коммита стора → первый Ctrl+Z «ничего не делает»
   (убирает невидимый пустой блок), только второй убирает картинку;
3. лишняя кареточная остановка для стрелок.

Вместо этого: после вставки объекта каретка **остаётся на нём** (§2.2), текст ниже рождается
при первом печатном символе. Вставка = один шаг undo.

### 2.4 Контракт фокуса

**Инвариант: каждая операция полотна заканчивается детерминированным фокусом; фокус никогда
не в `body`.** Проверяется vitest'ом через `document.activeElement` — тест-набор по таблице:

| Операция | Каретка после |
|---|---|
| Enter / Shift+Enter | начало новой строки |
| `makeQuestion` (одиночка) | конец подписи (набранный текст стал заголовком) |
| `makeQuestion`/`makeField` (изнутри группы) | поверхность нового блока **ниже группы**; пустой слеш-лаунчер удалён (§9, дефект Д2) |
| `addQuestionAfter` / `addFieldAfter` («+»-диалог) | подпись вопроса / поверхность поля (плейсхолдер или объект) |
| вставка `image`/`date`/`scale` | объектная остановка вставленного |
| Backspace-схлопывание | конец предыдущей **остановки** (лист-поля перескакиваются, §2.1); её нет → заголовок формы |
| Backspace в пустом поле-листе | предыдущая остановка (обычно подпись); поле НЕ удаляется (§2.1) |
| Cmd+Shift+Backspace (удаление блока/группы) | следующая строка после группы, иначе предыдущая, иначе заголовок |
| добавить вариант | новый вариант |
| удалить вариант | предыдущий вариант; его нет → подпись группы (TD-30) |
| undo/redo | первый блок, которого коснулся откат; блок исчез → его сосед |
| dnd мышью | фокус не трогается; Alt+стрелки — каретка едет с блоком |
| смена типа (`changeBlockType`) | поверхность блока в новом типе |

### 2.5 Один источник правды о фокусе

`selectedId` в сторе — мёртвый стейт: операции его ставят, но ни один компонент не читает;
реальным «текущим блоком» рулит параллельный `focusId` в `SlashEditor`. В фазе `selectedId`
**удаляется из стора** (вместе с `fixSelection`); фокус живёт в одном месте — фокус-движке
полотна (React-слой): реестр фокус-целей `Map<blockId, FocusTarget>` (строки регистрируют
цели), функция `focusBlock(id, edge)`. Стор остаётся чистым документом; его операции
возвращают id (уже возвращают) — фокус-движок их потребляет.

### 2.6 Адаптер каретки (задел под богатый текст)

Клавиатурный поток строки сейчас завязан на `selectionStart`/`selectionEnd` textarea
(`BlockRow.onLabelKeyDown`) — ровно эти ~200 строк перепишет будущий rich-text
(у `contenteditable` другой API — `Selection`/`Range`; разбор TECH-DEBT §5). Чтобы не
переписывать поток дважды, граница строки оформляется узким адаптером:
`caretAtStart()` / `caretAtEnd()` / `focus(pos)` (+ автовысота). Поток и фокус-движок
говорят только с адаптером; замена textarea → contenteditable позже трогает один модуль.
Формат хранения богатого текста фиксируется ADR-ом **сейчас** (плоские спаны `[{t, m[]}]`,
обоснование — TECH-DEBT §5), сам редактор — вне фазы.

## 3. Клавиатура

### 3.1 Принципы

- **Все шорткаты — по `e.code`**, не `e.key`: в кириллической раскладке `e.key='я'` ломает
  Ctrl+Z — проект уже наступал (комментарий в `BuilderScreen`). Правило распространяется на
  каждый новый биндинг с первого дня.
- **Не занимать клавиши, нужные тексту.** Del — это forward-delete символа; Cmd+Backspace на
  маке — «удалить до начала строки»; Alt/Shift+стрелки участвуют в выделении слов. Поэтому
  удаление блока — только модифицированная комбинация (§3.4), а Alt+↑/↓ (перемещение) не
  конфликтует (вертикальные стрелки выделением не заняты).
- **Полотно — один Tab-stop** (roving tabindex): Tab входит на полотно и выходит с него;
  внутри — стрелки и шорткаты. Кнопки-значки строк выпадают из Tab-обхода (мышиные
  удобства), их клавиатурные эквиваленты — шорткаты и меню действий (§3.3).

### 3.2 Карта шорткатов

Единый источник для кода, чипов-подсказок и шпаргалки — оформляется **модулем данных**
(`shortcuts.ts`: контекст × клавиша × действие × текст подсказки), из которого читают и
обработчики, и UI подсказок. Расхождение карты с поведением — баг.

**Текстовая строка** (подпись, абзац, `heading`, `consent`):

| Клавиша | Действие |
|---|---|
| печатный символ | печать |
| Enter | новый блок **после группы** |
| Shift+Enter | новый блок **внутрь группы** (после текущей строки) |
| Cmd/Ctrl+Enter | к контролу ответа своей группы; choice: к последнему варианту, список пуст → создать первый |
| `/` | литерал в текст + меню поверх (§3.5) |
| Backspace в начале | текстовое схлопывание в предыдущую строку; предыдущий — объект → удалить его |
| Del в конце | удалить объект ниже (зеркало Backspace) |
| Cmd+Shift+Backspace | удалить блок; на подписи — группу целиком; + тост (§3.4) |
| ↑/↓ на первой/последней визуальной строке | соседняя строка (с сохранением goal-column) |
| Alt+↑/↓ | переместить блок |
| Alt+Shift+↑/↓ | переместить группу |
| Cmd+. | меню действий блока (§3.3) |

**Вариант choice-блока:**

| Клавиша | Действие |
|---|---|
| Enter | новый вариант **после текущего** (не в конец — §9, дефект Д5) |
| Enter в пустом последнем варианте | удалить его и создать блок после группы (выход из списка, как в текстовых редакторах) |
| Cmd/Ctrl+Enter | новый вариант после текущего (единый жест «действие над ответом») |
| Backspace в пустом | удалить вариант → фокус на предыдущий; первый → на подпись группы (TD-30) |
| Alt+↑/↓ | переместить вариант (`moveOption` есть в сторе, биндинга не было) |
| ↑/↓ | по вариантам; на границах — наружу на соседние строки |

**Объект** (`image`/`date`/`scale`) — см. §2.2. **Заголовок формы:** Enter/↓ — к первому
блоку (есть); ↑ из первого блока — в заголовок (сейчас не работает). **Пустое полотно** —
как сейчас (Enter / «/» / печатный символ). **Везде:** Cmd+Z / Cmd+Shift+Z — undo/redo
(есть, документ-уровень); Cmd+/ — шпаргалка (§8); Esc — закрыть меню/шпаргалку.

### 3.3 Cmd+. — меню действий блока

Утверждено владельцем. Маленький поповер у текущей строки (Command-список, как слеш-меню):
**обязательность** (required — сейчас доступен только мышью), **ширина** half/full (§5),
**дублировать** (`duplicateBlock` в сторе есть, UI не было — пункт бэклога), **удалить**,
**сменить тип**. Закрывает клавиатурные пробелы, для которых нет вменяемых отдельных
шорткатов. `Period` по `e.code`, в браузерах не занят.

### 3.4 Удаление

Семантика Backspace **не меняется** (решение владельца): Backspace удаляет текст, блок
схлопывается только когда каретка в начале и текста не осталось. Объекты вписываются в это
правило буквально — у них текста нет, поэтому Backspace на объекте (или в начале строки под
ним — как уже работает для картинки) удаляет объект.

Явное удаление блока/группы — **Cmd+Shift+Backspace** (и пункт Cmd+.-меню): мгновенно,
**без диалога подтверждения**, с тостом **«Вопрос удалён · Ctrl+Z — вернуть»**. Решение
владельца (2026-07-24, после обсуждения): модальный диалог рвёт флоу, а страховка сильнее
диалога уже есть — undo восстанавливает группу в целости (снапшоты держат весь документ,
id блоков стабильны, связь с ответами/аналитикой не рвётся). Тост — штатный
toast-компонент shadcn (`sonner`, вендоренный `sonner.tsx`); заведён в этапе 13.0
(решение владельца: использовать компоненты shadcn, а не Radix-примитив напрямую).

### 3.5 Слеш-меню: инлайн-фильтрация

Сейчас «/» безусловно перехватывается (литерал не ввести — TD-33), а меню открывается со
**своим** полем поиска (Command-палитра) — каретка покидает строку. Новое поведение
(референс Notion/Tally):

- «/» **вводится в текст литералом**, меню открывается поверх;
- продолжение набора остаётся в тексте строки и фильтрует меню;
- ввод, не совпавший ни с одним пунктом, закрывает меню — текст (включая «/») остаётся:
  «и/или», «км/ч» набираются свободно (закрывает TD-33);
- Esc закрывает меню, текст остаётся;
- выбор пункта удаляет «/» и набранный фильтр из текста и применяет тип.

«+»-диалог (`BlockTypeDialog`) переиспользует тот же Command-список — два входа, один UI.

## 4. Группы: ритм, видимость, dnd

### 4.1 Диагноз: группы визуально не существуют

Отступ внутри группы и между группами — один и тот же `gap-2` (`SlashEditor`: `<ol>` и
внутренний контейнер `GroupRow`). Пользователь не видит, где кончается вопрос — отсюда
ощущение «в группу можно затащить несколько инпутов» и вся боль перетаскивания.

### 4.2 Единый ритм полотна (редактор = превью = рендерер)

Эталонный ритм задаёт `fields.css`, его носят превью и рендерер: `.rf-page` — заголовок →
форма **32px**; `.rf-form` — между вопросами/блоками **20px**; `.rf-field` — подпись → поле
внутри вопроса **8px**. Редактор эти классы для ритма не использует — пересобирает его из
Tailwind-обвязок (`py-1.5` строк «под hover-контролы», `gap-2`, `mt-7`, внутренние
`mt-2`/`mt-1.5`), подгоняя арифметику комментариями. Фактические расхождения: заголовок →
блоки 34px против 32; **подпись → поле ~28px против 8** (вопрос в редакторе «разваливается»,
в превью «собран»). Хрупкость задокументирована в самом fields.css: «меняешь эти числа —
правь полотно в SlashEditor руками».

Направление починки (владелец подтвердил: правильный вид — у превью/рендерера):

1. **Ритм — из одного источника**: полотно надевает rf-правила напрямую (группы — ритм
   `.rf-form`, внутренность группы — `.rf-field`, заголовок — 32px). Ручная арифметика и
   правило «правь SlashEditor руками» умирают.
2. **Обвязки — вне потока**: hover-зоны строк перестают занимать вертикаль — пары
   «отрицательный margin + равный padding» (кликабельная область растёт, лэйаут-бокс нет)
   либо absolute-зоны. Тот же принцип, что выстрадан для контролов (TD-22).
3. **Приёмка замером, не глазом** (правило проекта — computed-стили): эталонная форма всех
   типов, таблица вертикальных расстояний редактор/превью, критерий — ноль расхождений.

Бонус: синхронизация ритма **сама даёт визуальную идентичность групп** — 8px внутри против
20px снаружи кластеризуют вопрос, как в готовой форме.

Риск: кластер значков и тогл обязательности позиционируются от текущих `py-1.5`/`top-1.5`
и высот `h-6`/`h-7` (= line-height из fields.css) — при смене ритма выравнивание
перепроверяется на каждом типе строки.

### 4.3 Видимость групп: рейл и драг-рамка

- **Постоянная идентичность** мульти-группы: тонкий рейл/мягкий фон по hover и
  focus-within — второй слой поверх честного ритма.
- **Драг-рамка.** Текущий `ring` на `<li>` группы врёт: dnd-kit раздвигает строки
  CSS-трансформами, transform не меняет layout-бокс родителя — строки визуально уезжают за
  пределы статичной рамки (жалоба владельца: «заголовок не попадает в рамку, инпут
  оказывается за рамкой»). Новый механизм: в `onDragMove` считается union-rect **реальных
  (трансформированных)** rect'ов строк будущего состава группы; рамка — absolute-оверлей
  с CSS-переходом (умеет расширяться и анимируется). Статичный ring уходит.

### 4.4 Правило dnd: инпут не приземляется внутрь чужой группы

Инвариант «≤1 отвечаемого в группе» модель уже держит (`regroup`/`validateGroups`) — два
инпута никогда не делят groupId. Реальный дефект тоньше: отвечаемый блок, уроненный между
подписью и полем чужой группы, **молча крадёт подпись** (`regroup` переклеивает её на
пришельца, прежнее поле становится голым со сгенерированным именем) — колонки CSV и шаги
воронки тихо переименовываются. При этом слеш-меню такую вставку уже запрещает («вопрос
уходит новой группой ниже»), а dnd разрешает — два пути делают противоположное.

Решение владельца: **выровнять dnd с правилом меню** — отвечаемый блок, уроненный внутрь
чужой мульти-группы, приземляется **сразу под ней**. Философии не противоречит: жест
остаётся, меняется легальная точка приземления; молчаливая порча аналитики исчезает.
Перенос собственных блоков группы внутри неё самой остаётся свободным.

## 5. Half-ширина: два коротких поля в строке

**Модель — «ширина как свойство вопроса», не контейнер-колонка** (решение владельца):
`settings.width: 'full' | 'half'` на **отвечаемом блоке** (якоре группы; подпись следует за
группой). Рендер: два соседних half-вопроса автоматически упаковываются в один ряд; нечётный
half занимает свою половину; на мобильном (брейкпоинт `.rf-page`) — всегда стек.

Почему не контейнеры-строки: свойство сохраняет плоский список и **одномерный dnd** (два
выстраданных решения dnd не трогаются), `regroup` не меняется, аналитика/CSV не меняются
(порядок = порядок документа), а тогл ширины — клавиатурно-достижимое свойство (пункт
Cmd+.-меню). Контейнеры дали бы 2D-dnd и новую сущность схемы.

Whitelist типов на старте (визуально короткие контролы): `short_text`, `email`, `phone`,
`number`, `date`, `dropdown`. Валидация whitelist — Go + Zod синхронно.

Редактор показывает упаковку так же, как рендерер (WYSIWYG); dnd остаётся вертикальным
списком. Если драг по рядам джиттерит — приём: на время драга разворачивать полотно в
столбик (записать как решение при реализации). Это правка контракта → ADR + Go/Zod в одном
PR + тесты обеих сторон + бюджет рендерера.

## 6. Alt у картинки — удаляется целиком

Решение владельца: alt-инпут — инородное поле на полотне-тексте («скрытая метадата, которую
никто не заполняет»). Честная оговорка, зафиксированная при обсуждении: alt — не «подпись на
случай ошибки», а то, что читает скринридер; **но** пустой `alt=""` — корректная семантика
декоративной картинки (скринридер молча пропускает; рендерер уже подставляет `?? ''`), а
кому нужна подпись — есть путь лучше: text-блок под картинкой, видимый всем респондентам.

Так как живых пользователей нет (подтверждено владельцем), поле удаляется **из контракта
целиком**: Zod (`imageKey`/`alt` в `formSchema.ts` + superRefine), Go (`schema.go`:
`Alt`, `MaxAltLen`, ветки валидации), тесты обеих сторон, UI (`ImageField`), упоминания в
доках. Рендерер оставляет жёсткий `alt=""`.

## 7. Подсказки: три слоя, ничего в потоке

Урок TD-22 — закон: transient-элемент, занимающий место в потоке, схлопывается на
`mousedown` и съедает клики. Все подсказки — вне потока:

1. **Плейсхолдеры пустых строк** — подсказка прямо в месте каретки (нулевой риск, частично
   есть: «Текст, или „/" для поля»). Расширяются по контексту: тип блока × позиция.
2. **Чипы у сфокусированной строки** — absolute-оверлей в поле строки, проявление через
   `opacity`: 1–3 самых релевантных действия («Cmd+Enter — вариант»), из модуля карты (§3.2).
3. **Cmd+/ — шпаргалка**-оверлей: полная карта шорткатов текущего контекста, тот же источник.

Это закрывает вторую половину TD-26 (подсказки «добавить заголовок/поле») и пункт бэклога
«вывести подсказки прямо на полотно».

## 9. Риски

- **Два выстраданных решения dnd** (общая сортируемая вселенная блочного слоя; фильтр
  коллизий по слою — `EDITOR.md` §5) — их касаются только этапы 4 и 6. После каждого шага
  там — ручной чек-лист драга; симптом «блок замер под мышкой» = первым делом проверять,
  что `over` в контексте активного элемента.
- **TD-32** (полотно ре-рендерится целиком на каждый символ): фокус-движок добавляет
  подписки — мемоизация запрещена до React Profiler, по правилу реестра.
- **e2e `full-loop`** ходит через билдер кликами — этапы 1–3 его красят; правка селекторов
  в том же PR, что и ломающий шаг.
- **Новый e2e «билдер без мыши»**: сессия — **API-сидингом**, не UI-регистрацией
  (`registerBurst = 3` расходуется тремя существующими сценариями в ноль; лимит ради тестов
  не ослабляется — инвариант 6).
- **Ритм** двигает absolute-выравнивание значков (`h-6`/`h-7`, `top-1.5`) — проверка на
  каждом типе строки входит в шаг этапа 3.
