## Фаза 8. Полировка

### Шаг 2 — сделано

**Состояние — сделано.** В сторе билдера — стеки `past`/`future` (снапшоты `{blocks, submitLabel}`); все мутации документа проходят через приватный `commit(tag, producer)`: кладёт снапшот, чистит `future`, ставит `dirty`; no-op (граница move/reorder, чужой блок) историю не трогает. **Коалесинг текста** (решение владельца): непрерывный ввод в одно поле делит один шаг отмены (маркер `lastTag`), `required` и структурные операции — свой шаг. `hydrate` сбрасывает историю, `markSaved` её хранит, undo/redo ставят `dirty` и чинят выделение. Два прод-only нюанса, всплывшие при ручной проверке: (а) хоткей сверяется по `e.code` (`KeyZ`/`KeyY`), а не `e.key` — иначе при кириллической раскладке `Ctrl+Z` даёт `e.key='я'` и отмена молча ломалась; (б) поле названия сделано неконтролируемым (`defaultValue`) — контролируемый React-инпут стирает нативный стек undo браузера. 11 юнитов стора на историю/коалесинг/границы.

### Шаг 7 — сделано

**Состояние — сделано.** Реализовано как vite-SSR template-replace: в `web/renderer/index.html` — плейсхолдер `<!--og-meta-->`; Go читает собранный `index.html` при старте (в проде смонтирован в api read-only, `PUBLIC_RENDERER_INDEX_PATH=/srv/renderer/index.html`; mount в `compose.prod.yml`), заменяет плейсхолдер на OG-мету через `html/template`, ассеты берёт из HTML дословно. Рукописный `formPageTmpl` удалён; `PUBLIC_RENDERER_SCRIPT_PATH`/`STYLE_PATH` сняты из `config`/`.env.*`/`compose`; имена ассетов вернулись к дефолтным хешам под `/assets/*` (immutable-кэш). Favicon формы, который прод не показывал, теперь работает (шёл из собранного HTML). В dev `/r` отдаёт vite-dev — Go его не регистрирует (различие в одном конфиг-флаге, не в `if env==dev`). Юниты доказывают «новый ассет сборки не требует правок Go» (лишний `<link preload>` в фикстуре доезжает дословно) и экранирование `"><script>`; выбор mount вместо `go:embed` — чтобы `index.html` и ассеты всегда были из одной сборки (нет рассинхрона версий).

   **Проблема.** Сейчас страницу формы отдаёт рукописный `html/template` в `internal/forms/public_page.go`: «голова на сервере» (OG-мета для краулеров), «тело на клиенте» (React-SPA). Но этот шаблон **вручную перечисляет ассеты, которые генерит vite** — тег `<script>` на entry и `<link>` на CSS. Vite же на каждой сборке решает сам, какие файлы произвести и как их назвать. Из-за этого расхождения в фазе 7 дважды ловили баг прода, который не виден в dev (там vite-dev отдаёт исходники и инжектит CSS через JS): (а) шаблон ссылался на dev-путь `/src/main.tsx`, которого нет в сборке → пустая форма; (б) шаблон не выводил `<link>` на вынесенный CSS → форма без стилей. Каждый будущий ассет сборки (шрифт-preload, дополнительный чанк при code-split, модульный preload, favicon-манифест) — потенциально **третий** такой баг, который проявится только на проде. Оба раза чинили симптом (стабильные имена `/renderer.js`, `/renderer.css` + config-пути `PUBLIC_RENDERER_SCRIPT_PATH`/`PUBLIC_RENDERER_STYLE_PATH`), а не причину.

   **Причина** — дублирование источника истины: список ассетов формы существует в двух местах (собранный `index.html` и Go-шаблон) и обязан совпадать вручную. Это ровно тот антипаттерн, что запрещён по проекту в других местах (Zod↔Go, схема↔валидатор): один контракт — одно место.

   **Решение.** Go отдаёт `/r/{slug}`, **беря за основу собранный `web/renderer/dist/index.html` и вставляя в его `<head>` только OG-мета** (`og:title`/`og:description`/`og:image`/`og:url` + `<title>`/`<meta name=description>`). Все ссылки на ассеты (`<script>`, `<link>`, любые preload) берутся из собранного HTML как есть — Go их не перечисляет и не знает их имён. Расхождение становится невозможным по построению: что vite собрал, то Go и отдал.

   **Что учесть при реализации.**
   - **Доступ Go к собранному HTML.** api-контейнер сейчас не видит статику (её раздаёт Caddy из своего volume). Варианты: (1) смонтировать renderer-статику в api read-only и читать `index.html` при старте (кэшировать в памяти, не читать на каждый запрос); (2) встроить собранный `index.html` в Go-образ через `go:embed` — но это связывает Go-образ с фронт-сборкой и ломает наш порядок «образ собирается до фронтов», поэтому (1) предпочтительнее. Решить и, при (1), добавить mount в `compose.prod.yml`.
   - **Различие контуров (dev).** В dev собранного `index.html` нет — vite-dev генерит его на лету и инжектит CSS через JS. Значит нужен dev-путь: либо в dev Go продолжает отдавать минимальный шаблон со `<script src="/src/main.tsx">` (тогда шаблон остаётся, но только для dev и без CSS-заботы), либо Go в dev проксирует/читает `index.html` с vite-dev. Различие живёт в env/конфиге, а не в `if env==dev` (инвариант проекта).
   - **Безопасность (не ослабить инвариант 4).** Вставка в существующий HTML — только через безопасный парсинг/шаблонизацию: собранный `index.html` — **доверенный** (наш билд), но OG-значения (`title`/тизер) — **пользовательский текст** и по-прежнему экранируются `html/template`; `dangerouslySetInnerHTML`-эквивалентов (сырая склейка строк с пользовательским вводом) не вводить. Сохранить существующие тесты: 404 для черновика/закрытой, экранирование инъекции `"><script>` в title.
   - **Упрощение как бонус.** После рефактора `PUBLIC_RENDERER_SCRIPT_PATH` и `PUBLIC_RENDERER_STYLE_PATH` больше не нужны (ассеты приходят из HTML) — удалить их из `config`, `.env.*`, `compose`, доков. Стабильные имена `/renderer.js`/`/renderer.css` можно вернуть к хешированным (`entryFileNames`/`assetFileNames` по умолчанию) — это вернёт `immutable`-кэш на entry и CSS (сейчас они ревалидируются каждый визит).
   - **Проверка.** Тот же прогон, что вскрыл оба бага: собрать prod-local, опубликовать форму, `GET /r/{slug}` — в `<head>` есть и OG-мета, и все ассеты из собранного `index.html`; форма открывается со стилями; добавление в рендерер нового ассета (напр. отдельного чанка) **не** требует правок Go.

## Фаза 8.5. Продуктовый минимум: от «работает» к «выбрали бы»

### Шаг 1 — сделано

**Состояние — сделано.** Имена полей (решение владельца): плоские `thankYouText` и `redirectUrl` рядом с `submitLabel` — тот же прецедент (форма-уровень, необязательное, дефолт на стороне рендерера), вложенный `afterSubmit:{}` отклонён как лишний уровень (YAGNI). Контракт синхронен: Zod (`formSchema.ts`) + Go (`domain/schema.go`), лимиты 2000/2000, табличные тесты обеих сторон зеркалят друг друга. **Поведение при обоих заданных полях (решение владельца): показать текст, затем перейти через ~2 с** — человек успевает прочитать благодарность; без своего текста читать нечего, уходим сразу (`planThankYou`, чистая функция). Запасная ссылка «Перейти на сайт» показывается, когда переход уже запущен (заблокирован в iframe/фоне → не тупик). **Валидация redirect (решение владельца): строго в `ValidateSchema`, даже в черновике** — вопреки общему правилу «черновик ленив», т.к. значение идёт в `window.location` (инвариант 4). Цена — автосейв мог бы ловить 422 посреди набора URL, поэтому редактор коммитит поле по `blur` (локальный черновик до этого), а не на каждое нажатие; альтернатива «мягко + строго на публикации» отклонена: отдельного валидатора публикации в проекте нет, а до его появления `javascript:` уезжал бы в опубликованную версию. Рендерер проверяет ссылку повторно перед переходом (не доверяет схеме на месте использования). **Место в кабинете (решение владельца): страница настроек, не полотно** — полотно остаётся документом из блоков (кнопка отправки на нём остаётся: её видит респондент, правка на месте — WYSIWYG). Иконка-шестерёнка в шапке подменяет полотно страницей `FormSettings` — это третий вариант существующего `Mode` в `BuilderScreen` (превью так работало с самого начала), режим локальный: F5 возвращает в редактор, ссылки на настройки нет. Оформление признано владельцем временным («пока»): страница — посадочное место и для настроек шага 4 (закрытие формы, лимит мест). Стор: поля вошли в `Snapshot`, undo/redo разворачивают снапшот целиком (`...prev`) вместо перечисления полей руками — именно перечисление и теряет новое поле молча; юнит-регресс на это есть. Настройки применяются одним экшеном `setAfterSubmit` (одно нажатие «Сохранить» = один шаг undo); те же значения — no-op. Бюджет рендерера: 79.41 КиБ gzip из 95. Схему БД, контракт API и `entities`-эндпоинты шаг не трогает (только JSONB-документ). Доки: ARCHITECTURE §3.4, SCHEMA, `web/shared/fields/README.md`.

   **Сохранение настроек — явное, кнопкой (решение владельца).** Полотно живёт на автосейве, но настройки везде сохраняют кнопкой, и молчаливый автосейв ломал бы привычный флоу («сохранилось или нет?»). Поля держат локальный черновик, «Сохранить» разом коммитит их в стор и тут же уносит на сервер через `saveNow` (бывший `retry` из `useAutosave` — одна операция «сохранить сейчас, без дебаунса» на два вызова: повтор после ошибки и эта кнопка). «Назад к редактору» — на самой странице; иконка в шапке настройки только открывает (тумблером она была бы вторым выходом мимо диалога и неочевидным — по иконке не догадаться, что жать её надо второй раз). Уход с несохранёнными правками — `AlertDialog` «Остаться / Уйти без сохранения». **Осознанная граница:** диалог стережёт только «Назад»; уход через «Просмотр»/«Ответы»/«Поделиться» с несохранёнными настройками теряет их молча — оформление признано временным, при следующем заходе в эту зону закрыть.

   **Попутно починены два дефекта, вскрытые этим шагом (оба — не в его объёме, но блокировали демо-критерий):** (1) **автосейв не следил за новыми полями** — подписка в `useAutosave` сверяла только `blocks`/`submitLabel`, поэтому правка одних настроек ставила `dirty`, но сохранение не планировала (текст благодарности ждал бы чужой правки блока); теперь сверяются все поля документа. (2) **утечка внутреннего текста респонденту** — `submissions.Submit`/`ExportCSV` оборачивали сбой разбора опубликованной схемы через `%w`, сохраняя сентинел `domain.ErrValidation`: `respond.go` принимал нарушенный инвариант версии за ошибку ввода и отдавал 422 с текстом «не удалось разобрать схему: json: unknown field …» прямо на экран формы (сокрытие текста в `WriteError` работает только для 5xx). Теперь `%v` рвёт цепочку → 500, текст скрыт и залогирован с request_id; регресс-тест `TestSubmit_UnparsableVersionSchema_IsInternalNotValidation`. Второй слой той же утечки — рендерер показывал текст сервера при любом не-2xx; теперь 5xx с нашим конвертом даёт человеческое сообщение, а осмысленные 4xx (антиспам, лимит) едут своим текстом (ретраи на 502 без конверта не тронуты). Тот же класс в `forms.Publish` **не** чинился — кабинет, не публичная страница: вынесен в TECH-DEBT **TD-19**.

### Шаг 2 — сделано

**Состояние — сделано.** Четыре среза, по коммиту на каждый; контракт Zod+Go синхронно, тесты обеих сторон зеркалят друг друга. **Кодировка ответа — строкой у всех четырёх** (решение владельца): тип `Answer` (`string | string[]`) не расширен ни на число, ни на булев. У согласия это несущая деталь, а не экономия: булев `false` не равен `''`, не попал бы в `isEmpty` рендерера, и обязательность молча перестала бы работать — регресс-тест падает, если неотмеченное согласие перестаёт считаться пустым. **Телефон** — мягко: символы и число цифр (5..20), не формат страны; тесты фиксируют, что `+380`/`+1` проходят. **Dropdown** — отдельный тип на модели опций `single_choice` (тот же формат ответа, другой контрол — нативный `<select>`, на телефоне системное колесо). Ветвление «одиночный против множественного» переведено на предикаты `isSingleChoice()`/`isSingleChoiceType()` в трёх местах (ValidateAnswers, CSV, `formatAnswer`): при сравнении с конкретным типом dropdown молча уезжал в ветку multi и ждал массив — регресс-тест это ловит. **Шкала** — оба конца диапазона (решение владельца: `0 ≤ min < max ≤ 10` закрывает и 1–5, и NPS 0–10, который иначе потребовал бы правки контракта, когда формы уже опубликованы); `ScaleMin/ScaleMax` — **указатели**, т.к. 0 — законный минимум и с `omitempty` вылетал бы из JSON, делая «не задано» неотличимым от «задано 0»; концы выбираются `<select>`-ом, а не вводятся числом — иначе невалидные промежуточные состояния дают 422 автосейва на каждое нажатие (ловушка `redirectUrl`). Диапазон при валидации берётся из **той** версии схемы, по которой отправлен ответ. Бюджет рендерера: 80.05 КиБ gzip из 95 (четыре контрола стоили ~0.6 КиБ).

   **Отступление от буквы плана (решение владельца):** согласие **не** «всегда обязательное» — обязательность осталась обычным флагом `required`, включённым у нового блока. Необязательное согласие — реальный случай (маркетинг-opt-in, подписка на рассылку), а «всегда обязателен» потребовал бы спецслучая в `ValidateSchema` и запретил бы этот сценарий.

   **Попутно (вне объёма шага):** `AnswerField` в редакторе рисовал **захардкоженный** `<input type="date">` всем типам без плейсхолдера — шкала попала бы туда и выглядела датой; у неё теперь свой `ScaleInline` с живым превью делений. Доки: ARCHITECTURE §3.4 (типы, предикаты семантики, кодировка ответа), SCHEMA (типы, настройки шкалы, таблица кодировок), `web/shared/fields/README.md`.

### Шаг 3 — сводка сделана; колонки таблицы отложены (решение владельца):

**Состояние — сводка сделана; колонки таблицы отложены (решение владельца):** таблица — «исключительно UX», владелец дорабатывает её отдельным заходом, поэтому шаг закрыт только сводкой. Память плоская: в потоке копятся только счётчики — O(вариантов), не O(ответов). Цена решения: БД отдаёт серверу ответы, а не готовые числа. **Замер на dev (9999 ответов, 4 вопроса): ~96 мс.** Опасение владельца о нагрузке закрыто не рассуждением, а метрикой: handler пишет строку лога `submissions summary` с `form_id`, числом свёрнутых ответов и длительностью — длительность запроса middleware логирует и так, но без знаменателя она бесполезна (900 мс на 300 ответах и на 30 000 — разные новости). Это третий слой наблюдаемости из ARCHITECTURE §«Мониторинг» (счётчики в лог + `jq`, а не Prometheus на одном VPS); новых зависимостей ноль. Если лог покажет рост — вариант «SQL» вернётся на стол уже с фактами.

   **Место в кабинете (решение владельца): свой маршрут `/forms/$slug/summary`, а не локальный стейт вкладки** — ссылка сохраняется в закладки, F5 не сбрасывает, «Назад» браузера работает. Бары — на CSS (Tailwind кабинета; `rf-*` тут ни при чём — это не полотно формы). **Доработано сразу после (решение владельца, «сейчас неудобно находить сводку»):** три экрана одной формы — «Поделиться», «Ответы», «Сводка» — собраны в **табы** pathless-группы `_manage` (`forms.$slug._manage.tsx`) с общей шапкой (назад, название, статус, «Редактировать»); адреса не изменились, поэтому адресуемость сводки цела — табы это маршруты, а не стейт. До этого экраны были не соседями, а цепочкой: ответы прятались в меню карточки, сводка достижима только кнопкой со страницы ответов, назад к «Поделиться» — через «К формам». Клик по опубликованной **и закрытой** форме на дашборде ведёт теперь на «Ответы» (она роздана — ежедневный вопрос «что написали?»), черновик — по-прежнему в редактор. Табы — свои ссылки, а не shadcn `Tabs`: тот тянет `@radix-ui/react-tabs` (новая зависимость, список заморожен) и рассчитан на локальный стейт. Редактор в группу не входит — другой режим, во всю ширину полотна. Три почти одинаковые шапки схлопнулись в одну.

   **Знаменатель — `asked`, а не `total`:** сколько человек вопрос **видели** (ответы по версиям, где он был). Вопрос, добавленный в v2, иначе выглядел бы пропущенным у всех, кто отвечал по v1 — на форме CSV-демо это видно глазами: «Город» (только v2) даёт 5999 из 5999, «Телефон» (только v1) — 4000 из 4000, при 9999 ответах всего. Доля считается от ответивших; у **множественного выбора** сумма долей больше 100 % намеренно (доля от людей, не от галочек); у **согласия** база — `asked`, т.к. его «Нет» = `asked − answered` — снявший галочку и не тронувший вопрос это одно и то же осознанное «нет», а не пропуск. Модель вопросов — правило колонок CSV (объединение версий, подпись из свежайшей); у шкалы — все деления диапазона, включая нулевые (иначе бары врут о форме шкалы), у choice — невыбранные варианты с нулём.

   **Попутно (в объёме шага):** общее начало выгрузки и сводки вынесено в `versionedSchemas` и `eachSubmission` — копия курсорной логики в двух местах разъехалась бы на первой правке пагинации; `ExportCSV` переведён на них, интеграционный тест выгрузки зелёный. Склонение «ответ/ответа/ответов» переехало в `shared/format` (второй потребитель). Удаление ответа инвалидирует и сводку — иначе таблица и распределения расходятся на глазах. Контракт проверен **реальным ответом сервера**: фикстура Zod-теста снята curl'ом с dev-контура (выдуманная проверяла бы схему саму против себя).

   **Найдено, но не чинилось:** кабинет ретраит 4xx (`QueryClient` без `defaultOptions`), из-за чего несуществующая форма может залипнуть на «Загрузке» вместо «Форма не найдена» — воспроизводится и на нетронутой странице редактора, то есть не регрессия этого шага → **TD-20**. Грабля подсветки активного таба (конфликт Tailwind-утилит одинаковой специфичности: класс на элементе есть, вида нет; ловится только computed-стилем) записана в `web/CLAUDE.md`. ### Шаг 4 — сделано

**Состояние — сделано.** Три решения владельца зафиксированы в ADR §10:
   - **Живые настройки — колонки `forms`** (`close_at`/`response_limit`/`closed_message`, миграция **0007**), а не JSONB-мешок и не схема: настроек три и они стабильны, `response_limit` проверяется на горячем эндпоинте (типизированная колонка чище JSONB), а схема снапшотится при публикации — живой настройке там не место. «Фактически закрыта» **вычисляется** на чтении (`status=closed` ИЛИ дата прошла ИЛИ `count ≥ лимит`), `status` по дате/лимиту не флипается: крон не нужен, продление даты переоткрывает мгновенно.
   - **Лимит — жёсткий кап ровно N** (решение владельца, а не best-effort): приём под `pg_advisory_xact_lock` по форме сериализует конкурентные вставки, счёт точен, перебор невозможен; форма без лимита блокировку не берёт. Порядок «вставка → счёт» держит идемпотентность — ретрай принятого `submission_id` проходит мимо лимита и у заполненной формы. Размен «блокировка на самом атакуемом эндпоинте» записан в TECH-DEBT (**TD-21**) — вернуться, если станет узким местом. Тест гонки: 60 одновременных приёмов при лимите 10 → ровно 10 в БД, 10×201/50×410, данные не потеряны (под `-race`).
   - **Закрытая → `410` «приём закрыт», а не 404** (решение владельца — любая закрытая, включая снятую вручную): форма была публичной, её существование уже не секрет. Инвариант 5 сузился до **черновика** (никогда не публиковался → 404). Публичный `GET` закрытой отдаёт `410` с `{title, closedMessage}` (`Cache-Control: no-store` — закрытость живая); HTML `/r` отдаёт тот же SPA-шелл (200), клиент рисует «приём закрыт» из 410; приём ответа на закрытую → `410`.

   Настройки редактируются на странице настроек формы (шестерёнка билдера, посадочное место из шага 1) второй секцией — нативные `datetime-local`/`number`/`textarea`, новых зависимостей нет, сохранение своей кнопкой (`PATCH` фасет `closeSettings`). Контракт синхронен: Go (`domain.ValidateCloseSettings`, `domain.FormClosed`) + Zod (`entities/form.ts`), лимит текста 2000. Доки: ARCHITECTURE (§3 таблица, §3.4, §4.7, §перечень эндпоинтов, ADR §10), API.md, SCHEMA.md, TECH-DEBT (TD-21), `web/CLAUDE.md` (404-заметка про `/r`).

### Шаг 6 — сделано

**Состояние — сделано.** Пять срезов, по коммиту на каждый: миграция `0008` → модуль `internal/visits` с публичной ручкой → конверсия в приёме ответа → чтение в кабинете → биконы рендерера.

   **Порядок биконов задаётся явным `seq` (решение владельца, ADR §10).** `sendBeacon` не гарантирует порядок доставки, а `visibilitychange` шлёт бикон на каждое переключение вкладки — без `seq` поздно доехавший ранний бикон отбрасывает визит назад по воронке. Альтернатива «last-write-wins и записать погрешность» отклонена не из перфекционизма: её дефект по факту неотлаживаем — данные уже испорчены, гонку не воспроизвести. Цена решения — один `SMALLINT`. Апсерт двигает `last_block_id` только при большем `seq` **той же формы**: второе условие закрывает не гонку, а подделку — id визита выбирает клиент, а UUIDv7 угадываем по временно́му префиксу, поэтому без него ручкой одной формы правится строка другой. Оба условия покрыты интеграционными тестами; на условии `seq` прогнана мутация (убрать условие → тест краснеет).

   **Версия приезжает в теле бикона и обязана совпасть с опубликованной.** Иначе переиздание формы посреди чужой сессии приписало бы визит версии, которой человек не видел, и `last_block_id` искался бы в чужой схеме. Расхождение → 422, визит теряется намеренно; окно микроскопическое (бикон «открыли» уходит через миллисекунды после `GET`). Побочная выгода: второй запрос за `version_id` не нужен — id берётся из уже загруженной `PublicForm`.

   **Окно токена у визитов другое, чем у приёма ответа:** только верхняя граница (24 ч, переиспользование — TD-6). Нижняя (минимальное время заполнения, 3 с) неприменима по смыслу — бикон «открыли» уходит сразу после выдачи токена, и общая проверка отбрасывала бы ровно те визиты, ради которых ручка заведена.

   **Отметка конверсии — после коммита приёма, best-effort.** В транзакцию с advisory-lock не заносится: аналитика не имеет права ни отклонить принятый ответ (респондент увидел бы «не удалось отправить» на уже сохранённом ответе и отправил бы второй раз), ни усложнить самый атакуемый эндпоинт ради булева флага. Неизвестный, подделанный и неразбираемый `visit_id` дают 0 помеченных строк — штатный исход, ответ принимается. Цена — краш в окне между коммитом и отметкой занижает конверсию на единицу; записано осознанно.

   **Закрытая форма визитов не набирает (410).** Рендерер до бикона и не дойдёт (`GET` закрытой отдаёт 410), но ручка публичная, и принимать по ней то, чего не бывает в жизни, значит открыть способ портить владельцу конверсию визитами, которые ответом закончиться не могли.

   **Асимметрия чисел на карточке — осознанная.** «M ответов» это `submissionCount` (то же число, что в таблице ответов: расхождение между двумя экранами кабинета читалось бы как баг), а процент считается **по визитам** (`submitted/total`). Делить `submissionCount` на `visitCount` нельзя — это разные множества (ответ мог прийти без визита), их частное конверсией не является. Ноль просмотров даёт «Пока нет просмотров», а не «0 %»: «никто не открывал» и «открывали, но никто не отправил» — разные новости. Черновику блок не показывается вовсе.

   **Самая дальняя точка снимается `onFocusCapture` на обёртке блока в `FormView`, а не новым пропом у `@fields/BlockField`** — поля общие с превью билдера, аналитике публичной страницы там не место; обёртка стоит ноль байт в кабинете. Раскладку не ломает: в `fields.css` нет селекторов прямого потомка (проверено grep'ом).

   **Попутно (в объёме шага):** обёртка rate-limit по IP вынесена в `httpserver.RateLimitByIP` — это третий потребитель, а копии в `auth` и `submissions` уже начинали расходиться (вычисление IP за прокси, TD-1, чинилось только в одной). Трекер визита принимает строку запроса параметром, а не читает `window`, — остаётся чистой функцией и проверяется юнитом без DOM.

   Бюджет рендерера: **80.62 КиБ gzip из 95** (было 80.05 — биконы стоили 0.57 при заложенных в план 1–1.5). Проверено сквозняком на dev: бикон открытия → фокус в поле → уход со страницы → строка визита с `last_block_id` того блока, которого коснулись, `utm_source` из адреса, `submitted = true` после отправки; в мете **нет IP** (тест падает, если ключ с `ip`/`addr` появится), cookie рендерер не заводит. Под StrictMode одно открытие даёт **один** визит. Доки: ARCHITECTURE (§3 DDL, §4.4 rate limiting, дерево модулей, перечень публичных эндпоинтов, ADR §10), `API.md`, `SCHEMA.md`.

   Затрагивает схему БД и контракт API → миграция `0008` (0007 занял шаг 4 — закрытие формы), новый модуль `internal/visits` (repo/service/public_handler по образцу `submissions`), доки ARCHITECTURE §1/§3.3/§4.6/§5.2/§7 + `API.md` + `SCHEMA.md` — **в том же PR, что и код** (сегодня они описывают реальность, забегать вперёд им нельзя — TD-14). Бюджет рендерера: +~1–1.5 КиБ к 79.41 из 95.

### Шаг 6б — сделано

**Состояние — сделано.** Четыре среза: общая модель вопросов → свёртка и эндпоинт → интеграционные тесты → экран.

   **Отправивший форму — не отвал (главное решение шага).** Он тоже имеет `last_block_id`: того поля, которого коснулся последним. Без разделения все дошедшие до конца попали бы в «отвалились на последнем вопросе», и экран обвинял бы ровно тот вопрос, который люди успешно проходят — воронка врала бы тем сильнее, чем лучше работает форма. Поэтому `GROUP BY` идёт и по `submitted`: «дошёл до вопроса» считается по всем визитам, «остановился здесь» — только по неотправившим. Та же логика наверху: отправить, не тронув ни одного поля, можно у формы со всеми необязательными вопросами, и это не уход. Обе стороны покрыты юнитами и интеграционным тестом; ошибка была найдена при написании свёртки, до того как уехала на экран.

   **Агрегация здесь в SQL — не отступление от решения шага 3, а его обратная сторона.** Там на SQL пришлось бы переписать семантику ответа (что значит `"yes"`, что значит массив опций) — третью копию правил после Go и Zod. Здесь семантики нет вовсе: подсчёт строк по одной колонке, результат размером в число вопросов, а не визитов. Порядок и подписи шагов всё равно достраивает Go.

   **Модель вопросов вынесена в `domain.QuestionOrder` (решение владельца).** Правило «объединение блоков по всем версиям, порядок и подпись из свежайшей» существовало двумя копиями — в `NewCSVBuilder` и `NewSummaryBuilder`; воронка стала бы третьей. Копии именно этого правила опасны тем, что расхождение не падает, а молча показывает владельцу **разные формы** на соседних экранах. Оба существующих потребителя переведены на общую функцию, их тесты прошли без правок — они и были страховкой переноса. Сводка сохранила свой обход версий, но только ради опций: вариант, удалённый в свежей версии, всё ещё имеет выбравших его по старой.

   **Место — свой таб «Воронка» (решение владельца), а не секция сводки:** другой источник данных (визиты, не ответы), своё пустое состояние («просмотров пока нет» против «ответов пока нет») и свои загрузка/ошибка — на общей странице получились бы два спиннера и две коробки ошибки. Адресуемость та же, что у сводки: таб — маршрут, а не стейт.

   **Погрешность показана на самом экране, а не только в доках:** «дошёл» = «коснулся поля», проскроллившего и ушедшего не видно. Владелец читает числа вместе с этой оговоркой, а не после разбирательства.

   **Неизвестный `block_id`** (подделанный — ручка визитов публична на запись) в шаги не попадает и к соседнему вопросу не приписывается, но остаётся в общем счётчике визитов: врать про число открытий нельзя.

   **Проверено на прод-контуре (закрывает долг обоих шагов, 6 и 6б).** `make prod-local` + сценарий `e2e/tests/visits-funnel.spec.ts`: визит биконом под строгой CSP → «1 просмотр → 1 ответ (100 %)» на карточке → воронка без отвала на вопросе отправившего → `410` на визит к закрытой форме. Это единственное место, где вообще проверяется бикон: `sendBeacon` подчиняется `connect-src 'self'`, заблокированный бикон **не бросает исключения и молчит в консоли** — счётчик просто остался бы нулевым, а в dev CSP нет вовсе. Сценарий сделан отдельным от `full-loop`: он не зависит от билдера, иначе краснел бы от правок редактора, ничего не говоря про аналитику. `full-loop` при этом красный по причине, не связанной с аналитикой (первый клик по «+ Добавить блок» после слэш-вставки; файлы билдера этими шагами не менялись) — **TD-22**.

   Проверено сквозняком на dev: реальный ответ сервера снят curl'ом и стал фикстурой Zod-теста (выдуманная проверяла бы схему саму против себя); на форме с четырьмя визитами экран показал «4 просмотра → 1 отправка», «2 ушли, не тронув ни одного вопроса» и отвал на последнем вопросе, при этом отправивший, коснувшийся первого вопроса, в отвал не попал. Пустое состояние проверено на форме без визитов. Доки: `API.md`, ARCHITECTURE (перечень приватных эндпоинтов).

### Шаг 7 — перенесён в POST-MVP целиком (решение владельца), фаза 19

**Состояние — перенесён в POST-MVP целиком (решение владельца), фаза 19.** Владелец отклонил встроенные шаблоны как половинчатые: шаблоны нужны сразу со своими и публичными, иначе фичу придётся переоткрывать. Агент рекомендовал разделить (встроенные сейчас — они в любом сценарии пишутся руками, иначе галерея пустая; статические JSON стали бы сидом будущей таблицы, а выбрасывался бы только `import` списка вместо запроса к API) — рекомендация не принята. Причина отклонения принята как более весомая: **половинчатые шаблоны обещают библиотеку, которой нет**, и первый же новичок упирается в раздел «Публичные» с пустотой — то есть в ту же проблему чистого листа, ради которой шаг затевался.

   **Что перенос стоит фазе:** чистый лист у новичка остаётся до POST-MVP — при создании формы по-прежнему пустое полотно. Это единственная продуктовая дыра из аудита кабинета, которую фаза 8.5 сознательно не закрывает. Демо-сценарий фазы переписан (начинался словами «форма из шаблона»).

### Шаг 8 — сделано

**Состояние — сделано.** Два среза: бэкенд (запрос, сервис, транспорт, тесты) → дашборд.

   **Один SQL-запрос на три порядка вместо шести** (первая/следующая страница × три сортировки). Ключ сортировки нормализован к `bigint`: время — наносекунды эпохи, число ответов уже `bigint`. Отсюда неизменный формат курсора и одно место, где живёт правило порядка; альтернатива — шесть запросов с одинаковой двенадцатистрочной проекцией и шесть копий маппинга строки в Go, то есть ровно та копипаста, что запрещена PROCESS §8. Планировавшийся ради дедупликации view (и миграция под него) **не понадобился** — единственный запрос дедуплицировать нечем; шаг не трогает схему БД вовсе.

   **Порядок запечатан в курсоре, чужой курсор → 422** (а не молчаливая пересортировка): ключ у порядков измеряет разные величины, и курсор от другой сортировки дал бы не ошибку, а перемешанную выдачу с пропусками — дефект, который заметен не сразу и невоспроизводим постфактум. Курсор из двух частей (выданный до этого шага) читается как сортировка по умолчанию: открытая у кого-то страница не ломается в момент выкатки.

   **Цена решения — `CASE` в `ORDER BY` не даёт использовать `idx_forms_workspace` для построения порядка** (индекс отбирает строки воркспейса, сортирует sort-узел); индекс под `created_at` по той же причине не заводился. Опасение владельца о стоимости сортировки по числу ответов закрыто замером, а не рассуждением: **2,4–4,4 мс** на 98 формах, включая форму с 9999 ответами, одинаково на всех трёх порядках. Обещанная в плане лог-строка со счётчиком **не добавлена осознанно**: единственный доступный там знаменатель — размер страницы, а не число просканированных форм, то есть ровно бесполезная величина, от которой предостерегал опыт шага 3; длительность запроса middleware пишет и так.

   **Поиск идёт по `coalesce(name, title)`** — по тому, что человек видит на карточке, а не по «настоящему» заголовку: форма, переименованная в кабинете, обязана находиться по новому имени. Спецсимволы `LIKE` экранируются, иначе «50%» находит что угодно; интеграционный тест фиксирует, что «50%» находит ровно форму с процентом в названии.

   **Поиск и сортировка — в адресной строке** (то же решение, что у табов формы): ссылка на отфильтрованный дашборд ложится в закладки, F5 не сбрасывает, «Назад» работает. Параметры необязательны и умолчания в адрес не пишутся — иначе типы роутера потребовали бы перечислять search-параметры у **каждой** из десятка существующих ссылок на дашборд. Поиск и сортировка входят в query-ключ, а не фильтруют загруженное: список постраничный, клиентская фильтрация показывала бы совпадения только из подгруженных страниц, молча теряя остальные.

   **Пустых состояния стало два** — «форм нет» и «ничего не найдено»: предлагать создание формы в ответ на неудачный поиск значит подталкивать к дублю той формы, которая просто не нашлась.

   **Найдено самопроверкой после реализации (записано, не заметено).** (1) **`sort=responses` + курсор теряет строки:** ключ этой сортировки — счётчик, меняющийся между запросами страниц; форма, получившая ответы посреди листания, перепрыгивает курсор и не показывается ни на одной странице (воспроизведено на dev: форма с 21 ответом невидима). Опасность коррелирует со сценарием — «сортировать по ответам» жмут на активных формах, где ответы и приходят; смягчает то, что страница вмещает 50 форм и у большинства воркспейсов пагинации нет. Записано как погрешность в `SCHEMA.md`; починка (снапшот на листание) потребует ADR. (2) **`q` не был ограничен по длине** — принимался запрос в 50 000 символов, нарушение инварианта 3 (`MaxBytesReader` стережёт тело, а не query-строку); закрыто лимитом в 200 символов с тестом на границе. (3) **Счётчики карточки (ответы, просмотры, конверсия) не проверялись ни одним тестом**, хотя шаг переписал их вычисление со скалярных подзапросов на `LATERAL`; заведён `TestForms_ListCounters`, на нём прогнана мутация (убрать `FILTER` у `visit_submitted_count` → тест краснеет).

   Проверено сквозняком на dev (98 форм): поиск 98 → 1, сортировка по ответам поднимает наверх форму с 9999 ответами, подгрузка второй страницы под `sort=responses` проходит с курсором, несущим порядок; 422 на опечатку в `sort` и на курсор чужой сортировки; сброс поиска чистит и адрес, и поле. Доки: `API.md`, `SCHEMA.md`, ARCHITECTURE (перечень приватных эндпоинтов).

Пометка внесена в реестр (TD-21).

## Фаза 11. Вход через Яндекс ID

Первая фаза после MVP: план исчерпан, блокеров нет, очередь пуста → источник `POST-MVP.md`.
**Фаза переопределена решением владельца до начала работ:** вместо «Транзакционная почта и
восстановление пароля» — «Вход через Яндекс ID». Довод: потерянный доступ лечится устранением
причины (у аккаунта, заведённого провайдером, пароля нет вовсе), а не сбросом пароля по почте.
Почтовая часть целиком стала следующей фазой; VK ID отложен в `BACKLOG.md` — фаза обкатывает
механику на одном провайдере.

### Шаг 1 — сверка провайдеров; она же сломала посылку принятого решения

**Состояние — сделано; результат изменил ADR.** Владелец выбрал автосвязывание аккаунтов при
подтверждённом провайдером email (вариант «как у большинства SaaS»), и это было записано в
ADR-таблицу. Сверка документации показала, что **условие невыполнимо ни у одного провайдера:**
Яндекс `login.yandex.ru/info` отдаёт `default_email`/`emails` и **никакого признака
подтверждения**; у VK ID поле `verified` в `oauth2/user_info` означает верифицированный профиль
(галочка публичной персоны), а не почту.

Это не мелочь формулировки: реализация «автосвязывание при подтверждённом email» свелась бы либо
к связыванию по непроверенному адресу (то есть к дыре, которую сами же назвали дырой), либо к
неработающей ветке. Отдельно опасно поле `verified` — принять его за подтверждение почты
и есть исторический источник угонов этого класса.

Работа была остановлена, владельцу показан разбор с тремя вариантами. **Принято: связывание через
разовый ввод пароля** — безопасно независимо от семантики провайдера, сохраняет `UNIQUE` на
`users.email` (иначе «какой из двух аккаунтов» всплывало бы в сбросе пароля, биллинге и 152-ФЗ)
и не раздваивает данные. Ранее рассмотренный и отвергнутый вариант «разные аккаунты на каждый
способ входа» стоил бы уникальности email навсегда.

Прочее из сверки, записанное в план: у Яндекса PKCE поддержан (при нём секрет не обязателен),
`state` до 1024 символов; у VK PKCE **обязателен**, `state` от 32 символов, обмен кода требует
`device_id` из ответа авторизации.

### Шаг 2 — миграция 0009, пароль стал необязательным

**Состояние — сделано.** `user_identities` (PK по паре провайдер+идентификатор, каскад на
`users`) и `users.password_hash` → nullable. Отдельная таблица, а не колонки `yandex_id`/`vk_id`:
к аккаунту привязываются оба провайдера сразу, третий не потребует миграции `users`.
`users.email` остался `UNIQUE` — аккаунт на адрес один, способов входа в него несколько.

Следом за схемой поехал маппинг: `auth.User.PasswordHash` стал `*string` по конвенции проекта
(`ptrStr`/`pgText`, как в `forms`). **Содержательная часть шага — не схема, а ветка входа:**
аккаунт без пароля отвечает как на неверный пароль и **с тем же временем** (`equalizeTiming`).
Без выравнивания факт «этот адрес заведён через Яндекс» читался бы по времени ответа — тест
предъявлен мутацией и краснеет на 760 нс против миллисекунд argon2.

Down-миграция возвращает `NOT NULL` и **падает на базе, где уже есть OAuth-аккаунты**. Это
осознанно и записано комментарием: проставить таким аккаунтам пароль-заглушку значило бы сделать
вид, что откат безобиден, тогда как он лишает людей единственного способа входа.

### Шаг 3 — модуль `internal/oauth`

**Состояние — сделано.** Authorization code + PKCE на stdlib, без единой новой зависимости
(`golang.org/x/oauth2` отвергнут: экономит ~60 строк, половина из которых refresh-поток, который
не нужен — токен провайдера используется однократно и выбрасывается). Чек-лист безопасности,
каждый пункт с тестом: в ссылку уходит S256-challenge (verifier не утекает), токен профиля —
заголовком `Authorization`, а не query-параметром, `io.LimitReader` на ответы, таймаут 10 с,
тело ответа провайдера не попадает в текст ошибки (в нём бывает токен и чужой адрес).
`Challenge` сверен вектором из RFC 7636 приложение B — согласие со спецификацией, а не с самим
собой. Тест PKCE предъявлен мутацией.

`redirect_uri` отдельной переменной не имеет: собирается из `APP_ORIGIN`, что делает
рассинхронизацию адреса с origin кабинета невозможной в принципе.

### Шаги 4–5 — правила входа и эндпоинты; три находки ревью

**Состояние — сделано.** Таблица случаев стала кодом и таблицей тестов: привязка найдена — вход;
адрес свободен — новый аккаунт без пароля вместе с личным воркспейсом одной транзакцией; адрес
занят — сессия **не** выдаётся. Четыре эндпоинта; `/oauth/link` посажен на ведро логина (иначе
перебор переезжает на менее защищённую дверь) и отвечает за постоянное время.

Незавершённая привязка едет в подписанной cookie (HMAC с меткой назначения `oauth-link:`).
Подпись здесь не украшение: сессии на этом шаге ещё нет, значит нет и CSRF-защиты, а без подписи
можно было бы привязать к чужому аккаунту свою личность у провайдера и получить постоянный вход,
узнав чужой пароль один раз.

**Ревью субагентом нашло три дефекта, все починены в той же ветке:**

1. **Cookie состояния гасилась через `defer` — то есть не гасилась вовсе.** `http.Redirect` к
   моменту выполнения `defer` уже записал заголовки, `Set-Cookie` не уезжал, и `state` с
   `verifier` жили все 15 минут TTL, переставая быть одноразовыми. Классическая ловушка `defer`
   в HTTP-хендлере. Регрессионный тест на три исхода предъявлен мутацией.
2. **Недоступность провайдера и сбой БД отдавали JSON 500 на origin API**, оставляя человека без
   пути назад: колбэк — навигация браузера, ему нужен экран. Теперь редирект на `/login?oauth=…`,
   причина в лог (провайдер, стадия — без токена и email).
3. **Адрес, занятый аккаунтом без пароля, вёл на непроходимый экран привязки** (доказывать
   владение нечем, любой ввод давал бы 401 навсегда). Два спусковых крючка чинятся по-разному:
   гонка двух вкладок теперь разрешается повтором поиска привязки (вход, а не отказ), а смена
   личности у провайдера — отдельный исход `ErrProviderOnlyAccount` и **TD-34**.

Третью находку тесты бы не поймали: не было случая, где «email занят» встречается с «у найденного
нет пароля». Теперь есть.

### Шаг 6 — фронт кабинета

**Состояние — сделано.** Кнопка провайдера на входе и регистрации, экран привязки, сообщения об
исходах колбэка. Кнопка — `<a href>`, а не `onClick`+`fetch`: нужен полноценный переход браузера,
XHR за редиректом на чужой домен не пойдёт. Провайдер без подписи в `PROVIDER_LABELS` не рисуется
вовсе — бэк может обогнать фронт, и кнопка, ведущая в 404, хуже отсутствующей. Причина отказа
приезжает параметром адреса; мусор в нём гасит `catch`.

Проверено в браузере **выключенное** состояние (то, в котором прод жил до ключей): `/auth/providers`
отдаёт `[]`, кнопки и разделителя нет, кабинет выглядит ровно как до фазы.

### Шаг 7 — выкатка; первая уехала на прод сломанной

Починка — `v0.11.1`. По решению владельца защита сделана здесь же, а не отложена: **`check-docs`

### Шаг 13.6 — ряды из двух вопросов и вариантов

**Состояние — сделано со второй попытки; первая забракована владельцем.** Первая реализация
хранила ширину как состояние **пары** (`settings.width: 'half'` у обоих участников) и дала
четыре дефекта разом. Корень один: пары как сущности в плоском списке блоков **нет**, а
состояние несуществующей сущности приходится чинить руками при каждом распаде — и один из
путей распада всегда забывается.

Переписано поверх, без revert'ов: **один бит `settings.column: 'right'` у правого
участника** (тот же бит у `Option`), ширина не хранится, а выводится раскладчиком
`packRows`/`packOptionRows` — одно ядро на оба слоя и на все три поверхности. Левый участник
о правом не знает, поэтому чинить при распаде нечего.

Три решения, каждое против интуиции:

1. **Кросс-блочное условие намеренно не валидируется** ни в Go, ни в Zod. Инертный флаг
   легален — иначе undo и промежуточные состояния драга ловили бы 422 в автосейве. Вместо
   валидации — уборка `normalizeColumns`, спрашивающая **тот же раскладчик**, что рисует.
2. **Бит держится за конкретного соседа** (уточнение при реализации, в ADR и спеку). Сосед
   сменился — бит снят. Проверка «в каждой команде по отдельности» гарантированно отстаёт от
   следующей команды, и ряд начинал собираться сам, без просьбы.
3. **Полотно остаётся двумерным во время драга.** Прежнее «сворачиваем в столбик» отменено:
   в столбике появляется цель «между левым и правым», которая после упаковки значит не то,
   что показала.

Входов ровно два и оба — команда переноса, а не тумблер: жест (правая треть ряда) и
`Mod+Alt+←/→`. Тумблера ширины нет нигде — половинность не переключается, она возникает от
соседства.

### Шаг 14.1 — формат: ADR, контракт, апгрейд

2. `MaxTextLen` перестал ограничивать документ — 2000 кусков по одному символу проходили;

3. Браузер нормализует `style.color` при чтении (`#c026d3` → `rgb(...)`), и цвет доехал бы
   до схемы в форме, которую валидатор обязан отвергнуть, — значение марки переехало в

4. Правило `.rf-b` лежало в CSS кабинета, то есть опубликованная форма теряла жирный —
   марки переехали в общий `fields.css`.

Первые два нашли тесты, третий и четвёртый — нет.

### Шаг 14.2 — вывод: рендерер и превью

**Состояние — сделано.** Демо закрыто двумя наборами, а не прогоном глазами:

### Шаг 14.3 — поверхность строки

**Состояние — сделано.** `<textarea>` в текстовой строке больше нет, каталог `spike/` и его
переключатель удалены. Главное отличие от пробы — поверхность отдаёт **спаны**, а не плоскую
строку, поэтому разметку видят автосейв, история отмены и публикация. Обещание адаптера
каретки (фаза 13, §2.6) выполнено буквально: поток клавиш не переписывался.

Три решения, каждое куплено дефектом: поверхность неуправляемая (управляемый
contenteditable ронял бы каретку на каждом символе); ресинк из стора — только на внешнюю
правку и по сравнению ПО ЗНАЧЕНИЮ (иначе набор символа стирал бы разметку); между
`compositionstart` и `compositionend` поверхность не трогаем вовсе (IME). Вырезание «/»
пошло через `cutRange` по координатам текста — склейка строк стёрла бы разметку всей
подписи. Ссылка в **редактируемой** строке рисуется не `<a>`, а span с `data-href`:
кликабельная ссылка посреди contenteditable уводит со страницы по случайному клику.

### Шаг 14.4 — панель форматирования и шорткаты

**Состояние — сделано; браузерная проверка владельца дала четыре дефекта, все закрыты.** Ни
один не был доступен тестам: все четыре — про доставку события мыши и про лэйаут, а не про
модель.

1. **Меню ссылки не закрывалось кликом мимо.** `blur` строки этот случай не покрывает: при
   открытом поле адреса фокус уже в нём, и blur строки давно прошёл. Лечение — слушатель
   `mousedown` на документе, живущий пока панель открыта.
2. **Цвет невозможно было поменять** — и диагноз с первого раза оказался неверным. Первая
   версия лечила общий гард «панель не забирает фокус», сняв у выборщика `preventDefault`, —
   а именно он фокус и удержал бы. Настоящая причина: кнопка была `<label>` вокруг
   спрятанного `<input type="color">`, а метка пересылает клик контролу на `click` — ломалось
   же раньше, на `mousedown`: метка фокус не принимает, панель живёт в портале на `body`,
   фокусируемых предков у неё нет, фокус уходил из строки в никуда, строка на своём blur
   закрывала панель, и пересылать было уже некуда. Грабли TD-22, вид сбоку. Решение
   владельца — **свой выборщик** на shadcn Popover вместо нативного окна (оно вдобавок
   выпадало из вида кабинета).
3. **Замок прокрутки не работал**, потому что первая версия угадывала узел: класс
   `overflow-auto` на элементе не означает, что прокручивается именно он.
4. **Вторая версия замка дёргала экран и ломала шапку.** Шапка — `sticky`, а sticky
   перестаёт работать, когда у предка появляется `overflow: hidden`. Итоговое решение
   владельца: не прятать полосу прокрутки вовсе, только гасить `wheel`/`touchmove`. Цена
   названа вслух и записана в реестр — TD-43.

### Шаг 14.5 — финализация

**Состояние — сделано.** Оба билдерных e2e были красными с этапа 14.3, и обнаружилось это
**чтением кода**, а не ночным прогоном: держались они за то, чего больше не существует
(`textarea.rf-label` и `getByPlaceholder(...)`).

Чинилась не проверка, а строка. `placeholder` — атрибут `<input>`/`<textarea>`, и он же давал
строке **доступное имя**; contenteditable такой любезности не делает, то есть с 14.3
поверхность полотна была безымянной для скринридера вовсе. `RichLine` получил `aria-label`,
e2e берут строку по имени роли `textbox` — тем же способом, каким её слышит пользователь. Имя
и видимая подсказка разведены: у блока `text` подсказка появляется только под кареткой, а имя
мигать не имеет права.

Новый шаг форматирования в `builder-keyboard` (выделение стрелками + `Mod+B`, дальше проверка
`font-weight` с живого элемента прод-сборки у респондента) **в первый же прогон нашёл седьмой
дефект фазы**: марка ложилась на предыдущее выделение. Снимок, на котором стоит панель,
приезжает из `selectionchange` через состояние React — на кадр позже нажатия, — а команда
форматирования брала его первым. Правило теперь однозначное: пока фокус в строке, диапазон
даёт живое выделение и только оно; снимок нужен ровно в обратном случае (фокус ушёл в панель,
живого выделения там нет). У человека дефект почти незаметен — между двумя нажатиями он
думает дольше кадра, — поэтому его не увидел и владелец.

Непротекание разметки в данные закрыто тремя проверками по одной на поверхность (доступное
имя поля у респондента, карточка ответа, CSV) плюс `og:description`, снятым с prod-local
курлом. Доки: `EDITOR.md` §14 и карта клавиш, `fields/README.md` — как добавить марку.

### Итог фазы

**Заведено реестром:** TD-43 (замок прокрутки не ловит перетаскивание полосы мышью); TD-32
получил второго потребителя — выборщик цвета пишет в стор на каждом кадре жеста. Блокеров
нет. Закрытых пунктов реестра у фазы нет — она добавляла функциональность, а не чинила долг.

Два урока:

1. **Модельные тесты не видят границу «браузер ↔ наш код» в принципе.** Семь дефектов фазы —
   все семь на этой границе: доставка события мыши, `sticky` под `overflow`, нормализация
   цвета браузером, нарисованность марки, кадровое отставание состояния React от выделения.
   Юниты трижды поймали настоящие ошибки — и ни одной из этих семи. Единственная автоматика,
   которая по границе ходит, — e2e через билдер; поэтому шаг форматирования там теперь есть,
   и он окупился в первый же прогон.
2. **Неверный диагноз дороже отсутствующего.** Дефект «цвет не меняется» лечили дважды: первая
   починка снимала ровно ту защиту, которая была права, и выглядела правдоподобно, потому что
   объясняла симптом. Признак, который стоило заметить раньше: объяснение подходило к симптому,
   но не проверялось экспериментом — «а если вернуть `preventDefault`, палитра откроется?».

### Шаг 15.4 — ряд внутри вопроса

**Состояние — сделано.** Часть 2 версии v4: носитель кросс-группового бита переехал на ПЕРВЫЙ
блок группы, и смысл ключа стал задаваться местом блока — на голове «моя группа справа от
предыдущей», на любом другом «справа от предыдущего блока в моей группе». Один ключ, один
раскладчик, два уровня — не новая сущность, а снятие ограничения со старой. Раскладчик стал
двухпроходным (`packGroupRows` → `packRows`), вид приехал общим `fields.css` на три
поверхности, входы — жест (зона на строке подписи) и та же клавиша, уровень которой выбирает
`rowBitOwner`.

Дефект, найденный пробой ПЕРЕД следующим шагом (тесты его не видели): бит, который был
кросс-групповым, оставался на блоке, уехавшем с головы группы, — заголовок, выданный полю
(`Mod+Alt+T`), молча выкидывал вопрос из ряда и перестраивал его внутрь себя. Лечит
`reanchorRowBits`.

**Показ 15.4 владельцу переопределил остаток фазы.** Два решения подряд, оба на живой форме:
(1) **whitelist «умеют делить ряд» отменён целиком** — читаемость половинной колонки решает
автор формы, а не редактор, и заодно отменённое правило роняло случаи, о которых его довод
ничего не говорил (одинокий `text`/`heading`/`image` не мог встать в ряд ни с чем);
(2) **колонка ряда стала стопкой** — при длинном блоке слева справа помещается несколько
коротких. Обе правки уехали в ветку фазы отдельными коммитами, вне этапной сетки — процессный
промах, замеченный владельцем позже.

### Шаг 15.6 — двухколоночная секция (добавлен владельцем по ходу)

**Состояние — сделано.** Поставлен после показа: «мне нужно, чтобы в любую колонку в ряду можно
было кинуть сколько угодно блоков». Стопка справа оказалась половиной ответа — нужна была
СЕКЦИЯ из двух колонок, где каждая колонка стопка, а полноширинный блок под секцией её
закрывает. `settings.column` принял `'left'` наравне с `'right'`; версия НЕ поднималась —
правило только расширяет множество принимаемых документов.

Что уточнила реализация против спеки (все три записаны в §11):

- **`'left'` ПОСЛЕ `'right'` открывает НОВУЮ секцию.** Иначе две соседние секции в явной форме
  склеивались бы в одну 2+2, и у формы, собранной до этапа, молча менялось бы выравнивание.
- **Бит держится за КОМПАНИЮ секции**, а не за «личность по первому элементу»: тот ключ
  разваливал секцию от перестановки внутри неё.
- **Зоны жеста — стороны ряда**, а не «трети» (трети были деталью реализации 13.6 — замечание
  владельца: «про зону трети я вообще не понял, откуда у нас какие-то трети?»).

**Четыре дефекта, и ни один не был доступен прежним тестам.** Три нашёл владелец на живой форме
или я пробой перед следующим шагом: линия дропа ехала за блоком (dnd-kit отдаёт активный
элемент как `over`); в колонку нельзя было положить третий элемент (зона гасилась у того, кто
уже в секции); `Enter` из колонки вставлял строку МЕЖДУ колонками и разваливал структуру —
лечит `sectionSpanEnd` на всех путях вставки. Четвёртый нашёлся моей же пробой и был хуже
остальных: канон помечал битом `'left'` **заголовок формы**, то есть готовил документ, который
валидатор не принимает, — ряды теперь считаются по `rowGroups`, документу без заголовка.

Ревью этапа добавило ещё два: шаг вправо из левой колонки-одиночки разваливал стопку справа
(гашение «сирот» срабатывало на переезде внутри своей же секции), и позиция вопроса на оси
доезжала до подсказок строки ВАРИАНТА, убирая оттуда рабочие пункты. Попутно вскрылось третье,
глубже обоих: канон помечал левую колонку только там, где бита нет, — а «забранный» в неё
участник несёт `'right'`, и вставка второго элемента выгоняла из секции того, кто её открыл.

Клавиатура вышла шире плана: `Mod+Alt+←/→` стали ШАГОМ ПО ОСИ «полная ширина ↔ левая ↔ правая»
(`shiftColumn` + `rowPosition`), а не тумблером «в ряд / из ряда», и на краю оси пункт выпадает
из шпаргалки — обещать клавишу, которая молчит, нельзя.

### Шаг 15.5 — финализация

**Состояние — сделано.** Контракт фокуса §12 получил четыре строки и четыре теста на НАСТОЯЩЕМ
полотне (`SlashEditor` + стор), а не на изолированных строках со шпионом: шаг по оси переносит
блок в документе, колонки — отдельные контейнеры разметки, значит строка меняет DOM-родителя и
перемонтируется, и «каретка едет с блоком» держится уже не тем, что строку не тронули, а
страховкой движка (`last` + `focusLost`).

E2e дописаны под сквозной критерий фазы: `builder-keyboard` — заголовок формы правится как
обычная строка (`Mod+B`, откат `Mod+Z` тем же стеком), доезжает до респондента с разметкой, а
`<title>` остаётся плоским; секция собирается осью и держит стопку; `Enter` из колонки кладёт
строку под секцией; ряд внутри вопроса; на телефоне оба ряда разваливаются в стек.
`full-loop` — мышиная сторона снятого замка: у строки ответа свой кластер значков, её мусорка
удаляет СТРОКУ, а не вопрос. **Перенос поля мышью (dnd) в набор не добавлен** — это был бы
первый dnd-жест в наборе, и писать его вслепую под ночной прогон значит рисковать мигающим
тестом.

Справочники сверены целиком: `EDITOR.md` (§1 `form_title` и его инварианты, §6 `splitFormTitle`
на трёх поверхностях, §8 цепочка `v3→v4`, §11 ось, §12 фокус, §13 секция), `fields/README.md`,
скилл `editor-canvas`. `SCHEMA.md` и `API.md` фаза правила по ходу этапов.

## Фаза 16. Свойства блока

### Шаг 16.0. Контракт: ADR, спека, план

Задача пришла из сессии с владельцем 2026-07-30 (источник — **запрос человека**, `PROCESS.md`
§1.0): у каждого типа блока должно быть своё описанное место, настройки — по клику на ручке
блока, у каждого вопроса — имя для аналитики. Разговор шёл по спеке
[`DESIGN-block-settings.md`](DESIGN-block-settings.md), которая и стала первым артефактом.

**Что выяснилось при разборе кода, до всякого проектирования:**

- Знание о типе размазано по **девяти** местам, но больно ровно одно — редактор: в остальных
  оно собрано в исчерпывающий `switch`/enum, где забытый тип ловит компилятор или тест обеих
  сторон.
- Уникальная логика типа на полотне — не настройки, а **клавиатурное поведение поверхности
  строки**, и общая цепочка аккордов была скопирована трижды по 7–9 ветвей.
- **Гейта публикации нет вовсе.** Обещанное документами правило момента публикации («непустая
  подпись, ≥1 опция») не реализовано ни на бэке, ни в кабинете — `canPublish` смотрел только
  на «черновик сохранён». Значит «просим имя перед публикацией» — новый механизм, а не ещё
  одна проверка.
- Попап настроек **уже существовал** (`BlockActionMenu`, `Mod+.`) с теми же общими пунктами, а
  «настройки, адресованные группе» уже были реализованы пропом `requiredFor`. Работа
  сводилась к обобщению, а не к изобретению.
- Клик по ручке технически бесплатен: порог `activationConstraint: { distance: 6 }` стоял с
  фазы 13 ровно затем, «чтобы клик по ручке не начинал перетаскивание».

**Три решения владельца** (§10.1 спеки): срез по типам — **все три слоя, включая `entities`**
(владелец выбрал глубокий вариант против моей рекомендации «только редактор»); **старт до
тега `v0.15.0`** с названным риском; критерий 16.1 — уборка без смены поведения. Остальные
восемь решений оставлены открытыми и принимаются перед своими этапами — ADR-строка к ним
пишется тогда же, а не разом.

### Шаг 16.1. Срез по типам — три слоя

Разбит на три коммита-подэтапа **снизу вверх** (контракт → вид → редактор): обратный порядок
заставил бы `builder/kinds/*` сначала читать старые наборы-предикаты, а потом переписываться
на выведенные.

**16.1а — контракт.** Свойства типа объявлены в `entities/blocks/<type>.ts`; семь
наборов-предикатов (`CHOICE_TYPES`, `PLACEHOLDER_TYPES`, …) удалены, предикаты выводятся из
реестра. Три рукописные ветви `superRefine` («не имеет картинки/шкалы/опций») заменены одним
проходом по инвентарю закреплённых ключей.

Три условия, без которых глубокий срез сломал бы то, что чинит, — и все три оказались
предметными, а не формальными:

1. **Форма документа на проводе не изменилась**: `settings` остался тем же `strictObject`.
   Дискриминированное объединение по типу отклонено — оно меняет пути ошибок и форму зеркала в
   Go, то есть это смена контракта под видом уборки.
2. **У ключей РАЗНОЕ понятие пустоты, и это не небрежность:** `options: []` и `imageKey: ''` у
   чужого типа валидны с самого появления настроек, а `scaleMin: 0` — заданное значение (NPS).
   Общая проверка `!= null` начала бы отвергать уже сохранённые документы. Перенесено дословно
   в `OWNED_SETTINGS` и закреплено случаями в наборе.
3. **Критерий сформулирован как множество принимаемых документов**, а не как совпадение
   текстов ошибок: тексты у сгенерированной проверки меняться могли.

Go остался предикатным (решение владельца: реестр он импортировать не может), но состав типов
стал **одним** списком `blockTypes`, которым живёт `valid()`. Взамен ручной сверки сторон —
`TestBlockKindsParityWithFrontend`: читает файлы реестра фронта и падает на расхождении
состава типов, семьи, `carriesText`, `canShareRow` и кардинальности выбора.

**Ревью подтвердило эквивалентность замером, а не чтением:** 79 560 документов (17 типов ×
комбинации настроек) через старую и новую версию валидатора — расхождений accept/reject ноль;
153 сравнения предикатов — ноль. Единственное отличие: у не-scale блока с одним `scaleMax`
путь замечания переехал на `settings.scaleMax` (текст тот же).

**Четыре находки ревью — все про сторожей, ни одна про поведение.** Класс один: тест, который
молча перестаёт проверять, хуже отсутствующего.

- Парсер паритета читал **комментарии** как значения полей: `// carriesText: true — …` над
  полем `carriesText: false` подменял собой поле, и тест оставался зелёным при разошедшихся
  сторонах. Комментарии вырезаются до разбора.
- Состав типов на Go-стороне перечислялся **дважды** (switch в `valid()` и свой список в
  тесте). Тип, добавленный в Go и забытый в тесте, проходил паритет — а фронт отвергал
  документ целиком (`z.enum`), то есть опубликованная схема перестала бы разбираться у
  респондента.
- **Значимый нуль не сторожил никто:** случай стоял на самой шкале, где ключ закреплён и
  понятие «наличия» не проверяется вовсе. Перенесён на не-scale тип.
- `'title'`, упомянутый в комментарии внутри `BLOCK_TYPES`, приезжал в разобранный список
  фантомом и маскировал удаление типа.

**16.1б — вид.** `switch` на 14 ветвей в `FieldControl` заменён исчерпывающим
`Record<BlockType, Control | null>`; `null` у неотвечаемых — объявленный факт, а не пропуск.
Шесть текстовых контролов были шестью почти дословными копиями JSX — сведены к общему
`TextInput`; список вариантов single/multi — к `ChoiceList`. `RichText` вынесен в свой модуль:
контрол согласия его использует, и оставь он в `BlockField` — импорты замкнулись бы в цикл.

Эквивалентность проверена **двумя** замерами против старой реализации, и второй был не
формальностью: сравнение `innerHTML` (2380 рендеров, побайтово) **не видит обработчиков**,
поэтому отдельно сравнивалось поведение — change/click/blur на каждом интерактивном элементе.
Мутации, которые ловит только второй замер: шкала без снятия выбора повторным нажатием,
`multi_choice` с id вместо массива, снятый `onBlur`.

Две ловушки, которые не поймал бы ни один замер, потому что они про форму кода: `rows` вместе
с `type` в `TextInput` компилировался, а рисовалась `textarea` (тип поля молча терялся) —
пропсы стали разделённым объединением; `scale: null` в реестре компилируется, а значит
«контрола нет» — сторожит `fieldControls.test.ts`.

**16.1в — редактор.** Критерий выполнен буквально: в `BlockRow` не осталось ни одного
`block.type === …`, файл короче на 95 строк (1583 → 1489). В файлы типов уехали имя строки,
классы, высота кластера значков, глиф галочки у согласия, многострочность плейсхолдера,
наличие рядов у вариантов, контекст подсказок и сам контрол объектной остановки. `ScaleInline`
переехал в `kinds/scaleControl.tsx` — в этапе 16.3 выбор диапазона уедет оттуда в попап.

Контрол объектной остановки объявлен **компонентом**, а не строковым признаком: признак
пришлось бы разворачивать ветвлением в `BlockRow`, то есть оставить там ту же карту
«тип → контрол», которую этап уносит.

**Цикл импортов уронил девять наборов тестов.** Производный словарь иконок собирался на
инициализации модуля, а путь оказался замкнутым: глиф поля → иконки → реестр → файл типа →
контрол даты → глиф поля; реестр на тот момент `undefined` («Cannot convert undefined or null
to object»). Иконка стала функцией `typeIcon(t)` — обращение внутри функции происходит после
инициализации модулей. Урок общий: **производный словарь в графе с циклом неработоспособен в
принципе, а не «иногда»**; отложенный доступ — не оптимизация, а условие корректности.

**Что осталось хвостом.** Ревью подэтапов 16.1б и 16.1в свежим взглядом не пройдено — субагент
дважды оборвался на лимите сессии; предмет закрыт замерами и тремя постоянными сторожами, но
это не замена. Живая проверка полотна за владельцем: юниты держат модель и разметку, границу
«браузер ↔ наш код» они не видят.

### Шаг 16.2. Попап настроек блока и кластеры

**Записан задним числом при закрытии шага 16.4** (2026-07-31): разбор шага в журнал тогда не
попал, состояние жило только в `DEV-PLAN.md`. Факты — из спеки, ADR-строк и коммита `6b230ed`.

**Шесть решений владельца приняты до кода** (2026-07-30, спека §10.1). Главное из них —
**разворот решения 15.2**: у строки выбора в озаглавленном вопросе кластера значков нет вовсе.
Довод владельца: у списка было два этажа управления, различающихся парой пикселей, а цена
промаха разная — «удалить вариант» и «удалить поле выбора со всеми вариантами» не должны быть
соседними значками одного размера. Разворот записан ADR-строкой ДО кода, потому что он
отменяет действующую модель, записанную §4 `EDITOR.md`, а не добавляет новую.

**Вход в попап оказался бесплатным по конструкции.** Клик по грипу открывает настройки,
перетаскивание за ту же ручку по-прежнему тащит — и это не потребовало ни таймеров, ни
эвристик: порог активации `PointerSensor` стоял ровно затем, чтобы клик по ручке не начинал
драг. По тому же порогу (общая константа `DRAG_ACTIVATION_DISTANCE`) грип отличает свой клик
от **хвостового** `click`, который браузер шлёт после настоящего драга. Два числа с одним
смыслом обязаны быть одним числом: разъехавшись, они дают «иногда после переноса выскакивает
меню» — дефект, не воспроизводимый по заказу.

**Субъект настроек — обобщение, а не изобретение.** Проп `requiredFor` уже означал «строка
представляет поле своего вопроса», и считает его `GroupRow`, который один знает состав группы.
Отсюда всё правило целиком: подпись правит ПОЛЕ (смена типа меняет тип ответа, дублирование
копирует вопрос), голая строка и контент — себя.

**Контракт фокуса §12 перевёрнут в одном месте.** Попап — место, где каретку легче всего
потерять. Поэтому закрытие попапа САМО возвращает каретку на строку, а действия, уводящие её
осознанно, помечают себя флагом. Забытое действие тогда даёт не потерянную каретку, а каретку
на строке; `Esc` и клик мимо закрылись тем же правилом даром.

**`form_title` остался без попапа — следствие, а не упущение.** Спека требовала «ограниченный
попап», но после запретов (нельзя удалить, дублировать, сменить тип) в нём не осталось ни
одного пункта, а «пустой попап хуже отсутствующего» — довод самой спеки.

**Два пункта техдолга закрыты, и ни один — починкой кода.** TD-42 (автосейв терял правку при
уходе с полотна) чинить оказалось нечего: дыру закрыла фаза 15, а открытым пункт держало
отсутствие сторожа — сторож поставлен и предъявлен мутацией. TD-44 закрыт решением 6: строка
выбора не покидает свой вопрос вовсе, и асимметрия «мышью можно, клавиатурой нельзя» исчезла
вместе с жестом.

**Регрессию поймал владелец, а не тесты:** свой `onPointerDown` на грипе перебивал обработчик
dnd-kit и съедал драг. Ровно та граница «браузер ↔ наш код», на которой юниты слепы; сторож на
«нажатие доходит до dnd-kit» поставлен после.

### Шаг 16.3. Диапазон шкалы уехал с полотна

**Записан задним числом вместе с 16.2** (2026-07-31); факты — из коммита `607436f`.

Открытых решений у шага не было: он следует из §1 спеки — на полотне видно только то, что
увидит респондент, а выбор «от/до» респондент не видит. Это был единственный контрол
редактора, живший прямо в форме.

**Типовой раздел объявляет САМ ТИП** (поле `Settings` в `builder/kinds/<type>.tsx`) — та самая
«типовая секция», перенесённая из 16.2а к первому потребителю. Раздел — **компонент, а не
описание для генератора** (§3.5 спеки): связь «максимум хотя бы на шаг выше минимума» в
интерпретаторе стала бы веткой языка, и язык всегда был бы на шаг позади типов. Строки
раздела — общий набор (`kinds/settings.tsx`), и в нём ровно то, что понадобилось. Заодно
закрыта часть **TD-25**: нативных `select` в билдере не осталось.

Арифметика пары вынесена в чистую `nextScaleRange`: это единственное место, где здесь можно
сломать документ — `min >= max` отвергнет `ValidateSchema`, и автосейв ловил бы 422 на каждый
выбор значения.

**Предсказание спеки не сбылось, а нашлось обратное.** Спека ждала, что переезд сломает
селекторы `full-loop`; сценарий, однако, строит шкалу на дефолтном 1–5 и диапазон никогда не
трогал. Зато обнаружилось, что дорожка «попап → Radix-Select внутри Radix-поповера» не покрыта
ничем — ровно граница «браузер ↔ наш код». Шаг в `full-loop` добавлен; прогнать его можно
только против prod-local. Селектор этого шага пришлось починить уже в 16.4: он держался за
`role="group"` с именем вопроса, а на полотне такой группы нет — имя вопроса в `aria-label`
кладёт только `BlockField` (страница респондента и превью), `BlockControl` подписи не знает.

### Шаг 16.4. Имя вопроса

**Два решения приняты до кода** (владелец, 2026-07-31; ADR §10 `ARCHITECTURE.md`). Решение 3 —
модель **А**: имя есть *переопределение*, а не копия заголовка. Копия расходится с заголовком
молча при первой же его правке — ровно та путаница в аналитике, которую задача и лечит, а
честная копия требует третьего состояния «правил ли автор имя руками». Решение 4 — дубликаты
имён **не отслеживаются вовсе**; владелец отклонил мою рекомендацию «предупреждение в попапе»,
и отклонил обоснованно: предупреждение видит только тот, кто и так открыл попап, то есть
сигнала там, где ошибку совершают (второй вопрос), оно не даёт.

**Цена решения А снимается плейсхолдером, и это половина всей работы.** «Переопределение»
без показа того, что переопределяешь, — это поле, в которое автор вводит вслепую. Поэтому в
пустом поле стоит выведенное имя: буквально та строка, которая уйдёт в колонку CSV, если не
вводить ничего. Ради неё на фронте появилось зеркало `domain.questionLabel` без первой ступени
(`questionName.ts`). Зеркало — цена, названная вслух в комментарии: последнюю ступень («Тип N»)
Go собирает своей картой имён типов, фронт — подписью типа из реестра редактора, и
переименование подписи их разведёт. Второй набор имён типов на фронте стоил бы дороже — этап
16.1 их оттуда как раз убирал.

**Склейка истории приехала со своим первым потребителем**, как и планировал этап 16.2. Вида
правки `'setting'` не понадобилось: тег `updateBlockTag` строится по КЛЮЧАМ патча, и хватило
добавить `name` в список склеиваемых. Побочно это дало правильное поведение даром — набор
имени и набор подписи в один шаг не сливаются, потому что ключи разные, а общий шаг откатывал
бы вместе с именем весь заголовок.

**Поля `keeps` в реестре не появилось.** Спека предлагала его для «имя переживает смену типа»,
но что переносить, уже сказано предикатами, выведенными из реестра этапом 16.1
(`isAnswerableType`, `supportsPlaceholder`). Новое поле было бы вторым объявлением того же
факта — ровно тем, против чего фаза и затевалась.

**Найдено по дороге — плейсхолдер терял смену типа на `short_text → email`**, хотя оба типа
его показывают. Спека это предсказывала («одно правило чинит оба случая»), и так и вышло:
`carryPlaceholder` рядом с `carryLayout`. Соседний дефект — `single_choice → dropdown` стирает
набранные варианты — **не чинился**: этап про имя, а это своя задача (TD-47).

**Тест поймал не код, а обвязку теста, и это стоит запомнить.** «Стёртое имя убирает ключ»
краснел на верной реализации: обвязка рендерила снимок блоков вместо подписки на стор, поле
оставалось контролируемым от stale-значения, и React глотал возврат к пустой строке — значение
пропа не менялось. Полотно подписано на стор, значит и обвязка обязана быть подписана;
иначе проверяется не то, что делает редактор. Это тот же класс, что и «юниты не видят границу
браузер ↔ наш код»: расхождение обвязки с реальностью выглядит дефектом кода.

**Проверено:** `make lint`, `make test` (646 + 54 фронт, весь Go), бюджет рендерера 82.93 КиБ.
Новые сторожа предъявлены мутацией с обеих сторон контракта: снятая проверка «имя только у
отвечаемых» и снятый лимит длины красят по три кейса в Zod и в Go, снятый перенос имени и
снятая склейка — по тесту стора. **За владельцем** — живая проверка и e2e.

### Шаг 16.5. Гейт публикации

**Решение принято до кода** (владелец, 2026-07-31, спека §10.2 решение 5): гейт доменный с
зеркалом в TS, устройство — список, в v1 все три блокера. Владелец выбрал более широкий
вариант против осторожного «сузить до имени», и довод у широкого сильный: «непустая подпись,
≥1 опция» обещаны комментарием `ValidateSchema` с фазы 4 и не были реализованы нигде — то есть
документ врал четыре фазы подряд. Цена («форма, публиковавшаяся вчера с пустым списком
вариантов, сегодня получит отказ») названа вслух в ADR-строке.

**Главная граница этапа — не техническая, а смысловая:** правило момента ПУБЛИКАЦИИ против
правила ХРАНЕНИЯ. `ValidateSchema` обязана принимать недособранный черновик, иначе автосейв
ловил бы 422 посреди набора; поэтому гейт — отдельная функция, а не ещё одна ветка валидатора.
Это записано тестом, а не только комментарием: `TestPublishGate_BlockedDocumentsStayValid`
берёт документы, которые гейт отвергает, и требует, чтобы валидатор их принял.

**Список, а не одноразовая проверка.** Один блок может нарушить два правила (голый список
выбора без заголовка — безымянный вопрос И список без вариантов), и карта по `block_id`
второе замечание потеряла бы. Отсюда же новое поле конверта `blockers` рядом с `fields`:
приём тот же (`errors.As` по типизированной доменной ошибке), а форма другая, потому что
данные другие.

**Зеркало в TS — осознанная плата, и её пришлось развести аккуратнее, чем ожидалось.** Цепочка
вывода имени теперь читается двумя способами: у гейта имя первой ступенью (зеркало
`domain.authoredLabel`), у плейсхолдера поля — та же цепочка БЕЗ имени. Склеить их в один
вызов нельзя: имя стояло бы плейсхолдером самому себе. Разложено на три функции
(`inheritedName` / `authoredQuestionName` / `derivedQuestionName`), и это тот случай, когда
третья функция дешевле одного «умного» флага.

**Ревью этапов 16.2–16.4 (проведено параллельно) вернуло три подтверждённых дефекта**, все
починены до слияния, и два из них поучительны:

1. **Попап варианта ронял каретку в `body`** на `Esc`. Правило §12 у попапа БЛОКА было
   написано и покрыто тестом, у попапа ВАРИАНТА — нет, а комментарий рядом утверждал, что
   фокус ставит список. Утверждение верно для «дублировать»/«удалить» (состав меняется,
   срабатывает эффект) и неверно для закрытия без действия. **Урок: комментарий, объясняющий,
   почему кода нет, стареет вместе с кодом** — и в отличие от кода его не проверяет ничто.
2. **Тест «имя и текст — разные шаги отмены» не сторожил своё правило:** правки шли в разные
   блоки, а теги истории расходятся по `id` независимо от ключей патча. Мутация «тег без
   ключей» оставляла все 177 тестов зелёными — при том что в проде согласие (блок с `text` И
   `name`) теряло бы набранный текст одним `Mod+Z` вместе с именем. **Урок тот же, что и в
   16.4 про обвязку: тест, поставленный не на тот объект, зелёный по причине, к правилу
   отношения не имеющей.**
3. Имя вопроса не доехало до панели ответа в кабинете — четвёртая копия цепочки вывода
   подписи, о которой `ANALYTICS.md` предупреждает прямым текстом («копии этого правила не
   падают, а молча показывают владельцу разные формы на соседних экранах»). Починено там же.

Ревью нашло и **расхождение единиц у строковых лимитов** (руны на Go, UTF-16 в Zod) — оно
конвенционное, живёт с фазы 8 и касается всех строк схемы, поэтому чинится не здесь: TD-48.

**Гейт отменён владельцем в тот же день, после показа кода** («этот гейт мне не нравится»,
2026-07-31). Удалён целиком; ADR-строка переписана в отменяющую ДО удаления кода — сведения о
том, что гейт существовал и был снят решением, обязаны пережить его код, иначе следующий заход
построит то же самое, приняв отсутствие за упущение.

Спрошенное владельцем «подставлять дефолтное название, если названия нет нигде» строить не
пришлось: оно есть с фазы 8.7 — последняя ступень `questionLabel` даёт «Шкала 3». Это стоит
запомнить как приём: **прежде чем строить замену снятому механизму, стоит проверить, не
работает ли она уже.** Половина ответа на «уберём и сделаем вот так» была «уберём».

Свёрнуты обратно и половины цепочки имени, вынесенные под гейт (`authoredLabel`,
`authoredQuestionName`): у каждой остался один вызывающий, а функция, живущая ради удалённого
потребителя, — ещё один способ соврать читателю. Отмена обошлась дёшево именно потому, что
гейт был отдельной функцией с одним вызовом, а не ветками внутри `ValidateSchema`.

### Шаг 16.6. Контракт поверхности строки

Спека насчитала три копии цепочки аккордов — их оказалось **четыре плюс призрак списка**.
Это само по себе довод: копию, о которой забыли, не находят чтением, её находят, когда она
разошлась.

**Сведено не в общую реализацию, а в общий ПОРЯДОК** (`rowKeys.ts`): различия поверхностей
настоящие (уходит ли стрелка со строки, что значит `Backspace`, куда идёт печатный символ), и
попытка склеить их в одну функцию дала бы флаги вместо ясности. Поверхность объявляет
обработчики и два guard-а — `arrowLeaves` и `backspaceHandles`.

**Настоящая находка этапа — не дублирование, а то, чем оно держалось.** Порядок проверок был
устной традицией: голые матчеры `enter`/`backspace`/стрелок модификаторы не исключают, поэтому
`Mod+Enter` обязан ловиться раньше `Enter`, `Alt+Shift+↑↓` — раньше `Alt+↑↓`. Каждая из копий
выводила это заново, и одна уже носила рукописную заплату (`!chords.moveGroup(e)`) — то есть
вывела неточно и была починена локально. Теперь правило общее: **аккорд, подходящий под более
частный матчер, не проваливается в более общий** — `Alt+Shift+↑↓` глушится даже там, где
переносить группу нечем, потому что «перенести вопрос» не имеет права молча означать
«перенести строку».

**Два места, где поведение держалось на порядке веток, а не на решении, стали видимыми.**
`Mod+Enter` в призраке списка попадал в общую ветку `enter`; `Alt+Shift+↑↓` на варианте
попадал в `moveItem`, потому что ветки `moveGroup` там просто не было. Оба поведения
сохранены и объявлены вслух — второе с пометкой «карта обещает здесь другое». **Урок:
рефакторинг, который сводит копии, обязан отличать поведение-решение от поведения-совпадения;
второе он делает видимым, а не тихо исправляет** — иначе «уборка без смены поведения»
перестаёт быть уборкой.

### Шаг 16.7. Финализация

Финализировать почти нечего — и это главный факт шага. Все семь документов §12 спеки
правились **своими** этапами, поэтому к концу фазы не осталось долга «дописать доки». Это
прямое следствие правила проекта «документ обновляется в том же PR, что и код»; фаза 14 и 15
заканчивались иначе.

Осталась сводная таблица типов — и к ней **машинный сторож**: `make check-docs` сверяет строки
таблицы с `BLOCK_TYPES` в обе стороны (тип без строки и строка без типа красят прогон, обе
мутации предъявлены). Довод тот же, по которому в проекте вообще заведён этот скрипт:
«как добавить тип» — документ, куда идут за полнотой списка, и устаревшая карта там хуже
отсутствующей. Проверка, которая не краснеет, хуже отсутствующей (PROCESS §4).

**Итог фазы по её собственному критерию (§1 спеки):** четыре обещания из четырёх закрыты —
тип описан в одном месте; настройки уехали к ручке, полотно осталось WYSIWYG; у вопроса
появилось имя, видимое там же, где оно правится; правило «свойство типа — в файле типа,
отношение блоков — в центре» выдержало проверку на прочность в 16.6, где соблазн унести
клавиатурную цепочку в файлы типов был максимальным.

**Пятый этап (гейт публикации) в критерий §1 не входил и снят владельцем** — фаза кончается
там же, где начиналась по замыслу.
