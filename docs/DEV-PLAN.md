# План разработки по фазам — конструктор форм (MVP), редакция 2

Редакция под новое ограничение: **VPS пока нет**, вся разработка ведётся локально, CI живёт в GitHub. Деплой отодвинут в конец и разбит так, что почти вся его подготовка делается заранее без сервера — когда VPS появится, ввод прода в строй займёт один день, а не неделю.

## Три контура: как организована среда

Ключевая идея редакции: контуров не два, а три, и средний из них — секретное оружие разработки без сервера.

**Контур dev — ежедневная работа.** Postgres в Docker, Go-API через `go run` (или `air` с hot-reload) прямо на хосте, оба фронта через `vite dev` с HMR. Порты: api `:8080`, app `:5173`, renderer `:5174`; Vite проксирует `/api` и `/public` на `:8080`, поэтому CORS в dev не нужен. Максимальная скорость итерации: правка кода видна за секунды.

**Контур prod-local — репетиция прода у себя на машине.** Полная прод-сборка, запущенная локально: настоящие Docker-образы (distroless), настоящий `compose.prod.yml`, настоящий Caddy с доменами `app.localhost` и `f.localhost` (API — same-origin под `app.localhost/api`, отдельного домена нет — ADR §10; домены `*.localhost` резолвятся сами, Caddy выдаёт на них TLS от своего локального CA — получаем честный https без единой DNS-записи). Этот контур поднимается командой `make prod-local` и означает: **всё, что нужно для прода, кроме самого сервера, написано и проверено**. Когда появится VPS, изменится только имя хоста и способ доставки файлов.

**Контур prod — настоящий VPS.** Появится в фазе 9. К этому моменту от prod-local он будет отличаться четырьмя вещами: реальные домены и DNS, Let's Encrypt вместо локального CA, секреты из GitHub Secrets/серверного `.env`, бэкапы в offsite-хранилище. Всё остальное — байт в байт те же образы и тот же compose.

Чтобы три контура не разъехались, действует правило **одного бинарника и одного набора env-переменных**: приложение не знает, в каком контуре живёт; все различия (DSN базы, домены cookie, уровень логов, параметры rate limit) — только через окружение. Файлы: `.env.example` (документация всех переменных), `.env.dev`, `.env.prod-local` — в репозитории; `.env` прода — только на сервере. Никаких `if env == "dev"` в коде — это классический источник «на проде повело себя иначе».

CI в GitHub с первого дня, но без деплоя: его работа — линт, тесты, сборка фронтов и **сборка прод-образов** (публикация в GHCR по тегу). То есть релизные артефакты копятся в registry заранее; деплой потом — это «скачать готовое», а не «собрать на сервере».

## Как читать план

Формат прежний. Каждая фаза: **Цель** (абзац), **Шаги** (единицы «сел — сделал — закоммитил», от получаса до пары часов), **Демо в конце фазы** (что вы увидите глазами — критерий приёмки), **Definition of Done** (технический шлагбаум). Принципы: вертикальные срезы вместо слоёв; тесты внутри фазы, а не потом; уродливое-но-работающее раньше красивого.

Карта фаз:

```
Фаза 0. Фундамент и CI                   → «hello» одной командой, зелёный CI в GitHub
Фаза 1. Аутентификация                   → регистрация и вход через браузер
Фаза 2. Формы как сущности (CRUD)        → дашборд со списком форм
Фаза 3. Билдер                           → редактор блоков с автосохранением
Фаза 4. Публикация и публичный рендерер  → форма открывается по локальной ссылке
Фаза 5. Приём ответов                    → отправленный ответ ложится в базу
Фаза 6. Просмотр ответов и CSV           → таблица ответов и скачанный файл
Фаза 6.5. Редактор в стиле Tally         → сборка формы slash-редактором (билдер фазы 3 — временный)
Фаза 7. Prod-local: репетиция прода      → весь стек под https на *.localhost
Фаза 8. Полировка                        → undo/redo, drag-and-drop, тёмная тема
Фаза 8.5. Продуктовый минимум            → телефон и шкала, сводка ответов, лимит мест, просмотры и конверсия
Фаза 9. Ввод прода в строй (когда есть VPS) → продукт на реальном домене
Фаза 10. Эксплуатационная зрелость        → восстановленный бэкап, алерт в Telegram
```

Обратите внимание: полировка (фаза 8) и продуктовый минимум (фаза 8.5) сознательно стоят **до** деплоя — они не требуют сервера, а VPS может появиться в любой момент и фазы 9–10 просто «вклинятся», когда будут возможны.

## Фаза 0. Фундамент и CI

**Цель.** Монорепозиторий, где вся рутина автоматизирована с первого коммита: одна команда поднимает dev-контур, GitHub на каждый push гоняет полный набор проверок. Всё настроенное здесь экономит время в каждой следующей фазе.

**Шаги.**

1. Инициализировать репозиторий со структурой из архитектурного документа (`cmd/`, `internal/`, `web/app`, `web/renderer`, `migrations/`, `deploy/`). Пустые пакеты с `doc.go`, чтобы скелет был виден сразу.
2. `go.mod`, минимальный `cmd/api/main.go`: сервер на stdlib, маршрут `GET /healthz` → `{"status":"ok"}`, `slog` в JSON, чтение конфига из env через маленький хелпер с валидацией обязательных переменных при старте (упасть сразу, а не на первом запросе).
3. `compose.dev.yml`: только Postgres 16 с volume, порт на `127.0.0.1:5432`. Файлы `.env.example` и `.env.dev`.
4. Makefile — единая точка входа: `make dev` (БД + API с hot-reload), `make test`, `make lint`, `make migrate-up/down`, `make seed` (заглушка, наполнится позже). Раннер миграций — команда `./api migrate up` внутри бинарника (golang-migrate как библиотека); миграция `0001` — пустышка-проверка механизма.
5. `golangci-lint` (errcheck, govet, staticcheck, gofumpt) + конфиг.
6. Заготовки фронтендов: два Vite-проекта react-ts, strict TypeScript, eslint + prettier; в `vite.config.ts` приложения — proxy `/api → :8080`. Пока рендерят строку текста.
7. GitHub Actions, workflow `ci.yml`: на push и PR — линт Go, `go test -race`, `tsc --noEmit` + eslint + vitest для обоих фронтов, сборка обоих фронтов. Кэширование Go-модулей и node_modules, чтобы прогон был минуты, а не десятки минут. Красный CI = нельзя мержить (branch protection на main).

**Демо в конце фазы.** На чистой машине: `git clone`, `cp .env.dev .env`, `make dev` — через минуту `curl localhost:8080/healthz` отвечает JSON, `npm run dev` в обоих фронтах показывает страницы. В GitHub на коммите — зелёная галочка со всеми jobs.

**Definition of Done.** README «как запустить за 5 минут»; CI зелёный и быстрый (<5 минут с кэшами); `.env.example` описывает каждую переменную комментарием; приложение падает при старте с внятной ошибкой, если переменной не хватает.

## Фаза 1. Аутентификация

**Цель.** Полный контур учётных записей: регистрация, вход, сессия, выход. Первая настоящая вертикаль «БД → сервис → API → экран», на которой обкатываются все паттерны проекта: слои, формат ошибок, интеграционные тесты, работа TanStack Query с API.

**Шаги.**

1. Миграция `0002`: `users`, `workspaces`, `workspace_members`, `sessions`. Генератор UUIDv7 в `internal/domain` с юнит-тестом на монотонность.
2. Обёртка argon2id (параметры OWASP) + юнит-тесты.
3. Модуль `auth`, слой repo (sqlc): создание пользователя, поиск по email, CRUD сессий. Регистрация создаёт пользователя, личный воркспейс и членство **одной транзакцией**.
4. Слой service: `Register`, `Login` (одинаковое время ответа для «нет email» и «неверный пароль»), `Logout`, `GetMe`; доменные ошибки (`ErrEmailTaken`, `ErrInvalidCredentials`).
5. HTTP-слой: `/api/v1/auth/*`; cookie httpOnly+SameSite=Lax (флаг Secure — из env: в dev по http он выключен, в prod-local/prod включён — первый пример «различие контуров живёт в env»); CSRF-токен; middleware `RequireAuth`; единый `respond.go` с маппингом доменных ошибок; in-memory rate limit на `POST /auth/login`.
6. Фоновая горутина чистки истёкших сессий — заодно общий механизм периодических задач.
7. Интеграционные тесты против Postgres в testcontainers: регистрация → логин → me → logout → 401. Эти тесты гоняются и в CI (testcontainers работает на GitHub-раннерах из коробки).
8. Фронт: экраны Login/Register в layout-группе `_auth`; api-клиент (fetch-обёртка: CSRF-заголовок, разбор единого формата ошибок); layout-группа `_app` с загрузкой `/auth/me` и редиректом; кнопка выхода.

**Демо в конце фазы.** Локально в браузере: регистрируетесь → попадаете в пустое приложение со своим email в шапке → F5 — сессия жива → выход → защищённый маршрут редиректит на логин. Неверный пароль — человеческая ошибка под полем. Цикл curl'ом по `/auth/login` упирается в rate limit.

**Definition of Done.** Интеграционные тесты auth зелёные локально и в CI; в БД нет паролей и токенов в открытом виде; повторная регистрация на email — 409 с внятным сообщением.

## Фаза 2. Формы как сущности (CRUD)

**Цель.** Дашборд: создать форму, увидеть список, переименовать, удалить. Билдера ещё нет — форма пока карточка с названием. Появляется вся механика ресурсов с проверкой прав, копируемая дальше как паттерн.

**Шаги.**

1. Миграция `0003`: `forms`, `form_versions`; генератор slug (nanoid ~10 символов, свои 20 строк).
2. Repo: создание с пустой `draft_schema`, список по воркспейсу с курсорной пагинацией, получение, обновление title, удаление.
3. Service: каждая операция начинается с проверки членства в воркспейсе (анти-IDOR закладывается в первом же ресурсе). Юнит-тест на запрет чужого доступа обязателен.
4. HTTP: `GET/POST /forms`, `GET/PATCH/DELETE /forms/{id}`. Интеграционный тест: пользователь A не трогает форму пользователя B (404).
5. `make seed`: скрипт сидирования (пользователь + 60 форм) — нужен для проверки пагинации и дальше пригодится постоянно.
6. Фронт: `forms.index` — грид карточек через TanStack Query; «Новая форма» (мутация + инвалидация + переход в заглушку редактора); переименование инлайн; удаление с подтверждением; скелетоны; пустое состояние.
7. Заглушка маршрута `forms.$slug.edit`: показывает title и JSON черновика — точка входа фазы 3.

**Демо в конце фазы.** Создаёте три формы → карточки с датами → переименовали, удалили → F5, всё на месте. Второй аккаунт в инкогнито по чужому URL получает 404. После `make seed` список корректно листается.

**Definition of Done.** Тесты изоляции воркспейсов зелёные; пагинация проверена на 60 формах; мутации фронта корректно инвалидируют кэш Query.

## Фаза 3. Билдер

**Цель.** Сердце продукта: редактор, где форма собирается из блоков семи типов, всё автосохраняется. Публикации нет — билдер работает только с черновиком.

**Шаги.**

1. Контракт схемы: Zod-схемы `FormSchema`/`Block` в `web/*/src/entities` + зеркальные Go-типы с `ValidateSchema` (лимиты: ≤200 блоков, ≤100 опций, длины строк). Единственный шаг без картинки — он определяет язык обеих сторон.
2. Бэкенд: `PATCH /forms/{id}` принимает `draft_schema` → `ValidateSchema` → оптимистичная блокировка по `updated_at` (расхождение → 409). Интеграционные тесты: валидная схема сохраняется, мусор — 422, устаревший `updated_at` — 409.
3. Zustand-стор билдера: `{blocks, selectedId, dirty}`; операции add/update/remove/move/duplicate. Стор — чистый TypeScript без React, покрывается vitest сразу.
4. Каркас экрана: палитра типов слева, канвас-список в центре, панель настроек справа. Клик по типу добавляет блок, клик по блоку выделяет.
5. Редактирование: label/description инлайн на канвасе; справа — required и типоспецифика (для choice — редактор опций: добавить, переименовать, удалить, порядок).
6. Автосейв: дебаунс 800 мс → `PATCH` всей схемы; индикатор «Сохранение…/Сохранено/Ошибка — повторить»; при 409 — баннер «Изменено в другой вкладке»; предупреждение при уходе с несохранённым.
7. Перемещение блоков кнопками вверх/вниз (dnd — в фазе 8).
8. Живое превью (переключатель «Редактор/Превью»): блоки рендерятся как увидит респондент. Компоненты полей пишутся в общий пакет — фаза 4 переиспользует их в рендерере.

**Демо в конце фазы.** Накидываете анкету из 6–7 вопросов всех типов → превью показывает её глазами респондента → закрыли вкладку, открыли — всё на месте. Соседняя вкладка меняет ту же форму — первая честно сообщает о конфликте.

**Definition of Done.** Юниты стора и `ValidateSchema` зелёные; автосейв не теряет правки при непрерывном вводе 30 секунд; превью совпадает с набором блоков.

**Примечание о редакторе.** Палитра-канвас-редактор этой фазы — сознательно временный: его задача дать рабочий редактор, чтобы прогнать бэкенд через фазы 4–6. Целевой UX (markdown-полотно со slash-командами в стиле Tally) вынесен в отдельную фазу 6.5; он заменит только поверхность ввода, переиспользуя стор, схему, автосейв и превью этой фазы.

## Фаза 4. Публикация и публичный рендерер

**Цель.** Форма получает жизнь за пределами кабинета: «Опубликовать» создаёт иммутабельную версию, форма открывается по ссылке без входа. Локально роль «публичного домена» играет второй vite-порт — этого достаточно, чтобы увидеть и проверить всё поведение.

**Шаги.**

1. Публикация на бэке: `POST /forms/{id}/publish` одной транзакцией создаёт `form_versions` (version = max+1), ставит `published_version_id`, `status='published'`; `unpublish` → `closed`. Тесты: две публикации подряд — версии 1 и 2.
2. Публичный эндпоинт `GET /public/v1/forms/{slug}`: схема опубликованной версии + title; `Cache-Control: public, max-age=60` и ETag; 404 для черновиков и закрытых. Сюда же — HMAC-токен времени выдачи (поле для антиспама фазы 5).
3. Превью ссылок (Open Graph): HTML-документ страницы формы `/r/{slug}` отдаёт **Go**, а не статика — только так краулеры мессенджеров/соцсетей получат мета (они читают HTML, не выполняя JS). Go подставляет в `<head>` опубликованной формы `og:title`/`og:description` (из title и описания формы) и `og:image` — пока **общая брендовая заглушка** (базовый URL картинки из env; своя картинка на форму — пост-MVP, зависит от загрузки файлов). Тело документа грузит тот же React-SPA — «голова на сервере, тело на клиенте». **Безопасность:** title/описание — пользовательский текст, вставляется в мета только через автоэкранирование (`html/template`), никогда «сырым»; черновик/закрытая форма отдают **404**, как и JSON-ручка, — HTML-путь не раскрывает существование приватного; `dangerouslySetInnerHTML` по-прежнему под запретом. Одинаково во всех контурах (никакого «мета только на проде»).
4. Рендерер (`web/renderer`, vite на `:5174` с proxy `/public → :8080`): slug из pathname (`/r/{slug}`), рендер всех семи типов из общих компонентов фазы 3, ответы в `useReducer`, черновик ответов в sessionStorage. Экраны «загрузка», «форма недоступна» (в фазе 5 — единый 404: черновик, закрытая и несуществующая неотличимы) и «ошибка загрузки». (Позже, в фазе 8.5 шаг 4, закрытая форма отделена от 404: своя `410`-семантика и экран «приём закрыт» — см. раздел шага 4; черновик по-прежнему 404.)
5. Клиентская валидация по той же Zod-схеме: required, email, число, дата; ошибки по blur и при отправке.
6. Бюджет бандла рендерера проверяется в CI (превышение валит сборку), но порог **поднимается выше 60 КБ gzip** — React + react-dom исчерпывают его в одиночку; конкретное число фиксируется здесь. Запасной выход, если из-за веса не берётся Lighthouse ≥90: свап рендерера на `preact/compat` (алиас `react → preact/compat` только в сборке рендерера — компоненты остаются на React-API, `@fields` не трогаются). Кнопка «Отправить» пока дизейблится с подписью «скоро» либо пишет в консоль.
7. Кабинет: кнопка «Опубликовать» в шапке билдера; после — панель со ссылкой `localhost:5174/r/{slug}` (базовый URL публичной части — из env: ещё одно различие контуров, живущее в конфигурации), «Копировать», статус «Опубликовано · версия N», бейдж «Есть неопубликованные изменения», кнопка «Закрыть форму».

**Демо в конце фазы.** Публикуете анкету → копируете ссылку → открываете в инкогнито (и с телефона по локальной сети через `--host`): форма грузится мгновенно, поля работают, валидация подсказывает. Меняете вопрос без публикации — инкогнито по F5 видит старую версию; публикуете — новую.

**Definition of Done.** Тесты публикации/версий зелёные; бюджет бандла в CI работает; черновики недоступны по прямому URL ни при каком статусе (включая HTML-путь превью); превью-ссылка отдаёт корректные OG-мета опубликованной формы, а пользовательский текст в них экранирован (тест на инъекцию вида `"><script>` в title); Lighthouse (mobile) на рендерере ≥90 по Performance.

## Фаза 5. Приём ответов

**Цель.** Респондент отправляет ответ — он надёжно ложится в базу с привязкой к версии формы. Самый атакуемый эндпоинт делается сразу правильно: валидация, лимиты, антиспам, идемпотентность.

**Шаги.**

1. Миграция `0004`: `submissions`. Валидатор `ValidateAnswers(schema, answers)` — обязательность, типы, принадлежность опций, длины. Самая ветвистая функция проекта: табличные юнит-тесты (3–5 кейсов на тип блока) пишутся **до** реализации.
2. `POST /public/v1/forms/{slug}/submissions`: MaxBytesReader 256 КБ → статус формы → антиспам → `ValidateAnswers` против опубликованной версии → INSERT с `form_version_id` → 201. Ошибки — 422 с картой `block_id → сообщение`.
3. Антиспам: honeypot (заполнен → молчаливый 200 без записи) + HMAC-токен времени из фазы 4 (быстрее 3 секунд → отказ). Юниты на оба контура.
4. Идемпотентность: рендерер генерирует `submission_id` (UUIDv7) при первом нажатии «Отправить», ретраи шлют тот же id; конфликт PK на сервере = успех. Тест: двойной POST — одна строка.
5. Жёсткий rate limit по IP на эндпоинт, отдельный от общего.
6. Рендерер: состояние отправки, маппинг 422 на поля, авторетрай при обрыве сети (до 3 раз с бэкоффом), экран «Спасибо», очистка sessionStorage.
7. Сквозной интеграционный тест: создать → опубликовать → валидный ответ → невалидный ответ → проверить содержимое БД. Живая документация продукта.

**Демо в конце фазы.** Заполняете форму в инкогнито → «Спасибо». Без обязательного поля → ошибка у нужного поля. Обрываете сеть на середине отправки (DevTools offline), возвращаете — ответ уходит ровно один раз (видно по `SELECT count(*)`). У ответа в базе — id той версии, что была на экране.

**Definition of Done.** Табличные тесты `ValidateAnswers` покрывают все типы; дубль не создаётся; тело >256 КБ → 413; honeypot-ответы не попадают в БД.

## Фаза 6. Просмотр ответов и экспорт

**Цель.** Замкнуть петлю ценности: автор видит ответы в таблице и уносит их в CSV. После этой фазы MVP функционально полон — всё остальное готовит его к реальным людям.

**Шаги.**

1. `GET /forms/{id}/submissions`: курсорная пагинация по UUIDv7 (новые сверху), общий счётчик, у каждого ответа — его версия формы.
2. CSV-экспорт: стриминг `encoding/csv` в `ResponseWriter` без буферизации всего в память (тест на 10 000 сидированных строк — расширяем `make seed`). Колонки — объединение блоков по всем версиям (вопрос, удалённый в v2, остаётся колонкой для ответов v1); UTF-8 BOM для Excel; choice-ответы — подписями опций, не id.
3. Фронт `forms.$slug.responses`: таблица по вопросам актуальной версии, бесконечная подгрузка `useInfiniteQuery`, клик по строке — панель полного ответа (включая вопросы старых версий), счётчик «N ответов» на карточке в дашборде.
4. «Экспорт CSV» — обычная навигация на эндпоинт (cookie авторизует, браузер качает).
5. Удаление отдельного ответа с подтверждением (GDPR-гигиена).

**Демо в конце фазы.** Отправляете три ответа из инкогнито → они в таблице кабинета новыми сверху → открываете один целиком → «Экспорт CSV» → файл открывается в Excel с читаемой кириллицей и подписями опций. Публикуете v2 с изменённым вопросом, отвечаете — в таблице мирно живут ответы обеих версий.

**Definition of Done.** Экспорт 10 000 строк не растит память (профиль pprof); версии корректны в таблице и CSV; пагинация без дублей и потерь на границах страниц.

## Фаза 6.5. Редактор форм в стиле Tally

**Вставка после фазы 6.** К этому моменту весь конвейер (собрал → опубликовал → собрал ответы → выгрузил) работает end-to-end, и его продемонстрировал временный палитра-канвас-редактор фазы 3. Здесь он заменяется сигнатурным для продукта редактором: единое markdown-подобное полотно, где блоки добавляются slash-командой («/» → меню типов), текст правится инлайн, мышь нужна по минимуму. Это переработка поверхности ввода, а не фундамента — потому и стоит после ценностной петли, а не внутри неё.

**Расширение фазы (решение владельца продукта):** вместе со slash-редактором делается общий визуальный редизайн кабинета в стиле Notion/Tally — сайдбар-навигация вместо шапки, единый вид всех экранов (дашборд, таблица ответов, auth). Для этого в `web/app` снята заморозка зависимостей и подключён UI-слой **Tailwind CSS v4 + shadcn/ui** (см. ADR-сводку и `web/CLAUDE.md`). Инвариант: Tailwind/shadcn — только в кабинете; рендерер (`web/renderer`) остаётся на react+zod под бюджетом 95 КиБ, общие `@fields` не переводятся на Tailwind. Работа ведётся пятью вертикальными срезами: (A) фундамент Tailwind+shadcn и процессные документы; (B) сайдбар-оболочка; (C) рестайл существующих экранов; (D) slash-редактор; (E) уборка временного билдера фазы 3.

**Цель.** Сборка формы ощущается как письмо в редакторе: пишешь заголовок и текст вопроса прямо в полотне, «/» открывает список типов полей, Enter/стрелки/Backspace создают, двигают и сливают блоки как в обычном текстовом редакторе. Автосейв, версии, публикация — уже готовое из фаз 3–4; редактор просто дёргает те же операции стора.

**Что переиспользуется и что переписывается.** Остаются: модель `FormSchema`/`Block`, Zod- и Go-контракт, `ValidateSchema`, zustand-стор с операциями над блоками, автосейв (дебаунс → PATCH → 409), превью и общие компоненты полей `@fields`. Переписывается только поверхность: `Palette`/`Canvas`/`SettingsPanel` уступают место полотну-редактору, а типоспецифичные настройки (опции choice, required) переезжают из отдельной панели в инлайн-контролы у активного блока.

**Шаги (детализируются перед стартом).**

1. ~~Возможное расширение схемы «неотвечаемыми» блоками~~ **Сделано:** добавлен тип `text` — неотвечаемый абзац и дефолт новой строки (Enter/мышь создают его, «/» превращает в поле). Контракт расширен в Go (`internal/domain/schema.go`, `isContent()`) + Zod (`formSchema.ts`, `isContentType`) одним PR; `schemaVersion` не менялся (новое значение enum обратно совместимо). `text` исключён из `ValidateAnswers`, CSV и таблицы ответов, в рендерере — статический абзац. Заголовок секции/разделитель — при необходимости позже тем же паттерном.
2. Полотно: блоки как редактируемые строки; фокус и навигация с клавиатуры (Enter — новый блок, Backspace в пустом — слить/удалить, ↑/↓ — переход), инлайн-правка label/description.
3. Slash-меню: «/» в начале блока открывает фильтруемый список типов; выбор превращает блок в поле нужного типа. Мышиный фолбэк (кнопка «+») для доступности.
4. Инлайн-настройки: опции choice добавляются строками прямо под вопросом; required и типоспецифика — компактным контролом у активного блока.
5. Ввод и доступность: весь путь сборки управляем с клавиатуры; drag-and-drop блоков (dnd-kit) либо переезжает сюда из фазы 8, либо остаётся кнопками — решить на месте.

**Демо в конце фазы.** Форму из 6–7 вопросов собираешь, почти не отрывая рук от клавиатуры: пишешь вопрос → «/» → выбираешь тип → Enter → следующий. Превью и публичная ссылка показывают ровно то же; автосейв и конфликт-баннер работают как раньше.

**Definition of Done.** Клавиатурный путь сборки формы полон (создание, тип через «/», перемещение, удаление — без мыши); формы, созданные в билдере фазы 3, открываются в новом редакторе без потери данных (или через апгрейдер, если менялся `schemaVersion`); автосейв/версии/публикация не затронуты; превью совпадает с полотном.

**Состояние — закрыта (владелец продукта принял фазу).** Итог: редизайн кабинета на Tailwind+shadcn (сайдбар, дашборд, таблица ответов, auth); slash-редактор как документное полотно (название первой строкой, «/»-меню и модальный диалог «+» с выбором типа, клавиатурная навигация, dnd-kit-перетаскивание с фиксом сжатия блоков разной высоты, инлайн-опции choice); инлайн-контролы у блока — `required` (в правом поле блока) и `description`; «/» превращает в поле и уже заполненный `text`-блок (набранный текст становится подписью); неотвечаемый тип `text`; форма-уровневый `submitLabel` и `settings.placeholder` — оба расширяют контракт (Go+Zod+рендерер) с тестами. Публикация переехала на страницу «Поделиться» (`/forms/$slug/share`): публичная ссылка с копированием, предпросмотр карточки (зеркалит серверные OG-мета формы `/r/{slug}` — заголовок и тизер из первых вопросов) и управление (перепубликация изменений, закрытие, повторная публикация закрытой); черновик публикуется с редиректом туда, клик по опубликованной форме в списке ведёт туда же. Смена типа уже выбранного блока намеренно запрещена (только пересоздание). **Не делали (при необходимости — позже):** блоки-заголовки секций и разделитель.

## Фаза 7. Prod-local: репетиция прода без сервера

**Цель.** Собрать весь прод-контур у себя на машине. В конце фазы продукт работает под https на трёх `*.localhost`-доменах из настоящих прод-образов — то есть от реального прода его отделяет только наличие сервера. Всё, что здесь написано (Dockerfile, compose, Caddyfile, релизный пайплайн), потом переедет на VPS без изменений.

**Шаги.**

1. Multi-stage Dockerfile для Go: сборка в `golang:1.26` (в тон `go.mod`) → `distroless/static:nonroot`, `CGO_ENABLED=0`, ~25 МБ. Локальная проверка: образ собирается, healthz отвечает из контейнера.
2. `deploy/compose.prod.yml`: caddy + api + postgres; Postgres без порта наружу; healthcheck'и; `restart: unless-stopped`; api стартует после миграций (init-команда `migrate up` тем же образом).
3. `deploy/Caddyfile`: два сайта `app.localhost` (статика кабинета + `/api/*` в Go same-origin) и `f.localhost` (статика рендерера + `/r/*` и `/public/*` в Go) — Caddy сам выдаёт TLS от внутреннего CA; SPA-fallback, иммутабельный кэш `/assets/*`. Выделенного `api`-домена нет (ADR §10): кабинет и его API — один origin, поэтому CORS не нужен. Доменные имена — параметром окружения, чтобы этот же файл работал на проде с реальными доменами.
4. Прод-сборка фронтов: `vite build` обоих проектов, скрипт раскладки статики в volume Caddy. База API кабинета и публичного API — относительные пути (`/api`, `/public`), same-origin, VITE-переменных для них нет (ADR §10); через `VITE_*` на этапе сборки задаётся только `VITE_PUBLIC_BASE_URL` (ссылка на форму в бандле кабинета). Рендерер собирает entry и CSS со стабильными именами `/renderer.js` и `/renderer.css`, а пути к ним на HTML-странице `/r/{slug}` (её отдаёт Go, а не собранный `index.html`) Go берёт из `PUBLIC_RENDERER_SCRIPT_PATH` (dev `/src/main.tsx`, prod `/renderer.js`) и `PUBLIC_RENDERER_STYLE_PATH` (dev пусто — vite инжектит CSS через JS; prod `/renderer.css`). Оба огреха («голова на сервере» не знала про собранные ассеты) всплыли и закрыты здесь. *(Устарело: в фазе 8, шаг 7 эти пути и стабильные имена сняты по корню — Go строит `/r/{slug}` из собранного `index.html`, `PUBLIC_RENDERER_SCRIPT_PATH`/`STYLE_PATH` удалены, ассеты — дефолтные хеши.)*
5. `make prod-local`: собрать образ и статику, поднять `compose.prod.yml` с `.env.prod-local`, прогнать тонкий smoke; `make prod-local-down` — погасить (тома с данными остаются). Smoke (`scripts/prod-local-smoke.sh`) — проверка живости + того, чего не было в dev: `/healthz` по внутренней compose-сети (api без внешнего порта, distroless без curl); `app.localhost/` и `f.localhost/` → 200 через Caddy; `f.localhost/r/<несуществующий>` → 404 (путь Caddy→Go→Postgres); регистрация по https → `Set-Cookie: …Secure`; мутация без `X-CSRF-Token` → 403. Полное открытие опубликованной формы глазами — это e2e шага 7 и ручная визуальная проверка, не smoke. CORS не проверяем — его нет по устройству (ADR §10). Нюанс, всплывший здесь: `include .env; export` в Makefile + приоритет шелл-переменных над `--env-file` у compose — поэтому `.env.prod-local` источается в тот же рецепт (иначе контейнеры подхватывают dev-DSN). «Настоящий замочек» (демо-критерий) требует доверия к локальному CA Caddy — разово `make prod-local-trust` (sudo; Firefox — свой стор).
6. Релизный пайплайн в GitHub Actions: по git-тегу `v*` — сборка и публикация Go-образа в GHCR + сборка статики фронтов и прикрепление артефактом к GitHub Release. Деплоя нет — но каждый тег с этого момента даёт готовый к развёртыванию комплект.
7. Прогон Playwright e2e (регистрация → билдер → публикация → ответ с мобильного вьюпорта → таблица → CSV) против prod-local контура; добавить job в CI. Сделано двумя срезами: **7a** — пакет `e2e/` с одним сценарием (`@playwright/test`, санкционирован ARCHITECTURE §8), зелёный локально против `make prod-local`; **7b** — workflow `.github/workflows/e2e.yml` (`workflow_dispatch` + nightly `schedule`, не на каждый PR — стек тяжёлый): поднимает prod-local и гоняет e2e. Тест сторожит оба пойманных в фазе регресса (пустая форма без entry-скрипта, форма без стилей). Побочно e2e вскрыл гонку билдера (rename заголовка ↔ автосейв схемы по `updated_at` → 409) — вынесена отдельной задачей, тест её обходит.
8. Заголовки безопасности (CSP, nosniff, frame-options) в Caddyfile; проверить локально curl'ом; убедиться, что секреты не запечены в образ (`docker history`).

**Демо в конце фазы.** `make prod-local` — и через пару минут в браузере `https://app.localhost` (настоящий замочек), полный путь пользователя работает; `https://f.localhost/r/{slug}` открывает форму. В GitHub Releases на теге лежат образ и статика. Playwright-прогон зелёный.

**Definition of Done.** prod-local поднимается одной командой с нуля; e2e зелёный против него; куки/CSRF работают в честной https-схеме (same-origin кабинет+API); релиз по тегу воспроизводим.

## Фаза 8. Полировка

**Цель.** Пройтись по продукту руками и убрать трение. Сервера не требует, поэтому стоит до деплоя; если VPS появится раньше — фазы 9–10 можно вклинить перед ней без конфликтов.

**Шаги.**

1. Drag-and-drop блоков (dnd-kit) вместо кнопок вверх/вниз; кнопки остаются для клавиатурной доступности.
2. Undo/redo в билдере (стек снапшотов в сторе, Ctrl+Z/Ctrl+Shift+Z) + юниты.

   **Состояние — сделано.** В сторе билдера — стеки `past`/`future` (снапшоты `{blocks, submitLabel}`); все мутации документа проходят через приватный `commit(tag, producer)`: кладёт снапшот, чистит `future`, ставит `dirty`; no-op (граница move/reorder, чужой блок) историю не трогает. **Коалесинг текста** (решение владельца): непрерывный ввод в одно поле делит один шаг отмены (маркер `lastTag`), `required` и структурные операции — свой шаг. `hydrate` сбрасывает историю, `markSaved` её хранит, undo/redo ставят `dirty` и чинят выделение. Хоткеи Ctrl/Cmd+Z / Ctrl+Shift+Z / Ctrl+Y на весь экран билдера + кнопки в шапке (disabled по глубине стека). **Название формы в undo НЕ входит** — оно серверное состояние вне стора (rename отдельной колонки), откат отдан нативному undo браузера. Два прод-only нюанса, всплывшие при ручной проверке: (а) хоткей сверяется по `e.code` (`KeyZ`/`KeyY`), а не `e.key` — иначе при кириллической раскладке `Ctrl+Z` даёт `e.key='я'` и отмена молча ломалась; (б) поле названия сделано неконтролируемым (`defaultValue`) — контролируемый React-инпут стирает нативный стек undo браузера. 11 юнитов стора на историю/коалесинг/границы.
3. Пустые состояния и микро-UX: дашборд без форм, форма без ответов, дружелюбные 404, фокус-стили и tab-порядок в рендерере, человеческие сообщения о сетевых ошибках.

   **Состояние — сделано.** Большая часть закрыта по ходу прошлых фаз (инвариант `web/CLAUDE.md`: loading/error/empty обязательны у каждого экрана с данными): дашборд (empty + error + retry), таблица ответов («Ответов пока нет» + error), единый 404-экран рендерера, auth (`describeError` даёт человеческое «Сеть недоступна» для не-`ApiError`, поля с `role="alert"`/`aria-invalid`), ShareView (ошибки публикации). Добиты два пробела: (а) **app-level 404 кабинета** — `defaultNotFoundComponent` в `createRouter` (`main.tsx`) + `shared/NotFound.tsx` (полностраничный, вне оболочки `_app` — путь может быть без сессии; ссылка «К формам»); раньше неизвестный URL давал служебный текст TanStack. (б) **Фокус submit-кнопки рендерера** — `.rf-submit:focus-visible` в общем `fields.css` (у `rf-input`/`rf-mark` фокус уже был); поля и глифы выбора — настоящие `<input>`/`<textarea>`/radio/checkbox, tab-порядок натуральный. (в) **Error-boundary кабинета** — `defaultErrorComponent` (`shared/ErrorScreen.tsx`): краш лоадера/рендера маршрута даёт «Что-то пошло не так · Повторить/К формам» (reset перезапускает маршрут) вместо служебной ошибки TanStack. Схему БД/контракт API/`entities` шаг не трогает. **Про HTTP-коды (осознанно):** 404/ошибка кабинета — «мягкие» (HTTP 200 + SPA-fallback Caddy `try_files → index.html`, «404» рисует клиент; настоящий 404 требовал бы дублировать таблицу роутов на сервере — не делаем, стандарт для кабинета за логином). Публичная страница формы `/r/{slug}` — **настоящий 404** (Go: `PublicForm → ErrNotFound → respond.go → 404`, тест `TestPublicHTML_NotPublished_Returns404`): там код видят краулеры, и он честный.
4. ~~Тёмная тема рендерера по `prefers-color-scheme`~~ **Снято (решение владельца продукта).** Из объёма фазы 8 исключено; при необходимости — отдельной задачей пост-MVP. Номер шага сохранён (на «шаг N» ссылаются другие документы — сдвиг сломал бы ссылки).
5. Дубликация формы с дашборда и блока в билдере.

   **Состояние — частично (решение владельца: сейчас только форма).** Сделана **дубликация формы с дашборда** + разъезд «имя vs заголовок» (ADR §10, миграция 0006 `forms.name`). Модель: `title` — **публичный** заголовок (его видит респондент, OG-мета, рендерер не тронут), `name` — **внутреннее** имя дашборда (`NULL`→кабинет показывает `title`). Дубликат: `POST /api/v1/forms/{id}/duplicate` → `Duplicate` копирует `draft_schema` и `title` **дословно** (чистый заголовок), а суффикс `«(копия N)»` кладёт в `name`; `N` — без коллизий по соседям воркспейса (`ListFormNames` + `nextCopyName`: «(копия)», «(копия 2)»…, база без старого хвоста, обрезка по рунам). Новые `id`/`slug`, статус всегда `draft`, проверка членства — как везде. Переименование на дашборде теперь правит `name` (`PATCH {name}` → `UpdateName`, пусто→`NULL`); первая строка билдера по-прежнему правит `title`. Контракт: `Form.name` (Go+Zod), `PATCH` принимает ровно одно из `name`/`title`/`draftSchema`. Юниты: доступ, чистый title + суффикс в name, нумерация по соседям (табличный), обрезка, сброс имени. Интеграционные `TestForms_Duplicate` (title чистый, name=«(копия)», вторая копия=«(копия 2)», чужую нельзя) и `TestForms_UpdateName`. Фронт: `displayFormName(name ?? title)` на дашборде и в таблице ответов; пункт «Дублировать» в меню карточки; `useDuplicateForm`/`useUpdateFormName` инвалидируют список, **остаёмся на дашборде**. Доки: ARCHITECTURE (модель+ADR), SCHEMA, API. **UI дубликации блока в билдере пока НЕ делаем** — стор-операция `duplicateBlock` уже есть и покрыта тестом, контрол отложен.

Номер шага сохранён (сдвиг сломал бы ссылки).
7. **⚠️ ВАЖНО. Устранить хрупкость HTML-страницы формы `/r/{slug}`: Go должен рендерить её из собранного `index.html` рендерера, а не из рукописного шаблона.**

   **Состояние — сделано.** Реализовано как vite-SSR template-replace: в `web/renderer/index.html` — плейсхолдер `<!--og-meta-->`; Go читает собранный `index.html` при старте (в проде смонтирован в api read-only, `PUBLIC_RENDERER_INDEX_PATH=/srv/renderer/index.html`; mount в `compose.prod.yml`), заменяет плейсхолдер на OG-мету через `html/template`, ассеты берёт из HTML дословно. Рукописный `formPageTmpl` удалён; `PUBLIC_RENDERER_SCRIPT_PATH`/`STYLE_PATH` сняты из `config`/`.env.*`/`compose`; имена ассетов вернулись к дефолтным хешам под `/assets/*` (immutable-кэш). Favicon формы, который прод не показывал, теперь работает (шёл из собранного HTML). В dev `/r` отдаёт vite-dev — Go его не регистрирует (различие в одном конфиг-флаге, не в `if env==dev`). Юниты доказывают «новый ассет сборки не требует правок Go» (лишний `<link preload>` в фикстуре доезжает дословно) и экранирование `"><script>`; выбор mount вместо `go:embed` — чтобы `index.html` и ассеты всегда были из одной сборки (нет рассинхрона версий).

   **Проблема.** Сейчас страницу формы отдаёт рукописный `html/template` в `internal/forms/public_page.go`: «голова на сервере» (OG-мета для краулеров), «тело на клиенте» (React-SPA). Но этот шаблон **вручную перечисляет ассеты, которые генерит vite** — тег `<script>` на entry и `<link>` на CSS. Vite же на каждой сборке решает сам, какие файлы произвести и как их назвать. Из-за этого расхождения в фазе 7 дважды ловили баг прода, который не виден в dev (там vite-dev отдаёт исходники и инжектит CSS через JS): (а) шаблон ссылался на dev-путь `/src/main.tsx`, которого нет в сборке → пустая форма; (б) шаблон не выводил `<link>` на вынесенный CSS → форма без стилей. Каждый будущий ассет сборки (шрифт-preload, дополнительный чанк при code-split, модульный preload, favicon-манифест) — потенциально **третий** такой баг, который проявится только на проде. Оба раза чинили симптом (стабильные имена `/renderer.js`, `/renderer.css` + config-пути `PUBLIC_RENDERER_SCRIPT_PATH`/`PUBLIC_RENDERER_STYLE_PATH`), а не причину.

   **Причина** — дублирование источника истины: список ассетов формы существует в двух местах (собранный `index.html` и Go-шаблон) и обязан совпадать вручную. Это ровно тот антипаттерн, что запрещён по проекту в других местах (Zod↔Go, схема↔валидатор): один контракт — одно место.

   **Решение.** Go отдаёт `/r/{slug}`, **беря за основу собранный `web/renderer/dist/index.html` и вставляя в его `<head>` только OG-мета** (`og:title`/`og:description`/`og:image`/`og:url` + `<title>`/`<meta name=description>`). Все ссылки на ассеты (`<script>`, `<link>`, любые preload) берутся из собранного HTML как есть — Go их не перечисляет и не знает их имён. Расхождение становится невозможным по построению: что vite собрал, то Go и отдал.

   **Что учесть при реализации.**
   - **Доступ Go к собранному HTML.** api-контейнер сейчас не видит статику (её раздаёт Caddy из своего volume). Варианты: (1) смонтировать renderer-статику в api read-only и читать `index.html` при старте (кэшировать в памяти, не читать на каждый запрос); (2) встроить собранный `index.html` в Go-образ через `go:embed` — но это связывает Go-образ с фронт-сборкой и ломает наш порядок «образ собирается до фронтов», поэтому (1) предпочтительнее. Решить и, при (1), добавить mount в `compose.prod.yml`.
   - **Различие контуров (dev).** В dev собранного `index.html` нет — vite-dev генерит его на лету и инжектит CSS через JS. Значит нужен dev-путь: либо в dev Go продолжает отдавать минимальный шаблон со `<script src="/src/main.tsx">` (тогда шаблон остаётся, но только для dev и без CSS-заботы), либо Go в dev проксирует/читает `index.html` с vite-dev. Различие живёт в env/конфиге, а не в `if env==dev` (инвариант проекта).
   - **Безопасность (не ослабить инвариант 4).** Вставка в существующий HTML — только через безопасный парсинг/шаблонизацию: собранный `index.html` — **доверенный** (наш билд), но OG-значения (`title`/тизер) — **пользовательский текст** и по-прежнему экранируются `html/template`; `dangerouslySetInnerHTML`-эквивалентов (сырая склейка строк с пользовательским вводом) не вводить. Сохранить существующие тесты: 404 для черновика/закрытой, экранирование инъекции `"><script>` в title.
   - **Упрощение как бонус.** После рефактора `PUBLIC_RENDERER_SCRIPT_PATH` и `PUBLIC_RENDERER_STYLE_PATH` больше не нужны (ассеты приходят из HTML) — удалить их из `config`, `.env.*`, `compose`, доков. Стабильные имена `/renderer.js`/`/renderer.css` можно вернуть к хешированным (`entryFileNames`/`assetFileNames` по умолчанию) — это вернёт `immutable`-кэш на entry и CSS (сейчас они ревалидируются каждый визит).
   - **Проверка.** Тот же прогон, что вскрыл оба бага: собрать prod-local, опубликовать форму, `GET /r/{slug}` — в `<head>` есть и OG-мета, и все ассеты из собранного `index.html`; форма открывается со стилями; добавление в рендерер нового ассета (напр. отдельного чанка) **не** требует правок Go.

**Демо в конце фазы.** Пятиминутный демо-прогон без стыдных моментов: создать → собрать драг-энд-дропом → опубликовать → ответить с телефона → таблица и CSV.

**Definition of Done.** Undo/redo покрыт юнитами; билдер с 50 блоками не тормозит при вводе; страница формы `/r/{slug}` рендерится из собранного `index.html` (Go не перечисляет ассеты вручную; добавление ассета в сборку не требует правок Go; конфиги `PUBLIC_RENDERER_SCRIPT_PATH`/`PUBLIC_RENDERER_STYLE_PATH` удалены), инвариант экранирования OG-меты сохранён; ручной чек-лист по всем экранам (два браузера + телефон) без блокеров.

**Состояние — закрыта (владелец продукта принял фазу).** Итог: drag-and-drop блоков (шаг 1, сделан ещё в фазе 6.5 на dnd-kit); undo/redo в билдере со стеком снапшотов и коалесингом текста (шаг 2); пустые состояния и микро-UX — app-level 404 и error-boundary кабинета, фокус submit рендерера, аудит loading/error/empty (шаг 3); дубликация формы с дашборда с разъездом «внутреннее имя (`forms.name`) vs публичный заголовок (`forms.title`)» и нумерацией копий «(копия N)» (шаг 5, ADR §10, миграция 0006); страница формы `/r/{slug}` из собранного `index.html` (шаг 7). **Снято решением владельца:** тёмная тема рендерера (шаг 4) и целенаправленный профайлинг производительности + повторный Lighthouse (шаг 6) — при необходимости пост-MVP. **Не делали (при необходимости — позже):** UI дубликации блока в билдере (стор-операция `duplicateBlock` уже есть и покрыта тестом).

## Фаза 8.5. Продуктовый минимум: от «работает» к «выбрали бы»

**Цель.** Закрыть слой продуктовых дыр между технически работающим конструктором и инструментом, который живой человек предпочтёт привычным аналогам. Итог продуктового аудита кабинета: цикл «создать → опубликовать → собрать ответы» замкнут, но респондент после отправки упирается в фиксированную заглушку, среди типов вопросов нет телефона и выпадающего списка, ответы читаются только по одному в диалоге, форму нельзя ни встроить на сайт, ни закрыть по лимиту мест. Сервера фаза не требует (как и фаза 8) — VPS может появиться в любой момент, фазы 9–10 вклинятся без конфликтов. Порядок шагов — приоритет: фазу можно резать в любом месте, если сигналы пользователей потребуют другого. Самая ценная фича этого слоя — **email владельцу о новом ответе** — сознательно НЕ здесь: ей нужна транзакционная почта, она добавлена шагом в фазу 11 POST-MVP.

**Шаги.**

1. **Экран «после отправки»: свой текст благодарности и redirect.** Два необязательных поля в схеме формы (имена — в мини-дизайн-доке до кода): после успешной отправки рендерер показывает текст владельца вместо стандартной заглушки либо уводит по ссылке. Схема — контракт: Zod + Go + `ValidateSchema` синхронно, в одном PR (инвариант `web/CLAUDE.md`); иммутабельность версий покрывает настройки автоматически (респондент видит экран той версии, по которой отправил). Redirect валидируется на бэке: только абсолютный `http(s)`-URL, `javascript:` и прочие схемы отбрасываются.

   **Состояние — сделано.** Имена полей (решение владельца): плоские `thankYouText` и `redirectUrl` рядом с `submitLabel` — тот же прецедент (форма-уровень, необязательное, дефолт на стороне рендерера), вложенный `afterSubmit:{}` отклонён как лишний уровень (YAGNI). Контракт синхронен: Zod (`formSchema.ts`) + Go (`domain/schema.go`), лимиты 2000/2000, табличные тесты обеих сторон зеркалят друг друга. **Поведение при обоих заданных полях (решение владельца): показать текст, затем перейти через ~2 с** — человек успевает прочитать благодарность; без своего текста читать нечего, уходим сразу (`planThankYou`, чистая функция). Запасная ссылка «Перейти на сайт» показывается, когда переход уже запущен (заблокирован в iframe/фоне → не тупик). **Валидация redirect (решение владельца): строго в `ValidateSchema`, даже в черновике** — вопреки общему правилу «черновик ленив», т.к. значение идёт в `window.location` (инвариант 4). Цена — автосейв мог бы ловить 422 посреди набора URL, поэтому редактор коммитит поле по `blur` (локальный черновик до этого), а не на каждое нажатие; альтернатива «мягко + строго на публикации» отклонена: отдельного валидатора публикации в проекте нет, а до его появления `javascript:` уезжал бы в опубликованную версию. Рендерер проверяет ссылку повторно перед переходом (не доверяет схеме на месте использования). **Место в кабинете (решение владельца): страница настроек, не полотно** — полотно остаётся документом из блоков (кнопка отправки на нём остаётся: её видит респондент, правка на месте — WYSIWYG). Иконка-шестерёнка в шапке подменяет полотно страницей `FormSettings` — это третий вариант существующего `Mode` в `BuilderScreen` (превью так работало с самого начала), режим локальный: F5 возвращает в редактор, ссылки на настройки нет. Оформление признано владельцем временным («пока»): страница — посадочное место и для настроек шага 4 (закрытие формы, лимит мест). Стор: поля вошли в `Snapshot`, undo/redo разворачивают снапшот целиком (`...prev`) вместо перечисления полей руками — именно перечисление и теряет новое поле молча; юнит-регресс на это есть. Настройки применяются одним экшеном `setAfterSubmit` (одно нажатие «Сохранить» = один шаг undo); те же значения — no-op. Бюджет рендерера: 79.41 КиБ gzip из 95. Схему БД, контракт API и `entities`-эндпоинты шаг не трогает (только JSONB-документ). Доки: ARCHITECTURE §3.4, SCHEMA, `web/shared/fields/README.md`.

   **Сохранение настроек — явное, кнопкой (решение владельца).** Полотно живёт на автосейве, но настройки везде сохраняют кнопкой, и молчаливый автосейв ломал бы привычный флоу («сохранилось или нет?»). Поля держат локальный черновик, «Сохранить» разом коммитит их в стор и тут же уносит на сервер через `saveNow` (бывший `retry` из `useAutosave` — одна операция «сохранить сейчас, без дебаунса» на два вызова: повтор после ошибки и эта кнопка). «Назад к редактору» — на самой странице; иконка в шапке настройки только открывает (тумблером она была бы вторым выходом мимо диалога и неочевидным — по иконке не догадаться, что жать её надо второй раз). Уход с несохранёнными правками — `AlertDialog` «Остаться / Уйти без сохранения». **Осознанная граница:** диалог стережёт только «Назад»; уход через «Просмотр»/«Ответы»/«Поделиться» с несохранёнными настройками теряет их молча — оформление признано временным, при следующем заходе в эту зону закрыть.

   **Попутно починены два дефекта, вскрытые этим шагом (оба — не в его объёме, но блокировали демо-критерий):** (1) **автосейв не следил за новыми полями** — подписка в `useAutosave` сверяла только `blocks`/`submitLabel`, поэтому правка одних настроек ставила `dirty`, но сохранение не планировала (текст благодарности ждал бы чужой правки блока); теперь сверяются все поля документа. (2) **утечка внутреннего текста респонденту** — `submissions.Submit`/`ExportCSV` оборачивали сбой разбора опубликованной схемы через `%w`, сохраняя сентинел `domain.ErrValidation`: `respond.go` принимал нарушенный инвариант версии за ошибку ввода и отдавал 422 с текстом «не удалось разобрать схему: json: unknown field …» прямо на экран формы (сокрытие текста в `WriteError` работает только для 5xx). Теперь `%v` рвёт цепочку → 500, текст скрыт и залогирован с request_id; регресс-тест `TestSubmit_UnparsableVersionSchema_IsInternalNotValidation`. Второй слой той же утечки — рендерер показывал текст сервера при любом не-2xx; теперь 5xx с нашим конвертом даёт человеческое сообщение, а осмысленные 4xx (антиспам, лимит) едут своим текстом (ретраи на 502 без конверта не тронуты). Тот же класс в `forms.Publish` **не** чинился — кабинет, не публичная страница: вынесен в TECH-DEBT **TD-19**.

2. **Новые типы вопросов: телефон, выпадающий список, шкала, чекбокс-согласие.** Четыре вертикальных среза по чек-листу `web/shared/fields/README.md`: тип в Zod+Go, серверная валидация ответа, общее поле в `@fields` (бюджет рендерера!), пункт slash-меню, ячейка CSV, сводка (шаг 3). Телефон — мягкая серверная валидация (допустимые символы и длина, не жёсткий формат РФ). Dropdown переиспользует модель опций `single_choice` — различие только в рендере. Шкала — диапазон в настройках блока (1–5 … 1–10). Согласие — обязательный чекбокс с текстом владельца (юридический кирпичик под фазу 12 POST-MVP).

   **Состояние — сделано.** Четыре среза, по коммиту на каждый; контракт Zod+Go синхронно, тесты обеих сторон зеркалят друг друга. **Кодировка ответа — строкой у всех четырёх** (решение владельца): тип `Answer` (`string | string[]`) не расширен ни на число, ни на булев. У согласия это несущая деталь, а не экономия: булев `false` не равен `''`, не попал бы в `isEmpty` рендерера, и обязательность молча перестала бы работать — регресс-тест падает, если неотмеченное согласие перестаёт считаться пустым. **Телефон** — мягко: символы и число цифр (5..20), не формат страны; тесты фиксируют, что `+380`/`+1` проходят. **Dropdown** — отдельный тип на модели опций `single_choice` (тот же формат ответа, другой контрол — нативный `<select>`, на телефоне системное колесо). Ветвление «одиночный против множественного» переведено на предикаты `isSingleChoice()`/`isSingleChoiceType()` в трёх местах (ValidateAnswers, CSV, `formatAnswer`): при сравнении с конкретным типом dropdown молча уезжал в ветку multi и ждал массив — регресс-тест это ловит. **Шкала** — оба конца диапазона (решение владельца: `0 ≤ min < max ≤ 10` закрывает и 1–5, и NPS 0–10, который иначе потребовал бы правки контракта, когда формы уже опубликованы); `ScaleMin/ScaleMax` — **указатели**, т.к. 0 — законный минимум и с `omitempty` вылетал бы из JSON, делая «не задано» неотличимым от «задано 0»; концы выбираются `<select>`-ом, а не вводятся числом — иначе невалидные промежуточные состояния дают 422 автосейва на каждое нажатие (ловушка `redirectUrl`). Диапазон при валидации берётся из **той** версии схемы, по которой отправлен ответ. Бюджет рендерера: 80.05 КиБ gzip из 95 (четыре контрола стоили ~0.6 КиБ).

   **Отступление от буквы плана (решение владельца):** согласие **не** «всегда обязательное» — обязательность осталась обычным флагом `required`, включённым у нового блока. Необязательное согласие — реальный случай (маркетинг-opt-in, подписка на рассылку), а «всегда обязателен» потребовал бы спецслучая в `ValidateSchema` и запретил бы этот сценарий.

   **Попутно (вне объёма шага):** `AnswerField` в редакторе рисовал **захардкоженный** `<input type="date">` всем типам без плейсхолдера — шкала попала бы туда и выглядела датой; у неё теперь свой `ScaleInline` с живым превью делений. Доки: ARCHITECTURE §3.4 (типы, предикаты семантики, кодировка ответа), SCHEMA (типы, настройки шкалы, таблица кодировок), `web/shared/fields/README.md`.

3. **Ответы: колонки в таблице и вкладка «Сводка».** В таблице сейчас только дата и версия — добавить колонки первых отвечаемых блоков (длинный текст обрезается, полностью — в существующем диалоге). Вкладка «Сводка»: распределение по вариантам для choice-типов и шкалы (CSS-бары, без графических библиотек — список зависимостей заморожен), среднее/мин/макс для чисел, доля заполнивших для текстовых. Агрегация — на бэке (SQL по JSONB `answers`); браузеру сырые ответы целиком не выгружаются.

   **Состояние — сводка сделана; колонки таблицы отложены (решение владельца):** таблица — «исключительно UX», владелец дорабатывает её отдельным заходом, поэтому шаг закрыт только сводкой. Инвариант «браузеру сырые ответы целиком не выгружаются» соблюдён: наружу уходят счётчики (9999 ответов → тело 666 Б).

   **Агрегация — в Go, а не в SQL (решение владельца, отступление от буквы этого шага).** Семантика ответа (`yes` — отмеченное согласие, массив — множественный выбор, `"4"` — деление шкалы) живёт в типах блока, то есть в домене; выразить её ещё и на SQL значило бы завести **третью** копию правил после Go и Zod — ровно тот класс молчаливых ошибок, что описан в «трёх граблях» `web/shared/fields/README.md` (забытая ветка не падает, а трактует новый тип как соседний). Свёртка (`domain/summary.go`) — по образцу `CSVBuilder`, тот же диспатч по типам, поэтому сводка и выгрузка не могут разойтись в том, что значит ответ. Память плоская: в потоке копятся только счётчики — O(вариантов), не O(ответов). Цена решения: БД отдаёт серверу ответы, а не готовые числа. **Замер на dev (9999 ответов, 4 вопроса): ~96 мс.** Опасение владельца о нагрузке закрыто не рассуждением, а метрикой: handler пишет строку лога `submissions summary` с `form_id`, числом свёрнутых ответов и длительностью — длительность запроса middleware логирует и так, но без знаменателя она бесполезна (900 мс на 300 ответах и на 30 000 — разные новости). Это третий слой наблюдаемости из ARCHITECTURE §«Мониторинг» (счётчики в лог + `jq`, а не Prometheus на одном VPS); новых зависимостей ноль. Если лог покажет рост — вариант «SQL» вернётся на стол уже с фактами.

   **Место в кабинете (решение владельца): свой маршрут `/forms/$slug/summary`, а не локальный стейт вкладки** — ссылка сохраняется в закладки, F5 не сбрасывает, «Назад» браузера работает. Бары — на CSS (Tailwind кабинета; `rf-*` тут ни при чём — это не полотно формы). **Доработано сразу после (решение владельца, «сейчас неудобно находить сводку»):** три экрана одной формы — «Поделиться», «Ответы», «Сводка» — собраны в **табы** pathless-группы `_manage` (`forms.$slug._manage.tsx`) с общей шапкой (назад, название, статус, «Редактировать»); адреса не изменились, поэтому адресуемость сводки цела — табы это маршруты, а не стейт. До этого экраны были не соседями, а цепочкой: ответы прятались в меню карточки, сводка достижима только кнопкой со страницы ответов, назад к «Поделиться» — через «К формам». Клик по опубликованной **и закрытой** форме на дашборде ведёт теперь на «Ответы» (она роздана — ежедневный вопрос «что написали?»), черновик — по-прежнему в редактор. Табы — свои ссылки, а не shadcn `Tabs`: тот тянет `@radix-ui/react-tabs` (новая зависимость, список заморожен) и рассчитан на локальный стейт. Редактор в группу не входит — другой режим, во всю ширину полотна. Три почти одинаковые шапки схлопнулись в одну.

   **Знаменатель — `asked`, а не `total`:** сколько человек вопрос **видели** (ответы по версиям, где он был). Вопрос, добавленный в v2, иначе выглядел бы пропущенным у всех, кто отвечал по v1 — на форме CSV-демо это видно глазами: «Город» (только v2) даёт 5999 из 5999, «Телефон» (только v1) — 4000 из 4000, при 9999 ответах всего. Доля считается от ответивших; у **множественного выбора** сумма долей больше 100 % намеренно (доля от людей, не от галочек); у **согласия** база — `asked`, т.к. его «Нет» = `asked − answered` — снявший галочку и не тронувший вопрос это одно и то же осознанное «нет», а не пропуск. Модель вопросов — правило колонок CSV (объединение версий, подпись из свежайшей); у шкалы — все деления диапазона, включая нулевые (иначе бары врут о форме шкалы), у choice — невыбранные варианты с нулём.

   **Попутно (в объёме шага):** общее начало выгрузки и сводки вынесено в `versionedSchemas` и `eachSubmission` — копия курсорной логики в двух местах разъехалась бы на первой правке пагинации; `ExportCSV` переведён на них, интеграционный тест выгрузки зелёный. Склонение «ответ/ответа/ответов» переехало в `shared/format` (второй потребитель). Удаление ответа инвалидирует и сводку — иначе таблица и распределения расходятся на глазах. Контракт проверен **реальным ответом сервера**: фикстура Zod-теста снята curl'ом с dev-контура (выдуманная проверяла бы схему саму против себя).

   **Найдено, но не чинилось:** кабинет ретраит 4xx (`QueryClient` без `defaultOptions`), из-за чего несуществующая форма может залипнуть на «Загрузке» вместо «Форма не найдена» — воспроизводится и на нетронутой странице редактора, то есть не регрессия этого шага → **TD-20**. Грабля подсветки активного таба (конфликт Tailwind-утилит одинаковой специфичности: класс на элементе есть, вида нет; ловится только computed-стилем) записана в `web/CLAUDE.md`. Доки шага: `API.md` (эндпоинт), `ARCHITECTURE` §перечень приватных эндпоинтов, `TECH-DEBT` (TD-20), `web/CLAUDE.md`.

4. **Закрытие формы: по дате, по числу ответов, свой текст.** Сценарий «100 мест на мероприятие». Первые настройки формы вне схемы документа — где живут (колонки `forms` vs JSONB `settings`) решить через ADR до кода. Лимит проверяется сервером на приёме ответа; поведение на границе (строгая транзакционная проверка vs допустимый небольшой перебор) — зафиксировать выбор. Внимание, инвариант 5: сегодня закрытая форма неотличима от несуществующей (404); показ текста «приём закрыт» — осознанное изменение семантики для форм, закрытых настройкой владельца, — согласовать через ADR, черновики по-прежнему 404.

   **Состояние — сделано.** Три решения владельца зафиксированы в ADR §10:
   - **Живые настройки — колонки `forms`** (`close_at`/`response_limit`/`closed_message`, миграция **0007**), а не JSONB-мешок и не схема: настроек три и они стабильны, `response_limit` проверяется на горячем эндпоинте (типизированная колонка чище JSONB), а схема снапшотится при публикации — живой настройке там не место. «Фактически закрыта» **вычисляется** на чтении (`status=closed` ИЛИ дата прошла ИЛИ `count ≥ лимит`), `status` по дате/лимиту не флипается: крон не нужен, продление даты переоткрывает мгновенно.
   - **Лимит — жёсткий кап ровно N** (решение владельца, а не best-effort): приём под `pg_advisory_xact_lock` по форме сериализует конкурентные вставки, счёт точен, перебор невозможен; форма без лимита блокировку не берёт. Порядок «вставка → счёт» держит идемпотентность — ретрай принятого `submission_id` проходит мимо лимита и у заполненной формы. Размен «блокировка на самом атакуемом эндпоинте» записан в TECH-DEBT (**TD-21**) — вернуться, если станет узким местом. Тест гонки: 60 одновременных приёмов при лимите 10 → ровно 10 в БД, 10×201/50×410, данные не потеряны (под `-race`).
   - **Закрытая → `410` «приём закрыт», а не 404** (решение владельца — любая закрытая, включая снятую вручную): форма была публичной, её существование уже не секрет. Инвариант 5 сузился до **черновика** (никогда не публиковался → 404). Публичный `GET` закрытой отдаёт `410` с `{title, closedMessage}` (`Cache-Control: no-store` — закрытость живая); HTML `/r` отдаёт тот же SPA-шелл (200), клиент рисует «приём закрыт» из 410; приём ответа на закрытую → `410`.

   Настройки редактируются на странице настроек формы (шестерёнка билдера, посадочное место из шага 1) второй секцией — нативные `datetime-local`/`number`/`textarea`, новых зависимостей нет, сохранение своей кнопкой (`PATCH` фасет `closeSettings`). Контракт синхронен: Go (`domain.ValidateCloseSettings`, `domain.FormClosed`) + Zod (`entities/form.ts`), лимит текста 2000. Доки: ARCHITECTURE (§3 таблица, §3.4, §4.7, §перечень эндпоинтов, ADR §10), API.md, SCHEMA.md, TECH-DEBT (TD-21), `web/CLAUDE.md` (404-заметка про `/r`).

6. **Визиты: просмотры и конверсия.** На карточке дашборда и странице ответов — «N просмотров → M ответов (K %)». Реализация — не серверный счётчик открытий, а визиты (решение владельца, ADR §10): таблица `form_visits` (строка на визит: форма, версия, `last_block_id` — самая дальняя точка, `submitted`, `meta` с user_agent/referer/UTM, **без IP**), публичная ручка `POST /public/v1/forms/{slug}/visits` и два бикона из рендерера (`navigator.sendBeacon` умеет только POST): на монтировании — «открыли», на `pagehide`/`visibilitychange→hidden` — «дошёл до блока». Апсерт по клиентскому UUIDv7 — тот же приём идемпотентности, что у отправки (ARCHITECTURE §4.7). Доступ — тем же HMAC-токеном формы, что уже выдаётся при `GET /public/v1/forms/{slug}`; своё, четвёртое ведро rate-limit по образцу `submit` (обобщённая обёртка `rateLimit(limiter, msg)`, `ClientIP` и GC уже есть). `submitted` ставит сервер при приёме ответа: тело `POST …/submissions` получает **необязательный** `visitId` (визита нет → ответ принимается как сейчас) — отсюда точная конверсия вместо деления двух независимых чисел.

   **Почему бикон, а не серверный счётчик.** Серверный счёт занижен кэшем (`max-age=60`, `ETag`/304) и считает краулеров вместо людей, а главное — принципиально не может сказать, докуда дошёл ушедший, то есть не годится фундаментом под воронку (шаг 6б). Бикон снимает и проблему кэша.

   **Осознанные границы (записать, а не лечить).** Накрутка просмотров возможна: ручка публичная на запись, а HMAC-токен реиграбелен внутри 24 ч (TECH-DEBT §5) — ущерб ограничен неверным числом на своём же дашборде, не данными; backstop — rate-limit и honeypot, как у отправки. Потерянный бикон `pagehide` даёт визит с `last_block_id = NULL`, то есть слегка завышенный «отскок» (`visibilitychange` уменьшает, но не до нуля). Роллапа нет: строка на визит при нашем масштабе не растёт опасно — пересмотреть, когда станет. Cookie и localStorage не заводим: `visitId` живёт в памяти страницы, человек между визитами не узнаётся.

   **Визиты пишутся для всех, без оглядки на будущие тарифы.** Когда придёт биллинг (POST-MVP фаза 13), платным станет **показ** воронки и источников, а не сбор: не собирая с бесплатных, в момент апселла нечего показать — плашка рекламирует пустоту, вместо того чтобы показать владельцу его настоящее число. Здесь из этого следует одно: проверок плана в этом шаге нет и не закладывается заглушек под них (YAGNI) — точка проверки появится на чтении в фазе 13.

   **Состояние — сделано.** Пять срезов, по коммиту на каждый: миграция `0008` → модуль `internal/visits` с публичной ручкой → конверсия в приёме ответа → чтение в кабинете → биконы рендерера.

   **Порядок биконов задаётся явным `seq` (решение владельца, ADR §10).** `sendBeacon` не гарантирует порядок доставки, а `visibilitychange` шлёт бикон на каждое переключение вкладки — без `seq` поздно доехавший ранний бикон отбрасывает визит назад по воронке. Альтернатива «last-write-wins и записать погрешность» отклонена не из перфекционизма: её дефект по факту неотлаживаем — данные уже испорчены, гонку не воспроизвести. Цена решения — один `SMALLINT`. Апсерт двигает `last_block_id` только при большем `seq` **той же формы**: второе условие закрывает не гонку, а подделку — id визита выбирает клиент, а UUIDv7 угадываем по временно́му префиксу, поэтому без него ручкой одной формы правится строка другой. Оба условия покрыты интеграционными тестами; на условии `seq` прогнана мутация (убрать условие → тест краснеет).

   **Версия приезжает в теле бикона и обязана совпасть с опубликованной.** Иначе переиздание формы посреди чужой сессии приписало бы визит версии, которой человек не видел, и `last_block_id` искался бы в чужой схеме. Расхождение → 422, визит теряется намеренно; окно микроскопическое (бикон «открыли» уходит через миллисекунды после `GET`). Побочная выгода: второй запрос за `version_id` не нужен — id берётся из уже загруженной `PublicForm`.

   **Окно токена у визитов другое, чем у приёма ответа:** только верхняя граница (24 ч, переиспользование — TD-6). Нижняя (минимальное время заполнения, 3 с) неприменима по смыслу — бикон «открыли» уходит сразу после выдачи токена, и общая проверка отбрасывала бы ровно те визиты, ради которых ручка заведена.

   **Отметка конверсии — после коммита приёма, best-effort.** В транзакцию с advisory-lock не заносится: аналитика не имеет права ни отклонить принятый ответ (респондент увидел бы «не удалось отправить» на уже сохранённом ответе и отправил бы второй раз), ни усложнить самый атакуемый эндпоинт ради булева флага. Неизвестный, подделанный и неразбираемый `visit_id` дают 0 помеченных строк — штатный исход, ответ принимается. Цена — краш в окне между коммитом и отметкой занижает конверсию на единицу; записано осознанно.

   **Закрытая форма визитов не набирает (410).** Рендерер до бикона и не дойдёт (`GET` закрытой отдаёт 410), но ручка публичная, и принимать по ней то, чего не бывает в жизни, значит открыть способ портить владельцу конверсию визитами, которые ответом закончиться не могли.

   **Асимметрия чисел на карточке — осознанная.** «M ответов» это `submissionCount` (то же число, что в таблице ответов: расхождение между двумя экранами кабинета читалось бы как баг), а процент считается **по визитам** (`submitted/total`). Делить `submissionCount` на `visitCount` нельзя — это разные множества (ответ мог прийти без визита), их частное конверсией не является. Ноль просмотров даёт «Пока нет просмотров», а не «0 %»: «никто не открывал» и «открывали, но никто не отправил» — разные новости. Черновику блок не показывается вовсе.

   **Самая дальняя точка снимается `onFocusCapture` на обёртке блока в `FormView`, а не новым пропом у `@fields/BlockField`** — поля общие с превью билдера, аналитике публичной страницы там не место; обёртка стоит ноль байт в кабинете. Раскладку не ломает: в `fields.css` нет селекторов прямого потомка (проверено grep'ом).

   **Попутно (в объёме шага):** обёртка rate-limit по IP вынесена в `httpserver.RateLimitByIP` — это третий потребитель, а копии в `auth` и `submissions` уже начинали расходиться (вычисление IP за прокси, TD-1, чинилось только в одной). Трекер визита принимает строку запроса параметром, а не читает `window`, — остаётся чистой функцией и проверяется юнитом без DOM.

   Бюджет рендерера: **80.62 КиБ gzip из 95** (было 80.05 — биконы стоили 0.57 при заложенных в план 1–1.5). Проверено сквозняком на dev: бикон открытия → фокус в поле → уход со страницы → строка визита с `last_block_id` того блока, которого коснулись, `utm_source` из адреса, `submitted = true` после отправки; в мете **нет IP** (тест падает, если ключ с `ip`/`addr` появится), cookie рендерер не заводит. Под StrictMode одно открытие даёт **один** визит. Доки: ARCHITECTURE (§3 DDL, §4.4 rate limiting, дерево модулей, перечень публичных эндпоинтов, ADR §10), `API.md`, `SCHEMA.md`.

   Затрагивает схему БД и контракт API → миграция `0008` (0007 занял шаг 4 — закрытие формы), новый модуль `internal/visits` (repo/service/public_handler по образцу `submissions`), доки ARCHITECTURE §1/§3.3/§4.6/§5.2/§7 + `API.md` + `SCHEMA.md` — **в том же PR, что и код** (сегодня они описывают реальность, забегать вперёд им нельзя — TD-14). Бюджет рендерера: +~1–1.5 КиБ к 79.41 из 95.

6б. **Воронка: на каком вопросе уходят.** На странице ответов — распределение визитов по `last_block_id` с человеческими подписями из схемы версии («66 дошли до „ИНН", 51 из них дальше не пошёл»). Данные к этому моменту уже лежат, работа рисовальная (CSS-бары, как в сводке шага 3). Сегодня, пока форма — одна длинная страница, сигнал косвенный: касание поля, а не переход на страницу; проскроллившего и передумавшего не видно — записать как погрешность. С приходом многостраничных форм тот же столбец начнёт заполняться из перехода на страницу — точнее, без миграции.

   **Состояние — сделано.** Четыре среза: общая модель вопросов → свёртка и эндпоинт → интеграционные тесты → экран.

   **Отправивший форму — не отвал (главное решение шага).** Он тоже имеет `last_block_id`: того поля, которого коснулся последним. Без разделения все дошедшие до конца попали бы в «отвалились на последнем вопросе», и экран обвинял бы ровно тот вопрос, который люди успешно проходят — воронка врала бы тем сильнее, чем лучше работает форма. Поэтому `GROUP BY` идёт и по `submitted`: «дошёл до вопроса» считается по всем визитам, «остановился здесь» — только по неотправившим. Та же логика наверху: отправить, не тронув ни одного поля, можно у формы со всеми необязательными вопросами, и это не уход. Обе стороны покрыты юнитами и интеграционным тестом; ошибка была найдена при написании свёртки, до того как уехала на экран.

   **Агрегация здесь в SQL — не отступление от решения шага 3, а его обратная сторона.** Там на SQL пришлось бы переписать семантику ответа (что значит `"yes"`, что значит массив опций) — третью копию правил после Go и Zod. Здесь семантики нет вовсе: подсчёт строк по одной колонке, результат размером в число вопросов, а не визитов. Порядок и подписи шагов всё равно достраивает Go.

   **Модель вопросов вынесена в `domain.QuestionOrder` (решение владельца).** Правило «объединение блоков по всем версиям, порядок и подпись из свежайшей» существовало двумя копиями — в `NewCSVBuilder` и `NewSummaryBuilder`; воронка стала бы третьей. Копии именно этого правила опасны тем, что расхождение не падает, а молча показывает владельцу **разные формы** на соседних экранах. Оба существующих потребителя переведены на общую функцию, их тесты прошли без правок — они и были страховкой переноса. Сводка сохранила свой обход версий, но только ради опций: вариант, удалённый в свежей версии, всё ещё имеет выбравших его по старой.

   **Место — свой таб «Воронка» (решение владельца), а не секция сводки:** другой источник данных (визиты, не ответы), своё пустое состояние («просмотров пока нет» против «ответов пока нет») и свои загрузка/ошибка — на общей странице получились бы два спиннера и две коробки ошибки. Адресуемость та же, что у сводки: таб — маршрут, а не стейт.

   **Погрешность показана на самом экране, а не только в доках:** «дошёл» = «коснулся поля», проскроллившего и ушедшего не видно. Владелец читает числа вместе с этой оговоркой, а не после разбирательства.

   **Неизвестный `block_id`** (подделанный — ручка визитов публична на запись) в шаги не попадает и к соседнему вопросу не приписывается, но остаётся в общем счётчике визитов: врать про число открытий нельзя.

   **Проверено на прод-контуре (закрывает долг обоих шагов, 6 и 6б).** `make prod-local` + сценарий `e2e/tests/visits-funnel.spec.ts`: визит биконом под строгой CSP → «1 просмотр → 1 ответ (100 %)» на карточке → воронка без отвала на вопросе отправившего → `410` на визит к закрытой форме. Это единственное место, где вообще проверяется бикон: `sendBeacon` подчиняется `connect-src 'self'`, заблокированный бикон **не бросает исключения и молчит в консоли** — счётчик просто остался бы нулевым, а в dev CSP нет вовсе. Сценарий сделан отдельным от `full-loop`: он не зависит от билдера, иначе краснел бы от правок редактора, ничего не говоря про аналитику. `full-loop` при этом красный по причине, не связанной с аналитикой (первый клик по «+ Добавить блок» после слэш-вставки; файлы билдера этими шагами не менялись) — **TD-22**.

   Проверено сквозняком на dev: реальный ответ сервера снят curl'ом и стал фикстурой Zod-теста (выдуманная проверяла бы схему саму против себя); на форме с четырьмя визитами экран показал «4 просмотра → 1 отправка», «2 ушли, не тронув ни одного вопроса» и отвал на последнем вопросе, при этом отправивший, коснувшийся первого вопроса, в отвал не попал. Пустое состояние проверено на форме без визитов. Доки: `API.md`, ARCHITECTURE (перечень приватных эндпоинтов).

7. **Шаблоны форм.** 5–10 заготовленных `draft_schema` («запись на консультацию», «обратная связь», «регистрация на событие», «анкета кандидата», …) в диалоге создания формы: путь новичка до первой опубликованной формы — минута. Технически — статические JSON на фронте; тест прогоняет каждый через `ValidateSchema` (шаблон, разошедшийся со схемой, ловит CI, а не пользователь).

   **Состояние — перенесён в POST-MVP целиком (решение владельца), фаза 19.** Владелец отклонил встроенные шаблоны как половинчатые: шаблоны нужны сразу со своими и публичными, иначе фичу придётся переоткрывать. Агент рекомендовал разделить (встроенные сейчас — они в любом сценарии пишутся руками, иначе галерея пустая; статические JSON стали бы сидом будущей таблицы, а выбрасывался бы только `import` списка вместо запроса к API) — рекомендация не принята. Причина отклонения принята как более весомая: **половинчатые шаблоны обещают библиотеку, которой нет**, и первый же новичок упирается в раздел «Публичные» с пустотой — то есть в ту же проблему чистого листа, ради которой шаг затевался.

   **Что перенос стоит фазе:** чистый лист у новичка остаётся до POST-MVP — при создании формы по-прежнему пустое полотно. Это единственная продуктовая дыра из аудита кабинета, которую фаза 8.5 сознательно не закрывает. Демо-сценарий фазы переписан (начинался словами «форма из шаблона»).

8. **Дашборд при росте: поиск и сортировка.** Поиск по отображаемому имени (серверный, по `name ?? title`) и сортировка (по обновлению / созданию / числу ответов). Мелко, но после ~20 форм без этого кабинет тонет.

   **Состояние — сделано.** Два среза: бэкенд (запрос, сервис, транспорт, тесты) → дашборд.

   **Один SQL-запрос на три порядка вместо шести** (первая/следующая страница × три сортировки). Ключ сортировки нормализован к `bigint`: время — наносекунды эпохи, число ответов уже `bigint`. Отсюда неизменный формат курсора и одно место, где живёт правило порядка; альтернатива — шесть запросов с одинаковой двенадцатистрочной проекцией и шесть копий маппинга строки в Go, то есть ровно та копипаста, что запрещена PROCESS §7. Планировавшийся ради дедупликации view (и миграция под него) **не понадобился** — единственный запрос дедуплицировать нечем; шаг не трогает схему БД вовсе.

   **Порядок запечатан в курсоре, чужой курсор → 422** (а не молчаливая пересортировка): ключ у порядков измеряет разные величины, и курсор от другой сортировки дал бы не ошибку, а перемешанную выдачу с пропусками — дефект, который заметен не сразу и невоспроизводим постфактум. Курсор из двух частей (выданный до этого шага) читается как сортировка по умолчанию: открытая у кого-то страница не ломается в момент выкатки.

   **Цена решения — `CASE` в `ORDER BY` не даёт использовать `idx_forms_workspace` для построения порядка** (индекс отбирает строки воркспейса, сортирует sort-узел); индекс под `created_at` по той же причине не заводился. Опасение владельца о стоимости сортировки по числу ответов закрыто замером, а не рассуждением: **2,4–4,4 мс** на 98 формах, включая форму с 9999 ответами, одинаково на всех трёх порядках. Обещанная в плане лог-строка со счётчиком **не добавлена осознанно**: единственный доступный там знаменатель — размер страницы, а не число просканированных форм, то есть ровно бесполезная величина, от которой предостерегал опыт шага 3; длительность запроса middleware пишет и так.

   **Поиск идёт по `coalesce(name, title)`** — по тому, что человек видит на карточке, а не по «настоящему» заголовку: форма, переименованная в кабинете, обязана находиться по новому имени. Спецсимволы `LIKE` экранируются, иначе «50%» находит что угодно; интеграционный тест фиксирует, что «50%» находит ровно форму с процентом в названии.

   **Поиск и сортировка — в адресной строке** (то же решение, что у табов формы): ссылка на отфильтрованный дашборд ложится в закладки, F5 не сбрасывает, «Назад» работает. Параметры необязательны и умолчания в адрес не пишутся — иначе типы роутера потребовали бы перечислять search-параметры у **каждой** из десятка существующих ссылок на дашборд. Поиск и сортировка входят в query-ключ, а не фильтруют загруженное: список постраничный, клиентская фильтрация показывала бы совпадения только из подгруженных страниц, молча теряя остальные.

   **Пустых состояния стало два** — «форм нет» и «ничего не найдено»: предлагать создание формы в ответ на неудачный поиск значит подталкивать к дублю той формы, которая просто не нашлась.

   **Найдено самопроверкой после реализации (записано, не заметено).** (1) **`sort=responses` + курсор теряет строки:** ключ этой сортировки — счётчик, меняющийся между запросами страниц; форма, получившая ответы посреди листания, перепрыгивает курсор и не показывается ни на одной странице (воспроизведено на dev: форма с 21 ответом невидима). Опасность коррелирует со сценарием — «сортировать по ответам» жмут на активных формах, где ответы и приходят; смягчает то, что страница вмещает 50 форм и у большинства воркспейсов пагинации нет. Записано как погрешность в `SCHEMA.md`; починка (снапшот на листание) потребует ADR. (2) **`q` не был ограничен по длине** — принимался запрос в 50 000 символов, нарушение инварианта 3 (`MaxBytesReader` стережёт тело, а не query-строку); закрыто лимитом в 200 символов с тестом на границе. (3) **Счётчики карточки (ответы, просмотры, конверсия) не проверялись ни одним тестом**, хотя шаг переписал их вычисление со скалярных подзапросов на `LATERAL`; заведён `TestForms_ListCounters`, на нём прогнана мутация (убрать `FILTER` у `visit_submitted_count` → тест краснеет).

   Проверено сквозняком на dev (98 форм): поиск 98 → 1, сортировка по ответам поднимает наверх форму с 9999 ответами, подгрузка второй страницы под `sort=responses` проходит с курсором, несущим порядок; 422 на опечатку в `sort` и на курсор чужой сортировки; сброс поиска чистит и адрес, и поле. Доки: `API.md`, `SCHEMA.md`, ARCHITECTURE (перечень приватных эндпоинтов).

9. **Шаринг шире ссылки: embed и QR.** На экране «Поделиться» — сниппет `<iframe>` и QR-код ссылки. QR генерируется на клиенте: зависимость или ~200 строк своей реализации — через штатный вопрос о зависимостях. Для iframe проверить заголовки публичного домена в Caddyfile: CSP/`X-Frame-Options` сейчас, скорее всего, запрещают встраивание — ослаблять точечно только для `/r/*` (`frame-ancestors`), проверять на prod-local.

   **Состояние — отложен решением владельца** (был шагом 5, понижен в хвост фазы как нерелевантный сейчас). Шаг оставлен в плане, а не вычеркнут, ровно ради заметки про заголовки публичного домена: `frame-ancestors` для `/r/*` — единственное место фазы, где встраивание упирается в прод-контур, и всплыть оно должно до того, как embed кому-то понадобится, а не после.

**Демо в конце фазы.** Сценарий «регистрация на мероприятие» за пять минут: новая форма → собраны имя, телефон и шкала «откуда узнали» → лимит 100 ответов, свой текст «спасибо» с редиректом на сайт → опубликована → открыта по ссылке с телефона → после пары ответов в кабинете: ответы видны колонками, в сводке — распределение по шкале, на карточке — «просмотры → ответы».

**Definition of Done.** Каждый новый тип проходит полный цикл (билдер → публикация → ответ → таблица → сводка → CSV) с тестами обеих сторон контракта; redirect не принимает не-`http(s)` схемы (тест на `javascript:`); лимит ответов не теряет данные и не пускает лишнего сверх зафиксированного допуска (тест гонки); сводка агрегируется сервером; ручка визитов живёт под своим rate-limit и требует токен формы, рендерер не заводит ни одной cookie, конверсия считается по `visitId` (не делением двух счётчиков); бюджет рендерера (95 КиБ gzip) не превышен; e2e-сценарий дополнен новыми точками.

## Фаза 9. Ввод прода в строй (когда появится VPS)

**Цель.** Превратить prod-local в prod. Благодаря фазе 7 это фаза «подключения», а не «разработки»: весь код и конфиги готовы, меняются только адреса, сертификаты и способ доставки.

**Шаги.**

0. **Гейт: раздел `docs/TECH-DEBT.md` §1 пуст.** На момент правки этой строки гейт **пройден**: блокеры, ради которых он заводился (TD-1 rate limit за прокси, TD-2 лимит на регистрацию, TD-3 CSV-инъекция, TD-4 `WriteTimeout` рвёт стриминг CSV), закрыты и перенесены в «Закрыто». Гейт остаётся как правило, а не как список: перед выкаткой сверить §1 с реальностью — фазы 8.5 и далее могут завести новые блокеры. Каждый закрывается своим PR с переносом строки в «Закрыто».

2. DNS: A-записи `app.`, `f.` на IP (два домена, ADR §10). В Caddyfile — реальные домены через ту же env-переменную; Let's Encrypt включается сам. Здесь же выставить GitHub repo-переменную `VITE_PUBLIC_BASE_URL` на реальный `https://f.<домен>` — иначе релизный workflow (фаза 7, шаг 6) печёт статику с заглушкой; после этого перевыпустить тег.
3. Серверный `.env` (права 600): прод-секреты, сгенерированные заново (не копии из prod-local).
4. Первый деплой руками по инструкции: `docker compose pull` образа из GHCR (собранного ещё в фазе 7), rsync статики из GitHub Release, `up -d`. Прогнать smoke.
5. CD-пайплайн: расширить релизный workflow шагом деплоя по SSH (rsync статики + pull&up). Прогнать дважды, второй раз — откат на предыдущий тег.
6. Проверка отсутствия 502 при деплое (скрипт долбит healthz во время выкатки) — graceful shutdown уже написан, здесь он подтверждается.
7. Внешняя проверка безопасности: `nmap` с другой машины (только 22/80/443), Mozilla Observatory по заголовкам.

**Демо в конце фазы.** Продукт живёт на реальном домене с настоящим сертификатом; `git tag && push` доставляет изменение на прод за минуты без ручных команд; форма открывается с любого телефона из любой сети.

**Definition of Done.** Блокеры TECH-DEBT §1 закрыты (перенесены в «Закрыто»); деплой и откат по тегу воспроизводимы; во время деплоя нет 502; чек-лист пересоздания сервера записан и полон; секреты нигде не пересекаются с dev/prod-local.

## Фаза 10. Эксплуатационная зрелость

**Цель.** Превратить «работает на проде» в «можно давать живым людям и спать ночью». Почти без продуктового кода — зато с самыми дорогими страховками.

**Шаги.**

1. Бэкапы: cron каждые 6 часов — `pg_dump -Fc` → шифрование age → S3-совместимое хранилище **другого провайдера**; ротация 14 суточных + 8 недельных.
2. **Учебное восстановление**: чистый Postgres локально, восстановление вчерашнего бэкапа, приложение с ним работает. Процедура — в `deploy/RESTORE.md` с замером времени. Главный шаг фазы: непроверенный бэкап равен отсутствующему.
3. Мониторинг аптайма: Uptime Kuma не на этом VPS или внешний сервис → `/healthz` и публичная форма раз в минуту → алерт в Telegram. Учебное падение (`docker stop api`) — алерт должен прийти за ≤2 минуты.
4. Логи: ротация docker-логов, сводная строка на запрос (метод, паттерн, статус, длительность, request_id); шпаргалка `jq`-запросов («все 5xx за час», «медленные запросы») в `deploy/README.md`.
5. Нагрузочная проба публичного эндпоинта (`hey`/`vegeta`, ~200 rps на 2 минуты): rate limit и таймауты ведут себя как задумано; потолок VPS записан числом.

**Демо в конце фазы.** Три артефакта: база, восстановленная из бэкапа, с вашими вчерашними формами; алерт в Telegram во время учебного падения; строка в `deploy/README.md` «потолок — N rps на отправку ответов».

**Definition of Done.** Восстановление воспроизведено по инструкции «не подглядывая» (вами через неделю); алертинг проверен учебной аварией; нагрузочный потолок задокументирован.

## Правила ведения работ

Ветка на шаг или связку из 2–3 шагов, PR с зелёным CI, squash-merge в защищённый main. Конец каждой фазы — git-тег: до фазы 7 тег просто фиксирует веху, с фазы 7 он ещё и собирает релизные артефакты в GHCR, с фазы 9 — деплоит. Шаг, разросшийся больше чем на день, режется на два — это сигнал недодекомпозиции. Отступления от архитектуры фиксируются в ADR-таблице архитектурного документа, а не остаются устной легендой.
