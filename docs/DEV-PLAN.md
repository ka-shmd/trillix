# План разработки по фазам — конструктор форм (MVP), редакция 2

Редакция под новое ограничение: **VPS пока нет**, вся разработка ведётся локально, CI живёт в GitHub. Деплой отодвинут в конец и разбит так, что почти вся его подготовка делается заранее без сервера — когда VPS появится, ввод прода в строй займёт один день, а не неделю.

## Три контура: как организована среда

Ключевая идея редакции: контуров не два, а три, и средний из них — секретное оружие разработки без сервера.

**Контур dev — ежедневная работа.** Postgres в Docker, Go-API через `go run` (или `air` с hot-reload) прямо на хосте, оба фронта через `vite dev` с HMR. Порты: api `:8080`, app `:5173`, renderer `:5174`; Vite проксирует `/api` и `/public` на `:8080`, поэтому CORS в dev не нужен. Максимальная скорость итерации: правка кода видна за секунды.

**Контур prod-local — репетиция прода у себя на машине.** Полная прод-сборка, запущенная локально: настоящие Docker-образы (distroless), настоящий `compose.prod.yml`, настоящий Caddy с доменами `app.localhost` и `f.localhost` (API — same-origin под `app.localhost/api`, отдельного домена нет — ADR §10; домены `*.localhost` резолвятся сами, Caddy выдаёт на них TLS от своего локального CA — получаем честный https без единой DNS-записи). Этот контур поднимается командой `make prod-local` и означает: **всё, что нужно для прода, кроме самого сервера, написано и проверено**. Когда появится VPS, изменится только имя хоста и способ доставки файлов.

**Контур prod — настоящий VPS.** Появится в фазе 9. К этому моменту от prod-local он будет отличаться четырьмя вещами: реальные домены и DNS, Let's Encrypt вместо локального CA, секреты из GitHub Secrets/серверного `.env`, бэкапы в offsite-хранилище. Всё остальное — байт в байт те же образы и тот же compose.

Чтобы три контура не разъехались, действует правило **одного бинарника и одного набора env-переменных**: приложение не знает, в каком контуре живёт; все различия (DSN базы, домены cookie, уровень логов, параметры rate limit) — только через окружение. Файлы: `.env.example` (документация всех переменных), `.env.dev`, `.env.prod-local` — в репозитории; `.env` прода — только на сервере. Никаких `if env == "dev"` в коде — это классический источник «на проде повело себя иначе».

CI в GitHub с первого дня, но без деплоя: его работа — линт, тесты, сборка фронтов и **сборка прод-образов** (публикация в GHCR по тегу). То есть релизные артефакты копятся в registry заранее; деплой потом — это «скачать готовое», а не «собрать на сервере».

## Как читать план

Формат прежний. Каждая фаза: **Цель** (абзац), **Шаги** (единицы «сел — сделал — закоммитил», от получаса до пары часов), **Демо в конце фазы** (что вы увидите глазами — критерий приёмки), **Definition of Done** (технический шлагбаум). Принципы: вертикальные срезы вместо слоёв; тесты внутри фазы, а не потом; уродливое-но-работающее раньше красивого.

**Это документ о будущем.** У закрытого шага здесь остаётся одна строка — вердикт и ссылка; разбор (что реально сделано, какие решения принимались, что найдено попутно, что осознанно не делалось) живёт в [`JOURNAL.md`](JOURNAL.md). Разделение не косметическое: к июлю 2026 ретроспектива разрослась настолько, что план перестал читаться целиком (43 000 токенов — больше лимита одного чтения), то есть ответ на вопрос «что делать дальше» стоил дороже, чем кто-либо готов платить. Дописывать дёшево, переписывать дорого — поэтому журнал рос, а план тонул.

**Правило:** закрывая шаг, пиши разбор в журнал, а здесь оставляй строку `**Состояние — <вердикт>.**` со ссылкой. Если разбор снова начал расти внутри плана — он на неправильной стороне. Текущее состояние системы — [`STATUS.md`](STATUS.md).

Карта фаз:

```
Фаза 0. Фундамент и CI                   → «hello» одной командой, зелёный CI в GitHub
Фаза 1. Аутентификация                   → регистрация и вход через браузер
Фаза 2. Формы как сущности (CRUD)        → дашборд со списком форм
Фаза 3. Билдер                           → редактор блоков с автосохранением
Фаза 4. Публикация и публичный рендерер  → форма открывается по локальной ссылке
Фаза 5. Приём ответов                    → отправленный ответ ложится в базу
Фаза 6. Просмотр ответов и CSV           → таблица ответов и скачанный файл
Фаза 6.5. Редактор в стиле Tally         → сборка формы slash-редактором (билдер фазы 3 — временный)
Фаза 7. Prod-local: репетиция прода      → весь стек под https на *.localhost
Фаза 8. Полировка                        → undo/redo, drag-and-drop, тёмная тема
Фаза 8.5. Продуктовый минимум            → телефон и шкала, сводка ответов, лимит мест, просмотры и конверсия
Фаза 8.7. Вопрос как группа блоков       → заголовок, поле и контент — отдельные блоки в группе
Фаза 9. Ввод прода в строй (когда есть VPS) → продукт на реальном домене
Фаза 10. Эксплуатационная зрелость        → восстановленный бэкап, алерт в Telegram
Фаза 11. Вход через Яндекс ID             → регистрация и вход в один клик, без пароля
```

Обратите внимание: полировка (фаза 8) и продуктовый минимум (фаза 8.5) сознательно стоят **до** деплоя — они не требуют сервера, а VPS может появиться в любой момент и фазы 9–10 просто «вклинятся», когда будут возможны.

Фазами 0–10 MVP-план исчерпан. Фаза 11 — первая из [`POST-MVP.md`](POST-MVP.md), развёрнутая здесь по правилу «фаза разворачивается в раздел `DEV-PLAN.md` перед стартом»; следующие приходят так же.

## Фаза 0. Фундамент и CI

**Цель.** Монорепозиторий, где вся рутина автоматизирована с первого коммита: одна команда поднимает dev-контур, GitHub на каждый push гоняет полный набор проверок. Всё настроенное здесь экономит время в каждой следующей фазе.

**Шаги.**

1. Инициализировать репозиторий со структурой из архитектурного документа (`cmd/`, `internal/`, `web/app`, `web/renderer`, `migrations/`, `deploy/`). Пустые пакеты с `doc.go`, чтобы скелет был виден сразу.
2. `go.mod`, минимальный `cmd/api/main.go`: сервер на stdlib, маршрут `GET /healthz` → `{"status":"ok"}`, `slog` в JSON, чтение конфига из env через маленький хелпер с валидацией обязательных переменных при старте (упасть сразу, а не на первом запросе).
3. `compose.dev.yml`: только Postgres 16 с volume, порт на `127.0.0.1:5432`. Файлы `.env.example` и `.env.dev`.
4. Makefile — единая точка входа: `make dev` (БД + API с hot-reload), `make test`, `make lint`, `make migrate-up/down`, `make seed` (заглушка, наполнится позже). Раннер миграций — команда `./api migrate up` внутри бинарника (golang-migrate как библиотека); миграция `0001` — пустышка-проверка механизма.
5. `golangci-lint` (errcheck, govet, staticcheck, gofumpt) + конфиг.
6. Заготовки фронтендов: два Vite-проекта react-ts, strict TypeScript, eslint + prettier; в `vite.config.ts` приложения — proxy `/api → :8080`. Пока рендерят строку текста.
7. GitHub Actions, workflow `ci.yml`: на push и PR — линт Go, `go test -race`, `tsc --noEmit` + eslint + vitest для обоих фронтов, сборка обоих фронтов. Кэширование Go-модулей и node_modules, чтобы прогон был минуты, а не десятки минут. Красный CI = нельзя мержить (branch protection на main).

**Демо в конце фазы.** На чистой машине: `git clone`, `cp .env.dev .env`, `make dev` — через минуту `curl localhost:8080/healthz` отвечает JSON, `npm run dev` в обоих фронтах показывает страницы. В GitHub на коммите — зелёная галочка со всеми jobs.

**Definition of Done.** README «как запустить за 5 минут»; CI зелёный и быстрый (<5 минут с кэшами); `.env.example` описывает каждую переменную комментарием; приложение падает при старте с внятной ошибкой, если переменной не хватает.

## Фаза 1. Аутентификация

**Цель.** Полный контур учётных записей: регистрация, вход, сессия, выход. Первая настоящая вертикаль «БД → сервис → API → экран», на которой обкатываются все паттерны проекта: слои, формат ошибок, интеграционные тесты, работа TanStack Query с API.

**Шаги.**

1. Миграция `0002`: `users`, `workspaces`, `workspace_members`, `sessions`. Генератор UUIDv7 в `internal/domain` с юнит-тестом на монотонность.
2. Обёртка argon2id (параметры OWASP) + юнит-тесты.
3. Модуль `auth`, слой repo (sqlc): создание пользователя, поиск по email, CRUD сессий. Регистрация создаёт пользователя, личный воркспейс и членство **одной транзакцией**.
4. Слой service: `Register`, `Login` (одинаковое время ответа для «нет email» и «неверный пароль»), `Logout`, `GetMe`; доменные ошибки (`ErrEmailTaken`, `ErrInvalidCredentials`).
5. HTTP-слой: `/api/v1/auth/*`; cookie httpOnly+SameSite=Lax (флаг Secure — из env: в dev по http он выключен, в prod-local/prod включён — первый пример «различие контуров живёт в env»); CSRF-токен; middleware `RequireAuth`; единый `respond.go` с маппингом доменных ошибок; in-memory rate limit на `POST /auth/login`.
6. Фоновая горутина чистки истёкших сессий — заодно общий механизм периодических задач.
7. Интеграционные тесты против Postgres в testcontainers: регистрация → логин → me → logout → 401. Эти тесты гоняются и в CI (testcontainers работает на GitHub-раннерах из коробки).
8. Фронт: экраны Login/Register в layout-группе `_auth`; api-клиент (fetch-обёртка: CSRF-заголовок, разбор единого формата ошибок); layout-группа `_app` с загрузкой `/auth/me` и редиректом; кнопка выхода.

**Демо в конце фазы.** Локально в браузере: регистрируетесь → попадаете в пустое приложение со своим email в шапке → F5 — сессия жива → выход → защищённый маршрут редиректит на логин. Неверный пароль — человеческая ошибка под полем. Цикл curl'ом по `/auth/login` упирается в rate limit.

**Definition of Done.** Интеграционные тесты auth зелёные локально и в CI; в БД нет паролей и токенов в открытом виде; повторная регистрация на email — 409 с внятным сообщением.

## Фаза 2. Формы как сущности (CRUD)

**Цель.** Дашборд: создать форму, увидеть список, переименовать, удалить. Билдера ещё нет — форма пока карточка с названием. Появляется вся механика ресурсов с проверкой прав, копируемая дальше как паттерн.

**Шаги.**

1. Миграция `0003`: `forms`, `form_versions`; генератор slug (nanoid ~10 символов, свои 20 строк).
2. Repo: создание с пустой `draft_schema`, список по воркспейсу с курсорной пагинацией, получение, обновление title, удаление.
3. Service: каждая операция начинается с проверки членства в воркспейсе (анти-IDOR закладывается в первом же ресурсе). Юнит-тест на запрет чужого доступа обязателен.
4. HTTP: `GET/POST /forms`, `GET/PATCH/DELETE /forms/{id}`. Интеграционный тест: пользователь A не трогает форму пользователя B (404).
5. `make seed`: скрипт сидирования (пользователь + 60 форм) — нужен для проверки пагинации и дальше пригодится постоянно.
6. Фронт: `forms.index` — грид карточек через TanStack Query; «Новая форма» (мутация + инвалидация + переход в заглушку редактора); переименование инлайн; удаление с подтверждением; скелетоны; пустое состояние.
7. Заглушка маршрута `forms.$slug.edit`: показывает title и JSON черновика — точка входа фазы 3.

**Демо в конце фазы.** Создаёте три формы → карточки с датами → переименовали, удалили → F5, всё на месте. Второй аккаунт в инкогнито по чужому URL получает 404. После `make seed` список корректно листается.

**Definition of Done.** Тесты изоляции воркспейсов зелёные; пагинация проверена на 60 формах; мутации фронта корректно инвалидируют кэш Query.

## Фаза 3. Билдер

**Цель.** Сердце продукта: редактор, где форма собирается из блоков семи типов, всё автосохраняется. Публикации нет — билдер работает только с черновиком.

**Шаги.**

1. Контракт схемы: Zod-схемы `FormSchema`/`Block` в `web/*/src/entities` + зеркальные Go-типы с `ValidateSchema` (лимиты: ≤200 блоков, ≤100 опций, длины строк). Единственный шаг без картинки — он определяет язык обеих сторон.
2. Бэкенд: `PATCH /forms/{id}` принимает `draft_schema` → `ValidateSchema` → оптимистичная блокировка по `updated_at` (расхождение → 409). Интеграционные тесты: валидная схема сохраняется, мусор — 422, устаревший `updated_at` — 409.
3. Zustand-стор билдера: `{blocks, selectedId, dirty}`; операции add/update/remove/move/duplicate. Стор — чистый TypeScript без React, покрывается vitest сразу.
4. Каркас экрана: палитра типов слева, канвас-список в центре, панель настроек справа. Клик по типу добавляет блок, клик по блоку выделяет.
5. Редактирование: label/description инлайн на канвасе; справа — required и типоспецифика (для choice — редактор опций: добавить, переименовать, удалить, порядок).
6. Автосейв: дебаунс 800 мс → `PATCH` всей схемы; индикатор «Сохранение…/Сохранено/Ошибка — повторить»; при 409 — баннер «Изменено в другой вкладке»; предупреждение при уходе с несохранённым.
7. Перемещение блоков кнопками вверх/вниз (dnd — в фазе 8).
8. Живое превью (переключатель «Редактор/Превью»): блоки рендерятся как увидит респондент. Компоненты полей пишутся в общий пакет — фаза 4 переиспользует их в рендерере.

**Демо в конце фазы.** Накидываете анкету из 6–7 вопросов всех типов → превью показывает её глазами респондента → закрыли вкладку, открыли — всё на месте. Соседняя вкладка меняет ту же форму — первая честно сообщает о конфликте.

**Definition of Done.** Юниты стора и `ValidateSchema` зелёные; автосейв не теряет правки при непрерывном вводе 30 секунд; превью совпадает с набором блоков.

**Примечание о редакторе.** Палитра-канвас-редактор этой фазы — сознательно временный: его задача дать рабочий редактор, чтобы прогнать бэкенд через фазы 4–6. Целевой UX (markdown-полотно со slash-командами в стиле Tally) вынесен в отдельную фазу 6.5; он заменит только поверхность ввода, переиспользуя стор, схему, автосейв и превью этой фазы.

## Фаза 4. Публикация и публичный рендерер

**Цель.** Форма получает жизнь за пределами кабинета: «Опубликовать» создаёт иммутабельную версию, форма открывается по ссылке без входа. Локально роль «публичного домена» играет второй vite-порт — этого достаточно, чтобы увидеть и проверить всё поведение.

**Шаги.**

1. Публикация на бэке: `POST /forms/{id}/publish` одной транзакцией создаёт `form_versions` (version = max+1), ставит `published_version_id`, `status='published'`; `unpublish` → `closed`. Тесты: две публикации подряд — версии 1 и 2.
2. Публичный эндпоинт `GET /public/v1/forms/{slug}`: схема опубликованной версии + title; `Cache-Control: public, max-age=60` и ETag; 404 для черновиков и закрытых. Сюда же — HMAC-токен времени выдачи (поле для антиспама фазы 5).
3. Превью ссылок (Open Graph): HTML-документ страницы формы `/r/{slug}` отдаёт **Go**, а не статика — только так краулеры мессенджеров/соцсетей получат мета (они читают HTML, не выполняя JS). Go подставляет в `<head>` опубликованной формы `og:title`/`og:description` (из title и описания формы) и `og:image` — пока **общая брендовая заглушка** (базовый URL картинки из env; своя картинка на форму — пост-MVP, зависит от загрузки файлов). Тело документа грузит тот же React-SPA — «голова на сервере, тело на клиенте». **Безопасность:** title/описание — пользовательский текст, вставляется в мета только через автоэкранирование (`html/template`), никогда «сырым»; черновик/закрытая форма отдают **404**, как и JSON-ручка, — HTML-путь не раскрывает существование приватного; `dangerouslySetInnerHTML` по-прежнему под запретом. Одинаково во всех контурах (никакого «мета только на проде»).
4. Рендерер (`web/renderer`, vite на `:5174` с proxy `/public → :8080`): slug из pathname (`/r/{slug}`), рендер всех семи типов из общих компонентов фазы 3, ответы в `useReducer`, черновик ответов в sessionStorage. Экраны «загрузка», «форма недоступна» (в фазе 5 — единый 404: черновик, закрытая и несуществующая неотличимы) и «ошибка загрузки». (Позже, в фазе 8.5 шаг 4, закрытая форма отделена от 404: своя `410`-семантика и экран «приём закрыт» — см. раздел шага 4; черновик по-прежнему 404.)
5. Клиентская валидация по той же Zod-схеме: required, email, число, дата; ошибки по blur и при отправке.
6. Бюджет бандла рендерера проверяется в CI (превышение валит сборку), но порог **поднимается выше 60 КБ gzip** — React + react-dom исчерпывают его в одиночку; конкретное число фиксируется здесь. Запасной выход, если из-за веса не берётся Lighthouse ≥90: свап рендерера на `preact/compat` (алиас `react → preact/compat` только в сборке рендерера — компоненты остаются на React-API, `@fields` не трогаются). Кнопка «Отправить» пока дизейблится с подписью «скоро» либо пишет в консоль.
7. Кабинет: кнопка «Опубликовать» в шапке билдера; после — панель со ссылкой `localhost:5174/r/{slug}` (базовый URL публичной части — из env: ещё одно различие контуров, живущее в конфигурации), «Копировать», статус «Опубликовано · версия N», бейдж «Есть неопубликованные изменения», кнопка «Закрыть форму».

## Фаза 5. Приём ответов

**Цель.** Респондент отправляет ответ — он надёжно ложится в базу с привязкой к версии формы. Самый атакуемый эндпоинт делается сразу правильно: валидация, лимиты, антиспам, идемпотентность.

**Шаги.**

1. Миграция `0004`: `submissions`. Валидатор `ValidateAnswers(schema, answers)` — обязательность, типы, принадлежность опций, длины. Самая ветвистая функция проекта: табличные юнит-тесты (3–5 кейсов на тип блока) пишутся **до** реализации.
2. `POST /public/v1/forms/{slug}/submissions`: MaxBytesReader 256 КБ → статус формы → антиспам → `ValidateAnswers` против опубликованной версии → INSERT с `form_version_id` → 201. Ошибки — 422 с картой `block_id → сообщение`.
3. Антиспам: honeypot (заполнен → молчаливый 200 без записи) + HMAC-токен времени из фазы 4 (быстрее 3 секунд → отказ). Юниты на оба контура.
4. Идемпотентность: рендерер генерирует `submission_id` (UUIDv7) при первом нажатии «Отправить», ретраи шлют тот же id; конфликт PK на сервере = успех. Тест: двойной POST — одна строка.
5. Жёсткий rate limit по IP на эндпоинт, отдельный от общего.
6. Рендерер: состояние отправки, маппинг 422 на поля, авторетрай при обрыве сети (до 3 раз с бэкоффом), экран «Спасибо», очистка sessionStorage.
7. Сквозной интеграционный тест: создать → опубликовать → валидный ответ → невалидный ответ → проверить содержимое БД. Живая документация продукта.

**Демо в конце фазы.** Заполняете форму в инкогнито → «Спасибо». Без обязательного поля → ошибка у нужного поля. Обрываете сеть на середине отправки (DevTools offline), возвращаете — ответ уходит ровно один раз (видно по `SELECT count(*)`). У ответа в базе — id той версии, что была на экране.

**Definition of Done.** Табличные тесты `ValidateAnswers` покрывают все типы; дубль не создаётся; тело >256 КБ → 413; honeypot-ответы не попадают в БД.

## Фаза 6. Просмотр ответов и экспорт

**Цель.** Замкнуть петлю ценности: автор видит ответы в таблице и уносит их в CSV. После этой фазы MVP функционально полон — всё остальное готовит его к реальным людям.

**Шаги.**

1. `GET /forms/{id}/submissions`: курсорная пагинация по UUIDv7 (новые сверху), общий счётчик, у каждого ответа — его версия формы.

Колонки — объединение блоков по всем версиям (вопрос, удалённый в v2, остаётся колонкой для ответов v1); UTF-8 BOM для Excel; choice-ответы — подписями опций, не id.

## Фаза 6.5. Редактор форм в стиле Tally

**Вставка после фазы 6.** К этому моменту весь конвейер (собрал → опубликовал → собрал ответы → выгрузил) работает end-to-end, и его продемонстрировал временный палитра-канвас-редактор фазы 3. Здесь он заменяется сигнатурным для продукта редактором: единое markdown-подобное полотно, где блоки добавляются slash-командой («/» → меню типов), текст правится инлайн, мышь нужна по минимуму. Это переработка поверхности ввода, а не фундамента — потому и стоит после ценностной петли, а не внутри неё.

**Расширение фазы (решение владельца продукта):** вместе со slash-редактором делается общий визуальный редизайн кабинета в стиле Notion/Tally — сайдбар-навигация вместо шапки, единый вид всех экранов (дашборд, таблица ответов, auth). Для этого в `web/app` снята заморозка зависимостей и подключён UI-слой **Tailwind CSS v4 + shadcn/ui** (см. ADR-сводку и `web/CLAUDE.md`). Инвариант: Tailwind/shadcn — только в кабинете; рендерер (`web/renderer`) остаётся на react+zod под бюджетом 95 КиБ, общие `@fields` не переводятся на Tailwind. Работа ведётся пятью вертикальными срезами: (A) фундамент Tailwind+shadcn и процессные документы; (B) сайдбар-оболочка; (C) рестайл существующих экранов; (D) slash-редактор; (E) уборка временного билдера фазы 3.

**Цель.** Сборка формы ощущается как письмо в редакторе: пишешь заголовок и текст вопроса прямо в полотне, «/» открывает список типов полей, Enter/стрелки/Backspace создают, двигают и сливают блоки как в обычном текстовом редакторе. Автосейв, версии, публикация — уже готовое из фаз 3–4; редактор просто дёргает те же операции стора.

**Что переиспользуется и что переписывается.** Остаются: модель `FormSchema`/`Block`, Zod- и Go-контракт, `ValidateSchema`, zustand-стор с операциями над блоками, автосейв (дебаунс → PATCH → 409), превью и общие компоненты полей `@fields`. Переписывается только поверхность: `Palette`/`Canvas`/`SettingsPanel` уступают место полотну-редактору, а типоспецифичные настройки (опции choice, required) переезжают из отдельной панели в инлайн-контролы у активного блока.

**Шаги (детализируются перед стартом).**

1. ~~Возможное расширение схемы «неотвечаемыми» блоками~~ **Сделано:** добавлен тип `text` — неотвечаемый абзац и дефолт новой строки (Enter/мышь создают его, «/» превращает в поле). Контракт расширен в Go (`internal/domain/schema.go`, `isContent()`) + Zod (`formSchema.ts`, `isContentType`) одним PR; `schemaVersion` не менялся (новое значение enum обратно совместимо). `text` исключён из `ValidateAnswers`, CSV и таблицы ответов, в рендерере — статический абзац. Заголовок секции/разделитель — при необходимости позже тем же паттерном.
2. Полотно: блоки как редактируемые строки; фокус и навигация с клавиатуры (Enter — новый блок, Backspace в пустом — слить/удалить, ↑/↓ — переход), инлайн-правка label/description.

## Фаза 7. Prod-local: репетиция прода без сервера

**Цель.** Собрать весь прод-контур у себя на машине. В конце фазы продукт работает под https на трёх `*.localhost`-доменах из настоящих прод-образов — то есть от реального прода его отделяет только наличие сервера. Всё, что здесь написано (Dockerfile, compose, Caddyfile, релизный пайплайн), потом переедет на VPS без изменений.

**Шаги.**

1. Multi-stage Dockerfile для Go: сборка в `golang:1.26` (в тон `go.mod`) → `distroless/static:nonroot`, `CGO_ENABLED=0`, ~25 МБ. Локальная проверка: образ собирается, healthz отвечает из контейнера.
2. `deploy/compose.prod.yml`: caddy + api + postgres; Postgres без порта наружу; healthcheck'и; `restart: unless-stopped`; api стартует после миграций (init-команда `migrate up` тем же образом).
3. `deploy/caddy/Caddyfile`: два сайта `app.localhost` (статика кабинета + `/api/*` в Go same-origin) и `f.localhost` (статика рендерера + `/r/*` и `/public/*` в Go) — Caddy сам выдаёт TLS от внутреннего CA; SPA-fallback, иммутабельный кэш `/assets/*`. Выделенного `api`-домена нет (ADR §10): кабинет и его API — один origin, поэтому CORS не нужен. Доменные имена — параметром окружения, чтобы этот же файл работал на проде с реальными доменами.
4. Прод-сборка фронтов: `vite build` обоих проектов, скрипт раскладки статики в volume Caddy. База API кабинета и публичного API — относительные пути (`/api`, `/public`), same-origin, VITE-переменных для них нет (ADR §10); через `VITE_*` на этапе сборки задаётся только `VITE_PUBLIC_BASE_URL` (ссылка на форму в бандле кабинета). Рендерер собирает entry и CSS со стабильными именами `/renderer.js` и `/renderer.css`, а пути к ним на HTML-странице `/r/{slug}` (её отдаёт Go, а не собранный `index.html`) Go берёт из `PUBLIC_RENDERER_SCRIPT_PATH` (dev `/src/main.tsx`, prod `/renderer.js`) и `PUBLIC_RENDERER_STYLE_PATH` (dev пусто — vite инжектит CSS через JS; prod `/renderer.css`). Оба огреха («голова на сервере» не знала про собранные ассеты) всплыли и закрыты здесь. *(Устарело: в фазе 8, шаг 7 эти пути и стабильные имена сняты по корню — Go строит `/r/{slug}` из собранного `index.html`, `PUBLIC_RENDERER_SCRIPT_PATH`/`STYLE_PATH` удалены, ассеты — дефолтные хеши.)*
5. `make prod-local`: собрать образ и статику, поднять `compose.prod.yml` с `.env.prod-local`, прогнать тонкий smoke; `make prod-local-down` — погасить (тома с данными остаются). Smoke (`scripts/prod-local-smoke.sh`) — проверка живости + того, чего не было в dev: `/healthz` по внутренней compose-сети (api без внешнего порта, distroless без curl); `app.localhost/` и `f.localhost/` → 200 через Caddy; `f.localhost/r/<несуществующий>` → 404 (путь Caddy→Go→Postgres); регистрация по https → `Set-Cookie: …Secure`; мутация без `X-CSRF-Token` → 403. Полное открытие опубликованной формы глазами — это e2e шага 7 и ручная визуальная проверка, не smoke. CORS не проверяем — его нет по устройству (ADR §10). Нюанс, всплывший здесь: `include .env; export` в Makefile + приоритет шелл-переменных над `--env-file` у compose — поэтому `.env.prod-local` источается в тот же рецепт (иначе контейнеры подхватывают dev-DSN). «Настоящий замочек» (демо-критерий) требует доверия к локальному CA Caddy — разово `make prod-local-trust` (sudo; Firefox — свой стор).
6. Релизный пайплайн в GitHub Actions: по git-тегу `v*` — сборка и публикация Go-образа в GHCR + сборка статики фронтов и прикрепление артефактом к GitHub Release. Деплоя нет — но каждый тег с этого момента даёт готовый к развёртыванию комплект.
7. Прогон Playwright e2e (регистрация → билдер → публикация → ответ с мобильного вьюпорта → таблица → CSV) против prod-local контура; добавить job в CI. Сделано двумя срезами: **7a** — пакет `e2e/` с одним сценарием (`@playwright/test`, санкционирован ARCHITECTURE §8), зелёный локально против `make prod-local`; **7b** — workflow `.github/workflows/e2e.yml` (`workflow_dispatch` + nightly `schedule`, не на каждый PR — стек тяжёлый): поднимает prod-local и гоняет e2e. Тест сторожит оба пойманных в фазе регресса (пустая форма без entry-скрипта, форма без стилей). Побочно e2e вскрыл гонку билдера (rename заголовка ↔ автосейв схемы по `updated_at` → 409) — вынесена отдельной задачей, тест её обходит.
8. Заголовки безопасности (CSP, nosniff, frame-options) в Caddyfile; проверить локально curl'ом; убедиться, что секреты не запечены в образ (`docker history`).

**Демо в конце фазы.** `make prod-local` — и через пару минут в браузере `https://app.localhost` (настоящий замочек), полный путь пользователя работает; `https://f.localhost/r/{slug}` открывает форму. В GitHub Releases на теге лежат образ и статика. Playwright-прогон зелёный.

**Definition of Done.** prod-local поднимается одной командой с нуля; e2e зелёный против него; куки/CSRF работают в честной https-схеме (same-origin кабинет+API); релиз по тегу воспроизводим.

## Фаза 8.5. Продуктовый минимум: от «работает» к «выбрали бы»

**Цель.** Закрыть слой продуктовых дыр между технически работающим конструктором и инструментом, который живой человек предпочтёт привычным аналогам. Итог продуктового аудита кабинета: цикл «создать → опубликовать → собрать ответы» замкнут, но респондент после отправки упирается в фиксированную заглушку, среди типов вопросов нет телефона и выпадающего списка, ответы читаются только по одному в диалоге, форму нельзя ни встроить на сайт, ни закрыть по лимиту мест. Сервера фаза не требует (как и фаза 8) — VPS может появиться в любой момент, фазы 9–10 вклинятся без конфликтов. Порядок шагов — приоритет: фазу можно резать в любом месте, если сигналы пользователей потребуют другого. Самая ценная фича этого слоя — **email владельцу о новом ответе** — сознательно НЕ здесь: ей нужна транзакционная почта, она добавлена шагом в фазу 11 POST-MVP.

**Шаги.**

1. **Экран «после отправки»: свой текст благодарности и redirect.** Два необязательных поля в схеме формы (имена — в мини-дизайн-доке до кода): после успешной отправки рендерер показывает текст владельца вместо стандартной заглушки либо уводит по ссылке. Схема — контракт: Zod + Go + `ValidateSchema` синхронно, в одном PR (инвариант `web/CLAUDE.md`); иммутабельность версий покрывает настройки автоматически (респондент видит экран той версии, по которой отправил). Redirect валидируется на бэке: только абсолютный `http(s)`-URL, `javascript:` и прочие схемы отбрасываются.

   **Состояние — сделано.** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.5, шаг 1).
2. **Новые типы вопросов: телефон, выпадающий список, шкала, чекбокс-согласие.** Четыре вертикальных среза по чек-листу `web/shared/fields/README.md`: тип в Zod+Go, серверная валидация ответа, общее поле в `@fields` (бюджет рендерера!), пункт slash-меню, ячейка CSV, сводка (шаг 3). Телефон — мягкая серверная валидация (допустимые символы и длина, не жёсткий формат РФ). Dropdown переиспользует модель опций `single_choice` — различие только в рендере. Шкала — диапазон в настройках блока (1–5 … 1–10). Согласие — обязательный чекбокс с текстом владельца (юридический кирпичик под фазу 12 POST-MVP).

   **Состояние — сделано.** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.5, шаг 2).
3. **Ответы: колонки в таблице и вкладка «Сводка».** В таблице сейчас только дата и версия — добавить колонки первых отвечаемых блоков (длинный текст обрезается, полностью — в существующем диалоге). Вкладка «Сводка»: распределение по вариантам для choice-типов и шкалы (CSS-бары, без графических библиотек — список зависимостей заморожен), среднее/мин/макс для чисел, доля заполнивших для текстовых. Агрегация — на бэке (SQL по JSONB `answers`); браузеру сырые ответы целиком не выгружаются.

   **Состояние — сводка сделана; колонки таблицы отложены (решение владельца):.** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.5, шаг 3).
4. **Закрытие формы: по дате, по числу ответов, свой текст.** Сценарий «100 мест на мероприятие». Первые настройки формы вне схемы документа — где живут (колонки `forms` vs JSONB `settings`) решить через ADR до кода. Лимит проверяется сервером на приёме ответа; поведение на границе (строгая транзакционная проверка vs допустимый небольшой перебор) — зафиксировать выбор. Внимание, инвариант 5: сегодня закрытая форма неотличима от несуществующей (404); показ текста «приём закрыт» — осознанное изменение семантики для форм, закрытых настройкой владельца, — согласовать через ADR, черновики по-прежнему 404.

   **Состояние — сделано.** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.5, шаг 4).
6. **Визиты: просмотры и конверсия.** На карточке дашборда и странице ответов — «N просмотров → M ответов (K %)». Реализация — не серверный счётчик открытий, а визиты (решение владельца, ADR §10): таблица `form_visits` (строка на визит: форма, версия, `last_block_id` — самая дальняя точка, `submitted`, `meta` с user_agent/referer/UTM, **без IP**), публичная ручка `POST /public/v1/forms/{slug}/visits` и два бикона из рендерера (`navigator.sendBeacon` умеет только POST): на монтировании — «открыли», на `pagehide`/`visibilitychange→hidden` — «дошёл до блока». Апсерт по клиентскому UUIDv7 — тот же приём идемпотентности, что у отправки (ARCHITECTURE §4.7). Доступ — тем же HMAC-токеном формы, что уже выдаётся при `GET /public/v1/forms/{slug}`; своё, четвёртое ведро rate-limit по образцу `submit` (обобщённая обёртка `rateLimit(limiter, msg)`, `ClientIP` и GC уже есть). `submitted` ставит сервер при приёме ответа: тело `POST …/submissions` получает **необязательный** `visitId` (визита нет → ответ принимается как сейчас) — отсюда точная конверсия вместо деления двух независимых чисел.

   **Почему бикон, а не серверный счётчик.** Серверный счёт занижен кэшем (`max-age=60`, `ETag`/304) и считает краулеров вместо людей, а главное — принципиально не может сказать, докуда дошёл ушедший, то есть не годится фундаментом под воронку (шаг 6б). Бикон снимает и проблему кэша.

   **Осознанные границы (записать, а не лечить).** Накрутка просмотров возможна: ручка публичная на запись, а HMAC-токен реиграбелен внутри 24 ч (TECH-DEBT §5) — ущерб ограничен неверным числом на своём же дашборде, не данными; backstop — rate-limit и honeypot, как у отправки. Потерянный бикон `pagehide` даёт визит с `last_block_id = NULL`, то есть слегка завышенный «отскок» (`visibilitychange` уменьшает, но не до нуля). Роллапа нет: строка на визит при нашем масштабе не растёт опасно — пересмотреть, когда станет. Cookie и localStorage не заводим: `visitId` живёт в памяти страницы, человек между визитами не узнаётся.

   **Визиты пишутся для всех, без оглядки на будущие тарифы.** Когда придёт биллинг (POST-MVP фаза 13), платным станет **показ** воронки и источников, а не сбор: не собирая с бесплатных, в момент апселла нечего показать — плашка рекламирует пустоту, вместо того чтобы показать владельцу его настоящее число. Здесь из этого следует одно: проверок плана в этом шаге нет и не закладывается заглушек под них (YAGNI) — точка проверки появится на чтении в фазе 13.

   **Состояние — сделано.** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.5, шаг 6).
6б. **Воронка: на каком вопросе уходят.** На странице ответов — распределение визитов по `last_block_id` с человеческими подписями из схемы версии («66 дошли до „ИНН", 51 из них дальше не пошёл»). Данные к этому моменту уже лежат, работа рисовальная (CSS-бары, как в сводке шага 3). Сегодня, пока форма — одна длинная страница, сигнал косвенный: касание поля, а не переход на страницу; проскроллившего и передумавшего не видно — записать как погрешность. С приходом многостраничных форм тот же столбец начнёт заполняться из перехода на страницу — точнее, без миграции.

   **Состояние — сделано.** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.5, шаг 6б).
7. **Шаблоны форм.** 5–10 заготовленных `draft_schema` («запись на консультацию», «обратная связь», «регистрация на событие», «анкета кандидата», …) в диалоге создания формы: путь новичка до первой опубликованной формы — минута. Технически — статические JSON на фронте; тест прогоняет каждый через `ValidateSchema` (шаблон, разошедшийся со схемой, ловит CI, а не пользователь).

   **Состояние — перенесён в POST-MVP целиком (решение владельца), фаза 19.** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.5, шаг 7).
8. **Дашборд при росте: поиск и сортировка.** Поиск по отображаемому имени (серверный, по `name ?? title`) и сортировка (по обновлению / созданию / числу ответов). Мелко, но после ~20 форм без этого кабинет тонет.

   **Состояние — сделано.** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.5, шаг 8).
9. **Шаринг шире ссылки: embed и QR.** На экране «Поделиться» — сниппет `<iframe>` и QR-код ссылки. QR генерируется на клиенте: зависимость или ~200 строк своей реализации — через штатный вопрос о зависимостях. Для iframe проверить заголовки публичного домена в Caddyfile: CSP/`X-Frame-Options` сейчас, скорее всего, запрещают встраивание — ослаблять точечно только для `/r/*` (`frame-ancestors`), проверять на prod-local.

   **Состояние — перенесён в POST-MVP целиком (решение владельца), фаза 20.** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.5, шаг 9).
**Демо в конце фазы.** Сценарий «регистрация на мероприятие» за пять минут: новая форма → собраны имя, телефон и шкала «откуда узнали» → лимит 100 ответов, свой текст «спасибо» с редиректом на сайт → опубликована → открыта по ссылке с телефона → после пары ответов в кабинете: ответы видны колонками, в сводке — распределение по шкале, на карточке — «просмотры → ответы».

**Definition of Done.** Каждый новый тип проходит полный цикл (билдер → публикация → ответ → таблица → сводка → CSV) с тестами обеих сторон контракта; redirect не принимает не-`http(s)` схемы (тест на `javascript:`); лимит ответов не теряет данные и не пускает лишнего сверх зафиксированного допуска (тест гонки); сводка агрегируется сервером; ручка визитов живёт под своим rate-limit и требует токен формы, рендерер не заводит ни одной cookie, конверсия считается по `visitId` (не делением двух счётчиков); бюджет рендерера (95 КиБ gzip) не превышен; e2e-сценарий дополнен новыми точками.

**DoD: последний пункт закрыт (e2e).** Остальные пункты закрывались по ходу шагов; «e2e дополнен новыми точками» оставался наполовину — `visits-funnel` появился в шаге 6б, но новые типы вопросов, свой текст благодарности и лимит мест не проверялись в браузере ничем. Добито двумя правками: (1) в `full-loop` собираемая форма получила **шкалу и согласие** — они проходят тот же полный цикл, что требует первая строка DoD, и это единственное место, где проверяется, что их контролы вообще отрисовываются в прод-сборке (ряд кнопок и галочка берут вид из общего `fields.css`); (2) новый спек **`form-settings`** — свой текст благодарности доезжает через снапшот версии до экрана рендерера, а лимит в одно место закрывает форму сам, и второй респондент видит «приём закрыт» с текстом владельца.

**Почему `form-settings` отдельным файлом, а не строками в `full-loop`:** ему нужен ВТОРОЙ респондент (первый занимает единственное место), то есть ещё контекст и ещё отправка; пришитое к сборке формы кликами, это дало бы тест, который краснеет от правок билдера, ничего не говоря про настройки. Та же причина, по которой отдельным сделан `visits-funnel`. Отсюда правило, записанное в `e2e/README.md`: через билдер кликами ходит только `full-loop`, остальные строят форму запросами к API.

**Проверено не зелёным прогоном, а мутациями** (зелёный тест сам по себе не доказывает, что проверка на что-то реагирует). Три мутации, каждая краснеет ровно на своей проверке: убрать `thankYouText` из схемы → падает проверка текста благодарности; `responseLimit: null` → второй респондент видит форму вместо «приём закрыт»; убрать клик по делению шкалы → `aria-pressed` остаётся `false`. Последняя попутно показала, что контрол шкалы в прод-сборке реален (`<button aria-pressed="false" class="rf-scale-mark">4</button>`).

**Найдено попутно (записано, не заметено): сюита упёрлась в потолок rate-limit регистрации.** Каждый сценарий регистрирует свой аккаунт, а `registerBurst = 3` при пополнении ~1/30 с (`cmd/api/main.go`) — три спека расходуют бурст ровно в ноль. Холодный прогон проходит, но **повторный запуск в течение ~1,5 минут падает на шаге регистрации**, выглядя как сломавшийся тест (именно так и выглядел первый прогон мутации, пока причина не нашлась). Лимит ради тестов не ослабляется (инвариант 6) — ограничение записано в `e2e/README.md` вместе с выводом: четвёртый сценарий с регистрацией сделает сюиту красной сам по себе, и ему нужен другой способ заводить сессию.

**Состояние — закрыта (владелец продукта принял фазу).** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.5, итог).
**Перенесено в POST-MVP решением владельца:** шаблоны форм (шаг 7 → фаза 19 — половинчатые шаблоны обещают библиотеку, которой нет) и embed + QR (шаг 9 → фаза 20 — ссылка закрывает сегодняшние сценарии; заметка про `frame-ancestors` уехала вместе с шагом, чтобы не раствориться).

**Не делали (при необходимости — позже):** колонки первых вопросов в таблице ответов (хвост шага 3 — владелец дорабатывает таблицу отдельным заходом; сводка, ради которой шаг затевался, сделана).

**Открытый долг, заведённый фазой:** TD-20 (кабинет ретраит 4xx), TD-21 (advisory-lock на приёме ответа — померить под нагрузкой), TD-23 (у визитов нет срока хранения — до фазы 12), TD-24 (ведро rate-limit визитов не рассчитано на общий IP), TD-25 (аудит нативных контролов вместо shadcn). Ни один не блокер: раздел 1 TECH-DEBT пуст, гейт фазы 9 пройден.

## Фаза 8.7. Вопрос как группа блоков

**Вставка после фазы 8.5, до фазы 9.** Продуктовое решение владельца: перенять модель Tally, где вопрос — не один блок, а **группа самостоятельных блоков** (подпись + поле + контент между ними). Это добавление скоупа сверх исходного MVP (прецеденты — картинки автора §1 ARCHITECTURE и аналитика визитов) и дизайн-решение, зафиксированное в ADR-сводке (§10) и §3.4 ARCHITECTURE. Стоит **до** деплоя: меняет контракт схемы и требует апгрейдера версий — дешевле закрыть до реального прода, чем мигрировать живые формы.

**Цель.** Автор собирает вопрос из отдельных блоков: `title`/`label` (крупная/мелкая подпись), поле ввода и любой контент (`heading`/`text`/`image`) **между** подписью и полем. Заголовок и поле — отдельные пункты меню «/»; поле без подписи допустимо (форма может быть из одних полей, подпись в аналитике генерится). Перетаскивание не переклеивает подпись — привязка по группе (`groupId`), а не по позиции. Аналитика (CSV, сводка, воронка) остаётся честной: id отвечаемого блока — прежний ключ ответа и шаг воронки.

**Что переиспользуется и что переписывается.** Остаются: хранение схемы в JSONB, автосейв/версии/публикация, приём ответов, `internal/visits`, единая точка `QuestionOrder`. Переписываются: Go- и Zod-контракт блока (`groupId`, типы `title`/`label`/`heading`, снят `description`), `ValidateSchema` + предикаты (`isCaption`, расширенный `isContent`), апгрейдер `schemaVersion 1→2`, редактор (группы, «/»-пункты Title/Label, подсказки «добавить заголовок/поле», ведение `groupId` при добавлении/переносе/удалении), рендерер и `@fields` (рендер группы: подпись → контент → поле), `QuestionOrder` (подпись из группы + генерация имени).

**Шаги (детализируются перед стартом — план вертикального среза приносится на согласование).**

1. Контракт схемы v2 синхронно Go+Zod: `groupId`, типы `title`/`label`/`heading`, снятие `description`; предикаты `isCaption`/`isContent`; `ValidateSchema` (смежность блоков группы, ≤1 отвечаемого блока в группе). Тесты обеих сторон.
2. Апгрейдер `schemaVersion 1→2` (юниты, §8 ARCHITECTURE): старый блок `{label, description}` → группа `title(label) + text(description) + input` с сохранением id инпута; применяется на чтении к черновикам и опубликованным версиям.
3. `QuestionOrder`: подпись из `title`/`label` группы, генерация имени при отсутствии (плейсхолдер → тип+номер). CSV/сводка/воронка через неё — без правок логики.
4. Рендерер и `@fields`: рендер вопроса-группы (подпись → контент → контрол), новые контентные типы. Проверить бюджет 95 КиБ.
5. Редактор: группы на полотне, «/»-пункты Title/Label/Heading, подсказки «добавить заголовок/поле», ведение `groupId` при create/move/delete/slash; dnd на уровне блоков и групп.
6. Производные доки в том же PR: `SCHEMA.md`, `ANALYTICS.md` §4, `web/shared/fields/README.md`.

**Демо в конце фазы.** Собираешь вопрос: пишешь заголовок (`title`), вставляешь между ним и полем картинку-пример, добавляешь поле — всё отдельными блоками. Рядом — регистрационный блок из нескольких полей без заголовков, подписи которых в CSV/сводке сгенерированы из плейсхолдеров. **Definition of Done.** Контракт v2 синхронен Go/Zod с тестами обеих сторон; апгрейдер v1→v2 сохраняет id отвечаемых блоков и покрыт юнитами на трёх сценариях (пустая схема, форма без вопросов, форма с `description`); `QuestionOrder` даёт подпись из группы и осмысленную генерацию, CSV/сводка/воронка зелены на старых и новых формах; редактор ведёт группы без осиротевших подписей; бюджет рендерера 95 КиБ держится; производные доки обновлены в том же PR. Аналитический инвариант: ни одна колонка/шаг не теряет и не путает подпись при перетаскивании.

**Состояние — сделано (мелкая полировка отложена в TD-26).** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.7, итог).

## Фаза 11. Вход через Яндекс ID

**Цель.** Закрыть главный пробел MVP для живых пользователей — потерянный доступ — устранением причины, а не симптома: у человека, вошедшего через провайдера, пароля нет вовсе, забывать нечего, а email приходит уже подтверждённым. Побочная выгода — регистрация в один клик вместо придумывания пароля. Исходная редакция фазы в [`POST-MVP.md`](POST-MVP.md) лечила тот же пробел сбросом пароля по почте; **почтовая часть целиком переехала в следующую фазу** (провайдер, outbox, уведомление о новом ответе, сброс пароля, подтверждение email) — решение владельца, обсуждение 2026-07-22. Вход по паролю остаётся равноправным способом.

**Провайдер один — Яндекс ID; VK ID отложен** (решение владельца, 2026-07-22): фаза обкатывает механику, второй провайдер ложится в готовый каркас отдельным заходом. Практическое следствие — из объёма уходит добор почты: он был нужен только VK-аккаунтам, заведённым на телефон, а Яндекс отдаёт адрес всегда. Сверка VK (шаг 1) сохранена: она уже оплачена и понадобится, когда до него дойдут руки.

**Шаги.**

1. Сверка актуальной документации Яндекс ID и VK ID: эндпоинты, scope, отдаётся ли email и есть ли признак его подтверждения, обязателен ли PKCE. Регистрация приложений и redirect URI — действие владельца; отдельно проверить, принимается ли `localhost` для dev-контура.

   **Сверено 2026-07-22.** Яндекс: `oauth.yandex.ru/authorize` → `oauth.yandex.ru/token` → `login.yandex.ru/info` (`Authorization: OAuth <token>`); PKCE поддержан, при нём секрет не обязателен; `state` до 1024 символов; email в `default_email`/`emails`. VK ID: `id.vk.ru/authorize` → `id.vk.ru/oauth2/auth` → `id.vk.ru/oauth2/user_info`; **PKCE обязателен**, `state` не короче 32 символов, обмен кода требует `device_id` из ответа авторизации; email — только при выданном scope и согласии. **Признака подтверждения email не даёт ни один из двух**; поле `verified` у VK означает верифицированный профиль (галочка публичной персоны), а не почту — принять его за подтверждение адреса нельзя, это и есть исторический источник угонов этого класса. Отсюда правило связывания в шаге 4.
2. Миграция `0009`: таблица `user_identities` (`provider`, `provider_user_id`, `user_id` → `users` `ON DELETE CASCADE`, PK по паре провайдер+идентификатор) и `users.password_hash` → nullable. Отдельная таблица, а не колонки в `users`, — чтобы к одному аккаунту привязывались оба провайдера. `users.email` остаётся уникальным: аккаунт на адрес один, способов входа в него несколько.
3. Модуль `internal/oauth`: тип `Profile` и реализация Яндекса на stdlib. Маршруты параметризованы провайдером (`{provider}`), реестр — map с одной записью: это не абстракция впрок, а форма, в которую VK кладётся без переделки маршрутов и БД (он записан шагом плана, см. врезку к фазе). Чек-лист безопасности, каждый пункт с тестом: `state` в HttpOnly-cookie и сверка при возврате, PKCE S256, точное совпадение `redirect_uri`, таймаут HTTP-клиента, `io.LimitReader` на ответ провайдера, ни токен ни email не в логах. Две **опциональные** env-переменные: без ключей провайдер выключен.
4. Правила входа в `internal/auth` (таблица случаев = таблица тестов): identity найдена → вход в её аккаунт; identity нет и пользователя с таким email нет → создание пользователя без пароля вместе с личным воркспейсом в одной транзакции; **identity нет, но аккаунт с таким email есть → сессия не выдаётся**, человек попадает на экран «У вас уже есть аккаунт с этим адресом — войдите паролем один раз, и мы привяжем провайдера»; после успешного входа паролем создаётся `user_identities`, дальше вход в один клик. Автосвязывания нет ни при каких условиях — ADR §10: провайдеры не ручаются за принадлежность адреса.

   Незавершённое состояние там, где нужен второй шаг (привязка паролем), живёт в подписанной короткоживущей cookie по образцу HMAC из `internal/token` — без новой таблицы. Привязка и отвязка провайдера из настроек аккаунта — за рамками фазы.
5. Эндпоинты: `GET /auth/providers` (чтобы фронт не рисовал мёртвых кнопок), `GET /auth/oauth/{provider}/start`, `GET /auth/oauth/{provider}/callback`, `POST /auth/oauth/link` (пароль → привязка провайдера к существующему аккаунту). `/link` принимает пароль, поэтому живёт под тем же ведром rate-limit, что и `/login`, и обязан отвечать за постоянное время (`equalizeTiming`, `internal/auth/service.go`). Отдельное ведро — на `/callback`, с добавлением в задачу `ratelimit-gc`.
6. Фронт кабинета: кнопка «Войти через Яндекс» на экранах входа и регистрации — обычной ссылкой, а не `fetch` (нужен полноценный редирект браузера); маршрут «войдите паролем, чтобы привязать провайдера».
7. Прогон на проде, тег `v0.11.0`.

**Состояние — закрыта (шаги 1–7), тег `v0.11.1`.** Вход через Яндекс живёт на проде, подтверждён владельцем. Сверка провайдеров (шаг 1) **сломала посылку принятого решения**: признака подтверждения email не даёт ни Яндекс, ни VK, поэтому автосвязывание заменено на привязку через разовый ввод пароля (ADR §10). Ревью нашло три дефекта (гашение cookie через `defer`, JSON-500 вместо редиректа при сбое провайдера, непроходимый экран привязки) — все починены в той же ветке. Первая выкатка `v0.11.0` уехала на прод сломанной (переменные не доезжали до контейнера — якорь `x-app-env` перечисляет их поимённо); починка `v0.11.1` + новая проверка в `check-docs`, сторожащая этот класс. Фаза завела **TD-34**; VK ID отложен в [`BACKLOG.md`](BACKLOG.md). Разбор — [`JOURNAL.md`](JOURNAL.md) «Фаза 11».

**Демо в конце фазы.** На `app.trillix.ru/login` — кнопка «Войти через Яндекс». Нажатие у нового человека: экран согласия → возврат в кабинет залогиненным, в `user_identities` ровно одна строка, `password_hash` у него `NULL`. Повторный вход тем же способом не создаёт второго пользователя. Существующий парольный аккаунт продолжает входить паролем; вход через Яндекс с тем же адресом просит один раз ввести пароль и после этого приводит в тот же аккаунт — с его формами, а не в пустой дубль, и не отдаёт его тому, кто пароля не знает.

**Definition of Done.** Возврат на `/callback` с подменённым или отсутствующим `state` → 400 без выдачи сессии (тест); вход через провайдера при совпадении email не выдаёт сессию до успешного ввода пароля (тест — это и есть защита от захвата чужого аккаунта); интеграционный тест полного колбэка против фейкового провайдера зелёный; миграция проходит up/down/up на чистой базе; ни один токен провайдера не попадает в БД и логи.

## Фаза 12. Транзакционная почта и восстановление пароля

> Развёрнута из [`POST-MVP.md`](POST-MVP.md) (там названа «Фаза 11» — номер сдвинут вставкой фазы «Вход через Яндекс ID»; здесь она двенадцатая). Полное описание, цель, демо и DoD — там; здесь — детализация до вертикальных слайсов и рабочее состояние. Порядок фаз почта→юридика→деньги жёсткий: биллинг без почты невозможен.

**Цель** (цитата POST-MVP). Закрыть механизм отправки писем: сброс пароля («забыл пароль» сейчас не решается никак), подтверждение email при регистрации, уведомление владельцу о новом ответе. Заодно закрывается **TD-34** (аккаунт-без-пароля становится достижим через сброс). Почта понадобится и биллингу, и командам.

**Рамка outbox (согласована с владельцем 2026-07-22, ADR §10).** Общий транзакционный outbox — **узкий транспорт доставки наружу**, а не шина событий: строка = намерение доставки (`channel`+`payload`), диспетчер — тупой релей, внутренние реакции через него не ходят. Один транспорт (почта) сейчас; вебхуки (фаза 15) и телега — новыми значениями `channel` без переделки схемы.

**Шаги — вертикальными слайсами** (коммит после каждого; слайсы A–D пишутся и тестируются на dev-транспорте `log`, реальный провайдер и DNS нужны только к прод-демо в E):

- **A. Каркас почты.** Миграция `0010_outbox` (одна таблица, `channel`+`payload`+ретраи); модуль `internal/mail` (интерфейс `Mailer`, dev-`LogMailer`, `Service` с `EnqueueEmail`/`Dispatch` и бэкоффом); диспетчер как `periodic`-задача `outbox-dispatch`; config `MAIL_TRANSPORT`/`MAIL_FROM`; ADR-строка. Продюсеров ещё нет — проверяется прямым enqueue в тесте.
- **B. Сброс пароля** (ядро демо). Миграция `password_reset_tokens` (SHA-256, TTL 30 мин, одноразовый); `POST /auth/forgot-password` (всегда 200, rate-limit по IP и email, постоянное время — не раскрываем существование аккаунта) и `POST /auth/reset-password` (токен → новый пароль + инвалидация всех сессий); шаблон письма (первый потребитель `EnqueueEmail`); фронт-экраны «Забыли пароль?» / «Проверьте почту» / «Новый пароль».
- **C. Подтверждение email.** Мягкое: аккаунт работает сразу, неподтверждённый email помечен баннером в кабинете; письмо-подтверждение при регистрации.
- **D. Уведомление владельцу о новом ответе.** Первый продуктовый потребитель outbox: в транзакции приёма ответа пишется письмо владельцу со ссылкой в таблицу; тумблер на форме (для новых — вкл); **троттлинг-дайджест** «N ответов» не чаще раза в N минут (вирусная форма не засыпает владельца) — добавит ключ коалесинга в `outbox`.
- **E. Прод-обвязка** (инфраструктура владельца). Выбор провайдера — **Yandex Cloud Postbox** (та же экосистема, что Яндекс ID и бэкапы; доставляемость в Яндекс.Почту; рублёвая оплата; ADR §10). Реализация `Mailer` — один **SMTP**-клиент на stdlib `net/smtp` (не HTTP: SES-совместимый API Postbox потребовал бы SigV4/SDK, а зависимости заморожены); тот же транспорт бьёт в Postbox (прод) и Mailpit (prod-local). DNS SPF/DKIM/DMARC, Mailpit в prod-local, прогон mail-tester 9+/10.

**Состояние — в работе. грипа-входа; если у типа однажды появится своя настройка, реестр обязан выразить запреты

### Этап 16.5. Гейт публикации — сделан и ОТМЕНЁН владельцем

**Решение 5 принято утром 2026-07-31 и развёрнуто в тот же день, после показа кода:** «этот
гейт мне не нравится». Гейт был написан целиком (три блокера в домене, 422 со списком, зеркало
в кабинете, поповер «Что мешает» с переходом к блоку) и удалён — ADR-строка §10
[`ARCHITECTURE.md`](ARCHITECTURE.md) переписана в отменяющую **до** удаления кода, чтобы
следующий заход не принял отсутствие гейта за упущение и не построил его снова.

**Что стоит вместо него:** безымянный вопрос получает сгенерированное имя — и так было всегда,
цепочка `questionLabel` заканчивается «Тип N» с фазы 8.7. Подставлять было нечего: спрошенный
владельцем «дефолт, если названия нет нигде» уже существовал.

**Что вернулось вместе с отменой** (названо в ADR-строке): форма публикуется с пустой подписью
и со списком выбора без единого варианта. Обещание комментария `ValidateSchema` «непустая
подпись, ≥1 опция — правило момента публикации» снова не выполняется нигде, и сам комментарий
приведён в соответствие на обеих сторонах контракта — документ и код согласны в том, что
такого правила нет.

**Урок этапа — не технический.** Решение было принято по описанию, а развёрнуто по коду:
владелец увидел, чем гейт оказывается в работе, и передумал. Стоимость отмены оказалась низкой
ровно потому, что гейт был отдельной функцией с одним вызовом, а не ветками внутри валидатора.
Это довод в пользу того, как он был устроен, а не против того, что его написали.

> возможностей, единая точка проверки, мягкая деградация, риски): читать перед любым шагом,
> ссылки «§» ниже — на неё.
> Зона — новый модуль `internal/entitlements`, приём ответа (`internal/submissions`), воронка
> (`internal/visits`), транзакция регистрации (`internal/auth`), миграции, кабинет
> (`web/app`).

**Цель.** У воркспейса появляется тариф, у тарифа — лимиты, у лимитов — одна точка проверки.
Добавить возможность в платный тариф стоит трёх строк, убрать — одной строки данных без
выкатки. Денег фаза не принимает.

**Сквозной демо-критерий фазы (согласован с владельцем 2026-08-01, цитата §1 спеки).**
Воркспейс на плане с лимитом 5 ответов/месяц:

1. шестой ответ через публичную форму принимается — `curl` отдаёт 200, `SELECT count(*)` даёт 6;
2. в кабинете видно 5 ответов и плашку «1 ответ скрыт — лимит тарифа исчерпан»;
3. `GET /forms/{id}/funnel` отдаёт 402 `plan_required`, в кабинете вместо воронки — заглушка
   с настоящим числом не дошедших;
4. `UPDATE subscriptions SET plan_code = 'pro'` → **без перелогина и без деплоя**: таблица
   показывает 6 ответов, воронка открывается, плашка исчезает.

**Решения владельца 2026-08-01** (ADR §10 [`ARCHITECTURE.md`](ARCHITECTURE.md), подробности —
спека §11): Free — **100** ответов/мес; период — **календарный месяц** по Europe/Moscow;
экспорт CSV **скрывает** сверхлимитные наравне с таблицей; гейт числа воркспейсов — **ключ
данными, `CheckAccount` не пишется**, создание воркспейса отложено; в списке Pro на странице
тарифа — **только работающие** возможности, без обещаний будущих фаз.

### Шаг 1. Миграция и сид тарифов

`plans`, `subscriptions`, `workspace_usage`, колонка `submissions.over_quota` (§3). Три плана;
**все существующие воркспейсы → `legacy_free` с безлимитом по всем ключам** (§8); регистрация
заводит `subscriptions` в той же транзакции, что `user + workspace + membership` — инвариант
транзакции регистрации расширяется четвёртой строкой, воркспейса без подписки не бывает.

**Демо.** `make migrate-up` на копии прода: у каждого воркспейса ровно одна строка подписки,
план `legacy_free`, ни один лимит не активен; регистрация нового пользователя даёт подписку
`free` — видно `SELECT`ом; `make migrate-down` возвращает схему без следов.


**Состояние — сделано.** Три таблицы, колонка `over_quota`, сид трёх планов безлимитными, существующие воркспейсы на `legacy_free`, подписка в обеих транзакциях регистрации. Проверено циклом `migrate-up → down → up` на dev-базе; разбор — [`JOURNAL.md`](JOURNAL.md).

### Шаг 2. `internal/entitlements` — каталог и единая точка

Каталог ключей (§4), разрешение плана воркспейса, `CheckWorkspace` → `Decision`, `Snapshot`
для кабинета, сентинел `domain.ErrPlanRequired` → **402** `plan_required` в `respond.go`.
Табличные юнит-тесты на разбор `limits` (число, `null` = безлимит, булев ключ) и
`TestPlansCoverCatalog` (все ключи каталога × все планы — молчание плана краснеет).
`CheckAccount` **не пишется** (§5): единственный его потребитель отложен.

**Демо.** `TestPlansCoverCatalog` краснеет, если убрать ключ из `limits` любого плана
(предъявляется мутацией); `Decision` на безлимитном плане разрешает, на исчерпанном — нет.


**Состояние — сделано.** Каталог, `CheckWorkspace → Decision`, `Snapshot`, `PeriodStart`, сентинел `ErrPlanRequired` → 402. `CheckAccount` не писался — потребителя нет (решение владельца).

### Шаг 3. Квота ответов в приёме

`WorkspaceID` доезжает до `PublicForm` (одна колонка в существующем запросе, как
`NotifyOnSubmission`); инкремент `workspace_usage` тем же CTE, что вставка ответа; строка
сверх квоты помечается `over_quota` (§6). Приём **не отказывает никогда**.

**Демо.** Интеграционные тесты: ответ сверх квоты → 200 и `over_quota = true` в БД;
идемпотентный ретрай не растит счётчик; форма на исчерпанной квоте продолжает принимать
(сторож против путаницы с жёстким капом формы). Каждый предъявляется мутацией.


**Состояние — сделано.** `WorkspaceID` в `PublicForm`, CTE-инкремент, пометка `over_quota`, приём не отказывает никогда. Ревью нашло двойное чтение часов на границе месяца — починено переносом периода в `Decision` (`JOURNAL.md`).

### Шаг 4. Скрытие сверхлимитных в кабинете и возврат при апгрейде

Фильтр `WHERE NOT over_quota` в списке ответов, экспорте CSV и сводке; плашка со словами
«сохранены и откроются после перехода на Pro»; смена плана снимает пометку одной транзакцией.

**Демо.** На исчерпанной квоте: таблица и CSV показывают ровно лимит, плашка называет число
скрытых; после смены плана `UPDATE`ом — те же таблица и CSV отдают всё, плашки нет.
Анти-IDOR-тест на новый путь.


**Состояние — сделано.** Фильтр в листинге (и через него в CSV и сводке), в счётчиках карточки; `Repo.RevealHidden` возвращает всё. Ревью нашло потерю index-only у счётчиков — закрыто миграцией `0015` после замера.

### Шаг 5. Гейт воронки

`visits.Service.Funnel` спрашивает `CheckWorkspace(AnalyticsFunnel)`; отказ — 402
`plan_required` **с настоящим числом не дошедших в теле**; экран воронки в кабинете рисует
это число и предложение открыть разбивку (§7). Визиты по-прежнему пишутся всем.

**Демо.** На `free` — 402 и заглушка с числом; на `pro` — воронка; в обоих случаях
`form_visits` пополняется одинаково (`SELECT count(*)` до и после визита).


**Состояние — сделано.** 402 `plan_required`, авторизация строго перед тарифом, визиты собираются при любом плане, заглушка показывает настоящее число не дошедших. Числа в теле отказа нет — оно уже на странице (отступление названо вслух).

### Шаг 6. Страница «Тариф»

`GET /api/v1/workspaces/{id}/entitlements` (план, лимиты, расход, дата сброса) и страница
`/settings/plan`: текущий план, «Ответов в этом месяце: 87 из 100», список работающих
возможностей Pro, кнопка «Перейти на Pro» → заглушка «скоро». Обновить [`API.md`](API.md).

**Демо.** Страница показывает те же числа, что `SELECT` из `workspace_usage`; после приёма
ответа число растёт после перезагрузки.


**Состояние — сделано.** Ручка со своей проверкой членства в запросе, `CatalogOrder` для стабильного порядка, страница `/settings/plan`, пункт в сайдбаре, кнопка оплаты — честная заглушка. Живой проверки глазами не было.

### Шаг 7. Документы

`ARCHITECTURE.md` §3.3 (новые таблицы) — ADR-строки §10 внесены **до кода**, шагом 0;

Плюс **хендбук подсистемы** [`BILLING.md`](BILLING.md) со скиллом `billing-plan` (по образцу

**Демо.** `make check-docs` краснеет, если посадить `if plan == "free"` в сервис-метод

**Состояние — сделано.** Шестая проверка `check-docs` (предъявлена мутацией), правило в `internal/CLAUDE.md`, хендбук [`BILLING.md`](BILLING.md) со скиллом `billing-plan`, `STATUS.md` переписан, разбор фазы — в [`JOURNAL.md`](JOURNAL.md).

## Правила ведения работ

Ветка на шаг или связку из 2–3 шагов, PR с зелёным CI, squash-merge в `main` (который защищён дисциплиной, а не GitHub'ом — branch protection недоступна на текущем плане, подробности в `PROCESS.md` §5).

**С фазы 15 работы фазы собираются на общей ветке фазы** (решение владельца 2026-07-28): ветка
на этап → squash-merge в ветку фазы (`phase15/canvas-freedom`) → squash-merge ветки фазы в
`main` в конце фазы. Прежний порядок (этап уезжает в `main` сразу) остаётся для работ вне фаз —
задач из очереди, техдолга, дефектов прода. Конец каждой фазы — git-тег: до фазы 7 тег просто фиксирует веху, с фазы 7 он ещё и собирает релизные артефакты в GHCR, с фазы 9 — деплоит. Шаг, разросшийся больше чем на день, режется на два — это сигнал недодекомпозиции. Отступления от архитектуры фиксируются в ADR-таблице архитектурного документа, а не остаются устной легендой.
