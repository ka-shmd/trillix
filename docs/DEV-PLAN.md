# План разработки по фазам — конструктор форм (MVP), редакция 2

Редакция под новое ограничение: **VPS пока нет**, вся разработка ведётся локально, CI живёт в GitHub. Деплой отодвинут в конец и разбит так, что почти вся его подготовка делается заранее без сервера — когда VPS появится, ввод прода в строй займёт один день, а не неделю.

## Три контура: как организована среда

Ключевая идея редакции: контуров не два, а три, и средний из них — секретное оружие разработки без сервера.

**Контур dev — ежедневная работа.** Postgres в Docker, Go-API через `go run` (или `air` с hot-reload) прямо на хосте, оба фронта через `vite dev` с HMR. Порты: api `:8080`, app `:5173`, renderer `:5174`; Vite проксирует `/api` и `/public` на `:8080`, поэтому CORS в dev не нужен. Максимальная скорость итерации: правка кода видна за секунды.

**Контур prod-local — репетиция прода у себя на машине.** Полная прод-сборка, запущенная локально: настоящие Docker-образы (distroless), настоящий `compose.prod.yml`, настоящий Caddy с доменами `app.localhost` и `f.localhost` (API — same-origin под `app.localhost/api`, отдельного домена нет — ADR §10; домены `*.localhost` резолвятся сами, Caddy выдаёт на них TLS от своего локального CA — получаем честный https без единой DNS-записи). Этот контур поднимается командой `make prod-local` и означает: **всё, что нужно для прода, кроме самого сервера, написано и проверено**. Когда появится VPS, изменится только имя хоста и способ доставки файлов.

**Контур prod — настоящий VPS.** Появится в фазе 9. К этому моменту от prod-local он будет отличаться четырьмя вещами: реальные домены и DNS, Let's Encrypt вместо локального CA, секреты из GitHub Secrets/серверного `.env`, бэкапы в offsite-хранилище. Всё остальное — байт в байт те же образы и тот же compose.

Чтобы три контура не разъехались, действует правило **одного бинарника и одного набора env-переменных**: приложение не знает, в каком контуре живёт; все различия (DSN базы, домены cookie, уровень логов, параметры rate limit) — только через окружение. Файлы: `.env.example` (документация всех переменных), `.env.dev`, `.env.prod-local` — в репозитории; `.env` прода — только на сервере. Никаких `if env == "dev"` в коде — это классический источник «на проде повело себя иначе».

CI в GitHub с первого дня, но без деплоя: его работа — линт, тесты, сборка фронтов и **сборка прод-образов** (публикация в GHCR по тегу). То есть релизные артефакты копятся в registry заранее; деплой потом — это «скачать готовое», а не «собрать на сервере».

## Как читать план

Формат прежний. Каждая фаза: **Цель** (абзац), **Шаги** (единицы «сел — сделал — закоммитил», от получаса до пары часов), **Демо в конце фазы** (что вы увидите глазами — критерий приёмки), **Definition of Done** (технический шлагбаум). Принципы: вертикальные срезы вместо слоёв; тесты внутри фазы, а не потом; уродливое-но-работающее раньше красивого.

**Это документ о будущем.** У закрытого шага здесь остаётся одна строка — вердикт и ссылка; разбор (что реально сделано, какие решения принимались, что найдено попутно, что осознанно не делалось) живёт в [`JOURNAL.md`](JOURNAL.md). Разделение не косметическое: к июлю 2026 ретроспектива разрослась настолько, что план перестал читаться целиком (43 000 токенов — больше лимита одного чтения), то есть ответ на вопрос «что делать дальше» стоил дороже, чем кто-либо готов платить. Дописывать дёшево, переписывать дорого — поэтому журнал рос, а план тонул.

**Правило:** закрывая шаг, пиши разбор в журнал, а здесь оставляй строку `**Состояние — <вердикт>.**` со ссылкой. Если разбор снова начал расти внутри плана — он на неправильной стороне. Текущее состояние системы — [`STATUS.md`](STATUS.md).

## Фаза 0. Фундамент и CI

**Цель.** Монорепозиторий, где вся рутина автоматизирована с первого коммита: одна команда поднимает dev-контур, GitHub на каждый push гоняет полный набор проверок. Всё настроенное здесь экономит время в каждой следующей фазе.

**Шаги.**

1. Инициализировать репозиторий со структурой из архитектурного документа (`cmd/`, `internal/`, `web/app`, `web/renderer`, `migrations/`, `deploy/`). Пустые пакеты с `doc.go`, чтобы скелет был виден сразу.
2. `go.mod`, минимальный `cmd/api/main.go`: сервер на stdlib, маршрут `GET /healthz` → `{"status":"ok"}`, `slog` в JSON, чтение конфига из env через маленький хелпер с валидацией обязательных переменных при старте (упасть сразу, а не на первом запросе).
3. `compose.dev.yml`: только Postgres 16 с volume, порт на `127.0.0.1:5432`. Файлы `.env.example` и `.env.dev`.
4. Makefile — единая точка входа: `make dev` (БД + API с hot-reload), `make test`, `make lint`, `make migrate-up/down`, `make seed` (заглушка, наполнится позже). Раннер миграций — команда `./api migrate up` внутри бинарника (golang-migrate как библиотека); миграция `0001` — пустышка-проверка механизма.
5. `golangci-lint` (errcheck, govet, staticcheck, gofumpt) + конфиг.
6. Заготовки фронтендов: два Vite-проекта react-ts, strict TypeScript, eslint + prettier; в `vite.config.ts` приложения — proxy `/api → :8080`. Пока рендерят строку текста.
7. GitHub Actions, workflow `ci.yml`: на push и PR — линт Go, `go test -race`, `tsc --noEmit` + eslint + vitest для обоих фронтов, сборка обоих фронтов. Кэширование Go-модулей и node_modules, чтобы прогон был минуты, а не десятки минут. Красный CI = нельзя мержить (branch protection на main).

**Демо в конце фазы.** На чистой машине: `git clone`, `cp .env.dev .env`, `make dev` — через минуту `curl localhost:8080/healthz` отвечает JSON, `npm run dev` в обоих фронтах показывает страницы. В GitHub на коммите — зелёная галочка со всеми jobs.

**Definition of Done.** README «как запустить за 5 минут»; CI зелёный и быстрый (<5 минут с кэшами); `.env.example` описывает каждую переменную комментарием; приложение падает при старте с внятной ошибкой, если переменной не хватает.

## Фаза 1. Аутентификация

**Цель.** Полный контур учётных записей: регистрация, вход, сессия, выход. Первая настоящая вертикаль «БД → сервис → API → экран», на которой обкатываются все паттерны проекта: слои, формат ошибок, интеграционные тесты, работа TanStack Query с API.

**Шаги.**

1. Миграция `0002`: `users`, `workspaces`, `workspace_members`, `sessions`. Генератор UUIDv7 в `internal/domain` с юнит-тестом на монотонность.
2. Обёртка argon2id (параметры OWASP) + юнит-тесты.
3. Модуль `auth`, слой repo (sqlc): создание пользователя, поиск по email, CRUD сессий. Регистрация создаёт пользователя, личный воркспейс и членство **одной транзакцией**.
4. Слой service: `Register`, `Login` (одинаковое время ответа для «нет email» и «неверный пароль»), `Logout`, `GetMe`; доменные ошибки (`ErrEmailTaken`, `ErrInvalidCredentials`).
5. HTTP-слой: `/api/v1/auth/*`; cookie httpOnly+SameSite=Lax (флаг Secure — из env: в dev по http он выключен, в prod-local/prod включён — первый пример «различие контуров живёт в env»); CSRF-токен; middleware `RequireAuth`; единый `respond.go` с маппингом доменных ошибок; in-memory rate limit на `POST /auth/login`.
6. Фоновая горутина чистки истёкших сессий — заодно общий механизм периодических задач.
7. Интеграционные тесты против Postgres в testcontainers: регистрация → логин → me → logout → 401. Эти тесты гоняются и в CI (testcontainers работает на GitHub-раннерах из коробки).
8. Фронт: экраны Login/Register в layout-группе `_auth`; api-клиент (fetch-обёртка: CSRF-заголовок, разбор единого формата ошибок); layout-группа `_app` с загрузкой `/auth/me` и редиректом; кнопка выхода.

**Демо в конце фазы.** Локально в браузере: регистрируетесь → попадаете в пустое приложение со своим email в шапке → F5 — сессия жива → выход → защищённый маршрут редиректит на логин. Неверный пароль — человеческая ошибка под полем. Цикл curl'ом по `/auth/login` упирается в rate limit.

**Definition of Done.** Интеграционные тесты auth зелёные локально и в CI; в БД нет паролей и токенов в открытом виде; повторная регистрация на email — 409 с внятным сообщением.

## Фаза 2. Формы как сущности (CRUD)

**Цель.** Дашборд: создать форму, увидеть список, переименовать, удалить. Билдера ещё нет — форма пока карточка с названием. Появляется вся механика ресурсов с проверкой прав, копируемая дальше как паттерн.

**Шаги.**

1. Миграция `0003`: `forms`, `form_versions`; генератор slug (nanoid ~10 символов, свои 20 строк).
2. Repo: создание с пустой `draft_schema`, список по воркспейсу с курсорной пагинацией, получение, обновление title, удаление.
3. Service: каждая операция начинается с проверки членства в воркспейсе (анти-IDOR закладывается в первом же ресурсе). Юнит-тест на запрет чужого доступа обязателен.
4. HTTP: `GET/POST /forms`, `GET/PATCH/DELETE /forms/{id}`. Интеграционный тест: пользователь A не трогает форму пользователя B (404).
5. `make seed`: скрипт сидирования (пользователь + 60 форм) — нужен для проверки пагинации и дальше пригодится постоянно.
6. Фронт: `forms.index` — грид карточек через TanStack Query; «Новая форма» (мутация + инвалидация + переход в заглушку редактора); переименование инлайн; удаление с подтверждением; скелетоны; пустое состояние.
7. Заглушка маршрута `forms.$slug.edit`: показывает title и JSON черновика — точка входа фазы 3.

**Демо в конце фазы.** Создаёте три формы → карточки с датами → переименовали, удалили → F5, всё на месте. Второй аккаунт в инкогнито по чужому URL получает 404. После `make seed` список корректно листается.

**Definition of Done.** Тесты изоляции воркспейсов зелёные; пагинация проверена на 60 формах; мутации фронта корректно инвалидируют кэш Query.

## Фаза 3. Билдер

**Цель.** Сердце продукта: редактор, где форма собирается из блоков семи типов, всё автосохраняется. Публикации нет — билдер работает только с черновиком.

**Шаги.**

1. Контракт схемы: Zod-схемы `FormSchema`/`Block` в `web/*/src/entities` + зеркальные Go-типы с `ValidateSchema` (лимиты: ≤200 блоков, ≤100 опций, длины строк). Единственный шаг без картинки — он определяет язык обеих сторон.
2. Бэкенд: `PATCH /forms/{id}` принимает `draft_schema` → `ValidateSchema` → оптимистичная блокировка по `updated_at` (расхождение → 409). Интеграционные тесты: валидная схема сохраняется, мусор — 422, устаревший `updated_at` — 409.
3. Zustand-стор билдера: `{blocks, selectedId, dirty}`; операции add/update/remove/move/duplicate. Стор — чистый TypeScript без React, покрывается vitest сразу.
4. Каркас экрана: палитра типов слева, канвас-список в центре, панель настроек справа. Клик по типу добавляет блок, клик по блоку выделяет.
5. Редактирование: label/description инлайн на канвасе; справа — required и типоспецифика (для choice — редактор опций: добавить, переименовать, удалить, порядок).
6. Автосейв: дебаунс 800 мс → `PATCH` всей схемы; индикатор «Сохранение…/Сохранено/Ошибка — повторить»; при 409 — баннер «Изменено в другой вкладке»; предупреждение при уходе с несохранённым.
7. Перемещение блоков кнопками вверх/вниз (dnd — в фазе 8).
8. Живое превью (переключатель «Редактор/Превью»): блоки рендерятся как увидит респондент. Компоненты полей пишутся в общий пакет — фаза 4 переиспользует их в рендерере.

**Демо в конце фазы.** Накидываете анкету из 6–7 вопросов всех типов → превью показывает её глазами респондента → закрыли вкладку, открыли — всё на месте. Соседняя вкладка меняет ту же форму — первая честно сообщает о конфликте.

**Definition of Done.** Юниты стора и `ValidateSchema` зелёные; автосейв не теряет правки при непрерывном вводе 30 секунд; превью совпадает с набором блоков.

**Примечание о редакторе.** Палитра-канвас-редактор этой фазы — сознательно временный: его задача дать рабочий редактор, чтобы прогнать бэкенд через фазы 4–6. Целевой UX (markdown-полотно со slash-командами в стиле Tally) вынесен в отдельную фазу 6.5; он заменит только поверхность ввода, переиспользуя стор, схему, автосейв и превью этой фазы.

## Фаза 4. Публикация и публичный рендерер

**Цель.** Форма получает жизнь за пределами кабинета: «Опубликовать» создаёт иммутабельную версию, форма открывается по ссылке без входа. Локально роль «публичного домена» играет второй vite-порт — этого достаточно, чтобы увидеть и проверить всё поведение.

**Шаги.**

1. Публикация на бэке: `POST /forms/{id}/publish` одной транзакцией создаёт `form_versions` (version = max+1), ставит `published_version_id`, `status='published'`; `unpublish` → `closed`. Тесты: две публикации подряд — версии 1 и 2.
2. Публичный эндпоинт `GET /public/v1/forms/{slug}`: схема опубликованной версии + title; `Cache-Control: public, max-age=60` и ETag; 404 для черновиков и закрытых. Сюда же — HMAC-токен времени выдачи (поле для антиспама фазы 5).
3. Превью ссылок (Open Graph): HTML-документ страницы формы `/r/{slug}` отдаёт **Go**, а не статика — только так краулеры мессенджеров/соцсетей получат мета (они читают HTML, не выполняя JS). Go подставляет в `<head>` опубликованной формы `og:title`/`og:description` (из title и описания формы) и `og:image` — пока **общая брендовая заглушка** (базовый URL картинки из env; своя картинка на форму — пост-MVP, зависит от загрузки файлов). Тело документа грузит тот же React-SPA — «голова на сервере, тело на клиенте». **Безопасность:** title/описание — пользовательский текст, вставляется в мета только через автоэкранирование (`html/template`), никогда «сырым»; черновик/закрытая форма отдают **404**, как и JSON-ручка, — HTML-путь не раскрывает существование приватного; `dangerouslySetInnerHTML` по-прежнему под запретом. Одинаково во всех контурах (никакого «мета только на проде»).
4. Рендерер (`web/renderer`, vite на `:5174` с proxy `/public → :8080`): slug из pathname (`/r/{slug}`), рендер всех семи типов из общих компонентов фазы 3, ответы в `useReducer`, черновик ответов в sessionStorage. Экраны «загрузка», «форма недоступна» (в фазе 5 — единый 404: черновик, закрытая и несуществующая неотличимы) и «ошибка загрузки». (Позже, в фазе 8.5 шаг 4, закрытая форма отделена от 404: своя `410`-семантика и экран «приём закрыт» — см. раздел шага 4; черновик по-прежнему 404.)
5. Клиентская валидация по той же Zod-схеме: required, email, число, дата; ошибки по blur и при отправке.
6. Бюджет бандла рендерера проверяется в CI (превышение валит сборку), но порог **поднимается выше 60 КБ gzip** — React + react-dom исчерпывают его в одиночку; конкретное число фиксируется здесь. Запасной выход, если из-за веса не берётся Lighthouse ≥90: свап рендерера на `preact/compat` (алиас `react → preact/compat` только в сборке рендерера — компоненты остаются на React-API, `@fields` не трогаются). Кнопка «Отправить» пока дизейблится с подписью «скоро» либо пишет в консоль.
7. Кабинет: кнопка «Опубликовать» в шапке билдера; после — панель со ссылкой `localhost:5174/r/{slug}` (базовый URL публичной части — из env: ещё одно различие контуров, живущее в конфигурации), «Копировать», статус «Опубликовано · версия N», бейдж «Есть неопубликованные изменения», кнопка «Закрыть форму».

**Демо в конце фазы.** Публикуете анкету → копируете ссылку → открываете в инкогнито (и с телефона по локальной сети через `--host`): форма грузится мгновенно, поля работают, валидация подсказывает. Меняете вопрос без публикации — инкогнито по F5 видит старую версию; публикуете — новую.

**Definition of Done.** Тесты публикации/версий зелёные; бюджет бандла в CI работает; черновики недоступны по прямому URL ни при каком статусе (включая HTML-путь превью); превью-ссылка отдаёт корректные OG-мета опубликованной формы, а пользовательский текст в них экранирован (тест на инъекцию вида `"><script>` в title); Lighthouse (mobile) на рендерере ≥90 по Performance.

## Фаза 5. Приём ответов

**Цель.** Респондент отправляет ответ — он надёжно ложится в базу с привязкой к версии формы. Самый атакуемый эндпоинт делается сразу правильно: валидация, лимиты, антиспам, идемпотентность.

**Шаги.**

1. Миграция `0004`: `submissions`. Валидатор `ValidateAnswers(schema, answers)` — обязательность, типы, принадлежность опций, длины. Самая ветвистая функция проекта: табличные юнит-тесты (3–5 кейсов на тип блока) пишутся **до** реализации.
2. `POST /public/v1/forms/{slug}/submissions`: MaxBytesReader 256 КБ → статус формы → антиспам → `ValidateAnswers` против опубликованной версии → INSERT с `form_version_id` → 201. Ошибки — 422 с картой `block_id → сообщение`.
3. Антиспам: honeypot (заполнен → молчаливый 200 без записи) + HMAC-токен времени из фазы 4 (быстрее 3 секунд → отказ). Юниты на оба контура.
4. Идемпотентность: рендерер генерирует `submission_id` (UUIDv7) при первом нажатии «Отправить», ретраи шлют тот же id; конфликт PK на сервере = успех. Тест: двойной POST — одна строка.
5. Жёсткий rate limit по IP на эндпоинт, отдельный от общего.
6. Рендерер: состояние отправки, маппинг 422 на поля, авторетрай при обрыве сети (до 3 раз с бэкоффом), экран «Спасибо», очистка sessionStorage.
7. Сквозной интеграционный тест: создать → опубликовать → валидный ответ → невалидный ответ → проверить содержимое БД. Живая документация продукта.

**Демо в конце фазы.** Заполняете форму в инкогнито → «Спасибо». Без обязательного поля → ошибка у нужного поля. Обрываете сеть на середине отправки (DevTools offline), возвращаете — ответ уходит ровно один раз (видно по `SELECT count(*)`). У ответа в базе — id той версии, что была на экране.

**Definition of Done.** Табличные тесты `ValidateAnswers` покрывают все типы; дубль не создаётся; тело >256 КБ → 413; honeypot-ответы не попадают в БД.

## Фаза 6. Просмотр ответов и экспорт

**Цель.** Замкнуть петлю ценности: автор видит ответы в таблице и уносит их в CSV. После этой фазы MVP функционально полон — всё остальное готовит его к реальным людям.

**Шаги.**

1. `GET /forms/{id}/submissions`: курсорная пагинация по UUIDv7 (новые сверху), общий счётчик, у каждого ответа — его версия формы.
2. CSV-экспорт: стриминг `encoding/csv` в `ResponseWriter` без буферизации всего в память (тест на 10 000 сидированных строк — расширяем `make seed`). Колонки — объединение блоков по всем версиям (вопрос, удалённый в v2, остаётся колонкой для ответов v1); UTF-8 BOM для Excel; choice-ответы — подписями опций, не id.
3. Фронт `forms.$slug.responses`: таблица по вопросам актуальной версии, бесконечная подгрузка `useInfiniteQuery`, клик по строке — панель полного ответа (включая вопросы старых версий), счётчик «N ответов» на карточке в дашборде.
4. «Экспорт CSV» — обычная навигация на эндпоинт (cookie авторизует, браузер качает).
5. Удаление отдельного ответа с подтверждением (GDPR-гигиена).

**Демо в конце фазы.** Отправляете три ответа из инкогнито → они в таблице кабинета новыми сверху → открываете один целиком → «Экспорт CSV» → файл открывается в Excel с читаемой кириллицей и подписями опций. Публикуете v2 с изменённым вопросом, отвечаете — в таблице мирно живут ответы обеих версий.

**Definition of Done.** Экспорт 10 000 строк не растит память (профиль pprof); версии корректны в таблице и CSV; пагинация без дублей и потерь на границах страниц.

## Фаза 6.5. Редактор форм в стиле Tally

**Вставка после фазы 6.** К этому моменту весь конвейер (собрал → опубликовал → собрал ответы → выгрузил) работает end-to-end, и его продемонстрировал временный палитра-канвас-редактор фазы 3. Здесь он заменяется сигнатурным для продукта редактором: единое markdown-подобное полотно, где блоки добавляются slash-командой («/» → меню типов), текст правится инлайн, мышь нужна по минимуму. Это переработка поверхности ввода, а не фундамента — потому и стоит после ценностной петли, а не внутри неё.

**Расширение фазы (решение владельца продукта):** вместе со slash-редактором делается общий визуальный редизайн кабинета в стиле Notion/Tally — сайдбар-навигация вместо шапки, единый вид всех экранов (дашборд, таблица ответов, auth). Для этого в `web/app` снята заморозка зависимостей и подключён UI-слой **Tailwind CSS v4 + shadcn/ui** (см. ADR-сводку и `web/CLAUDE.md`). Инвариант: Tailwind/shadcn — только в кабинете; рендерер (`web/renderer`) остаётся на react+zod под бюджетом 95 КиБ, общие `@fields` не переводятся на Tailwind. Работа ведётся пятью вертикальными срезами: (A) фундамент Tailwind+shadcn и процессные документы; (B) сайдбар-оболочка; (C) рестайл существующих экранов; (D) slash-редактор; (E) уборка временного билдера фазы 3.

**Цель.** Сборка формы ощущается как письмо в редакторе: пишешь заголовок и текст вопроса прямо в полотне, «/» открывает список типов полей, Enter/стрелки/Backspace создают, двигают и сливают блоки как в обычном текстовом редакторе. Автосейв, версии, публикация — уже готовое из фаз 3–4; редактор просто дёргает те же операции стора.

**Что переиспользуется и что переписывается.** Остаются: модель `FormSchema`/`Block`, Zod- и Go-контракт, `ValidateSchema`, zustand-стор с операциями над блоками, автосейв (дебаунс → PATCH → 409), превью и общие компоненты полей `@fields`. Переписывается только поверхность: `Palette`/`Canvas`/`SettingsPanel` уступают место полотну-редактору, а типоспецифичные настройки (опции choice, required) переезжают из отдельной панели в инлайн-контролы у активного блока.

**Шаги (детализируются перед стартом).**

1. ~~Возможное расширение схемы «неотвечаемыми» блоками~~ **Сделано:** добавлен тип `text` — неотвечаемый абзац и дефолт новой строки (Enter/мышь создают его, «/» превращает в поле). Контракт расширен в Go (`internal/domain/schema.go`, `isContent()`) + Zod (`formSchema.ts`, `isContentType`) одним PR; `schemaVersion` не менялся (новое значение enum обратно совместимо). `text` исключён из `ValidateAnswers`, CSV и таблицы ответов, в рендерере — статический абзац. Заголовок секции/разделитель — при необходимости позже тем же паттерном.
2. Полотно: блоки как редактируемые строки; фокус и навигация с клавиатуры (Enter — новый блок, Backspace в пустом — слить/удалить, ↑/↓ — переход), инлайн-правка label/description.
3. Slash-меню: «/» в начале блока открывает фильтруемый список типов; выбор превращает блок в поле нужного типа. Мышиный фолбэк (кнопка «+») для доступности.
4. Инлайн-настройки: опции choice добавляются строками прямо под вопросом; required и типоспецифика — компактным контролом у активного блока.
5. Ввод и доступность: весь путь сборки управляем с клавиатуры; drag-and-drop блоков (dnd-kit) либо переезжает сюда из фазы 8, либо остаётся кнопками — решить на месте.

**Демо в конце фазы.** Форму из 6–7 вопросов собираешь, почти не отрывая рук от клавиатуры: пишешь вопрос → «/» → выбираешь тип → Enter → следующий. Превью и публичная ссылка показывают ровно то же; автосейв и конфликт-баннер работают как раньше.

**Definition of Done.** Клавиатурный путь сборки формы полон (создание, тип через «/», перемещение, удаление — без мыши); формы, созданные в билдере фазы 3, открываются в новом редакторе без потери данных (или через апгрейдер, если менялся `schemaVersion`); автосейв/версии/публикация не затронуты; превью совпадает с полотном.

**Состояние — закрыта (владелец продукта принял фазу).** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 6.5, итог).

## Фаза 7. Prod-local: репетиция прода без сервера

**Цель.** Собрать весь прод-контур у себя на машине. В конце фазы продукт работает под https на трёх `*.localhost`-доменах из настоящих прод-образов — то есть от реального прода его отделяет только наличие сервера. Всё, что здесь написано (Dockerfile, compose, Caddyfile, релизный пайплайн), потом переедет на VPS без изменений.

**Шаги.**

1. Multi-stage Dockerfile для Go: сборка в `golang:1.26` (в тон `go.mod`) → `distroless/static:nonroot`, `CGO_ENABLED=0`, ~25 МБ. Локальная проверка: образ собирается, healthz отвечает из контейнера.
2. `deploy/compose.prod.yml`: caddy + api + postgres; Postgres без порта наружу; healthcheck'и; `restart: unless-stopped`; api стартует после миграций (init-команда `migrate up` тем же образом).
3. `deploy/caddy/Caddyfile`: два сайта `app.localhost` (статика кабинета + `/api/*` в Go same-origin) и `f.localhost` (статика рендерера + `/r/*` и `/public/*` в Go) — Caddy сам выдаёт TLS от внутреннего CA; SPA-fallback, иммутабельный кэш `/assets/*`. Выделенного `api`-домена нет (ADR §10): кабинет и его API — один origin, поэтому CORS не нужен. Доменные имена — параметром окружения, чтобы этот же файл работал на проде с реальными доменами.
4. Прод-сборка фронтов: `vite build` обоих проектов, скрипт раскладки статики в volume Caddy. База API кабинета и публичного API — относительные пути (`/api`, `/public`), same-origin, VITE-переменных для них нет (ADR §10); через `VITE_*` на этапе сборки задаётся только `VITE_PUBLIC_BASE_URL` (ссылка на форму в бандле кабинета). Рендерер собирает entry и CSS со стабильными именами `/renderer.js` и `/renderer.css`, а пути к ним на HTML-странице `/r/{slug}` (её отдаёт Go, а не собранный `index.html`) Go берёт из `PUBLIC_RENDERER_SCRIPT_PATH` (dev `/src/main.tsx`, prod `/renderer.js`) и `PUBLIC_RENDERER_STYLE_PATH` (dev пусто — vite инжектит CSS через JS; prod `/renderer.css`). Оба огреха («голова на сервере» не знала про собранные ассеты) всплыли и закрыты здесь. *(Устарело: в фазе 8, шаг 7 эти пути и стабильные имена сняты по корню — Go строит `/r/{slug}` из собранного `index.html`, `PUBLIC_RENDERER_SCRIPT_PATH`/`STYLE_PATH` удалены, ассеты — дефолтные хеши.)*
5. `make prod-local`: собрать образ и статику, поднять `compose.prod.yml` с `.env.prod-local`, прогнать тонкий smoke; `make prod-local-down` — погасить (тома с данными остаются). Smoke (`scripts/prod-local-smoke.sh`) — проверка живости + того, чего не было в dev: `/healthz` по внутренней compose-сети (api без внешнего порта, distroless без curl); `app.localhost/` и `f.localhost/` → 200 через Caddy; `f.localhost/r/<несуществующий>` → 404 (путь Caddy→Go→Postgres); регистрация по https → `Set-Cookie: …Secure`; мутация без `X-CSRF-Token` → 403. Полное открытие опубликованной формы глазами — это e2e шага 7 и ручная визуальная проверка, не smoke. CORS не проверяем — его нет по устройству (ADR §10). Нюанс, всплывший здесь: `include .env; export` в Makefile + приоритет шелл-переменных над `--env-file` у compose — поэтому `.env.prod-local` источается в тот же рецепт (иначе контейнеры подхватывают dev-DSN). «Настоящий замочек» (демо-критерий) требует доверия к локальному CA Caddy — разово `make prod-local-trust` (sudo; Firefox — свой стор).
6. Релизный пайплайн в GitHub Actions: по git-тегу `v*` — сборка и публикация Go-образа в GHCR + сборка статики фронтов и прикрепление артефактом к GitHub Release. Деплоя нет — но каждый тег с этого момента даёт готовый к развёртыванию комплект.
7. Прогон Playwright e2e (регистрация → билдер → публикация → ответ с мобильного вьюпорта → таблица → CSV) против prod-local контура; добавить job в CI. Сделано двумя срезами: **7a** — пакет `e2e/` с одним сценарием (`@playwright/test`, санкционирован ARCHITECTURE §8), зелёный локально против `make prod-local`; **7b** — workflow `.github/workflows/e2e.yml` (`workflow_dispatch` + nightly `schedule`, не на каждый PR — стек тяжёлый): поднимает prod-local и гоняет e2e. Тест сторожит оба пойманных в фазе регресса (пустая форма без entry-скрипта, форма без стилей). Побочно e2e вскрыл гонку билдера (rename заголовка ↔ автосейв схемы по `updated_at` → 409) — вынесена отдельной задачей, тест её обходит.
8. Заголовки безопасности (CSP, nosniff, frame-options) в Caddyfile; проверить локально curl'ом; убедиться, что секреты не запечены в образ (`docker history`).

**Демо в конце фазы.** `make prod-local` — и через пару минут в браузере `https://app.localhost` (настоящий замочек), полный путь пользователя работает; `https://f.localhost/r/{slug}` открывает форму. В GitHub Releases на теге лежат образ и статика. Playwright-прогон зелёный.

## Фаза 8.5. Продуктовый минимум: от «работает» к «выбрали бы»

**Цель.** Закрыть слой продуктовых дыр между технически работающим конструктором и инструментом, который живой человек предпочтёт привычным аналогам. Итог продуктового аудита кабинета: цикл «создать → опубликовать → собрать ответы» замкнут, но респондент после отправки упирается в фиксированную заглушку, среди типов вопросов нет телефона и выпадающего списка, ответы читаются только по одному в диалоге, форму нельзя ни встроить на сайт, ни закрыть по лимиту мест. Сервера фаза не требует (как и фаза 8) — VPS может появиться в любой момент, фазы 9–10 вклинятся без конфликтов. Порядок шагов — приоритет: фазу можно резать в любом месте, если сигналы пользователей потребуют другого. Самая ценная фича этого слоя — **email владельцу о новом ответе** — сознательно НЕ здесь: ей нужна транзакционная почта, она добавлена шагом в фазу 11 POST-MVP.

   **Состояние — сделано.** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.5, шаг 4).
6. **Визиты: просмотры и конверсия.** На карточке дашборда и странице ответов — «N просмотров → M ответов (K %)». Реализация — не серверный счётчик открытий, а визиты (решение владельца, ADR §10): таблица `form_visits` (строка на визит: форма, версия, `last_block_id` — самая дальняя точка, `submitted`, `meta` с user_agent/referer/UTM, **без IP**), публичная ручка `POST /public/v1/forms/{slug}/visits` и два бикона из рендерера (`navigator.sendBeacon` умеет только POST): на монтировании — «открыли», на `pagehide`/`visibilitychange→hidden` — «дошёл до блока». Апсерт по клиентскому UUIDv7 — тот же приём идемпотентности, что у отправки (ARCHITECTURE §4.7). Доступ — тем же HMAC-токеном формы, что уже выдаётся при `GET /public/v1/forms/{slug}`; своё, четвёртое ведро rate-limit по образцу `submit` (обобщённая обёртка `rateLimit(limiter, msg)`, `ClientIP` и GC уже есть). `submitted` ставит сервер при приёме ответа: тело `POST …/submissions` получает **необязательный** `visitId` (визита нет → ответ принимается как сейчас) — отсюда точная конверсия вместо деления двух независимых чисел.

   **Почему бикон, а не серверный счётчик.** Серверный счёт занижен кэшем (`max-age=60`, `ETag`/304) и считает краулеров вместо людей, а главное — принципиально не может сказать, докуда дошёл ушедший, то есть не годится фундаментом под воронку (шаг 6б). Бикон снимает и проблему кэша.

   **Осознанные границы (записать, а не лечить).** Накрутка просмотров возможна: ручка публичная на запись, а HMAC-токен реиграбелен внутри 24 ч (TECH-DEBT §5) — ущерб ограничен неверным числом на своём же дашборде, не данными; backstop — rate-limit и honeypot, как у отправки. Потерянный бикон `pagehide` даёт визит с `last_block_id = NULL`, то есть слегка завышенный «отскок» (`visibilitychange` уменьшает, но не до нуля). Роллапа нет: строка на визит при нашем масштабе не растёт опасно — пересмотреть, когда станет. Cookie и localStorage не заводим: `visitId` живёт в памяти страницы, человек между визитами не узнаётся.

   **Визиты пишутся для всех, без оглядки на будущие тарифы.** Когда придёт биллинг (POST-MVP фаза 13), платным станет **показ** воронки и источников, а не сбор: не собирая с бесплатных, в момент апселла нечего показать — плашка рекламирует пустоту, вместо того чтобы показать владельцу его настоящее число. Здесь из этого следует одно: проверок плана в этом шаге нет и не закладывается заглушек под них (YAGNI) — точка проверки появится на чтении. **Сбылось:** гейт `analytics_funnel` реализован фазой 17 этого плана (402 `plan_required` на чтении воронки), код сбора визитов про тарифы по-прежнему не знает.

   **Состояние — сделано.** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.5, шаг 6).
6б. **Воронка: на каком вопросе уходят.** На странице ответов — распределение визитов по `last_block_id` с человеческими подписями из схемы версии («66 дошли до „ИНН", 51 из них дальше не пошёл»). Данные к этому моменту уже лежат, работа рисовальная (CSS-бары, как в сводке шага 3). Сегодня, пока форма — одна длинная страница, сигнал косвенный: касание поля, а не переход на страницу; проскроллившего и передумавшего не видно — записать как погрешность. С приходом многостраничных форм тот же столбец начнёт заполняться из перехода на страницу — точнее, без миграции.

   **Состояние — сделано.** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.5, шаг 6б).
7. **Шаблоны форм.** 5–10 заготовленных `draft_schema` («запись на консультацию», «обратная связь», «регистрация на событие», «анкета кандидата», …) в диалоге создания формы: путь новичка до первой опубликованной формы — минута. Технически — статические JSON на фронте; тест прогоняет каждый через `ValidateSchema` (шаблон, разошедшийся со схемой, ловит CI, а не пользователь).

QR генерируется на клиенте: зависимость или ~200 строк своей реализации — через штатный вопрос о зависимостях. Для iframe проверить заголовки публичного домена в Caddyfile: CSP/`X-Frame-Options` сейчас, скорее всего, запрещают встраивание — ослаблять точечно только для `/r/*` (`frame-ancestors`), проверять на prod-local.

**Демо в конце фазы.** Сценарий «регистрация на мероприятие» за пять минут: новая форма → собраны имя, телефон и шкала «откуда узнали» → лимит 100 ответов, свой текст «спасибо» с редиректом на сайт → опубликована → открыта по ссылке с телефона → после пары ответов в кабинете: ответы видны колонками, в сводке — распределение по шкале, на карточке — «просмотры → ответы».

**Definition of Done.** Каждый новый тип проходит полный цикл (билдер → публикация → ответ → таблица → сводка → CSV) с тестами обеих сторон контракта; redirect не принимает не-`http(s)` схемы (тест на `javascript:`); лимит ответов не теряет данные и не пускает лишнего сверх зафиксированного допуска (тест гонки); сводка агрегируется сервером; ручка визитов живёт под своим rate-limit и требует токен формы, рендерер не заводит ни одной cookie, конверсия считается по `visitId` (не делением двух счётчиков); бюджет рендерера (95 КиБ gzip) не превышен; e2e-сценарий дополнен новыми точками.

**DoD: последний пункт закрыт (e2e).** Остальные пункты закрывались по ходу шагов; «e2e дополнен новыми точками» оставался наполовину — `visits-funnel` появился в шаге 6б, но новые типы вопросов, свой текст благодарности и лимит мест не проверялись в браузере ничем. Добито двумя правками: (1) в `full-loop` собираемая форма получила **шкалу и согласие** — они проходят тот же полный цикл, что требует первая строка DoD, и это единственное место, где проверяется, что их контролы вообще отрисовываются в прод-сборке (ряд кнопок и галочка берут вид из общего `fields.css`); (2) новый спек **`form-settings`** — свой текст благодарности доезжает через снапшот версии до экрана рендерера, а лимит в одно место закрывает форму сам, и второй респондент видит «приём закрыт» с текстом владельца.

**Почему `form-settings` отдельным файлом, а не строками в `full-loop`:** ему нужен ВТОРОЙ респондент (первый занимает единственное место), то есть ещё контекст и ещё отправка; пришитое к сборке формы кликами, это дало бы тест, который краснеет от правок билдера, ничего не говоря про настройки. Та же причина, по которой отдельным сделан `visits-funnel`. Отсюда правило, записанное в `e2e/README.md`: через билдер кликами ходит только `full-loop`, остальные строят форму запросами к API.

**Проверено не зелёным прогоном, а мутациями** (зелёный тест сам по себе не доказывает, что проверка на что-то реагирует). Три мутации, каждая краснеет ровно на своей проверке: убрать `thankYouText` из схемы → падает проверка текста благодарности; `responseLimit: null` → второй респондент видит форму вместо «приём закрыт»; убрать клик по делению шкалы → `aria-pressed` остаётся `false`. Последняя попутно показала, что контрол шкалы в прод-сборке реален (`<button aria-pressed="false" class="rf-scale-mark">4</button>`).

**Найдено попутно (записано, не заметено): сюита упёрлась в потолок rate-limit регистрации.** Каждый сценарий регистрирует свой аккаунт, а `registerBurst = 3` при пополнении ~1/30 с (`cmd/api/main.go`) — три спека расходуют бурст ровно в ноль. Холодный прогон проходит, но **повторный запуск в течение ~1,5 минут падает на шаге регистрации**, выглядя как сломавшийся тест (именно так и выглядел первый прогон мутации, пока причина не нашлась). Лимит ради тестов не ослабляется (инвариант 6) — ограничение записано в `e2e/README.md` вместе с выводом: четвёртый сценарий с регистрацией сделает сюиту красной сам по себе, и ему нужен другой способ заводить сессию.

**Состояние — закрыта (владелец продукта принял фазу).** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.5, итог).

## Фаза 8.7. Вопрос как группа блоков

**Вставка после фазы 8.5, до фазы 9.** Продуктовое решение владельца: перенять модель Tally, где вопрос — не один блок, а **группа самостоятельных блоков** (подпись + поле + контент между ними). Это добавление скоупа сверх исходного MVP (прецеденты — картинки автора §1 ARCHITECTURE и аналитика визитов) и дизайн-решение, зафиксированное в ADR-сводке (§10) и §3.4 ARCHITECTURE. Стоит **до** деплоя: меняет контракт схемы и требует апгрейдера версий — дешевле закрыть до реального прода, чем мигрировать живые формы.

**Цель.** Автор собирает вопрос из отдельных блоков: `title`/`label` (крупная/мелкая подпись), поле ввода и любой контент (`heading`/`text`/`image`) **между** подписью и полем. Заголовок и поле — отдельные пункты меню «/»; поле без подписи допустимо (форма может быть из одних полей, подпись в аналитике генерится). Перетаскивание не переклеивает подпись — привязка по группе (`groupId`), а не по позиции. Аналитика (CSV, сводка, воронка) остаётся честной: id отвечаемого блока — прежний ключ ответа и шаг воронки.

**Что переиспользуется и что переписывается.** Остаются: хранение схемы в JSONB, автосейв/версии/публикация, приём ответов, `internal/visits`, единая точка `QuestionOrder`. Переписываются: Go- и Zod-контракт блока (`groupId`, типы `title`/`label`/`heading`, снят `description`), `ValidateSchema` + предикаты (`isCaption`, расширенный `isContent`), апгрейдер `schemaVersion 1→2`, редактор (группы, «/»-пункты Title/Label, подсказки «добавить заголовок/поле», ведение `groupId` при добавлении/переносе/удалении), рендерер и `@fields` (рендер группы: подпись → контент → поле), `QuestionOrder` (подпись из группы + генерация имени).

**Шаги (детализируются перед стартом — план вертикального среза приносится на согласование).**

1. Контракт схемы v2 синхронно Go+Zod: `groupId`, типы `title`/`label`/`heading`, снятие `description`; предикаты `isCaption`/`isContent`; `ValidateSchema` (смежность блоков группы, ≤1 отвечаемого блока в группе). Тесты обеих сторон.
2. Апгрейдер `schemaVersion 1→2` (юниты, §8 ARCHITECTURE): старый блок `{label, description}` → группа `title(label) + text(description) + input` с сохранением id инпута; применяется на чтении к черновикам и опубликованным версиям.
3. `QuestionOrder`: подпись из `title`/`label` группы, генерация имени при отсутствии (плейсхолдер → тип+номер). CSV/сводка/воронка через неё — без правок логики.
4. Рендерер и `@fields`: рендер вопроса-группы (подпись → контент → контрол), новые контентные типы. Проверить бюджет 95 КиБ.
5. Редактор: группы на полотне, «/»-пункты Title/Label/Heading, подсказки «добавить заголовок/поле», ведение `groupId` при create/move/delete/slash; dnd на уровне блоков и групп.
6. Производные доки в том же PR: `SCHEMA.md`, `ANALYTICS.md` §4, `web/shared/fields/README.md`.

**Демо в конце фазы.** Собираешь вопрос: пишешь заголовок (`title`), вставляешь между ним и полем картинку-пример, добавляешь поле — всё отдельными блоками. Рядом — регистрационный блок из нескольких полей без заголовков, подписи которых в CSV/сводке сгенерированы из плейсхолдеров. Формы, созданные до фазы, открываются без потери данных (апгрейдер v1→v2), ответы и воронка по ним считаются как раньше. Перетаскивание блоков не путает подписи в аналитике.

**Definition of Done.** Контракт v2 синхронен Go/Zod с тестами обеих сторон; апгрейдер v1→v2 сохраняет id отвечаемых блоков и покрыт юнитами на трёх сценариях (пустая схема, форма без вопросов, форма с `description`); `QuestionOrder` даёт подпись из группы и осмысленную генерацию, CSV/сводка/воронка зелены на старых и новых формах; редактор ведёт группы без осиротевших подписей; бюджет рендерера 95 КиБ держится; производные доки обновлены в том же PR. Аналитический инвариант: ни одна колонка/шаг не теряет и не путает подпись при перетаскивании.

**Состояние — сделано (мелкая полировка отложена в TD-26).** Разбор, решения и найденное по ходу — [JOURNAL.md](JOURNAL.md) (фаза 8.7, итог).

## Фаза 11. Вход через Яндекс ID

**Цель.** Закрыть главный пробел MVP для живых пользователей — потерянный доступ — устранением причины, а не симптома: у человека, вошедшего через провайдера, пароля нет вовсе, забывать нечего, а email приходит уже подтверждённым. Побочная выгода — регистрация в один клик вместо придумывания пароля. Исходная редакция фазы в [`POST-MVP.md`](POST-MVP.md) лечила тот же пробел сбросом пароля по почте; **почтовая часть целиком переехала в следующую фазу** (провайдер, outbox, уведомление о новом ответе, сброс пароля, подтверждение email) — решение владельца, обсуждение 2026-07-22. Вход по паролю остаётся равноправным способом.

**Провайдер один — Яндекс ID; VK ID отложен** (решение владельца, 2026-07-22): фаза обкатывает механику, второй провайдер ложится в готовый каркас отдельным заходом. Практическое следствие — из объёма уходит добор почты: он был нужен только VK-аккаунтам, заведённым на телефон, а Яндекс отдаёт адрес всегда. Сверка VK (шаг 1) сохранена: она уже оплачена и понадобится, когда до него дойдут руки.

**Шаги.**

1. Сверка актуальной документации Яндекс ID и VK ID: эндпоинты, scope, отдаётся ли email и есть ли признак его подтверждения, обязателен ли PKCE. Регистрация приложений и redirect URI — действие владельца; отдельно проверить, принимается ли `localhost` для dev-контура.

   **Сверено 2026-07-22.** Яндекс: `oauth.yandex.ru/authorize` → `oauth.yandex.ru/token` → `login.yandex.ru/info` (`Authorization: OAuth <token>`); PKCE поддержан, при нём секрет не обязателен; `state` до 1024 символов; email в `default_email`/`emails`. VK ID: `id.vk.ru/authorize` → `id.vk.ru/oauth2/auth` → `id.vk.ru/oauth2/user_info`; **PKCE обязателен**, `state` не короче 32 символов, обмен кода требует `device_id` из ответа авторизации; email — только при выданном scope и согласии. **Признака подтверждения email не даёт ни один из двух**; поле `verified` у VK означает верифицированный профиль (галочка публичной персоны), а не почту — принять его за подтверждение адреса нельзя, это и есть исторический источник угонов этого класса. Отсюда правило связывания в шаге 4.
2. Миграция `0009`: таблица `user_identities` (`provider`, `provider_user_id`, `user_id` → `users` `ON DELETE CASCADE`, PK по паре провайдер+идентификатор) и `users.password_hash` → nullable. Отдельная таблица, а не колонки в `users`, — чтобы к одному аккаунту привязывались оба провайдера. `users.email` остаётся уникальным: аккаунт на адрес один, способов входа в него несколько.
3. Модуль `internal/oauth`: тип `Profile` и реализация Яндекса на stdlib. Маршруты параметризованы провайдером (`{provider}`), реестр — map с одной записью: это не абстракция впрок, а форма, в которую VK кладётся без переделки маршрутов и БД (он записан шагом плана, см. врезку к фазе). Чек-лист безопасности, каждый пункт с тестом: `state` в HttpOnly-cookie и сверка при возврате, PKCE S256, точное совпадение `redirect_uri`, таймаут HTTP-клиента, `io.LimitReader` на ответ провайдера, ни токен ни email не в логах. Две **опциональные** env-переменные: без ключей провайдер выключен.
4. Правила входа в `internal/auth` (таблица случаев = таблица тестов): identity найдена → вход в её аккаунт; identity нет и пользователя с таким email нет → создание пользователя без пароля вместе с личным воркспейсом в одной транзакции; **identity нет, но аккаунт с таким email есть → сессия не выдаётся**, человек попадает на экран «У вас уже есть аккаунт с этим адресом — войдите паролем один раз, и мы привяжем провайдера»; после успешного входа паролем создаётся `user_identities`, дальше вход в один клик. Автосвязывания нет ни при каких условиях — ADR §10: провайдеры не ручаются за принадлежность адреса.

   Незавершённое состояние там, где нужен второй шаг (привязка паролем), живёт в подписанной короткоживущей cookie по образцу HMAC из `internal/token` — без новой таблицы. Привязка и отвязка провайдера из настроек аккаунта — за рамками фазы.
5. Эндпоинты: `GET /auth/providers` (чтобы фронт не рисовал мёртвых кнопок), `GET /auth/oauth/{provider}/start`, `GET /auth/oauth/{provider}/callback`, `POST /auth/oauth/link` (пароль → привязка провайдера к существующему аккаунту). `/link` принимает пароль, поэтому живёт под тем же ведром rate-limit, что и `/login`, и обязан отвечать за постоянное время (`equalizeTiming`, `internal/auth/service.go`). Отдельное ведро — на `/callback`, с добавлением в задачу `ratelimit-gc`.
6. Фронт кабинета: кнопка «Войти через Яндекс» на экранах входа и регистрации — обычной ссылкой, а не `fetch` (нужен полноценный редирект браузера); маршрут «войдите паролем, чтобы привязать провайдера».
7. Прогон на проде, тег `v0.11.0`.

**Состояние — закрыта (шаги 1–7), тег `v0.11.1`.** Вход через Яндекс живёт на проде, подтверждён владельцем. Сверка провайдеров (шаг 1) **сломала посылку принятого решения**: признака подтверждения email не даёт ни Яндекс, ни VK, поэтому автосвязывание заменено на привязку через разовый ввод пароля (ADR §10). Ревью нашло три дефекта (гашение cookie через `defer`, JSON-500 вместо редиректа при сбое провайдера, непроходимый экран привязки) — все починены в той же ветке. Первая выкатка `v0.11.0` уехала на прод сломанной (переменные не доезжали до контейнера — якорь `x-app-env` перечисляет их поимённо); починка `v0.11.1` + новая проверка в `check-docs`, сторожащая этот класс. Фаза завела **TD-34**; VK ID отложен в [`BACKLOG.md`](BACKLOG.md). Разбор — [`JOURNAL.md`](JOURNAL.md) «Фаза 11».

**Демо в конце фазы.** На `app.trillix.ru/login` — кнопка «Войти через Яндекс». Нажатие у нового человека: экран согласия → возврат в кабинет залогиненным, в `user_identities` ровно одна строка, `password_hash` у него `NULL`. Повторный вход тем же способом не создаёт второго пользователя. Существующий парольный аккаунт продолжает входить паролем; вход через Яндекс с тем же адресом просит один раз ввести пароль и после этого приводит в тот же аккаунт — с его формами, а не в пустой дубль, и не отдаёт его тому, кто пароля не знает.

**Definition of Done.** Возврат на `/callback` с подменённым или отсутствующим `state` → 400 без выдачи сессии (тест); вход через провайдера при совпадении email не выдаёт сессию до успешного ввода пароля (тест — это и есть защита от захвата чужого аккаунта); интеграционный тест полного колбэка против фейкового провайдера зелёный; миграция проходит up/down/up на чистой базе; ни один токен провайдера не попадает в БД и логи.

## Фаза 12. Транзакционная почта и восстановление пароля

> Развёрнута из [`POST-MVP.md`](POST-MVP.md) (там названа «Фаза 11» — номер сдвинут вставкой фазы «Вход через Яндекс ID»; здесь она двенадцатая). Полное описание, цель, демо и DoD — там; здесь — детализация до вертикальных слайсов и рабочее состояние. Порядок фаз почта→юридика→деньги жёсткий: биллинг без почты невозможен.

**Цель** (цитата POST-MVP). Закрыть механизм отправки писем: сброс пароля («забыл пароль» сейчас не решается никак), подтверждение email при регистрации, уведомление владельцу о новом ответе. Заодно закрывается **TD-34** (аккаунт-без-пароля становится достижим через сброс). Почта понадобится и биллингу, и командам.

**Рамка outbox (согласована с владельцем 2026-07-22, ADR §10).** Общий транзакционный outbox — **узкий транспорт доставки наружу**, а не шина событий: строка = намерение доставки (`channel`+`payload`), диспетчер — тупой релей, внутренние реакции через него не ходят. Один транспорт (почта) сейчас; вебхуки (фаза 15) и телега — новыми значениями `channel` без переделки схемы.

**Шаги — вертикальными слайсами** (коммит после каждого; слайсы A–D пишутся и тестируются на dev-транспорте `log`, реальный провайдер и DNS нужны только к прод-демо в E):

- **A. Каркас почты.** Миграция `0010_outbox` (одна таблица, `channel`+`payload`+ретраи); модуль `internal/mail` (интерфейс `Mailer`, dev-`LogMailer`, `Service` с `EnqueueEmail`/`Dispatch` и бэкоффом); диспетчер как `periodic`-задача `outbox-dispatch`; config `MAIL_TRANSPORT`/`MAIL_FROM`; ADR-строка. Продюсеров ещё нет — проверяется прямым enqueue в тесте.
- **B. Сброс пароля** (ядро демо). Миграция `password_reset_tokens` (SHA-256, TTL 30 мин, одноразовый); `POST /auth/forgot-password` (всегда 200, rate-limit по IP и email, постоянное время — не раскрываем существование аккаунта) и `POST /auth/reset-password` (токен → новый пароль + инвалидация всех сессий); шаблон письма (первый потребитель `EnqueueEmail`); фронт-экраны «Забыли пароль?» / «Проверьте почту» / «Новый пароль».
- **C. Подтверждение email.** Мягкое: аккаунт работает сразу, неподтверждённый email помечен баннером в кабинете; письмо-подтверждение при регистрации.
- **D. Уведомление владельцу о новом ответе.** Первый продуктовый потребитель outbox: в транзакции приёма ответа пишется письмо владельцу со ссылкой в таблицу; тумблер на форме (для новых — вкл); **троттлинг-дайджест** «N ответов» не чаще раза в N минут (вирусная форма не засыпает владельца) — добавит ключ коалесинга в `outbox`.
- **E. Прод-обвязка** (инфраструктура владельца). Выбор провайдера — **Yandex Cloud Postbox** (та же экосистема, что Яндекс ID и бэкапы; доставляемость в Яндекс.Почту; рублёвая оплата; ADR §10). Реализация `Mailer` — один **SMTP**-клиент на stdlib `net/smtp` (не HTTP: SES-совместимый API Postbox потребовал бы SigV4/SDK, а зависимости заморожены); тот же транспорт бьёт в Postbox (прод) и Mailpit (prod-local). DNS SPF/DKIM/DMARC, Mailpit в prod-local, прогон mail-tester 9+/10.

**Состояние — в работе. Слайсы A, B, C, D закрыты кодом** (A: миграция 0010, `internal/mail`, диспетчер, config, ADR; B: сброс пароля, миграция 0011, экраны кабинета; C: подтверждение email, миграция 0012, баннер и `/verify-email`; D: уведомление владельцу о новом ответе, миграция 0013, коалесцирующий дайджест, тумблер в настройках формы). Юнит + интеграционные тесты зелёные (в т.ч. троттлинг: M ответов → одна строка outbox с `count=M`). **Решение по OAuth (слайс C):** вход через провайдера считается подтверждением email — аккаунт без пароля заведён через Яндекс, а чтобы завести аккаунт у провайдера, надо владеть его почтой; баннер и письмо подтверждения остаются только парольным регистрациям (адрес вводят руками). Флаг `email_verified` в текущей системе не гейтит ничего, кроме баннера, поэтому решение без последствий для безопасности и не противоречит запрету автосвязывания по email (ADR §10). **Слайс E — код закрыт, ждёт инфраструктуры владельца.** Реализованы: `SMTPMailer` (stdlib `net/smtp`, три режима TLS, MIME-кодирование темы, base64-тело), ветка `smtp` в конфиге и composition root, Mailpit в prod-local, раннбук Postbox в `deploy/README.md`. Проверено локально: prod-local поднят на SMTP-транспорте, регистрация → письмо подтверждения доставлено в Mailpit (тема-кириллица раскодирована, ссылка в теле цела). Остаётся **владельцу** (аккаунт/DNS, я не могу): завести Postbox, подтвердить домен (DKIM/SPF/DMARC), создать ключ, положить `MAIL_SMTP_*` в серверный `.env`; финальный DoD — mail-tester ≥9/10 с прода. Побочно починен латентный дефект: `MAIL_FROM` в `.env.prod-local` без кавычек ронял `. ./.env.prod-local` в `make prod-local`.

**Демо в конце фазы** (цитата POST-MVP). «Забыли пароль» → письмо во «Входящие» (не спам) за секунды → форма нового пароля → старые сессии разлогинены, новый пароль работает; повторная ссылка — «токен использован». Отправка ответа приносит владельцу письмо со ссылкой в таблицу ответов.

**Definition of Done** (цитата POST-MVP). Письма проходят mail-tester 9+/10; несуществующий email неотличим по ответу и времени; отправка асинхронна и переживает недоступность провайдера (ретраи в логах); интеграционные тесты полного цикла сброса зелёные; шквал ответов не даёт шквала писем (троттлинг покрыт тестом).

## Фаза 14. Богатый текст в блоках

> Выросла из верхнего пункта [`BACKLOG.md`](BACKLOG.md), сессия с владельцем 2026-07-26

**Цель.** Автор оформляет текст внутри любого текстового блока полотна: жирность, курсив,
подчёркивание, зачёркивание, цвет текста, цвет фона, ссылка. Список марок открыт — следующая
стоит три строки. Респондент видит ровно то же оформление; в данные (CSV, сводка, воронка,
`og:description`) разметка не протекает никогда.

**Сквозной демо-критерий фазы** (согласован с владельцем 2026-07-26):

> Автор выделяет часть текста в любом текстовом блоке и применяет к выделению семь марок —
> панелью над выделением и шорткатами; результат виден в самой строке, а не только в превью.

> сводки, шагах воронки и `og:description` этот текст приходит **без разметки, одной
> строкой**. Форма, собранная до фазы, открывается как раньше. `Mod+Z` откатывает
> форматирование тем же стеком, что и остальные правки. E2e `builder-keyboard` зелёный.

**Скоуп** (решения владельца): блоки `title`, `label`, `heading`, `text`, `consent`; варианты
выбора, экран «Спасибо» и текст кнопки — **вне фазы**; цвет свободный, не палитра токенов.

**Шесть этапов:** 14.0 проба «свой contenteditable или Tiptap» · 14.1 формат и апгрейд ·
14.2 вывод в рендерер и превью · 14.3 поверхность строки · 14.4 панель и шорткаты ·
14.5 финализация.

**Состояние — закрыта, тег `v0.14.0`** (влита #90). Формат хранения — `schemaVersion: 3`,
плоские спаны (Go + Zod зеркально), апгрейд на чтении цепочкой v1→v2→v3, **миграции БД нет**;
наружу схема уходит каноном (`CanonicalV3`). Проба 14.0 подтвердилась: строка полотна — **свой

3. `GET /forms/{id}/funnel` отдаёт 402 `plan_required`, вместо воронки — заглушка с настоящим
   числом не дошедших;
4. `UPDATE subscriptions SET plan_code = 'pro'` → **без перелогина и без деплоя**: таблица
   показывает 6 ответов, воронка открывается, плашка исчезает.

**Решения владельца 2026-08-01** (ADR §10 [`ARCHITECTURE.md`](ARCHITECTURE.md)): Free — **100**
ответов/мес; период — **календарный месяц** по Europe/Moscow; экспорт CSV **скрывает**
сверхлимитные наравне с таблицей; гейт числа воркспейсов — ключ данными, `CheckAccount` не
пишется, создание воркспейса отложено; в списке Pro — только работающие возможности.

**Состояние — закрыта, тег `v0.17.0`** (влита #92). Миграция `0014` (`plans`, `subscriptions`,
`workspace_usage`, `submissions.over_quota`) плюс `0015` (индекс счётчиков кабинета);
`internal/entitlements` — **единственная точка «можно ли»**: ключи гейтов в коде, значения на
план в `plans.limits`, `if plan ==` вне пакета запрещён и сторожится шестой проверкой
`check-docs`. Мягкая квота в приёме ответа: ответ сохраняется **всегда**, сверхлимитный
помечается и скрывается только в кабинете, инкремент расхода едет тем же SQL-утверждением, что
вставка. Гейт воронки — 402 `plan_required` при собираемых для всех визитах.

**Гейты приехали ВЫКЛЮЧЕННЫМИ:** миграция сидирует все три плана безлимитными, все
существующие воркспейсы → `legacy_free`. Включение — отдельный `UPDATE` (готовый текст
комментарием в `migrations/0014_billing.up.sql`), он же аварийный тумблер обратно.
Фаза завела **TD-49**. **Открытое расхождение спеки с реализацией** (§1 критерий 4 против §6,
открытие скрытых ответов) — требует решения владельца, см. [`STATUS.md`](STATUS.md).
**Разбор — [`JOURNAL.md`](JOURNAL.md), раздел «Фаза 17».**

## Правила ведения работ

Ветка на шаг или связку из 2–3 шагов, PR с зелёным CI, squash-merge в `main` (который защищён дисциплиной, а не GitHub'ом — branch protection недоступна на текущем плане, подробности в `PROCESS.md` §5).

**С фазы 15 работы фазы собираются на общей ветке фазы** (решение владельца 2026-07-28): ветка
на этап → squash-merge в ветку фазы (`phase15/canvas-freedom`) → squash-merge ветки фазы в
`main` в конце фазы. Прежний порядок (этап уезжает в `main` сразу) остаётся для работ вне фаз —
задач из очереди, техдолга, дефектов прода. Конец каждой фазы — git-тег: до фазы 7 тег просто фиксирует веху, с фазы 7 он ещё и собирает релизные артефакты в GHCR, с фазы 9 — деплоит. Шаг, разросшийся больше чем на день, режется на два — это сигнал недодекомпозиции. Отступления от архитектуры фиксируются в ADR-таблице архитектурного документа, а не остаются устной легендой.

## Фаза 18. Командные пространства

**Развёрнута из фазы 14 [`POST-MVP.md`](POST-MVP.md)** (нумерации разошлись — см. «Как читать план»).

**Цель.** Собрать урожай с решения, заложенного в первой миграции: `workspaces`/`workspace_members` были там с самого начала, и все проверки прав уже шли через членство. Фаза достраивает продукт поверх готового фундамента — и попутно чинит модель подписки, которая на нескольких пространствах давала нелепицу «купил Pro, а созданное пространство на Free».

**Слайсы.**

Переезд сделан ОДНОЙ миграцией вопреки правилу двух релизов — решение владельца 2026-08-02: пользователей у продукта ещё нет, страховать некого; исключение и условие его отмены записаны в `migrations/CLAUDE.md`. **Состояние — закрыт.**
2. **B. Пространства становятся явными.** `POST /workspaces`, `CheckAccount` и счётчик пространств, `workspaceId` параметром в списке и создании формы (отсутствие = личное), пункт «Пространства» в сайдбаре, текущее пространство в адресной строке. **Состояние — закрыт**, проверен в браузере.
3. **C. Права по действию.** `domain.Action`, матрица «роль × действие», `Can`/`AllowedActions`, сторож `role == …` в `check-docs`, анти-IDOR-тесты под роли. `forms` перестал проверять членство сам. **Состояние — закрыт.**
4. **D. Приглашения** (`0017`). Токен по образцу сброса пароля, письмо одной транзакцией, просмотр без сессии, приём с проверкой адреса, лимит мест. **Состояние — закрыт.**
5. **E. Участники.** Состав, снятие доступа, выход, сторож последнего владельца в SQL; страница участников и экран приглашения. **Состояние — закрыт**, приглашение проверено в браузере.

**Демо в конце фазы.** Приглашаете коллегу по email → он принимает, видит формы пространства и правит их, но страница тарифа ему недоступна → вы отзываете доступ, формы у него исчезают. Отдельно: тариф владельца упал — командное пространство закрылось для всех, личное осталось, опубликованная форма продолжает принимать ответы.

**Definition of Done.** Матрица прав покрыта построчно; анти-IDOR-тесты обновлены под роли (не только «чужой не может», но и «editor не может»); нельзя остаться без владельца; приглашения одноразовы и истекают; `make lint` и `make test` зелёные; e2e-сценарий `workspace-team` добавлен и прогнан.

**Состояние — фаза закрыта**, PR #95, тег `v0.18.0`. Разбор по слайсам — [`JOURNAL.md`](JOURNAL.md). Открытым остался один пункт DoD: сквозной сценарий целиком глазами не пройден (отзыв доступа и обе заморозки проверены тестами и e2e).

## Фаза 19. Многостраничные формы

> Источник — **запрос владельца** (`PROCESS.md` §1.0), сессия 2026-08-05: работы нет ни в
> [`POST-MVP.md`](POST-MVP.md), ни в очереди, поэтому критерий приёмки сформулирован здесь и
> согласуется до кода. Замысел, отвергнутые альтернативы и цена принятых решений —
> [`design/multipage.md`](design/multipage.md). **Номер 19 занят в обоих документах разным:**
> там это шаблоны форм (см. «Как читать план»).

**Цель.** Длинная анкета перестаёт отпугивать стеной вопросов: автор режет её разрывами
страниц, респондент идёт по шагам. Второй результат — не косметический: воронка перестаёт
быть косвенной. Сегодня «дошёл» означает «коснулся поля», проскроллившего и передумавшего не
видно; с переходами между страницами тот же столбец `form_visits.last_block_id` начинает
заполняться точнее — **без миграции и без новых полей**, как и было обещано ADR §10 и
[`SCHEMA.md`](SCHEMA.md) в момент, когда воронку строили.

**Решения владельца 2026-08-05** (в ADR §10 [`ARCHITECTURE.md`](ARCHITECTURE.md) вносятся
**вместе с кодом** соответствующего шага, а не сейчас — прецедент outbox'а, `POST-MVP.md`
фаза 11): разбиение **ручным разрывом**, а не режимом «один вопрос — одна страница»; прогресс
**«Шаг 2 из 4» плюс полоска, всегда**, «Назад» свободен, оглавления со скачком нет; хром
страницы (обложка, логотип, `h1`) — **только на первой**. Цена последнего решения и условие
его пересмотра записаны в спеке §2.3.

**Шаги.**

1. **Контракт: тип `page_break` в обе стороны + разрыв на полотне.** Файл типа во фронтовом
   реестре (семья `content`, без текста, `canShareRow: false`, без настроек), зеркало в
   `internal/domain/schema.go` (список типов и три предиката), паритет-тест. Общий хелпер
   разбиения `splitPages` рядом с `groupBlocks` в `@fields/groups` — один источник для трёх
   поверхностей. `schemaVersion` **не поднимается**, апгрейдера нет. Демо: форма с разрывом
   сохраняется и читается, CSV, сводка и модель вопросов её не замечают (тест).

   **Состояние — закрыт** (включил простую строку на полотне и пункт меню: контентный тип
   без них в реестрах невыразим). Разбор — [`JOURNAL.md`](JOURNAL.md), «Фаза 19».
2. **Страница как понятие в редакторе.** Метка «Страница N» на разделителе, считанная тем
   же разбиением, что режет форму респонденту; перенос границы обычным переносом группы.
   Демо: автор двигает разрыв — вопросы под ним меняют страницу, undo возвращает.

   **Состояние — закрыт**; обещанная уборка инертных разрывов отменена (разрыв — содержимое
   автора, а не выводимая метаданная). Разбор — [`JOURNAL.md`](JOURNAL.md).
3. **Рендерер: страницы у респондента.** Показ по одной, «Далее»/«Назад», прогресс, отправка
   только на последней; валидация текущей страницы на «Далее» и всей формы на «Отправить» с
   перебросом на страницу первой ошибки; хром на первой; прокрутка вверх, фокус на первое
   поле, `aria-live` о смене шага; номер страницы в `sessionStorage` рядом с ответами;
   `pushState`/`popstate` под системную кнопку «Назад». Бэкенд не трогается. Демо: форма из
   трёх страниц заполняется и отправляется по публичной ссылке, ответ виден в кабинете.
4. **Билдер видит то же, что респондент.** Превью листает страницы теми же кнопками и с тем
   же хромом. Демо: превью формы из четырёх страниц совпадает с публичной постранично.

   **Состояние — закрыт**; список страниц в шапке отменён как YAGNI (разделители уже
   подписаны номерами). Разбор — [`JOURNAL.md`](JOURNAL.md).
5. **Аналитика: бикон на переходе.** Переход на страницу шлёт визит с `last_block_id` первого
   отвечаемого блока новой страницы; внутри страницы работает прежнее «касание поля», сервер
   по-прежнему берёт максимум по `seq`. Правок в Go и SQL нет. Демо (**только prod-local** —
   бикон подчиняется CSP): визит, ушедший на третьей странице, стоит в воронке на её первом
   вопросе.
6. **e2e и замер.** Шестой сценарий `multipage` против prod-local; прогон `npm run perf` до и
   после шага 2 с коммитом результатов — разрывы добавляют droppable'ов, а старт драга и так
   стоит ~126 мс на **TD-55**. **Состояние — сценарий написан, ПРОГОН И ЗАМЕР ОТКРЫТЫ**
   (владелец забрал живую проверку себе, 2026-08-05).

**Демо в конце фазы.** В билдере ставите два разрыва → по публичной ссылке форма открывается
первой страницей с обложкой и «Шаг 1 из 3» → «Далее» не пускает, пока не заполнено
обязательное поле **этой** страницы, и молчит про поля следующих → «Назад» возвращает ответы
нетронутыми, системная кнопка «Назад» на телефоне делает то же → отправка с последней
страницы даёт в таблице и CSV ответ, неотличимый от ответа на одностраничную форму → в
воронке визит, закрывший вкладку на третьей странице, стоит на её первом вопросе, а не на
последнем поле, которого коснулись руками.

**Состояние — код фазы закрыт и влит; DoD закрыт не полностью.** Открыты два пункта, оба
машинные и оба за владельцем: прогон e2e-сценария `multipage` и замер `npm run perf` против
свежего prod-local, плюс живая проверка глазами. Разбор фазы по шагам, находки ревью и четыре
примерки индикатора шагов — [`JOURNAL.md`](JOURNAL.md), раздел «Фаза 19». Как устроено сейчас —
[`EDITOR.md`](EDITOR.md) §1 и §6, [`ANALYTICS.md`](ANALYTICS.md) §«Самая дальняя точка».

**Definition of Done.** Форма **без разрывов** рендерится и ведёт себя ровно как до фазы
(регресс-тест на три поверхности); паритет типов Go↔фронт зелёный; пустая страница невозможна
на выходе стора и при этом не даёт 422 в промежуточных состояниях (тест на оба); серверная
валидация ответа не знает о страницах (тест «ответ, собранный из всех страниц, принимается
тем же кодом»); бюджет рендерера ≤ 45 КиБ gzip; `make lint`, `make test`, `make check-docs`
зелёные; e2e `multipage` добавлен и прогнан; ADR-строки принятых решений внесены; живые
справочники ([`EDITOR.md`](EDITOR.md), [`ANALYTICS.md`](ANALYTICS.md),
[`fields/README.md`](../web/shared/fields/README.md)) правятся тем же PR, что и код.

**Состояние — фаза закрыта, все семь слайсов сделаны, ни один не снят и не перенесён.**
Definition of Done выполнен целиком; единственное отступление — пункт про превью-`iframe`
успел побывать снятым (вынесен в TD-60) и вернулся вместе с починкой до конца фазы. Разбор,
заведённый долг (TD-59, TD-61) и то, чем проверено, — [`JOURNAL.md`](JOURNAL.md), «Итог фазы».

## Фаза 20. Встраивание форм в чужие сайты: блок, виджет, страница

> Источник — **запрос владельца** (`PROCESS.md` §1.0), сессия 2026-08-05. Он же снял условие
> старта фазы 20 [`POST-MVP.md`](POST-MVP.md) («запускается по первой живой просьбе повесить
> форму на сайт»). Замысел, отвергнутые альтернативы и цена решений —
> [`design/embed.md`](design/embed.md). **Номер 20 занят в обоих документах разным** (см. «Как
> читать план»), и **скоуп относительно `POST-MVP` изменён:** там было «`<iframe>`-сниппет и
> QR», здесь — три формата встраивания и загрузчик к ним; **QR в фазу не входит** и остаётся
> невзятым хвостом фазы 20 `POST-MVP`.

**Цель.** Форма перестаёт быть только ссылкой и начинает жить частью чужой страницы: заявкой
на лендинге, кнопкой «оставить отзыв» в блоге, онбордингом внутри чужого продукта. Сегодня это
не «неудобно», а невозможно: рендерер отдаёт `X-Frame-Options: SAMEORIGIN` и `frame-ancestors
'self'`, то есть сниппет на чужом сайте покажет пустой прямоугольник. Второй результат —
инфраструктурный: у проекта появляется публичный клиентский артефакт, живущий на чужих
страницах, и вместе с ним правило, как его версионировать.

**Решения владельца 2026-08-05** (ADR-строки вносятся **вместе с кодом** соответствующего
шага — прецедент outbox'а, [`POST-MVP.md`](POST-MVP.md) фаза 11): три формата показывают один
и тот же `/r/{slug}` **во фрейме**, рендер в DOM хоста запрещён; `frame-ancestors *` сразу,
без списка доменов; настройки вставки живут **только в сниппете**, схема и API не трогаются;
виджет v1 — **только по клику**; «страница» — full-page iframe в двух подрежимах (в потоке и
оверлеем), кастомный домен в фазу не входит; предзаполнение — **по `block_id`**, контекст
ответа ждёт спроса. Обоснования — [`design/embed.md`](design/embed.md) §2 и §8.

**Шаги.**

1. **Заголовки и embed-режим рендерера.** Точечное ослабление `handle /r/*` в
   [`Caddyfile`](../deploy/caddy/Caddyfile) (снятие `X-Frame-Options`, `frame-ancestors *`),
   правка ARCHITECTURE §7 тем же PR; параметр `?embed=…`: компактные поля, компактные
   статус-экраны, выключенный автофокус, отправка `ready`/`resize`/`page`/`submit`. Демо:
   `curl -I` на prod-local показывает новые заголовки, кабинет остаётся `DENY`, форма
   грузится во фрейме со стороннего origin.

   **Состояние — закрыт в коде**; `curl -I` на prod-local за владельцем, статически проверено
   `caddy adapt`.
2. **Загрузчик: блок и голый iframe.** `web/renderer/embed/v1.ts` классическим IIFE, однотеговый
   сниппет через `document.currentScript`, авторесайз, проброс UTM, `redirect` на хост. Свой
   каталог сборки и **свой бюджет 4 КиБ gzip** — `check-bundle.mjs` считает весь JS в `dist/`
   рендерера, и без разделения файл съест половину его запаса. Демо: блок на посторонней
   странице растёт по мере заполнения, внутреннего скролла нет.

   **Состояние — закрыт**, загрузчик 2.45 КиБ gzip из 4 (вместе с шагами 3–4).
3. **Виджет.** Плавающая кнопка и `data-trillix-open` на чужом элементе, модалка: Esc, клик по
   подложке, ✕, focus-trap, возврат фокуса на триггер, блокировка скролла хоста с компенсацией
   скроллбара, полный экран на мобильном. Демо: форма открывается с чужой кнопки и корректно
   закрывается с клавиатуры.

   **Состояние — закрыт**; ловушка фокуса неполная по устройству фреймов (события клавиатуры
   внутри формы живут в другом документе) — держится на `focusin`, разбор в журнале.
4. **Страница.** `100dvh` в потоке и `position: fixed` оверлеем, авторесайз выключен;
   императивный API (`mount`/`open`/`close`/`on`) — его требует онбординг в SPA, где контейнер
   появляется после старта скрипта. Демо: форма на весь экран чужой страницы и она же
   оверлеем поверх приложения.

   **Состояние — закрыт**, сделан одним заходом с шагом 3: режим `page` уже читался из
   атрибутов, и оставлять его молча работающим как блок было нельзя.
5. **Кабинет: экран «Встроить».** Два уровня (обывателю — три формата, превью и одна строка
   кода с инструкциями под площадки; разработчику — свёрнутое «Подключить из кода» с API и
   объектом `prefill`), сборка сниппета чистой функцией с юнитами, живое превью **настоящим**
   `embed/v1.js`. Предзаполнение по `block_id` в рендерере плюс предупреждение о смене id при
   пересоздании вопроса. Демо: скопированная строка работает на постороннем сайте без правок.

   **Состояние — закрыт**; живое превью загрузчиком отменено (у кабинета `script-src 'self'`,
   а автоматический фрейм засчитывал бы визит на каждый заход) — спека §9 уточнена.
6. **e2e против prod-local.** Посторонний origin — статик-сервером Playwright на
   `http://127.0.0.1` (прод-конфиг ради теста не трогаем): страница-хозяин грузит форму
   блоком и **отправляет из неё ответ**, виджет открывается и закрывается по Esc. Единственное
   место, где ослабление заголовков проверяется по-настоящему — в dev CSP нет вовсе.

   **Состояние — сценарий написан, ПРОГОН ОТКРЫТ** (нужен поднятый prod-local; живая проверка
   за владельцем). Посторонний origin взят через `page.route`, прод-конфиг ради теста не тронут.

**Демо в конце фазы.** Владелец формы копирует на экране «Встроить» одну строку, вставляет её
в свою страницу на Тильде → форма появляется блоком, растёт по мере заполнения, отправленный
ответ виден в кабинете неотличимо от пришедшего по ссылке → тот же сниппет с другим атрибутом
даёт кнопку «Оставить заявку» с модалкой → третий вариант открывает форму на весь экран, и
предзаполненная почта уже стоит в поле, которое автор добавил сам.

**Definition of Done.** Форма грузится во фрейме с постороннего origin на prod-local и
принимает оттуда ответ (регресс на заголовки); кабинет (`app`) остаётся `DENY` — ослабление не
протекло на второй сайт (тест); `embed/v1.js` ≤ 4 КиБ gzip и **не входит** в бюджет рендерера,
бюджет рендерера ≤ 45 КиБ; сниппет и ссылка ведут на один публичный URL (юнит на сборщик
сниппета); голый `<iframe>` без скрипта работает (сайты с жёстким `script-src`); виджет
закрывается с клавиатуры и возвращает фокус на триггер; ARCHITECTURE §7 описывает фактические
заголовки; ADR-строки §14 спеки внесены; `make lint`, `make test`, `make check-docs` зелёные;
e2e-сценарий `embed` добавлен и прогнан.

## Фаза 21. Условная логика в формах

> **Развёрнута из фазы 16 [`POST-MVP.md`](POST-MVP.md)** «Условная логика в формах»
> (нумерации разошлись — см. «Как читать план»; номер 21 в `POST-MVP` не занят вовсе).
> Скоуп v1 выбран владельцем 2026-08-06 и **шире** написанного там: четыре возможности плюс
> вложенные группы условий. Замысел, отвергнутые альтернативы и цена решений —
> [`design/logic.md`](design/logic.md); **текст фазы 16 `POST-MVP` устарел в трёх местах, и
> спека §1.1 говорит, в каких** (он писался при `schemaVersion: 1`, когда вопрос был одним
> блоком, а страниц не существовало).

**Цель.** Форма перестаёт быть линейной. Сегодня все вопросы видят все: уточнение по редкой
ветке удлиняет анкету каждому, «какой у вас питомец?» показывается тем, у кого питомца нет, а
обязательность выражается только словами «если да, заполните ниже». Фаза даёт автору условие —
на видимость вопроса, на видимость варианта, на обязательность и на путь между страницами.
Второй результат — проверка того, ради чего схему держали в JSONB: формат обязан вырасти на
четыре необязательных поля **без миграции и без подъёма `schemaVersion`**.

**Решения владельца 2026-08-06** (восемь строк ADR §10 [`ARCHITECTURE.md`](ARCHITECTURE.md)
внесены вместе со спекой, до кода — случай тот же, что у фазы 18, где решения меняли модель
данных): скоуп v1 — **все четыре** возможности (видимость вопроса, обязательность по условию,
скрытие вариантов, переходы между страницами) плюс **вложенные группы** И/ИЛИ; носитель правила
видимости — **головной блок группы**; битая и «смотрящая вперёд» ссылка **инертна**, а не
запрещена валидатором; переходы — **только вперёд**; сервер **отбрасывает** ответы на скрытое и
хранит нормализованную карту; знаменатель сводки — **«вопрос показан»**; логика **бесплатна на
всех тарифах**. Две строки ADR названы **отменяющими** обещания фазы 16 `POST-MVP` (валидация
ссылок и «общий пакет на три потребителя») — чтобы их не построили заново.

**Слайсы.** Ядро — первым и без UI: у четырёх возможностей один вычислитель, и написать его
четыре раза по кусочкам означало бы четыре разных семантики. После любого следующего слайса
можно остановиться — продукт остаётся целым.

1. **Ядро: дерево условий и вычислитель.** Формат узла (`all`/`any`/лист) в Zod и Go, лимиты
   глубины/размера/длины, внутриблочные проверки (спека §3.6); `planForm`/`PlanForm` —
   план формы одним проходом (§4.1), тройное правило «источник не решён» (§4.2), инвариант
   `plan(schema, normalize(a)) == plan(schema, a)` (§4.4). Табличные тесты одинакового состава
   с обеих сторон плюс паритет-тест на состав операторов. Ни UI, ни применения. Демо: таблица
   кейсов зелёная в Go и в vitest, форма без правил проходит регресс всех трёх поверхностей.

   **Состояние — закрыт** (ветка `phase21/slice1-core`). Дерево условий и вычислитель есть с
   обеих сторон, 77 подтестов в Go и 80 в vitest одинакового состава, паритет операторов и
   чисел лимитов машинный (`logicparity_test.go` читает TypeScript). Семантика инертности
   свелась к одной фразе — «инертное правило равно отсутствующему»; уточнения, найденные по
   ходу (обход пропущенных страниц, невидимая пустая страница, третье зеркало `splitPages` в
   Go, место вычислителя в `@fields`, а не в `entities`), внесены в спеку §4.1/§4.2/§6.
2. **Видимость вопросов.** Рендерер и превью прячут скрытые группы; `NormalizeAnswers` в
   приёме ответа (обязательность только среди видимых, ответы на скрытое отбрасываются, ответ
   на несуществующий блок по-прежнему 422); секция «Показывать, если» в попапе настроек с
   редактором вложенных групп; бейдж на строке и предупреждения об инертных правилах.
   Замер `check:bundle`. Демо: «Есть ли питомец?» → «Да» показывает «Какой?», curl с ответом
   на скрытый вопрос принят, но скрытого значения в таблице нет.

   **Состояние — закрыт** (ветка `phase21/slice2-visibility`). Приём ответа ходит через
   `domain.NormalizeAnswers` (вычистка → план → проверка), рендерер и превью считают форму
   `planForm`; правило задаётся диалогом «Показывать, если» с вложенными группами, на строке
   полотна — бейдж, инертные правила предупреждают текстом. Бюджет рендерера 36.61 из 45 КиБ.
   **Превью стало заполняемым** — без ответов ветку не проверить (спека §6.2, решение слайса);
   `changeBlockType` больше не роняет правила (риск §9 закрыт).
3. **Обязательность по условию.** `requiredIf` у отвечаемого блока, взаимоисключающий с
   `required` (три состояния в UI), учёт в нормализации. Демо: телефон обязателен только при
   выборе «хочу звонок», скрытый вопрос не обязателен никогда.

   **Состояние — закрыт** (ветка `phase21/slice3-required`). Обязательность стала строкой
   настроек «Нет / Всегда / По условию…» вместо пункта-переключателя (два флага, из которых
   невыразимо третье состояние, собрали бы документ, отвергаемый схемой); диалог правил —
   тот же, что у видимости, отличаются только тексты. **Звёздочка теперь считается по
   плану, а не по флагу** (`groupMeta(blocks, plan.required)`) — без этого условно
   обязательное поле отказывало бы в отправке, ничем не помеченное; на полотне у неё
   появилось третье, приглушённое состояние «обязателен по условию».
4. **Скрытие вариантов.** `visibleIf` у `Option`, вычистка id скрытых вариантов из ответа
   (в том числе из массива `multi_choice`), пункт в попапе варианта. Демо: каскадный список —
   выбрал «Собака», вариант «лоток» во втором списке не показывается и не принимается.

   **Состояние — закрыт** (ветка `phase21/slice4-options`). Рендер получает блок уже
   отфильтрованным (`withVisibleOptions`), а не множество видимых через контракт контролов:
   иначе о видимости пришлось бы знать каждому типу поля, включая будущие, — и бесплатно
   починились буквенные бейджи (считаются по видимому списку, без дырок). Диалог правила
   перестал знать, где живёт правило: ему дают условие и колбэк записи — правил стало три,
   и третья ветка в каждой его строке была бы платой за экономию одного пропа.
5. **Переходы между страницами.** `jumpIf` у разрыва (цель — id другого разрыва либо `end`),
   стек посещённых страниц в рендерере вместо арифметики индексов, линии шагов по симуляции
   пути, тот же обход на бэке. Замер `check:bundle`. Демо: ветка «Нет» перескакивает страницу
   уточнений и приходит к отправке; ответы на пропущенной странице в базу не попадают.

   **Состояние — закрыт** (ветка `phase21/slice5-jumps`). **Стек посещённых страниц не
   понадобился, и это главная находка слайса:** план отдаёт `pages` уже как пройденный путь,
   поэтому «Далее»/«Назад» остались ±1 по массиву, а линии шагов — его длиной; стек был бы
   вторым представлением того же знания, которое пришлось бы держать в согласии с ответами.
   Рендерер и превью не тронуты вовсе — слайс это UI переходов (диалог со списком правил на
   разрыве, цели только вперёд плюс «к отправке») плюс тесты обеих поверхностей.
6. **Сводка: знаменатель «показан».** `asked` считается пересчётом видимости по сохранённым
   ответам, а не по составу версии. Демо: вопрос редкой ветки показывает «12 из 34», а не
   «12 из 400».

   **Состояние — закрыт** (ветка `phase21/slice6-summary`). `SummaryBuilder` держит блоки
   каждой версии (одной карты типов для видимости не хватает) и считает план на каждый
   ответ; знаменатель теперь стоит на двух условиях сразу — «был в версии» И «показали
   этому респонденту». На карточке появилась оговорка «вопрос показали N из M», когда
   знаменатель меньше числа ответов формы: без неё владелец сравнивает «12 из 34» с «400
   ответов» и читает расхождение как поломку. Асимметрия с воронкой (её починить нечем —
   визит не хранит ответов) записана в [`ANALYTICS.md`](ANALYTICS.md).
7. **Финализация.** Сценарий e2e `logic` (ветвление + пропуск страницы + скрытый вариант),
   `npm run perf` на полотне, живые справочники: [`EDITOR.md`](EDITOR.md) (раздел про логику),
   [`ANALYTICS.md`](ANALYTICS.md) (ограничение воронки), [`API.md`](API.md)/[`SCHEMA.md`](SCHEMA.md),
   [`STATUS.md`](STATUS.md), скилл-справочник; шапка спеки переписывается на архивную.

   **Состояние — закрыт** (ветка `phase21/slice7-final`). Сценарий `logic` написан и
   **прогнан против prod-local — зелёный**: скрытый вопрос отсутствует в DOM, условно
   обязательный держит «Далее», скрытый вариант не приходит в список, переход «к отправке»
   заканчивает форму, присланный вручную ответ на скрытое принят и не сохранён, знаменатель
   сводки честный. Заодно прогнан весь набор: шесть сценариев зелёные, `multipage` и `embed`
   красные **в своей обвязке** — заведены как TD-58 и TD-57 с диагнозом.

   **Замер полотна и ревью поймали один и тот же класс регресса дважды.** Сперва замер:
   попап настроек подписывался на весь массив блоков, а он отрисован у каждой строки.
   Потом ревью ветки: сужение подписки обходили сами диалоги правил — закрытые, но
   **смонтированные** у каждой карточки варианта, они подписаны на `blocks` и
   перерисовывались на каждый символ. Мера — `perChar.scriptMs` (время задачи шумит и
   первый регресс скрыло): на 199 блоках 7.73 на `main` → 10.9 в фазе → 4.2–4.5 после
   починки. Диалоги теперь монтируются только открытыми, попапы подписываются только
   открытыми, бейдж — на **показанные строки**, а не на массив и не на «состав документа»
   (тот не меняется при `changeBlockType`, и правило, ставшее инертным, оставалось бы
   помеченным действующим). Пара замеров — `e2e/perf/results/phase21-before-review.json` и
   `phase21.json`.

   **Ревью ветки нашло ещё три дефекта, все починены:** свободный ввод значения условия не
   был ограничен `MAX_LOGIC_VALUE_LEN` (вставка длинной строки роняла автосейв в 422 без
   единого объяснения автору); превью объясняло пустой экран условиями даже когда условий в
   форме нет (документ из одного разрыва); `STATUS.md` противоречил сам себе про замер.

**Демо в конце фазы.** Форма «Есть ли у вас питомец?» → при «Да» появляется «Какой?», при
«Собака» во втором списке нет варианта «лоток» → ветка «Нет» перескакивает страницу уточнений
и приходит сразу к отправке, линии шагов показывают путь, который получается при этих ответах
→ поле «Телефон» обязательно только при выборе «Хочу звонок» → присланный curl'ом ответ на
скрытый вопрос принят, но скрытого значения нет ни в таблице, ни в CSV, ни в сводке → сводка
показывает «заполнили 12 из 34, кому вопрос показали» → форма без единого правила ведёт себя
ровно как до фазы.

**Definition of Done.** Форма **без правил** рендерится и ведёт себя байт в байт как до фазы
(регресс на три поверхности); `schemaVersion` не поднят, старые опубликованные версии читаются
без апгрейдера; вычислитель покрыт табличными тестами **одинакового состава** в Go и в vitest,
паритет операторов сторожится тестом; инвариант §4.4 покрыт тестом (пересчёт по сохранённому
ответу даёт исходную видимость); серверная валидация не доверяет клиентской видимости
(тест «ответ на скрытый вопрос отброшен, а не сохранён»); обход страниц завершается по
построению (тест на инертность перехода назад); кросс-блочные условия **не** дают 422 в
промежуточных состояниях драга и undo (тест на оба); бюджет рендерера ≤ 45 КиБ gzip;
`make lint`, `make test`, `make check-docs` зелёные; e2e `logic` добавлен и прогнан; живые
справочники правятся тем же PR, что и код.

**Состояние — фаза закрыта, все семь слайсов сделаны, ни один не снят и не перенесён.**
Definition of Done выполнен целиком; единственное отступление — пункт про превью-`iframe`
успел побывать снятым (вынесен в TD-60) и вернулся вместе с починкой до конца фазы. Разбор,
заведённый долг (TD-59, TD-61) и то, чем проверено, — [`JOURNAL.md`](JOURNAL.md), «Итог фазы».
Открытым остаётся **продуктовое решение, а не пункт DoD**: `form_design_custom` открыт всем
планам, поэтому вживую 402 показывает форма со своим CSS, а не с цветами (спека §13.3,
включение — один `UPDATE`). Живой просмотр шторки и превью глазами — за владельцем.

## Фаза 22. Оформление формы: тема, цвета, шрифт, лэйаут, свой CSS

> **Источник — запрос владельца** (`PROCESS.md` §1.0), сессия 2026-08-09. Номер 22 не занят
> ни в одном документе: [`POST-MVP.md`](POST-MVP.md) кончается фазой 20, и оформления формы
> там нет вовсе. Замысел, отвергнутые альтернативы и цена решений —
> [`design/theme.md`](design/theme.md).
>
> **Фаза отменяет одно записанное следствие.** ADR §10 [`ARCHITECTURE.md`](ARCHITECTURE.md)
> в строке про свободный цвет спана (фаза 14) утверждает: «цвета в схеме абсолютные, поэтому
> тёмная тема рендерера смысла не имеет — публичная форма остаётся светлой». Строка правится
> вместе со спекой, до кода; формат спанов **не меняется**.

**Цель.** Вид формы перестаёт быть одним на всех. Сегодня он зашит в `fields.css` замерами с
живой формы Tally — хороший вид, но автор с фирменным цветом не может его применить, форма на
тёмном лендинге остаётся белым прямоугольником, а колонка под таблицу вариантов не
расширяется. Продукт при этом позиционируется как глубоко настраиваемый конструктор — так
записано в ADR §10 в обосновании свободного цвета текста, и оформление формы это обещание
проверяет целиком. Второй результат — **первый гейт на качество, а не на количество**: из
пяти сегодняшних ключей каталога четыре считают объём, и ни один не продаёт «выглядит как мы».

**Решения владельца 2026-08-09** (строки ADR §10 вносятся вместе со спекой, до кода — случай
тот же, что у фаз 18 и 21, где решения меняли модель данных): оформление живёт **в схеме**
рядом с `cover`/`logo`, `schemaVersion` **не поднимается**; тем ровно **две**, дропдауном;
`theme` — **отдельное поле** ради `color-scheme`, а `auto` по системной настройке **отвергнут**;
тёмная тема **разрешена** и несовместимость с крашеным текстом лечится **предупреждением, а не
запретом**; шрифты — **только self-hosted с кириллицей**; гейт своих значений — **на публикации**,
гейт бейджа — **на отдаче** (и потому переживает даунгрейд по-разному, спека §9.4); бейдж
«Сделано в Trillix» **вводится сейчас**, пока платящих нет; свой CSS — **в этой же фазе**,
последним слайсом.

**Слайсы.** Первый — без единой новой возможности: пока `--rf-surface` означает и холст, и
заливку поля, а пять размеров шкалы записаны литералами, всё остальное будет заплатками
поверх зашитых чисел. После любого следующего слайса можно остановиться — продукт остаётся
целым; слайс 7 самодостаточен и при необходимости отрезается в отдельную фазу.

1. **Разложение токенов.** `--rf-surface` разделяется на `--rf-canvas` и `--rf-field-bg`;
   `--rf-field-shadow`/`--rf-focus-shadow`/`--rf-selected-shadow` собираются из составляющих
   (`--rf-ring`, два слоя тени, фокус — производная акцента); шесть размеров переводятся на
   `calc()` от базы через безразмерные отношения (шкала уже соотносительная — 2.5 / 1.5 /
   1.25 / 1 / 0.875 / 0.75, спека §3.3). Новой функциональности ноль. Демо: вид формы не
   изменился — сравнение computed-стилей старого и нового CSS, `e2e` зелёные, `npm run perf`
   без регресса.

   **Состояние — закрыт** (`phase22/slice1-tokens`): вид не изменился, подтверждено сравнением
   computed-стилей старого и нового CSS. Разбор — [`JOURNAL.md`](JOURNAL.md).

2. **Модель и контракт.** `design` в `FormSchema` (Go + Zod, зеркала), валидатор с границами,
   `designToVars` в `web/shared` и её зеркало на Go, паритет-тест по составу переменных. Ни
   UI, ни применения. Демо: табличные тесты одинакового состава с обеих сторон, 422 на мусор,
   форма без `design` даёт пустой набор переменных.

   **Состояние — закрыт** (`phase22/slice2-model`): `design` в схеме, зеркала Go ↔ Zod, паритет по
   составу переменных, спискам и границам. Разбор — [`JOURNAL.md`](JOURNAL.md).

3. **Шторка «Оформление» и выбор темы.** Выезжающая панель поверх полотна (образец — Tally),
   тема дропдауном на два значения, применение на всех трёх поверхностях. Демо: выбрал тёмную
   тему — полотно за шторкой и превью потемнели, опубликовал — форма тёмная.

   **Состояние — закрыт** (`phase22/slice3-panel`): шторка и выбор темы; набор готовых тем начат и
   отменён решением владельца. Разбор — [`JOURNAL.md`](JOURNAL.md).

4. **Свои значения.** Цвета (холст, поле, текст, приглушённый, акцент, кнопка), скругление,
   вид контура, шрифт из курируемого списка (self-hosted woff2, кириллица, `swap`, preload
   выбранного, новый порог веса в `check:bundle`), ширина колонки, базовый кегль, плотность,
   выравнивание, кнопка отправки. Предупреждение о контрасте и предупреждение о крашеных
   спанах при тёмной теме. Демо: форма в фирменных цветах и своём шрифте, кнопка во всю
   колонку.

   **Состояние — закрыт** (`phase22/slice4-values`): все свои значения плюс шрифт; предупреждение о
   крашеном тексте построено и снято владельцем. Разбор — [`JOURNAL.md`](JOURNAL.md).

5. **Публичный контур.** Критические переменные в `<style>` из Go (точка вставки
   `<!--og-meta-->` уже есть), `color-scheme`, `theme-color`, тема на экранах «Спасибо»,
   «форма закрыта», ошибка и загрузка; связка «прозрачный фон embed + тема автора». Демо:
   тёмная форма открывается тёмной **с первого кадра**, после отправки не мигает белым.

   **Состояние — закрыт** (`phase22/slice5-public`): первый кадр за сервером — оформление уехало в
   атрибуты тега `<html>`, а не в `<style>` головы, как обещала спека. Разбор — [`JOURNAL.md`](JOURNAL.md).

6. **Тарифы и бейдж.** Три ключа каталога (`form_design_custom`, `form_custom_css`,
   `form_branding`), миграция `plans.limits` по всем планам, 402 на публикации после
   авторизации, плашка и замок в редакторе, бейдж на форме и на экранах, замер цены гейта
   бейджа на публичном пути. Демо: черновик со своими цветами на бесплатном тарифе
   **сохраняется**, но не публикуется; бейдж стоит на бесплатной форме и снят на платной.

   **Состояние — закрыт** (`phase22/slice6-plans`): две точки гейта разной природы — оформление на
   публикации, бейдж на отдаче. Разбор — [`JOURNAL.md`](JOURNAL.md).

   **Демо-критерий выполняется механикой, но не данными, и это осознанно.** Гейт
   `form_design_custom` стоит и отвечает 402 — проверено тестами сервиса, — но в
   `plans.limits` он открыт **всем планам** (миграция `0018`): раскладка «что входит во
   Free» упирается в нерешённое (когда включать Free и на скольких ответах, спека §13.3).
   За пейгейт ушли только свой CSS и бейдж (`0019`), поэтому вживую 402 показывает форма
   со своим CSS, а не с цветами. Включение — один `UPDATE` без выкатки, **решение за
   владельцем**; до него формулировку демо читать как «публикация с платной настройкой
   отвечает 402», а не «с цветами».

7. **Свой CSS.** `class` у блока и `design.css` у формы, превью переезжает в `iframe`,
   лимит длины, отказ на `</`, сторож текста согласия, документированное подмножество `rf-*`
   как публичный контракт. Демо: правило автора доехало до респондента и не тронуло кабинет.

   **Состояние — закрыт** (`phase22/slice7-css`) **целиком, включая переезд превью в
   `iframe`**. Переезд сперва отложили в TD-60 (превью не показывало CSS вовсе, и автор
   писал правила вслепую) и закрыли до конца фазы: превью получило свой документ и
   отдельный корень React. Разбор — [`JOURNAL.md`](JOURNAL.md).

**Демо в конце фазы.** Автор открывает «Оформление», выбирает тёмную тему → полотно, превью и
опубликованная форма темнеют одинаково → задаёт свой акцент, шрифт с кириллицей, широкую
колонку и кнопку во всю ширину → публичная ссылка открывается сразу в этом виде, без вспышки
белым, и экран «Спасибо» после отправки тоже тёмный → на бесплатном тарифе публикация формы
с платной настройкой (сегодня это свой CSS — см. оговорку у слайса 6)
отвечает 402 со списком того, что мешает, а черновик при этом продолжает сохраняться → бейдж
«Сделано в Trillix» стоит на бесплатной форме и отсутствует на платной → свой CSS красит
помеченный блок у респондента и не трогает кабинет → форма, у которой оформление не трогали,
выглядит **байт в байт как до фазы**.

**Definition of Done.** Форма **без `design`** рендерится и ведёт себя байт в байт как до фазы
(регресс на три поверхности — первым пунктом, а не последним); `schemaVersion` не поднят,
старые опубликованные версии читаются без апгрейдера; `designToVars` покрыта табличными
тестами **одинакового состава** в Go и в vitest, паритет состава переменных сторожится тестом;
валидатор отвергает выход за диапазон, а не зажимает; гейт публикации **не роняет автосейв**
(тест «черновик с платными ключами сохраняется 200, публикуется 402»); порядок «авторизация →
тариф» покрыт тестом (чужая форма — 404 до гейта); отдача бейджа покрыта тремя сочетаниями
«намерение × тариф»; `TestPlansCoverCatalog` знает три новых ключа; свой CSS не покидает
превью-`iframe` (тест на утечку в кабинет — e2e `design`, шаг 3);
в `fields.css` нет ни одного нового литерального
кегля; бюджет рендерера ≤ 45 КиБ gzip, шрифты ≤ нового порога; `npm run perf` без регресса по
`perChar.scriptMs`; `make lint`, `make test`, `make check-docs` зелёные; e2e `design` добавлен
и прогнан; живые справочники ([`EDITOR.md`](EDITOR.md), [`BILLING.md`](BILLING.md),
[`SCHEMA.md`](SCHEMA.md), [`API.md`](API.md), [`fields/README.md`](../web/shared/fields/README.md))
правятся тем же PR, что и код.

**Состояние — фаза закрыта, все семь слайсов сделаны, ни один не снят и не перенесён.**
Definition of Done выполнен целиком; единственное отступление — пункт про превью-`iframe`
успел побывать снятым (вынесен в TD-60) и вернулся вместе с починкой до конца фазы. Разбор,
заведённый долг (TD-59, TD-61) и то, чем проверено, — [`JOURNAL.md`](JOURNAL.md), «Итог фазы».
Открытым остаётся **продуктовое решение, а не пункт DoD**: `form_design_custom` открыт всем
планам, поэтому вживую 402 показывает форма со своим CSS, а не с цветами (спека §13.3,
включение — один `UPDATE`). Живой просмотр шторки и превью глазами — за владельцем.

## Фаза 23. Настройки аккаунта: профиль, пароль, почта, второй фактор, способы входа, удаление

> **Источник — запрос владельца** (`PROCESS.md` §1.0), сессия 2026-08-13. Номер 23 не занят ни
> в одном документе: [`POST-MVP.md`](POST-MVP.md) кончается фазой 20. Замысел, отвергнутые
> альтернативы и цена решений — [`design/account-settings.md`](design/account-settings.md).
>
> **Фаза правит одну строку ADR §10** [`ARCHITECTURE.md`](ARCHITECTURE.md): «scope
> минимальный — идентификатор и email». Имя приезжает из `login.yandex.ru/info` только при
> разрешении `login:info`, то есть пункт «данные подтягиваем из OAuth» без расширения scope
> невыполним. Строка правится вместе со слайсом B, до его кода.
>
> **Фаза закрывает [TD-53](TECH-DEBT.md)** — осиротевший воркспейс при удалении хозяина.
> Реестр предписывал решать судьбу пространства тогда, когда удаление появится в продукте;
> оно появляется здесь.

**Цель.** Сегодня аккаунт неуправляем: имени у человека нет вовсе, пароль меняется только
через «забыл пароль», адрес не меняется никак, второго фактора нет, привязанный Яндекс
невидим и неотключаем, а уйти из продукта нельзя — удаления нет ни ручкой, ни операцией.
Это не фичи поверх продукта, а то, чего от кабинета ждут по умолчанию: отсутствие каждого
пункта по отдельности объяснимо, а вместе они означают, что аккаунт мы завести умеем, а
обслуживать — нет.

**Решения владельца 2026-08-13** (все четыре — в спеке, с отвергнутыми альтернативами): второй
фактор — **TOTP без QR** (stdlib, новых зависимостей ноль; секрет строкой и ссылка
`otpauth://` вместо картинки); **scope расширяем** правкой ADR; формы удалённого аккаунта
**уходят в 404**; **`provider_email` сохраняем**, иначе карточка не может сказать, какой
именно аккаунт Яндекса подключён. Плюс решение по ходу планирования: смена почты —
**двухшаговая**, через письмо на новый адрес.

**Слайсы.** Порядок неслучаен: G знает про второй фактор (подтверждение удаления), F — про
пароль. После любого слайса можно остановиться, продукт остаётся целым.

1. **A. Каркас экрана и профиль.** Миграция `0021` (`users.first_name`/`last_name`,
   `user_identities.provider_email` — колонка заводится здесь, заполняется в E: миграция
   дешевле одна), `PATCH /account/profile`, `GET /auth/me` и `entities/user.ts` прирастают
   полями, роут `/settings/account`, живой пункт сайдбара вместо `disabled`-заглушки. Демо:
   вписал имя → F5 → на месте, в сайдбаре имя вместо email.

   **Состояние — закрыт** (`phase23/sliceA-profile`): миграция `0021`, `PATCH /account/profile`,
   экран и живой пункт сайдбара. Критерий проверен `curl` против живого бинарника; экран
   глазами не смотрели.

2. **B. Имя из Яндекса.** `oauth.Profile` += `FirstName`/`LastName`, `fetchProfile`,
   заполнение при создании аккаунта и **только пустых полей** при привязке; строка ADR §10.
   Демо: новый аккаунт через Яндекс открывает настройки с уже заполненными полями.
   **Требует действия владельца:** разрешение `login:info` в консоли Яндекс ID на **обоих**
   приложениях (dev и прод) — без него поля придут пустыми.

   **Состояние — код закрыт, ждёт разрешения в консоли** (`phase23/sliceB-yandex-name`).
   Профиль ездит от провайдера до сервиса структурой `IdentityProfile`, заполнение — через
   `COALESCE` (мутация «COALESCE наоборот» роняет интеграционный тест). Уточнение против
   спеки: на шаге привязки имя не проставляется — в подписанной cookie его нет, приедет на
   ближайшем входе. Строка ADR §10 про scope переписана.

3. **C. Пароль.** `POST /account/password` (у аккаунта без пароля — «задать», без текущего),
   разрыв всех сессий кроме текущей, письмо-уведомление. Демо: сменил пароль → второй браузер
   получает 401, текущая вкладка работает, письмо пришло.

   **Состояние — закрыт** (`phase23/sliceC-password`). Уточнение против спеки: рвутся **все**
   сессии, включая текущую, а взамен открывается новая — cookie переставляет ответ. Отдельный
   запрос «удали всё, кроме этого хеша» не понадобился, и токен заодно ротируется. В объекте
   пользователя появился `hasPassword` — без него кабинет не знает, спрашивать ли текущий
   пароль. Мутации «не рвать сессии» и «не переставить cookie» роняют интеграционный тест.

4. **D. Почта.** Миграция `0022`, `POST /account/email` + `POST /auth/confirm-email-change`,
   письмо на новый адрес и уведомление на старый, проверка занятости дважды. Демо: сменил
   адрес → в `users` он появился только после перехода по ссылке из письма.

   **Состояние — закрыт** (`phase23/sliceD-email`). Уточнение против спеки: сессии при смене
   адреса **не рвутся** — второй шаг не аутентифицирован, и разрыв ничего не защищает (защита
   — пароль на первом шаге и уведомление на старый адрес). Названа вслух дыра для аккаунтов
   без пароля: её закрывает слайс F. Экран подтверждения — свой маршрут `/confirm-email-change`
   по образцу `/verify-email`.

5. **E. Способы входа.** `GET /account/identities`, `DELETE /account/identities/{provider}`
   с гейтом «останется ли способ войти», привязка через `intent=link` в HttpOnly-cookie со
   сверкой `user_id`, заполнение `provider_email`. Демо: карточка «Яндекс · адрес · дата»,
   отвязка последнего способа входа — 409.

   **Состояние — закрыт** (`phase23/sliceE-identities`). Уточнение против плана: привязка
   начинается со **своего адреса** `/account/identities/{provider}/start` за `RequireAuth`, а
   не с `?intent=link` у публичного `/start` — так «намерение ставит только вошедший» стало
   свойством маршрута. Сверка id из подписи с текущей сессией покрыта тестом «намерение на
   чужой аккаунт»: без неё жертву можно заманить прицепить к себе личность атакующего.

6. **F. Второй фактор.** Миграция `0023`, TOTP на stdlib, резервные коды, шифрование секрета
   AES-GCM ключом HKDF от `FORM_TOKEN_SECRET`, ветка входа через challenge-cookie на всех
   путях входа, включая OAuth. Демо: вход в инкогнито просит код; резервный код срабатывает
   один раз.

   **Состояние — закрыт** (`phase23/sliceF-totp`). Ключ HKDF взят из stdlib `crypto/hkdf`
   (Go 1.24+), поэтому `golang.org/x/crypto` не понадобился вовсе. Сверх плана: **защита от
   повтора кода** — номер израсходованного шага в `user_totp.last_step`, отметка атомарным
   `UPDATE`. Проверка TOTP сверена с векторами RFC 6238, а не с собственной реализацией.
   Найден и починен настоящий дефект: правка `/auth/me` не применилась, и сборку чинил
   жёсткий `false` — интеграционный тест поймал.

7. **G. Удаление.** Миграция `0024`, `POST /account/delete`, слепота чтений к помеченным,
   404 публичных форм, отказ владельцу непустого командного пространства; TD-53 переезжает в
   «Закрыто». Демо: после удаления вход не работает, форма отвечает 404, `deleted_at` не NULL.

   **Состояние — закрыт** (`phase23/sliceG-delete`). Уточнение против спеки:
   подтверждение строже — пароль (если есть) **и** код второго фактора (если включён), по
   образцу выключения фактора: удаление необратимо. Слепота к пометке стоит у всех ЧЕТЫРЁХ
   чтений пользователя, а занятость адреса спрашивается отдельным запросом `EmailTaken` —
   иначе подтверждение смены почты на адрес удалённого падало бы на `UNIQUE` вместо 409.
   Вопрос «мешают ли команды» задаёт `auth`, отвечает `workspaces` (импорт невозможен —
   цикл; сравнение с ролью вне модуля запрещено), связь — интерфейс плюс `WithTeams` в `main`.
   Мутации «удалять без кода при включённом факторе» и «пускать владельца непустой команды»
   роняют свои тесты.

**Демо в конце фазы.** Критерий приёмки целиком — [`design/account-settings.md`](design/account-settings.md) §1:
шесть пунктов, от «вписал имя, и в сайдбаре имя вместо email» до «после удаления вход не
работает, а опубликованная форма отвечает 404».

**Definition of Done.** Каждый эндпоинт мутации — за `RequireAuth` **и** `RequireCSRF`, с
`MaxBytesReader`; `login-2fa` сидит в **общем ведре** с `/auth/login` (тест на это, а не
слово в документе); отвязка последнего способа входа и удаление владельца непустой команды
покрыты интеграционными тестами обоих исходов; TOTP-верификатор покрыт табличным тестом с
окном ±1 шаг и **отказом на повторное использование** кода; резервный код сгорает (тест);
секрет TOTP не появляется ни в логах, ни в ответах после `enable`; смена пароля и почты рвут
чужие сессии и не рвут текущую (тест); подтверждение смены почты на занятый адрес даёт 409, а
не падение на `UNIQUE`; публичная форма удалённого владельца отвечает 404; ни одна новая
проверка e2e не заведена отдельным сценарием со своим входом — `loginBurst = 5`, проверки
встраиваются туда, где сессия уже есть; [`API.md`](API.md), [`SCHEMA.md`](SCHEMA.md),
[`WORKSPACES.md`](WORKSPACES.md) и строка ADR правятся тем же PR, что и код; `make lint`,
`make test`, `make check-docs` зелёные.

## Фаза 24. Загрузка файлов в ответах: блок «файл», приватный бакет, presigned-поток

**Источник — фаза 17 [`POST-MVP.md`](POST-MVP.md)**, развёрнутая здесь по правилу «фаза
разворачивается в раздел `DEV-PLAN.md` перед стартом». Спека и детализированный критерий
приёмки — [`design/answer-files.md`](design/answer-files.md), согласована с владельцем
2026-08-17. ⚠ Одноимённая фаза 17 `DEV-PLAN` — тарифы, закрыта.

**Цель.** Респондент прикладывает к ответу файл. Технически — первое появление объектного
хранилища в **публичном** контуре: до сих пор в бакет писал только автор под сессией, а
теперь право записи выдаётся анониму, и это самая опасная новая поверхность продукта.
Отсюда вся конструкция: байты идут в хранилище напрямую (Go их не видит), но право на
запись выписывает Go — на один ключ, один размер и пять минут.

**Три решения владельца 2026-08-17**, принятые до кода: поток — presigned PUT напрямую (как
в DoD фазы `POST-MVP`, ценой правки CSP и настройки CORS на бакете); ключ квоты
`storage_per_workspace` заводится сразу, безлимитом у всех планов; поле у респондента —
полный вид, зона перетаскивания и прогресс (бюджет рендерера при этом мерить по факту).

**Шаги** (они же слайсы, спека §10).

1. **Транспорт.** `blob.Presign` (PUT и GET, `response-*`-переопределения у GET) и
   `blob.HeadObject` — оба отложены с фазы S3-медиа как YAGNI, потребитель появился.
   Интеграционный тест против MinIO проверяет главное: подписанный `Content-Length`
   реально не даёт положить больше.
2. **Тип блока `file`** сквозь контракт: файл типа и реестры обеих сторон, три настройки
   (`maxFiles`, `maxFileSize`, `accept`), формат ответа (массив `uploadId`),
   `ValidateAnswers`, CSV, сводка. Тест паритета Go↔TS краснеет, пока тип не заполнен.
3. **Хранилище.** Миграция `submission_files`, модуль `internal/answerfiles` по образцу
   `internal/media`, **приватный** второй бакет и его env.
4. **Выдача слота.** `POST /public/v1/forms/{slug}/uploads`: своё ведро лимитера по IP,
   токен формы, белый и чёрный списки типов, квота воркспейса → presigned PUT. Заявление
   загрузки при приёме ответа: `HeadObject`, сверка размера, `claimed_at`.
5. **Жизненный цикл.** Скачивание автором (`302` на presigned GET с
   `Content-Disposition: attachment`), удаление объектов вместе с ответом, формой и
   пространством, периодическая чистка незаявленных загрузок старше суток.
6. **Полотно.** Поле с зоной перетаскивания и прогрессом на трёх поверхностях, настройки
   блока, пункт slash-меню и глиф типа.
7. **Инфраструктура и справочники.** `connect-src` для домена форм в `Caddyfile`, CORS на
   бакете (руками у провайдера — шаг владельца), бакет в `backup.sh` и `RESTORE.md`;
   `S3.md`, `API.md`, `SCHEMA.md`, `EDITOR.md`, `fields/README.md`.

**Демо в конце фазы.** Критерий приёмки целиком — [`design/answer-files.md`](design/answer-files.md)
§1: шесть пунктов, от «бросил PDF с телефона, автор скачал его из таблицы» до «загрузка без
отправленной формы исчезает из бакета сама».

**Definition of Done.** Байты файлов не проходят через Go-процесс; осиротевшие объекты
собираются (тест TTL-чистки); presigned-подписи не позволяют превысить лимиты (тест против
MinIO, а не слово в документе); `.svg` и `.exe` отбиваются **до** начала загрузки; файлы
никогда не отдаются с наших доменов и только как вложение; скачивание чужого файла даёт 404
(анти-IDOR-тест); удаление ответа уносит объект; файлы ответов нигде не декодируются и не
распаковываются; бакет добавлен в бэкап-процедуру; справочники и строка ADR правятся тем же
PR, что и код; `make lint`, `make test`, `make check-docs` зелёные.

## Фаза 25. Интеграция с Google Таблицами

**Развёрнута из ЧАСТИ фазы 15 [`POST-MVP.md`](POST-MVP.md)** («Вебхуки и интеграции»):
берётся только интеграция, вебхуки и Telegram остаются там (нумерации разошлись — см. «Как
читать план»). Спека, согласованная до кода, —
[`design/integrations-gsheets.md`](design/integrations-gsheets.md); критерий приёмки её §12.

**Цель.** У формы появляется место для интеграций — пятый таб рядом со «Сводкой» и
«Воронкой», — и первая из них: ответы сами ложатся строками в Google Таблицу автора.
Выгрузка CSV сегодня устаревает в момент скачивания, и любой процесс поверх ответов
начинается с ручного «скачай ещё раз». Фаза собирает урожай с готового фундамента: `outbox`
[спроектирован под второй канал](../migrations/0010_outbox.up.sql) с первого дня, событие
«новый ответ» уже пишется, `CSVBuilder` уже умеет строку и шапку, AES-GCM-запечатывание
секрета уже написано для TOTP.

**Слайсы.**

0. **ADR до кода.** Пять строк (спека §11): хранение чужих refresh-токенов у интеграций
   (не отменяя одноразовость токена у входа), подключение принадлежит пространству, таблицу
   создаёт продукт ради несенситивного scope `drive.file`, канал в существующем outbox,
   payload из идентификаторов ради горячего пути приёма, `ActionIntegrationManage` у
   владельца (последнее — без строки ADR: это применение уже принятого «право по действию»).
1. **A. Аккаунт Google подключается к пространству** (`0029`). `internal/integrations`,
   OAuth `access_type=offline` на stdlib по образцу `internal/oauth`, refresh-токен под
   AES-256-GCM с HKDF-меткой, `ActionIntegrationManage` в матрице прав,
   подключение/отключение, отзыв на стороне Google best-effort, отключение при уходе
   участника (`ON DELETE CASCADE` у `connected_by`).
2. **B. Форма получает таблицу.** Создание таблицы от имени подключённого аккаунта, шапка из
   общей модели вопросов, `form_integrations`, `CSVBuilder.Columns()` — сопоставление
   «колонка листа ↔ вопрос» по ключу, а не по подписи.
3. **C. Живая доставка.** Канал `gsheets` в диспетчере outbox, продюсер после коммита
   ответа (транзакции на быстром пути приёма нет — спека §6, правка по факту),
   `values.append` с `valueInputOption=RAW` (формула респондента обязана доехать текстом),
   добавление колонки под новый вопрос, окончательный отказ провайдера метит интеграцию
   сломанной и гасит событие.
4. **D. Догрузка и «Перезалить всё».** Отсечка `backfill_before`, статус `backfilling`,
   живые строки ждут в outbox, пачки по сотне строк; та же механика — кнопкой лечения.
5. **E. Экран «Интеграции».** Пятый таб в `_manage`, пять состояний пункта «Google
   Таблицы», причина поломки человеческим текстом, `editor` видит, но не подключает.
6. **F. Документы и e2e.** `docs/INTEGRATIONS.md` + скилл `integration-sheets`, `API.md`,
   `SCHEMA.md`, `.env.example`, `deploy/`, e2e-сценарий против фейкового Google.

**Демо в конце фазы.** Спека §12 целиком: от «подключил Google и увидел в таблице все ранее
накопленные ответы» до «`=1+1` из текстового поля лежит в ячейке текстом» и «отключил —
новые строки не идут, старые на месте».

**Definition of Done.** Спека §12. Коротко: refresh-токен в БД только шифротекстом и нигде в
логах; `editor` и чужой получают отказ на подключение (анти-IDOR обеих ролей); недоступность
Google не роняет приём ответа и не плодит дублей после восстановления; безнадёжное событие
не ретраится вечно; догрузка не задерживает письма; справочники правятся тем же PR, что код.
