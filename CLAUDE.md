# Конструктор форм (аналог Tally) — MVP

SaaS-конструктор форм. Стек: Go (stdlib-first, минимум зависимостей), PostgreSQL 16, React + TypeScript + TanStack. Монорепозиторий: Go-API в `cmd/` и `internal/`, кабинет в `web/app`, публичный рендерер в `web/renderer`, миграции в `migrations/`, инфраструктура в `deploy/`. Разработка ведётся только локально (контуры dev и prod-local), CI — GitHub Actions; деплоя на сервер нет до фазы 9.

## Источники истины (при конфликте побеждает верхний)

1. `docs/ARCHITECTURE.md` — модель данных, слои, контракт API, ADR-таблица. «Как устроено и почему».
2. `docs/DEV-PLAN.md` — фазы и шаги с демо-критериями. «Что делаем и когда».
3. `docs/PROCESS.md` — рабочий цикл, границы задачи, тестирование, git, Definition of Done. «Как работаем».

Правила работы с документами:

- Перед первой задачей сессии: найти текущую фазу в DEV-PLAN (сверившись с состоянием кода), прочитать её раздел, релевантные разделы ARCHITECTURE и `docs/PROCESS.md`.
- Код, противоречащий ARCHITECTURE.md, не пишется. Отступление — сначала правка ADR-таблицы через согласование с человеком, потом код.
- Реальность разошлась с документом → документ обновляется в том же PR, что и код.
- Два документа противоречат друг другу → остановиться и спросить, процитировав оба места.

`docs/POST-MVP.md` — фазы после MVP; в текущую работу не входит, читается только по явному запросу.

`docs/TECH-DEBT.md` — реестр известного техдолга (дефекты кода и расхождения документов с реальностью), выявленного аудитами. Не источник истины: при конфликте побеждают ARCHITECTURE/DEV-PLAN. Блокеры из него — гейт фазы 9. Пункт закрывается в том же PR, что и починка (строка переезжает в раздел «Закрыто»).

`docs/API.md` и `docs/SCHEMA.md` — **производные** справочники (эндпоинты и таблицы «как есть»), не источники истины: при конфликте с ARCHITECTURE побеждает ARCHITECTURE. Правятся в том же PR, что и код, который их меняет (новый эндпоинт/поле/миграция → обновить справочник тогда же).

## Конвенции по зонам (подгружаются автоматически при работе с файлами зоны)

- `internal/CLAUDE.md` — Go: слои, ошибки, sqlc, логи, конфигурация, разрешённые зависимости.
- `web/CLAUDE.md` — фронтенд: разделение стейта, Zod-типы, структура, мутации, бюджет рендерера.
- `migrations/CLAUDE.md` — база данных и миграции.

## Команды (единая точка входа — Makefile, появляется в фазе 0)

```
make dev            # Postgres в Docker + API с hot-reload; фронты: npm run dev в web/app (:5173) и web/renderer (:5174)
make lint           # golangci-lint + eslint + tsc --noEmit
make test           # go test -race + vitest; интеграционные — против testcontainers
make migrate-up / migrate-down
make seed           # сидирование данных (пользователь + формы)
make prod-local     # репетиция прода на *.localhost (фаза 7)
```

## Рабочий цикл (кратко; полностью — docs/PROCESS.md)

Понять (назвать демо-критерий из DEV-PLAN; двусмысленность → один вопрос с вариантами до начала) → изучить существующее (код-образец: модуль `auth` — эталон слоёв, `respond.go` — эталон ошибок; grep перед созданием нового) → план 3–7 пунктов (показать человеку, если затронуты схема БД, контракт API или общие типы `entities`) → малые вертикальные шаги (миграция → repo → service → handler → тест → фронт) с коммитом после каждого → `make lint && make test` + ручная проверка демо-критерия → честный отчёт: что сделано, чем проверено (реальный вывод, не «должно работать»), что осознанно НЕ сделано.

Не делать шаги будущих фаз «раз уж я тут»; не рефакторить чужой код мимоходом; YAGNI — закон.

## Зависимости

Списки разрешённых зависимостей заморожены (Go — в `internal/CLAUDE.md`, фронт — в `web/CLAUDE.md`). Добавление ЛЮБОЙ новой — только через вопрос человеку с обоснованием «почему 50 строк своего кода хуже». Обновление версий — никогда «заодно» с фичей, только отдельной задачей.

## Инварианты безопасности (нарушение любого — блокер, что бы ни требовала задача)

1. Каждый handler приватного API — за `RequireAuth`; каждый service-метод по ресурсу начинается с проверки членства в воркспейсе. Id из URL не является доказательством права доступа.
2. Пароли — только argon2id-хеш; токены сессий в БД — только SHA-256. Ни то ни другое не логируется.
3. Весь пользовательский ввод валидируется на бэке независимо от фронта; `MaxBytesReader` — на каждом эндпоинте с телом.
4. Пользовательский контент рендерится как текст; `dangerouslySetInnerHTML` запрещён во всём репозитории.
5. Публичные эндпоинты не раскрывают существование приватного (черновик → 404, не 403) и не отдают ничего, кроме опубликованной версии.
6. Rate limit не отключается и не ослабляется «чтобы тест прошёл» — в тестах лимитер инжектируется пермиссивной реализацией.
7. Секреты не попадают в код, коммиты, логи, образы и отчёты. Файл `.env` не читается и не цитируется целиком.
