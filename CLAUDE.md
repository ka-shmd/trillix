# Конструктор форм (аналог Tally) — MVP

SaaS-конструктор форм. Стек: Go (stdlib-first, минимум зависимостей), PostgreSQL 16, React + TypeScript + TanStack. Монорепозиторий: Go-API в `cmd/` и `internal/`, кабинет в `web/app`, публичный рендерер в `web/renderer`, миграции в `migrations/`, инфраструктура в `deploy/`. Три контура: dev, prod-local и **живой прод** (автодеплой по git-тегу). CI — GitHub Actions.

Текущее состояние — в `docs/STATUS.md`; здесь оно намеренно не дублируется, чтобы не протухало.

## С чего начинать сессию

**`docs/STATUS.md` — одна страница: что живо, где находится разработка, открытый долг, хвосты.**
Она впрыскивается в контекст хуком `SessionStart`, поэтому читать её отдельно не нужно — но
на неё нужно опираться. Всё остальное — по требованию, а не «на всякий случай».

Дальше — только то, что относится к задаче: раздел текущей фазы в `DEV-PLAN.md`, затронутые
разделы `ARCHITECTURE.md`, справочник своей зоны (приезжает скиллом, см. ниже). Читать все
источники целиком в начале сессии не надо: это десятки тысяч токенов про прошлое, из-за
которых на саму работу контекста не остаётся.

## Источники истины (при конфликте побеждает верхний)

1. `docs/ARCHITECTURE.md` — модель данных, слои, контракт API, ADR-таблица. «Как устроено и почему».
2. `docs/DEV-PLAN.md` — фазы и шаги с демо-критериями. «Что делаем и когда».
3. `docs/PROCESS.md` — рабочий цикл, границы задачи, тестирование, git, Definition of Done. «Как работаем».

Правила работы с документами:

- Код, противоречащий ARCHITECTURE.md, не пишется. Отступление — сначала правка ADR-таблицы через согласование с человеком, потом код.
- Реальность разошлась с документом → документ обновляется в том же PR, что и код. Часть расхождений ловится машиной: `make check-docs` (дерево модулей, миграции, env-переменные, ссылки на техдолг) — гоняется в CI.
- Два документа противоречат друг другу → остановиться и спросить, процитировав оба места.

**Состояние и история — разные документы.** `docs/STATUS.md` отвечает «что верно сейчас» и
**переписывается**; `docs/JOURNAL.md` — append-only разбор закрытых шагов (что сделано, какие
решения принимались, что найдено попутно), **читается грепом, а не целиком**. Закрывая шаг,
разбор пиши в журнал, в план оставляй строку с вердиктом. Закрывая фазу — `/phase-close`.

`docs/POST-MVP.md` — фазы после MVP; в текущую работу не входит, читается только по явному запросу. Демо-критерии у всех десяти фаз уже написаны; фаза перед стартом разворачивается в раздел `DEV-PLAN.md`.

**⚠ «Фаза N» без указания документа — двусмысленность.** У проекта две независимые нумерации, и с номера 11 они разошлись: фаза 17 `DEV-PLAN` — тарифы (закрыта), фаза 17 `POST-MVP` — файлы в ответах (не начата); фаза 13 `DEV-PLAN` — полотно, фаза 13 `POST-MVP` — биллинг. Таблица соответствия — `DEV-PLAN.md` §«Как читать план». **Пиши «фаза N `DEV-PLAN`» или «фаза N `POST-MVP`»,** голый номер в старом тексте читай по контексту документа, в котором он написан.

`docs/design/` — **архив спек закрытых фаз**: «почему так решили», отвергнутые альтернативы. Не описывает сегодняшний продукт и **проигрывает живым справочникам при любом расхождении**; планировать работу по этим текстам нельзя (часть разделов описывает непринятое или отменённое — отмечено в шапках). Указатель — `docs/design/README.md`. Новая спека пишется сразу туда, при закрытии фазы шапка переписывается на архивную (`/phase-close`).

`docs/BACKLOG.md` — очередь задач вне плана (продуктовые идеи, «надо бы»). Порядок = приоритет. **MVP-план кончается фазой 10**, после чего источников задач несколько, и у части из них (запрос человека, очередь, дефект прода, операционная работа) **готового критерия приёмки нет** — он пишется и согласуется с человеком до кода. Полная таблица источников — `PROCESS.md` §1.0. Задача без согласованного критерия не начинается.

`docs/AGENTS-GUIDE.md` — руководство **для человека**: какие хуки/скиллы/субагенты установлены и как ими пользоваться. Агенту читать незачем (правила для него — здесь и в `PROCESS.md`), но при вопросе «как у вас устроена работа с агентами» отвечать нужно оттуда.

`docs/TECH-DEBT.md` — реестр известного техдолга (дефекты кода и расхождения документов с реальностью), выявленного аудитами. Не источник истины: при конфликте побеждают ARCHITECTURE/DEV-PLAN. Блокеры из него — гейт выкатки на прод. Пункт закрывается в том же PR, что и починка (строка переезжает в раздел «Закрыто»).

`docs/API.md` и `docs/SCHEMA.md` — **производные** справочники (эндпоинты и таблицы «как есть»), не источники истины: при конфликте с ARCHITECTURE побеждает ARCHITECTURE. Правятся в том же PR, что и код, который их меняет (новый эндпоинт/поле/миграция → обновить справочник тогда же).

## Комментарии в коде

Комментарий пишется **справочным регистром: факт, а не аргумент**. Длина не ограничена —
объяснение механизма стоит своих строк. Ограничены два жанра, которые при правке строки
читать незачем:

- **История** — что было раньше, что отменили, сколько было редакций, чья была реакция.
  Ей место в `JOURNAL.md`; в коде остаётся ссылка одной строкой: `// история — JOURNAL,
  «<заголовок записи>»`.
- **Убеждение** — доводы в пользу уже принятого решения, нажим, повтор мысли другими
  словами. Убеждать нужно было в PR, комментарий решение излагает.

Причина не в опрятности: комментарии тянут около половины токенов боевого кода (точная
доля — в отчёте `make check-comments`), и это налог на каждую сессию по файлу. Всегда
остаются **мина** («иначе undo молча потеряет поле»), **зеркало** («зеркалит
`SCHEMA_VERSION` в formSchema.ts») и **ссылка на справочник** — их незнание ломает тихо,
и найти их поиском нельзя, потому что искать не догадаешься.

Сторож — `make check-comments` (внутри `make lint`): ловит маркеры истории без ссылки на
журнал; на длину не смотрит.

## Команды (единая точка входа — Makefile, появляется в фазе 0)

```
make dev            # Postgres в Docker + API с hot-reload; фронты: npm run dev в web/app (:5173) и web/renderer (:5174)
make lint           # golangci-lint + eslint + tsc --noEmit + check-docs
make test           # go test -race + vitest; интеграционные — против testcontainers
make migrate-up / migrate-down
make seed           # сидирование данных (пользователь + формы)
make prod-local     # репетиция прода на *.localhost (фаза 7)
```

## Рабочий цикл (кратко; полностью — docs/PROCESS.md)

Понять (назвать критерий приёмки — цитатой из плана либо своей формулировкой, согласованной с человеком, PROCESS §1.0; двусмысленность → один вопрос с вариантами до начала) → изучить существующее (код-образец: модуль `auth` — эталон слоёв, `respond.go` — эталон ошибок; grep перед созданием нового) → план 3–7 пунктов (показать человеку, если затронуты схема БД, контракт API или общие типы `entities`) → малые вертикальные шаги (миграция → repo → service → handler → тест → фронт) с коммитом после каждого → `make lint && make test` + ручная проверка критерия приёмки + ревью субагентом `reviewer` → честный отчёт: что сделано, чем проверено (реальный вывод, не «должно работать»), что осознанно НЕ сделано.

Не делать шаги будущих фаз «раз уж я тут»; не рефакторить чужой код мимоходом; YAGNI — закон.

## Зависимости

Списки разрешённых зависимостей заморожены (Go — в `internal/CLAUDE.md`, фронт — в `web/CLAUDE.md`). Добавление ЛЮБОЙ новой — только через вопрос человеку с обоснованием «почему 50 строк своего кода хуже». Обновление версий — никогда «заодно» с фичей, только отдельной задачей.

## Инварианты безопасности (нарушение любого — блокер, что бы ни требовала задача)

1. Каждый handler приватного API — за `RequireAuth`; каждый service-метод по ресурсу начинается с проверки членства в воркспейсе **и достаточности роли** (`workspaces.Can` — по действию, не по роли). Id из URL не является доказательством права доступа.
2. Пароли — только argon2id-хеш; токены сессий в БД — только SHA-256. Ни то ни другое не логируется.
3. Весь пользовательский ввод валидируется на бэке независимо от фронта; `MaxBytesReader` — на каждом эндпоинте с телом.
4. Пользовательский контент рендерится как текст; `dangerouslySetInnerHTML` запрещён во всём репозитории.
5. Публичные эндпоинты не раскрывают существование приватного (черновик → 404, не 403) и не отдают ничего, кроме опубликованной версии.
6. Rate limit не отключается и не ослабляется «чтобы тест прошёл» — в тестах лимитер инжектируется пермиссивной реализацией.
7. Секреты не попадают в код, коммиты, логи, образы и отчёты. Файл `.env` не читается и не цитируется целиком.
