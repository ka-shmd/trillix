# Конвенции Go (cmd/, internal/)

## Зависимости — заморожены

Runtime: `pgx/v5`, `golang.org/x/crypto`, `golang-migrate`, `google/uuid`. Dev-time: `sqlc`, `golangci-lint`, `testcontainers-go`. Добавление ЛЮБОЙ другой — только через вопрос человеку с обоснованием «почему 50 строк своего кода хуже». Токен-бакет, nanoid, чтение env — десятки строк, пишутся руками (и уже написаны — искать в `internal/`, grep перед созданием нового). UUIDv7 — из `github.com/google/uuid` (замороженная runtime-зависимость выше); единая точка генерации — `domain.NewID`.

## Go-инструменты — по явному списку пакетов, не `./...`

`go test` / `go vet` / `golangci-lint` запускаются по `./cmd/... ./internal/... ./migrations/...`, а **не** по `./...`: последний заползает в `web/**/node_modules`, где npm-пакеты (например `flatted`) приносят посторонние `.go`-файлы и ломают прогон. Go не умеет игнорировать `node_modules`. В `Makefile` это переменная `GO_PKGS`; в CI — те же пути. Новый top-level Go-каталог → добавить его и в `GO_PKGS`, и в CI.

## Слои и направление зависимостей

`handler → service → repo`, домен в центре. Handler не содержит бизнес-проверок; service не знает про HTTP; repo не содержит логики. Интерфейсы репозиториев объявляются на стороне потребителя (в пакете сервиса). Модули (`auth`, `forms`, `submissions`) общаются только через интерфейсы сервисов — прямой импорт чужого repo запрещён.

## Ошибки

Доменные ошибки — сентинелы/типы в `internal/domain/errors.go`; оборачивать с контекстом: `fmt.Errorf("publish form %s: %w", id, err)`. Маппинг на HTTP-статусы существует ровно в одном месте — `respond.go`; добавлять новый `http.Error(...)` в handler'ах запрещено. Ошибки не глотаются: либо обработана, либо обёрнута и возвращена, либо (на самом верху) залогирована через slog с request_id.

## Контексты

`context.Context` — первый аргумент везде ниже handler'а; передавать, не сохранять в структурах; уважать отмену в долгих операциях (стриминг CSV — проверять `ctx.Err()` между чанками).

## SQL

Весь SQL — в sqlc-запросах (`.sql`-файлы + `sqlc generate`); строковая конкатенация SQL запрещена без исключений. Транзакции открываются в service-слое через хелпер `postgres.WithTx`; repo-методы принимают исполнителя (pool или tx) и не открывают транзакций сами. Инвариант «регистрация = user + workspace + membership одной транзакцией» и «публикация = version + published_version_id одной транзакцией» — неприкосновенны.

## Логи

Только `slog` из контекста (с request_id), только структурные поля (`slog.String("form_id", ...)`), никаких `fmt.Println`/`log.Printf`. Уровни: Debug — трассировка, Info — бизнес-события (форма опубликована), Warn — ожидаемые аномалии (rate limit сработал), Error — то, что требует внимания человека. В логи не попадают: пароли, токены, содержимое ответов респондентов, email в паре с ответами.

## Конфигурация

Новая настройка = поле в `config.Config` + строка в `.env.example` с комментарием + валидация при старте + значения в `.env.dev` и `.env.prod-local`. Все четыре — в одном коммите. `os.Getenv` вне пакета `config` запрещён. Ветвление по имени окружения (`if env == "dev"`) запрещено — ветвиться можно только по смысловым флагам (`cfg.CookieSecure`).

## Тесты

Юнит-тесты герметичны и не требуют Docker (`make test-unit` / обычный `go test`). Интеграционные тесты (эндпоинт против настоящего Postgres — PROCESS §3) помечаются `//go:build integration` и поднимают базу через хелпер `internal/pgtest` (один контейнер на пакет из `TestMain`, изоляция — `TRUNCATE ... CASCADE` между тестами). Гоняются под тегом: `make test-go` / `go test -tags=integration` (и так же в CI); без тега тот же `go test` их не собирает. Эталон — `internal/auth/integration_test.go`. В интеграционном тесте rate-limiter подменяется `ratelimit.AllowAll{}` (инвариант 6), а не ослабляется.
